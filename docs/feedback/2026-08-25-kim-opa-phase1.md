## สรุปว่าอะไรพลาด

phase นี้ผ่านการตรวจอัตโนมัติทั้งหมด (`check.php` 0 ต้องแก้ · ชุดทดสอบ 103 ข้อผ่าน) **แต่ผู้ใช้เปิดดูแล้วบอกว่าหน้าใช้ไม่ได้และ layout แย่** — และเขาถูก

สาเหตุรากไม่ใช่เรื่องความสามารถ แต่เป็น **ช่องว่างในตัวมาตรฐานเอง 3 ช่อง**

1. **มาตรฐานคุม token แต่ไม่คุมการจัดหน้า** — `design.md` บอกว่าสีอะไร ขนาดเท่าไหร่ ห้ามเขียนค่าดิบ ซึ่ง `check.php` ตรวจได้หมด แต่ไม่มีข้อไหนบอกว่า "หน้าหนึ่งประกอบขึ้นมายังไง" ผลคือ AI ปั้น token ครบ 152 ตัว แล้วเอา component ของโครงเปล่ามาต่อกันตรงๆ ซึ่งผ่านทุกกฎแต่หน้าตาไม่มีลำดับสายตา
2. **นิยาม "เสร็จ" ข้อ 3 ตรวจไม่ได้เลยด้วยเครื่อง** — "เปิดหน้าจริงในเบราว์เซอร์ดูแล้ว ... ฟังก์ชันถูกแต่หน้าตายังไม่ดี ถือว่ายังไม่เสร็จ" เป็นข้อเดียวที่ไม่มีเครื่องมือรองรับ AI จึงตีความว่า "เปิดดูแล้วไม่พัง" แทน "เปิดดูแล้วดี" และรายงานว่าเสร็จ
3. **ขั้นตอน C1→C2→C3 ไม่มีอะไรบังคับลำดับหรือบังคับให้ใช้ wireframe** — ทำ backend ก่อนแล้วค่อยห่อหน้าให้พอทำงานก็ติ๊กครบได้เหมือนกัน · wireframe 41 หน้าที่ทำในช่วง B ไม่ถูกเปิดดูอีกเลยตอนลงมือ

# ส่วนที่ 1 — ข้อผิดพลาดเชิงกระบวนการ

## 1.1 ทำ C2 ก่อน C1 แล้วไม่มีใครรู้

**เกิดอะไร** ไล่ทำ migration → model → service → controller → route ให้จบก่อน แล้วค่อยเขียนหน้าตอนท้าย
ผลคือหน้าถูกทำแบบเร่ง กลายเป็นการห่อ component ให้พอมีที่ยัดข้อมูล ไม่ใช่การออกแบบหน้า

**ทำไมมาตรฐานไม่จับได้** `PLAN.md` มี checkbox 5 ช่องเรียงกัน แต่ไม่มีที่บันทึกว่าทำจริงตอนไหน จะติ๊กย้อนหลังพร้อมกันตอนจบก็ได้

**วิธีแก้ที่มาตรฐาน**
- ให้ `stages/2-develop.md` เขียนชัดว่า **C1 ต้องมี output ที่ตรวจได้ก่อนเริ่ม C2** คือ "หน้าที่เปิดดูได้ด้วยข้อมูลปลอม" ไม่ใช่แค่ไฟล์ view ที่ยังไม่มีข้อมูลจริง
- เพิ่มการตรวจใน `check.php`: ถ้ามี Controller ที่ `view()` ชี้ไปหาไฟล์ view ที่ยังไม่มี → error · ถ้ามี view ที่ไม่มี Controller ไหนเรียก → warn (เจอ view ตายที่ไม่มีใครเปิด)

## 1.2 ไม่ได้ประกอบหน้าจาก wireframe ที่ทำไว้เอง

**เกิดอะไร** ทำ wireframe ขาวดำ 41 หน้าจบในช่วง B แล้วตอน C1 เขียนหน้าใหม่จากศูนย์ ไม่เปิด wireframe เทียบแม้แต่ครั้งเดียว

**ผลจริงที่วัดได้** wireframe ทุกหน้ามีโครงนี้

```
<h1>ผู้ใช้ระบบ</h1>
<p class="sub">เฉพาะเจ้าของร้านเข้าหน้านี้ได้ · ปิดใช้งานแล้วประวัติการกระทำยังอยู่ครบ</p>
```

หน้าจริงที่ทำออกมา **ไม่มีทั้ง `<h1>` ในเนื้อหาและไม่มีประโยคอธิบาย ทั้ง 10 หน้า** — ชื่อหน้าไปอยู่ใน topbar ตัวเล็ก คำอธิบายหายไปเลย
นี่คือสาเหตุอันดับหนึ่งที่หน้า "ดูแย่": ทุกอย่างในหน้ามีน้ำหนักเท่ากันหมด ไม่มีจุดเริ่มให้สายตา

**วิธีแก้ที่มาตรฐาน**
- `stages/2-develop.md` ขั้น C1 ต้องเขียนเป็นคำสั่งบังคับ: **"เปิด `project/wireframes/<หน้านั้น>.html` ขึ้นมาเทียบ แล้วไล่ทีละบล็อกว่าอยู่ครบไหม"** ไม่ใช่ "ประกอบหน้าจาก wireframe" ซึ่งกำกวมพอให้ตีความว่า "ทำหน้าตามที่เข้าใจ"
- เพิ่มการตรวจ `design/page-head-required`: ทุกไฟล์ใน `app/Views/pages/**` ที่ใช้ layout หลัก ต้องมีหัวเพจ (จาก layout กลางหรือในหน้าเอง) — ตรวจได้จริงด้วยการหา `page-head` ใน layout หรือ `<h1` ในหน้า
- ให้ `_wire.css` ของ wireframe **ใส่คลาสชื่อเดียวกับ component จริง** (`page-head`, `page-lead`, `filters`, `card-table`) เพื่อให้การเทียบเป็นการจับคู่ชื่อ ไม่ใช่การเทียบด้วยตา

## 1.3 ติ๊ก checklist ทั้งที่ยังไม่ได้ทำ

**เกิดอะไร** ติ๊ก `[x] C3 animation` แล้ววงเล็บกำกับว่า "ยังไม่มี motion เพราะ DESIGN.md บอกว่าไม่ทำ animation กับสิ่งที่กดซ้ำทั้งวัน"

เหตุผลไม่ผิด แต่ **การตัดสินว่า "ไม่ทำ" ไม่ใช่ "ทำแล้ว"** — และ `DESIGN.md` ไม่ได้ห้าม animation ทั้งหมด ห้ามเฉพาะปุ่มที่กดซ้ำทั้งวัน ยังเหลือหน้าเข้าและ feedback ตอนกดที่ทำได้

**วิธีแก้ที่มาตรฐาน**
- ใน `CLAUDE.md` ข้อ 4 เพิ่มบรรทัด: **"ขั้นที่ตัดสินว่าไม่ทำ ให้เขียน `[-]` พร้อมเหตุผล ห้ามใส่ `[x]`"** และให้ `check.php` ตรวจว่า `PLAN.md` ไม่มี `[x]` ที่บรรทัดเดียวกันมีคำว่า "ยังไม่" หรือ "ไม่ได้ทำ"
- `stages/2-develop.md` ขั้น C3 ควรมี **รายการขั้นต่ำที่ทุกโปรเจคต้องมี** ไม่ใช่ปล่อยว่าง: หน้าเข้า · feedback ตอนกด · การเข้าออกของ toast/modal · `prefers-reduced-motion` ครบทุกตัว — มีรายการแล้วจะ "ตัดสินว่าไม่ทำทั้งขั้น" ไม่ได้

## 1.4 ไม่ได้ใช้ skill ที่มาตรฐานกำหนดไว้เอง

`standard/skills.md` §7 เขียนว่าช่วง C ต้องใช้ `frontend-design` ตอนประกอบหน้า และช่วง D ใช้ `impeccable` ตรวจคุณภาพ — **ไม่ได้เรียกทั้งสองตัว**

ตอนเรียก `frontend-design` จริงในรอบแก้ คำถามแรกที่มันบังคับให้ตอบคือ *"ทิศทางคืออะไร และอะไรทำให้หน้านี้จำได้"* ซึ่งเป็นคำถามระดับหน้า ไม่ใช่ระดับ token — ถ้าถามคำถามนี้ตั้งแต่ C1 กฎการจัดหน้าจะเกิดขึ้นตั้งแต่ต้น

**วิธีแก้ที่มาตรฐาน**
- ย้ายรายการ skill ต่อขั้นจาก `skills.md` §7 (ซึ่งอ่านครั้งเดียวตอนเริ่มเครื่องใหม่) ไปอยู่ใน `stages/2-develop.md` ตรงหัวข้อของขั้นนั้นๆ **ให้เห็นตอนกำลังทำขั้นนั้น** — ไฟล์ที่อ่านครั้งเดียวตอนต้นงานจะถูกลืมเสมอเมื่อเดินยาว
- `/wf` ควรพิมพ์บรรทัดเตือนตอนขึ้นขั้น C1 ว่า "ขั้นนี้ต้องเรียก `frontend-design`"

## 1.5 ตีความคำตอบของผู้ใช้เป็นการอนุมัติสิ่งที่เขาไม่ได้พูดถึง

ที่ประตู B ส่งลิงก์ wireframe พร้อมถาม 2 คำถาม (ฐานข้อมูล, push) · ผู้ใช้ตอบแค่ 2 คำถามนั้น **ไม่เอ่ยถึง wireframe เลย** แล้วผมเดินหน้าต่อเหมือนได้อนุมัติแล้ว

**วิธีแก้ที่มาตรฐาน**
- รูปแบบรายงานที่ประตูใน `/wf` ควรแยก **"สิ่งที่ต้องอนุมัติ"** ออกจาก **"คำถามที่ต้องตอบ"** เป็นสองหัวข้อ และเขียนกฎว่า **ถ้าคำตอบไม่ครอบคลุมรายการที่ต้องอนุมัติ ต้องถามย้ำเฉพาะรายการที่ขาด ห้ามเดินต่อ**
- ประตู B ควรบังคับให้ผู้ใช้ตอบแยกเป็นข้อ เช่น "wireframe: โอเค / ขอแก้ ..." เพราะการอนุมัติดีไซน์ด้วยคำว่า "ทำเลย" คือความกำกวมที่แพงที่สุดในทั้ง flow

# ส่วนที่ 2 — ช่องว่างของตัวมาตรฐานที่ทำให้หน้าออกมาไม่ดี (สำคัญที่สุด)

`design.md` ตอบได้ว่า **สีอะไร ขนาดเท่าไหร่** แต่ตอบไม่ได้ว่า **หน้าประกอบขึ้นมายังไง** ซึ่งเป็นสิ่งที่ตัดสินว่าหน้าดูดีหรือไม่

ด้านล่างคือกฎที่ผมต้องเขียนขึ้นมาเองในรอบแก้ (ใส่ไว้ที่ `project/DESIGN.md` หัวข้อ "กฎการจัดหน้า" — ตอนนี้มี 10 ข้อ)
**ทั้งหมดควรย้ายไปอยู่ใน `standard/design.md` เพราะไม่มีข้อไหนเป็นเรื่องเฉพาะร้านนี้**

**ข้อเสนอเพิ่มเติม: โครงเปล่าควรมี `partials/page-head.php` มาให้เลย** พร้อม layout ที่ include ไว้แล้ว
ถ้าไม่มีให้ AI จะไม่สร้างขึ้นมาเอง เพราะมันไม่รู้ว่าขาด — เหมือน footer ที่มาตรฐานบอกเองว่า "ข้อนี้ถูกข้ามบ่อยที่สุดถ้าไม่มีใครสั่ง"

# ส่วนที่ 5 — รอบที่ผู้ใช้ตรวจเอง (2026-08-24) และสิ่งที่เจอเพิ่มจากการแก้

รอบนี้ผู้ใช้เปิด wireframe และหน้าจริงดูเอง แล้วชี้มา 5 ข้อ · **ทั้ง 5 ข้อไม่มีข้อไหนที่ `check.php` จับได้ และไม่มีข้อไหนที่อ่านจากโค้ดแล้วเห็น** — เห็นได้ด้วยการเปิดหน้าดูอย่างเดียว

## 5.1 ที่ว่างข้างขวาโล่งอยู่ข้างเดียว ทำให้หน้าดูไม่สมดุล

**ผู้ใช้เห็นว่า** หน้าตั้งค่าเว้นพื้นที่ครึ่งขวาโล่งไว้โดยไม่มีเหตุผล

**ต้นเหตุ** หัวเพจกับแถบแท็บกว้างเต็มพื้นที่ (1,160px) ขณะที่การ์ดฟอร์มกว้าง 760px และชิดซ้าย
ไม่มีใครสั่งให้เป็นแบบนั้น มันเป็นผลข้างเคียงของการที่ **แต่ละ component คุมความกว้างของตัวเอง แต่ไม่มีใครคุมความกว้างของ "หน้า"**

**ทางแก้** ทำ `.page[data-width]` เป็นคอลัมน์เดียวของหน้า อยู่กลางพื้นที่ Controller ส่งมาเป็นคำเดียว `form` / `list` / `wide`
แล้ว **เอา `fit-content` ที่เคยใส่ไว้ทีละ component ออกทั้งหมด** เพราะความกว้างเป็นเรื่องของหน้า ไม่ใช่ของ component

**เป็นบทเรียนของมาตรฐานว่า** กฎ "ทุกอย่างเป็นของกลาง" ต้องครอบถึง **ความกว้างของหน้า** ด้วย ไม่ใช่แค่สีกับระยะห่าง
→ ควรเพิ่มเป็นกฎการจัดหน้าข้อ 8 ใน `standard/design.md` และให้โครงเปล่ามี `.page[data-width]` ใน layout มาให้เลย

## 5.2 ปุ่มลัดช่วงวันอยู่ในการ์ดตัวกรอง ทำให้แถบกรองยาวเกินจำเป็น

**ผู้ใช้เห็นว่า** ควรย้ายออกมาอยู่เหนือการ์ดตัวกรอง

**ต้นเหตุ** ผมมองว่าปุ่มลัดคือ "ตัวกรองอีกแบบ" จึงยัดเข้าไปในแถบเดียวกัน
แต่ตามพฤติกรรมจริงมันต่างกันคนละเรื่อง — **ช่องกรองกรอกแล้วต้องกดค้นหา ปุ่มลัดกดแล้วค้นหาให้เลย**
วางปนกันผู้ใช้จึงไม่รู้ว่ากดแล้วต้องกดค้นหาอีกไหม และแถบกรองยาวจนต้องห่อบรรทัด

**ทางแก้** แยกเป็น `.quick-range` วางเหนือการ์ดตัวกรอง · ปุ่มลัดอยู่นอกฟอร์ม จึงต้องอ้างฟอร์มด้วย `id` ไม่ใช่ `closest('form')`
→ ควรเป็นกฎการจัดหน้าข้อ 9 ใน `standard/design.md`: **สิ่งที่ทำงานทันทีเมื่อกด ต้องไม่อยู่ปนกับสิ่งที่ต้องกดยืนยันอีกที**

## 5.3 รายการตัวเลือกของ `select` ไม่มีสไตล์ เป็นของ OS

**ต้นเหตุ** โครงเปล่าจัดสไตล์แค่ `select` ตัวกล่อง แต่ **ไม่ได้ตั้งสีของ `option`** และไม่ได้ปิด `appearance`
ผลคือลูกศรเป็นลูกศรของ Windows และรายการที่กางออกมาเป็นกล่องสีขาวของ OS โผล่อยู่บนพื้นครีม/พื้นน้ำเงินเข้ม

**ทางแก้** ปิด `appearance` แล้ววาดลูกศรเองด้วย `::after` (เส้นขอบ 2 ด้านหมุน 45°) และตั้ง `option { background-color / color }` ให้ตรงธีม

**‼️ ผมแก้ข้อนี้ผิดในรอบแรก และผู้ใช้ต้องบอกซ้ำ** — รอบแรกผมตั้งสี `option` แล้วสรุปว่าพอ
แต่รายการที่กางออกมายังเป็นแผงของ OS อยู่: ฟอนต์ไม่ใช่ Sarabun ระยะห่างเป็นของ Windows มุมไม่มน ไม่มีเงา และแถบไฮไลต์เป็นสีฟ้าของระบบปฏิบัติการ
**การตั้งสี `option` เปลี่ยนได้แค่ 2 ค่าจากสิบกว่าค่าที่ตาเห็น จึงไม่ใช่การแก้ เป็นการลดอาการ**

**ทางแก้จริง** วาด listbox เองตาม pattern ARIA combobox (`.select-button` + `ul[role="listbox"]`)
โดย `<select>` ตัวจริงยังอยู่ในหน้าเสมอเป็นตัวเก็บค่าและตัวส่งฟอร์ม

| รายละเอียดที่ต้องทำให้ถูก | ถ้าทำผิดจะเป็นอะไร |
|---|---|
| ซ่อน `<select>` ด้วยการ **clip** ไม่ใช่ `display:none` | control ที่ `display:none` เบราว์เซอร์โฟกัสไม่ได้ ถ้ามี `required` ฟอร์มจะไม่ส่ง **โดยไม่มี error ให้เห็นเลย** |
| ตั้งค่าแล้วต้อง `dispatchEvent(new Event('change'))` เอง | การตั้งค่าด้วยสคริปต์ไม่ยิง event · ตัวสลับภาษาที่ใช้ `data-auto-submit` จะหยุดทำงานเงียบๆ |
| `select` ที่ `disabled` ไม่ต้องแปลง | ปุ่มที่เราวาดไม่รู้จัก `disabled` ของ select เอง จะกลายเป็นช่องที่ผู้จัดการกดเปิดได้ทั้งที่ไม่มีสิทธิ์แก้ |
| แยก "ตัวที่ชี้อยู่" ออกจาก "ตัวที่เลือกไว้แล้ว" | ถ้าไฮไลต์เหมือนกัน ผู้ใช้ไม่รู้ว่ากด Enter แล้วจะได้อันไหน · ผมใช้พื้นสีหลัก = ตัวที่ชี้ · เครื่องหมายถูก + ตัวหนา = ตัวที่เลือกไว้ |
| คีย์บอร์ดต้องครบ ลูกศร Home End Enter Esc และ **พิมพ์ตัวอักษรเพื่อกระโดด** | listbox ที่ไม่มี type-ahead ช้ากว่า `select` ของ OS ที่มันไปแทน ซึ่งแปลว่าทำให้แย่ลง |
| ป้ายชื่อของช่องต้องตัด `*` ออกก่อนเอาไปเป็น `aria-label` | screen reader อ่านว่า "ดอกจัน" ต่อท้ายชื่อทุกช่องที่บังคับกรอก |

**หลักที่ควรเขียนลง `standard/design.md`**
> ถ้า control นั้น **กางอะไรออกมาเมื่อกด** แผงที่กางออกมาเป็นของ OS ที่จัดสไตล์ไม่ได้เสมอ → **ต้องปั้นใหม่**
> ถ้าเป็นแค่กล่องปิด (`input`, `textarea`, `checkbox`) จัดสไตล์ได้พอ → ไม่ต้องปั้นใหม่

หลักข้อนี้ตอบล่วงหน้าได้ทั้ง `select` ปฏิทิน `input[type=color]` `input[type=file]` และ `<details>` โดยไม่ต้องลองผิดทีละตัว
→ และควรใส่ **listbox ที่เขียนเองมาให้ในโครงเปล่า** เหมือนที่ควรใส่ปฏิทิน เพราะเป็น control ที่ทุกโปรเจคใช้

## 5.4 แผงปฏิทินของ `input[type="date"]` ไม่เข้ากับระบบ

**ต้นเหตุ** แผงปฏิทินของเบราว์เซอร์ **จัดสไตล์ไม่ได้เลยแม้แต่ค่าเดียว** เป็นแผงของ OS ล้วน

**ทางแก้ที่เลือก** เขียนแผงปฏิทินเอง (`.datepicker` + `setupDatePicker()` ใน `app.js`) **ไม่เพิ่ม dependency** ตามกฎเหล็กข้อ 2
โดยยังใช้ `input type="date"` เป็นตัวเก็บค่า ไม่เปลี่ยนเป็น `text` — ค่าจึงยังเป็น ISO คริสต์ศักราช พิมพ์เองได้ และ validate ของเบราว์เซอร์ยังทำงาน

รายละเอียดที่ต้องทำให้ถูกและควรเป็นแม่แบบของมาตรฐาน

| เรื่อง | ทำยังไง | ถ้าทำผิดจะเป็นอะไร |
|---|---|---|
| ชื่อเดือน / ชื่อวัน | ใช้ `Intl.DateTimeFormat(locale)` ของเบราว์เซอร์ | hardcode ภาษาไทยลง JS = ขัดกฎ i18n และเพิ่มภาษาใหม่ต้องแก้ JS |
| พ.ศ. | `Intl` ของ locale `th` ให้ พ.ศ. มาเอง (2569) ตรงกับที่ `format_date()` ของ PHP แสดง | คำนวณ +543 เองใน JS = มีสองที่ที่ต้องแก้เวลาเปลี่ยนกฎ |
| เริ่มสัปดาห์วันจันทร์ | คำนวณจากวันที่รู้ว่าเป็นจันทร์ แล้ววน 7 วัน | ใช้ `getDay()` ตรงๆ ได้อาทิตย์เป็นวันแรก ซึ่งไม่ตรงกับปฏิทินไทย |
| ถ้า JS พัง | CSS ที่ซ่อนปุ่มปฏิทินของเบราว์เซอร์ **ผูกกับคลาสที่ JS ใส่** (`.date-input`) | ซ่อนด้วย CSS ตรงๆ แล้ว JS พัง = ไม่มีปฏิทินให้ใช้เลย |
| คีย์บอร์ด | ลูกศรเดินวัน · PageUp/Down เปลี่ยนเดือน · Enter เลือก · Esc ปิดแล้วคืน focus | ปฏิทินที่กดได้แต่เมาส์ = ใช้ไม่ได้สำหรับคนที่พิมพ์เร็วและ screen reader |
| ตำแหน่งแผง | เช็คที่ว่างด้านล่างแล้วพลิกขึ้น (`data-flip`) | แผงถูกตัดที่ขอบจอเวลาช่องอยู่ล่างหน้า |

## 5.5 แถบเลื่อนเป็นของเบราว์เซอร์

**ทางแก้** `scrollbar-color` + `scrollbar-width` (มาตรฐาน CSS) และ `::-webkit-scrollbar-*` สำหรับ Chromium
ใช้ `border` โปร่งกับ `background-clip: content-box` ให้หัวจับดูบางแต่ยังกดโดนง่าย
→ ควรอยู่ในโครงเปล่าตั้งแต่ต้น เพราะทุกโปรเจคที่ไม่ใช่ธีมขาวเทาจะเจอปัญหานี้ทั้งหมด

## บั๊กที่เจอเพิ่มระหว่างแก้ 5 ข้อข้างบน

### 5.6 ‼️ animation ของผมเองทำให้แผงปฏิทินถูกทับ — stacking context ค้าง

**อาการ** แผงปฏิทินเปิดแล้วโดนการ์ดตารางที่อยู่ถัดไปทับ ทั้งที่ตั้ง `z-index: 30` แล้ว

**ต้นเหตุ** C3 animation ของผมเขียนว่า

```css
.page > .stack > * { animation: rise var(--duration-normal) var(--ease-enter) both; }
```

`animation-fill-mode: both` ทำให้ค่าที่คีย์เฟรมกำหนด **ค้างอยู่หลัง animation จบ** ซึ่งรวมถึง `transform`
ตรวจด้วย `getComputedStyle` แล้วได้ `transform: matrix(1, 0, 0, 1, 0, 0)` — เป็น identity matrix ที่ไม่ทำอะไรเลย
แต่ **`transform` ที่ไม่ใช่ `none` สร้าง stacking context** ทุกบล็อกในหน้าจึงกลายเป็นกรงขัง `z-index` ของลูกตัวเอง

**ทางแก้** เปลี่ยนเป็น `backwards` — ได้สถานะเริ่มต้นตอนยังรอ `animation-delay` แล้วปล่อยคืนทุกค่าเมื่อจบ

**ทำไมเรื่องนี้สำคัญกับมาตรฐาน** มันเป็นบั๊กที่
- **มองไม่เห็นจนกว่าจะมี dropdown ตัวแรกในระบบ** ซึ่งอาจเป็นอีกหลาย phase ถัดไป
- อ่าน CSS แล้วดูถูกทุกบรรทัด
- แก้ตอนเจอทีหลังต้องไล่หาว่าใครสร้าง stacking context ซึ่งใช้เวลานาน

→ `standard/design.md` ควรเขียนเป็นกฎว่า **animation ที่แตะ `transform` ต้องใช้ `fill-mode: backwards` ห้ามใช้ `both`/`forwards`** เว้นแต่ต้องการสถานะปลายทางค้างจริงๆ
→ และควรเพิ่มการตรวจใน `check.php`: เจอ `animation` ที่มี `both` หรือ `forwards` ในไฟล์ CSS → warn พร้อมอธิบายเหตุผล

### 5.7 ‼️ `toISOString().slice(0, 10)` ในโครงเปล่าให้วันที่ผิดไป 1 วัน

**ต้นเหตุ** โครงเปล่าเขียนไว้ว่า

```js
function isoDate(date) { return date.toISOString().slice(0, 10); }
```

`toISOString()` แปลงเป็น **UTC ก่อน** · ไทยเป็น UTC+07:00 จึงเลื่อนย้อนหลัง 7 ชั่วโมง
ผลคือทุกครั้งที่พนักงานกดปุ่มลัด "วันนี้" **ก่อน 07:00 ตามเวลาไทย จะได้ช่วงวันของเมื่อวาน**
ร้านที่เปิดถึงตี 2-3 และตัดรอบวันทำการตี 4 คือเวลาที่ใช้ปุ่มนี้พอดี

**ทางแก้** ประกอบสตริงจาก `getFullYear()` / `getMonth()` / `getDate()` ซึ่งเป็นเวลาเครื่อง ไม่แปลงเขตเวลา

→ ควรแก้ในโครงเปล่าและ **เขียนเป็นกฎใน `standard/rule.md` ว่าห้ามใช้ `toISOString()` เพื่อเอาวันที่** ควบคู่กับกฎเรื่องเก็บ ค.ศ. ที่มีอยู่แล้ว
เป็นบั๊กประเภทเดียวกับกฎ "เก็บ ค.ศ. แปลง พ.ศ. ตอนแสดง" คือผิดแล้วไม่มี error และรู้ตัวตอนตัวเลขรายงานเพี้ยน

### 5.8 ผมเขียน CSS ที่ทับกฎของตัวเองในไฟล์เดียวกัน

**อาการ** พอใส่คอลัมน์ของหน้าใน wireframe แล้ว หัวเรื่องอยู่กลางที่ 700px แต่การ์ดยังกว้างเต็มจอ

**ต้นเหตุ** ผมเขียนสองกฎในไฟล์เดียวกันที่ขัดกันเอง

```css
.main > * { max-width: var(--wf-col, 100%); }   /* specificity 0,1,0 */
.main.form .card { max-width: 100%; }            /* specificity 0,2,1 — ชนะ */
```

กฎที่สองผมเขียนเพื่อลบ `max-width` ที่เคยใส่ inline ไว้ทีละการ์ด แต่ผม**ลบ inline ออกไปแล้วก่อนหน้านั้น** กฎนี้จึงเหลือแต่ผลเสีย

**บทเรียน** ไม่ใช่บั๊กของมาตรฐาน แต่เป็นบทเรียนของวิธีทำงาน: **แก้ต้นเหตุแล้วต้องลบกฎที่เขียนไว้กันอาการออกด้วย** ไม่งั้นกฎกันอาการจะกลายเป็นอาการใหม่
→ เป็นเหตุผลสนับสนุนว่าการ **ถ่ายภาพหน้าจริงทุกครั้งหลังแก้** จับได้ทันที ซึ่งควรเป็นข้อบังคับใน `standard/testing.md`

### 5.9 ตัวแปรของ partial ค้างข้ามรอบ loop

**อาการที่จะเกิด** ช่อง `select` แคบตามช่องข้อความที่อยู่ก่อนหน้ามันโดยไม่มีใครสั่ง

**ต้นเหตุ** `partials/field.php` ถูก include ในขอบเขตเดียวกับหน้า และ **ไม่ล้างตัวแปรของตัวเองตอนจบ**
ซึ่งเป็นเรื่อง**จำเป็น** เพราะหลายหน้าตั้ง `$type` / `$required` ครั้งเดียวแล้วอาศัยให้ค้างถึงช่องถัดไปโดยเจตนา
แต่ผลข้างเคียงคือ partial ที่วน loop สร้างหลายช่อง (เช่น `setting-fields.php`) ต้องล้างตัวแปรที่ไม่ใช้เองทุกรอบ

**ทางแก้ในโปรเจคนี้** ล้าง `$fieldWidth = ''` ทุกรอบของ loop และเขียนเตือนไว้ในหัวไฟล์ `field.php`

→ `standard/components.md` ควรกำหนดสัญญาให้ชัดว่า **partial ที่รับตัวแปรผ่านขอบเขตร่วม ต้องประกาศในหัวไฟล์ว่า "ค่าค้างข้ามการ include"** และคนที่วน loop ต้องล้างเอง
เป็นตระกูลเดียวกับบั๊ก `$rows` ในส่วนที่ 3 ข้อ 3 — ต้นเหตุเดียวกันคือ **PHP `include` ใช้ scope ร่วม** ซึ่งเป็นจุดอ่อนที่ใหญ่ที่สุดของ pattern นี้

### 5.10 ‼️ ผมลดอาการแล้วรายงานว่าแก้แล้ว (บทเรียนของวิธีทำงาน)

รอบแรกของข้อ 5.3 ผมตั้งสี `option` แล้วเขียนในรายงานว่า "แก้แล้ว" พร้อมอธิบายข้อจำกัดของเบราว์เซอร์ประกอบ
ผู้ใช้เปิดดูแล้วบอกว่า **"มันยังไม่มี css เหมือนเดิม"** ซึ่งถูก — เพราะสิ่งที่ตาเห็นแทบไม่เปลี่ยน

**สิ่งที่ผมทำผิดไม่ใช่เรื่องเทคนิค แต่เป็นเรื่องเกณฑ์การตัดสินว่า "เสร็จ"**
ผมใช้เกณฑ์ "ทำเท่าที่วิธีนี้ทำได้" แทนเกณฑ์ "ผลลัพธ์ที่ผู้ใช้เห็นถึงเป้าหรือยัง"
และผมมีหลักฐานอยู่ในมือแล้วว่ายังไม่ถึง — **ผมไม่ได้ถ่ายภาพตอนรายการกางออกมา** ทั้งที่ถ่ายภาพอย่างอื่นครบ
ถ้าถ่ายก็จะเห็นทันทีว่ายังเป็นแผงของ Windows

**ข้อเสนอต่อมาตรฐาน**
- `standard/testing.md` ต้องเขียนเป็นข้อบังคับว่า **component ที่ต้องกดก่อนจะเห็น ต้องมีภาพตอนเปิดอยู่** ไม่ใช่แค่ภาพตอนปิด
  นี่เป็นข้อเดียวที่กันข้อผิดพลาดชนิดนี้ได้จริง เพราะมันเปลี่ยนจาก "เชื่อคำอธิบายของตัวเอง" เป็น "ดูภาพ"
- `CLAUDE.md` นิยามของ "เสร็จ" ควรเพิ่มบรรทัด: **ถ้าแก้ได้แค่บางส่วน ต้องเขียนว่า "ลดอาการแล้ว ยังไม่ถึงเป้า" ห้ามเขียนว่า "แก้แล้ว"**
  การอธิบายข้อจำกัดของเครื่องมือประกอบ ไม่ได้ทำให้งานที่ยังไม่ถึงเป้ากลายเป็นงานที่เสร็จ

## 6.1 หน้ารวมคู่มือแสดง slug เป็นชื่อบทความ

**อาการ** หน้ารวมคู่มือขึ้นเป็นลิงก์ข้อความเปล่าที่มีแต่ `getting-started` `signing-in` `audit-logs`

**ต้นเหตุ** โครงเปล่าเขียนหน้ารวมไว้แค่ `<a>...<?= e($item['slug']) ?></a>`
ทั้งที่บทความแต่ละไฟล์มี `$manual_title` กับ `$manual_summary` อยู่แล้วตามที่ `standard/features/manual.md` ข้อ 3 บังคับ
— **มีข้อมูลอยู่แล้วแต่ไม่ได้เอามาใช้** slug เป็นภาษาอังกฤษเสมอและไม่ใช่ภาษาคน จึงกลายเป็นหน้าที่ผู้ใช้อ่านไม่รู้เรื่อง

**ทางแก้** Controller อ่าน meta จากไฟล์บทความเอง (`include` แล้วกลืน output ทิ้ง) แล้วส่งชื่อจริงกับคำโปรยให้หน้ารวม
ต้องทำในเมธอดแยกเพื่อไม่ให้ตัวแปรของบทความรั่วไปทับตัวแปรของ Controller

**ไม่ทำทะเบียนชื่อบทความซ้ำอีกที่** — ถ้าเก็บชื่อไว้ใน `config/manuals.php` ด้วย วันหนึ่งจะไม่ตรงกับชื่อในบทความ

→ โครงเปล่าควรเขียนหน้ารวมแบบนี้มาให้เลย เพราะ `manual.md` บังคับให้บทความมี `$manual_title` อยู่แล้ว การไม่ใช้มันคือการทิ้งของที่บังคับให้ทำ

## 6.2 หน้ารวมคู่มือไม่มีลำดับสายตา เป็นรายการ bullet เปล่า

ผู้ใช้ออกแบบมาเป็น **การ์ดทางเข้าแบบ grid มีไอคอน ชื่อ และคำโปรย** ซึ่งดีกว่าจริง เพราะหน้านี้คือ "เลือกทางเข้า" ไม่ใช่ "อ่านรายการ"

**ทำเป็น component กลางชื่อ `.tile-grid` / `.tile`** ไม่ใช่สไตล์ของหน้าคู่มือ
เพราะ `manual.md` ข้อ 6 ห้ามทำสไตล์แยกเฉพาะหน้าคู่มือ และ dashboard ใน phase 8 จะใช้ pattern เดียวกันนี้

**ไอคอนต่อบทความเก็บที่ `config/manuals.php`** (คีย์ `icon`) ไม่ใช่ hardcode ในหน้า
เพราะทะเบียนคือที่ที่อธิบายโครงสร้างของบทความอยู่แล้ว · ต้องเป็นชื่อจากชุดไอคอนกลางเท่านั้น ห้ามไฟล์ SVG แยก

→ `standard/features/manual.md` ข้อ 6 ควรระบุรูปแบบหน้ารวมให้ชัดว่าเป็น **การ์ดทางเข้า** ไม่ใช่รายการลิงก์
และควรเพิ่มคีย์ `icon` ลงในตัวอย่างทะเบียน

## 6.3 ‼️ `[hidden]` ไม่ซ่อนอะไรเลยเมื่อ component ตั้ง `display: flex`

**อาการ** ช่องค้นหากรองได้ถูก ตัวนับขึ้น "3 บทความ" ถูก **แต่การ์ดทั้ง 10 ใบยังโผล่อยู่บนหน้า**

**ต้นเหตุ** `[hidden]` ของเบราว์เซอร์คือ `display: none` ที่ specificity ต่ำสุด
`.tile { display: flex }` ของเราจึงทับมันทั้งหมด · JS ตั้ง `element.hidden = true` สำเร็จจริง แต่ CSS ไม่ยอมซ่อน

**เป็นบั๊กที่หลอกที่สุดในบรรดาที่เจอมา** เพราะทุกอย่างที่ตรวจได้ด้วยโค้ดถูกหมด — JS ถูก ตัวนับถูก `element.hidden` เป็น `true` จริง
เห็นได้ทางเดียวคือดูหน้าจริง

**ทางแก้** `[hidden] { display: none !important; }` ในชั้น `reset`
`!important` ในชั้นล่างชนะ declaration ปกติของชั้นที่สูงกว่า ซึ่งเป็นพฤติกรรมที่ต้องการตรงนี้พอดี

**‼️ และนี่คือความผิดของผมที่ควรบันทึกไว้:** ผมเจอบั๊กนี้มาก่อนแล้ว **สองครั้ง** (แผงปฏิทินและ listbox)
แต่ทั้งสองครั้งผมแก้ด้วยการเขียน `.datepicker[hidden] { display: none }` และ `.select-list[hidden] { display: none }` **ทีละตัว**
ซึ่งคือการแก้อาการที่จุดที่เจอ ไม่ใช่แก้ต้นเหตุ — ผลคือ component ตัวที่สามเจอบั๊กเดิมซ้ำ
**เห็นอาการเดียวกันครั้งที่สองต้องหยุดถามว่าต้นเหตุร่วมคืออะไร ไม่ใช่แปะ patch ตัวที่สอง**
(ตรงกับหลัก "เห็นรูปแบบเดิมโผล่ครั้งที่สองเมื่อไหร่ ต้องดึงเป็นของกลางทันที" ใน `CLAUDE.md` ข้อ 18 ซึ่งผมท่องได้แต่ใช้ไม่ทัน)

→ **`[hidden] { display: none !important }` ควรอยู่ในชั้น reset ของโครงเปล่าตั้งแต่ต้น** เป็นบรรทัดเดียวที่กันบั๊กนี้ได้ทั้งระบบตลอดไป

## 6.4 ช่องค้นหาที่พิมพ์แล้วไม่เกิดอะไรถ้า JS พัง

**หลักที่ใช้** ช่องค้นหาที่กรองด้วย JS ต้อง **ให้ JS สร้างช่องนั้นเอง ห้ามเขียนไว้ในหน้า**
ถ้าเขียนไว้ในหน้าแล้ว JS พัง ผู้ใช้จะได้ช่องที่พิมพ์แล้วไม่เกิดอะไรเลย ซึ่ง **แย่กว่าไม่มีช่อง** เพราะเขาจะสรุปว่าระบบพังหรือไม่มีข้อมูล

เป็นหลักเดียวกับที่ใช้กับปฏิทิน (CSS ที่ซ่อนปุ่มปฏิทินของเบราว์เซอร์ผูกกับคลาสที่ JS ใส่)
→ ควรเขียนเป็นกฎใน `standard/design.md`: **ของที่ทำงานได้เพราะ JS ต้องถูกสร้างโดย JS**

## 6.5 ข้อความที่ JS ต้องใช้

`app.js` ต้องมีข้อความ (ชื่อเดือน ปุ่มล้าง placeholder ของช่องค้นหา ข้อความตอนไม่พบ) แต่ **JS อ่านไฟล์ภาษาของ PHP ไม่ได้ และ CSP ห้าม inline script**

ทางที่ใช้: ส่งผ่าน `data-*` attribute — ของทั้งระบบไว้ที่ `partials/js-lang.php` · ของเฉพาะหน้าไว้ที่ element ของหน้านั้น
และสิ่งที่ `Intl` ของเบราว์เซอร์ให้ได้ (ชื่อเดือน ชื่อวัน พ.ศ.) **ไม่ต้องส่ง** ให้ใช้ `Intl` แทนเพื่อไม่ให้มีคำแปลซ้ำสองที่

→ โครงเปล่าควรมี `partials/js-lang.php` มาให้ พร้อมกฎว่า **ห้าม hardcode ข้อความใน `app.js`** ซึ่งตอนนี้ `i18n.md` ไม่ได้พูดถึงฝั่ง JS เลย

## 6.6 โลโก้ย่อ — เหตุผลของผู้ใช้หนักกว่าเหตุผลของผม

ผมเลือกตัดตราประทับจากโลโก้มาใช้เป็น mark ย่อ เพราะโลโก้เต็มย่อลง 32px แล้วรายละเอียดหาย
ผู้ใช้เห็นของจริงแล้วสั่งให้ใช้ **โลโก้เต็ม** เพราะการตัดเฉพาะตราทำให้ **จำแบรนด์ไม่ได้** — ซึ่งเป็นหน้าที่หลักของโลโก้ ตรงกว่าเรื่องความคมชัด

ทำโดยขยายเป็น 40px และวางบนวงกลมพื้นครีม (ไฟล์โลโก้มีมุมโปร่งใสและหมึกดำกลางภาพ วางบนพื้นน้ำเงินเข้มตรงๆ แล้วจม)

**บทเรียน** การตัดสินใจด้านดีไซน์ที่ **ลดทอนตัวตนของแบรนด์** ควรถามผู้ใช้ ไม่ใช่ตัดสินเองแล้วบันทึกเหตุผลไว้
→ `standard/design.md` ควรระบุว่าเรื่องที่ต้องถามเสมอมีอะไรบ้าง: **การใช้โลโก้แบบตัดส่วน · การเปลี่ยนสีหลักของแบรนด์ · การตัดฟีเจอร์ที่ผู้ใช้เอ่ยถึงเอง**

## 6.7 เบี่ยงเบนจาก `manual.md` ที่บันทึกไว้

`manual.md` ข้อ 6 เขียนว่า "ช่องค้นหา: ใส่เมื่อบทความเยอะจนหาไม่เจอจริงๆ — **บทความไม่กี่ชิ้นไม่ต้องทำ**"

# ส่วนที่ 7 — ข้อผิดพลาดที่ผู้ใช้ต้องเป็นคนเปิดของดูเอง

## 7.1 ‼️ ไม่ได้เปิด wireframe ให้ผู้ใช้ดู แค่ส่ง path ไปให้

**ผู้ใช้เป็นคนบอกให้บันทึกข้อนี้** และมันเป็นต้นเหตุที่แท้จริงของงานแก้หน้าตาทั้งสามรอบในส่วนที่ 5 และ 6

**เกิดอะไรจริง**

| ตอนไหน | ผมทำอะไร | ผลที่ได้ |
|---|---|---|
| จบช่วง B | รายงานที่ประตูว่า "ตรวจ wireframe แล้วบอกว่าโอเค" แล้วแนบ **path ของไฟล์** `project/wireframes/index.html` | ผู้ใช้ตอบแค่ 2 คำถามที่ผมถามเรื่องฐานข้อมูลกับ push · **ไม่ได้เอ่ยถึง wireframe เลย** |
| ผมตีความ | เอา "ทำเอาเลย" มาเป็นการอนุมัติดีไซน์ | เดินหน้าทำ Phase 1 ทั้ง phase บนดีไซน์ที่ไม่มีใครเคยเห็น |
| หลังจบ Phase 1 | ผู้ใช้เปิดหน้าจริงแล้วบอกว่าใช้ไม่ได้ | ต้องรื้อ C1 ทำใหม่ |
| ผู้ใช้ถามกลับมาว่า | **"ฉันสามารถไปเปิดดู wireframe ได้ที่ไหน? ฉันไม่เคยดูเลยและก็ไม่รู้ว่าอยู่ที่ไหน"** | ยืนยันว่าเขาไม่เคยเห็น wireframe เลยตลอดทั้ง phase |
| ผมเพิ่งเปิดให้ดู | เปิดให้ **หลังจากผู้ใช้ถามหา** | หลังจากนั้นเขาชี้ปัญหาดีไซน์ได้ 5 ข้อทันทีในรอบเดียว |

**ต้นเหตุ**

การส่ง `project/wireframes/index.html` เป็นข้อความ **ไม่ใช่การให้ผู้ใช้ดู** — มันคือการบอกพิกัดแล้วโยนภาระการเปิดให้เขา
ไฟล์เป็น HTML ที่อยู่ในเครื่อง ต้องเปิดจาก file explorer หรือลาก path ไปวางในเบราว์เซอร์ ซึ่ง **ไม่ใช่สิ่งที่คนที่ไม่ใช่ dev รู้ว่าต้องทำ**
ผมมีเครื่องมือเปิดเบราว์เซอร์อยู่ในมือตลอดเวลาและใช้มันถ่ายภาพให้ตัวเองดูหลายสิบครั้ง **แต่ไม่เคยใช้มันเปิดให้ผู้ใช้ดู**

**ต้นทุนจริงของข้อนี้** เท่ากับงานแก้หน้าตาสามรอบ — กฎการจัดหน้า 10 ข้อ · pattern กลาง 16 ตัว · listbox กับปฏิทินที่ต้องเขียนเอง
ถ้าผู้ใช้เห็น wireframe ตั้งแต่ประตู B เขาจะชี้เรื่อง "ที่ว่างข้างขวาโล่ง" และ "ปุ่มลัดอยู่ในการ์ดกรอง" ได้ตั้งแต่ตอนนั้น
ซึ่งตอนนั้นแก้คือแก้ไฟล์ HTML ขาวดำ ไม่ใช่รื้อโค้ดที่ทำเสร็จแล้ว

**สิ่งที่มาตรฐานต้องเปลี่ยน**

1. **ที่ประตูทุกบาน สิ่งที่ต้องอนุมัติต้อง "ถูกเปิดให้เห็น" ไม่ใช่ "ถูกอ้างถึง"**
   - ของที่เป็นหน้าเว็บในเครื่อง → **เปิดในเบราว์เซอร์ให้เลย** (`Start-Process`, `open`, `xdg-open`)
   - ของที่เป็นหน้าเว็บบน dev server → เปิด URL ให้
   - ของที่เป็นภาพ → แนบภาพในรายงาน ไม่ใช่บอกว่าภาพอยู่ที่ไหน
   - ของที่เป็นเอกสาร → สรุปสาระที่ต้องตัดสินใจลงในรายงาน **ไม่ใช่บอกให้ไปอ่านเอง**

2. **รายงานที่ประตูต้องแยก "สิ่งที่ต้องอนุมัติ" ออกจาก "คำถามที่ต้องตอบ"**
   และ **ถ้าคำตอบของผู้ใช้ไม่ครอบคลุมรายการที่ต้องอนุมัติ ห้ามเดินต่อ ต้องถามย้ำเฉพาะรายการที่ขาด**
   (ข้อนี้ซ้ำกับส่วนที่ 1.5 — ตอนนี้มีหลักฐานว่ามันเกิดจริงและราคาเท่าไหร่แล้ว จึงควรเลื่อนความสำคัญขึ้น)

3. **ห้ามตีความคำตอบที่ไม่ได้พูดถึงเรื่องนั้นว่าเป็นการอนุมัติเรื่องนั้น**
   ผู้ใช้ตอบเรื่องฐานข้อมูลกับ push ไม่ได้แปลว่าเขาอนุมัติ wireframe · **การเงียบไม่ใช่การอนุมัติ**

4. **เพิ่มเข้า `standard/flow.md` เป็นเงื่อนไขก่อนออกจากช่วง B**
   `[ ] ผู้ใช้ยืนยันว่า **ได้เปิดดู wireframe แล้ว** ไม่ใช่แค่ตอบข้อความอื่นในรายงานเดียวกัน`

**หลักสั้นๆ ที่ควรจำ**

> ถ้าผู้ใช้ต้องหาวิธีเปิดของที่เราทำเอง แปลว่าเรายังไม่ได้ส่งของ

## 7.2 ไอคอนบนแท็บเบราว์เซอร์ไม่ได้เปลี่ยนตามโลโก้

**ผู้ใช้เป็นคนเห็นและบอก** หลังจากผมเปลี่ยนโลโก้ในแถบเมนูไปแล้วรอบหนึ่ง

**ต้นเหตุ** ผมมองโลโก้เป็น "องค์ประกอบในหน้า" จึงเปลี่ยนแค่ที่ `layouts/*.php` ตรงที่เป็น `<img>` ในเนื้อหา

**รายการที่โลโก้ปรากฏ ซึ่งควรเป็น checklist ในมาตรฐาน**

| ที่ไหน | ไฟล์ | ข้อควรระวัง |
|---|---|---|
| แถบเมนู / topbar | `logo-192.png` บนวงกลมพื้นครีม | มุมโปร่งใส หมึกดำจมบนพื้นเข้ม |
| หน้าเข้าสู่ระบบ | `logo-192.png` บนวงกลมพื้นครีม | ขนาดใหญ่ ต้องคมบนจอความละเอียดสูง |
| **แท็บเบราว์เซอร์** | `favicon-32.png` + `favicon-180.png` | **แถบแท็บเป็นสีเข้มหรือสีอ่อนตามธีมของเครื่องผู้ใช้ ไม่ใช่ตามธีมของระบบเรา** — ต้องมีพื้นทึบ |
| จอ TV / บัตรคิวที่พิมพ์ | ยังไม่ทำ (phase 6-7) | บัตรพิมพ์เป็นขาวดำ ต้องมีเวอร์ชันที่อ่านออกเมื่อไม่มีสี |

→ `standard/design.md` ควรมี checklist "ที่ที่โลโก้ปรากฏ" ให้ไล่ครบทุกที่เมื่อโลโก้เปลี่ยน
เพราะการเปลี่ยนโลโก้เกิดขึ้นทีเดียวแต่ปรากฏหลายที่ และที่ที่ลืมง่ายที่สุดคือที่ที่ไม่อยู่ในหน้า

→ และควรมีสคริปต์สร้าง favicon จากโลโก้มาให้ในโครงเปล่า (โปรเจคนี้ทำไว้ที่ `scripts/make-favicon.php`)
เพราะการทำ favicon ด้วยมือทุกครั้งคือเหตุผลที่ทำให้คนข้ามมัน

# ส่วนที่ 8 — เรื่องสี (2026-08-24 รอบสี่)

ผู้ใช้เปิดของจริงทั้งสองโหมดแล้วบอกสามข้อ

> การใช้สีที่แย่มาก สีหลักของระบบคือสีแดงแต่หน้าตาที่เห็นมีสีแดงน้อยมาก
> ร่วมถึงตอนเปลี่ยนเป็นสว่างสีหลักจากแดงกลายเป็นสีน้ำตาล
> การใช้สีที่แย่ทำให้หน้าตาของแต่ละหน้าดูจืดไม่สวย
> ตอนที่กดย่อขนาดของ sidebar ตัวไอคอนมันเล็กลง ทำให้ดูยาก

## 8.1 ‼️ ผมเอาความกลัวเรื่องหนึ่ง ไปตัดสินอีกเรื่องหนึ่ง

**สิ่งที่ผมทำ** ผู้ใช้ให้ palette มาตั้งแต่ช่วง A และบอกว่า **แดงคือสีหลัก**
ผมเขียนลง `DESIGN.md` ว่า *"แดงไม่ใช่สีของปุ่มหลัก"* แล้วยก `brand.primary` ให้น้ำเงินเข้ม
เหตุผลที่ผมใช้: กลัวพนักงานสับสนระหว่างปุ่ม "เรียกคิว" ที่กดวันละร้อยครั้ง กับ "ยกเลิกคิว" ที่กดผิดแล้วเดือดร้อน

**ความกลัวนั้นถูก แต่ทางแก้ที่ผมเลือกผิด**

ความสับสนของปุ่มเป็นปัญหาของ **รูปทรง** ไม่ใช่ปัญหาของ **สีแบรนด์**
แก้ได้ด้วยกฎเดียวคือ "ปุ่มทำลายข้อมูลเป็นปุ่มโครงร่างพร้อมไอคอน ห้ามเป็นปุ่มทึบ"
ซึ่งใช้เวลาเขียนสามบรรทัด และไม่ต้องเอาสีแดงออกจากแบรนด์เลย

ผมจ่ายด้วยของที่แพงกว่า (ตัวตนของแบรนด์) เพื่อซื้อของที่ถูกกว่า (ความชัดของปุ่ม) ทั้งที่ซื้อได้ด้วยเงินคนละกระเป๋า

**และผมพลาดชั้นที่สอง** — `#780000` ที่ผมเก็บไว้เป็น "สีเอกลักษณ์" ในโหมดสว่าง
**อ่านออกมาเป็นน้ำตาลบนพื้นครีม ไม่ใช่แดง** เท่ากับโหมดที่ผู้ใช้เปิดดูไม่มีสีแดงเลย
ผมมีภาพหน้าจอโหมดสว่างอยู่ในมือหลายรอบแล้วและไม่เห็นเรื่องนี้ เพราะผมตรวจ "contrast ผ่านไหม" ไม่ได้ตรวจ "สีนี้ยังเป็นสีที่ผู้ใช้สั่งมาไหม"

**สิ่งที่มาตรฐานต้องมี**

1. **สีที่ผู้ใช้ระบุมาเองเป็นข้อกำหนด ไม่ใช่ข้อเสนอ** — เบี่ยงเบนได้แต่ **ต้องถามก่อน ไม่ใช่บันทึกเหตุผลแล้วทำ**
   `standard/design.md` ควรเขียนว่า: ถ้าจะไม่ใช้สีที่ผู้ใช้ให้มาเป็นสีหลัก **ต้องถามที่ประตู A พร้อมภาพเทียบสองทาง**
2. **ตรวจว่า token ที่ generate ออกมายังตรงกับเจตนาของแบรนด์** ไม่ใช่ตรวจแค่ contrast
   คำถามที่ควรมีในเกณฑ์ผ่านของช่วง B: *"เปิดหน้าจริงแล้วเห็นสีที่ผู้ใช้ให้มาไหม ทั้งสองโหมด"*
3. **สีเดียวกันในโหมดต่างกันให้ความรู้สึกต่างกัน** — `#780000` บนพื้นเข้มคือแดงเข้ม บนพื้นครีมคือน้ำตาล
   ต้องเลือกค่าให้ **หมวดสีที่คนเรียก** ตรงกันทั้งสองโหมด ไม่ใช่แค่ contrast ผ่าน

## 8.2 ‼️ ผมอ้างว่าตรวจ contrast แล้ว แต่คำอ้างนั้นตรวจซ้ำไม่ได้ และผิด

`DESIGN.md` เดิมเขียนว่า **"ตรวจ contrast แล้วทุกคู่ 48 คู่ผ่านเกณฑ์ 4.5:1 ทั้งสองโหมด"**

รอบนี้ผมเขียน `scripts/check-contrast.php` ที่อ่านค่าจาก `DESIGN.md` โดยตรง แล้วรันกับพาเลตต์เดิม
ผลคือ **ตก 7 คู่**

| ตกที่ไหน | ได้เท่าไหร่ | ต้องได้ |
|---|---|---|
| ขอบช่องกรอกบนพื้นหน้า (สว่าง) | 1.85:1 | 3.0 |
| ขอบช่องกรอกบนการ์ด (สว่าง) | 2.02:1 | 3.0 |
| ขอบช่องกรอกบนพื้นหน้า (มืด) | 2.19:1 | 3.0 |
| ขอบช่องกรอกบนการ์ด (มืด) | 1.99:1 | 3.0 |
| แถบตราประทับบนพื้นหน้า (มืด) | 2.92:1 | 3.0 |
| แถบตราประทับบนการ์ด (มืด) | 2.64:1 | 3.0 |
| หมายเลขคิวบนจอ TV (สว่าง) | 1.15:1 | 4.5 |

**ขอบช่องกรอกที่ 1.85:1 คือของจริงที่ผู้ใช้สายตาไม่ดีจะหาช่องกรอกไม่เจอ** — เป็นข้อ WCAG 1.4.11 ที่มาตรฐานตั้งใจจะคุมอยู่แล้ว

**ต้นเหตุ** ผมคำนวณด้วยมือตอนตัดสิน `DESIGN.md` แล้วเขียนผลลงเอกสารเป็นประโยค
ประโยคในเอกสาร **ไม่ใช่การตรวจ** เพราะ
- ไม่มีใครรันซ้ำได้ ต้องเชื่อผมอย่างเดียว
- ตอนแก้สีรอบต่อไป ไม่มีอะไรบอกว่าคำอ้างนั้นหมดอายุแล้ว
- ผมนับเฉพาะคู่ "ข้อความบนพื้น" แล้วลืมคู่ "เส้นขอบของ control" ซึ่งเป็นเกณฑ์ 3:1 คนละข้อกัน

**สิ่งที่มาตรฐานต้องมี**

→ **สคริปต์ตรวจ contrast ที่อ่านจาก `DESIGN.md` โดยตรง ต้องอยู่ในโครงเปล่า** และควรถูกเรียกจาก `check.php`
→ รายการคู่ที่ต้องตรวจต้องครอบ **เส้นขอบของ control และแถบกราฟิก (3:1)** ไม่ใช่แค่ข้อความ (4.5:1)
→ กฎที่ควรเขียนไว้: **ห้ามเขียนผลการตรวจเป็นประโยคในเอกสาร ถ้าไม่มีคำสั่งที่รันซ้ำได้กำกับ**

โปรเจคนี้ทำไว้ที่ `scripts/check-contrast.php` — ตรวจ 41 คู่ × 2 โหมด = 82 คู่ ตอนนี้ผ่านหมด

## 8.3 token ไม่ได้ทำให้สี "ปรากฏ" เอง

**อาการที่ผู้ใช้เรียกว่า "จืด"** เกิดจากสีแบรนด์ถูกใช้แค่ที่ปุ่มหลักและแถบเมนูที่เลือกอยู่
ที่เหลือของหน้าเป็นเทากับน้ำเงินหมด แม้ token จะถูกทุกค่า

**บทเรียน** การมี token สีแบรนด์ **ไม่เท่ากับ** การที่หน้าดูเป็นสีนั้น
ต้องมีรายการชัดๆ ว่า **สีแบรนด์ต้องปรากฏที่ไหน** ไม่งั้นมันจะไปกองอยู่แค่ปุ่ม

รายการที่ใช้ในโปรเจคนี้ — ควรเป็นตัวอย่างใน `standard/design.md`

| ที่ | ใช้อะไร |
|---|---|
| ปุ่มหลักของหน้า | พื้นทึบ `primary` |
| เมนูที่เลือกอยู่ | พื้นทึบ `primary` เต็มความกว้าง |
| แถบใต้/บนแท็บที่เปิด | เส้น `sealStroke` สี `primary` |
| หัวเพจและหัวข้อย่อย | แถบตราประทับ `accent` |
| กรอบไอคอนของการ์ดทางเข้า | สี `accent` · ชี้แล้วเป็นพื้นทึบ `primary` |
| วงแหวน focus | `primary` |
| เลขหน้าที่เปิดอยู่ | พื้นทึบ `primary` |

**และรายการที่ห้ามใช้สีแบรนด์**

- ‼️ **ห้ามพาดเส้นสีแบรนด์เต็มความกว้างของการ์ด** — รอบนี้ผมลองใส่แล้วถ่ายภาพดู
  มันอ่านออกมาเป็น **"แถบแจ้งเตือนว่ามีอะไรผิด"** ไม่ใช่สีแบรนด์ · เอาออกแล้ว
  สีแบรนด์ต้องอยู่ที่สิ่งที่ **มีความหมาย** (กดได้ / บอกตำแหน่ง / เป็นหัวเรื่อง) ไม่ใช่พาดไปทั่วเพื่อให้เห็นสี
- ลิงก์ในเนื้อความ — ถ้าลิงก์เป็นแดงด้วย มันจะชนกับปุ่มหลักและข้อความผิดพลาดซึ่งแดงทั้งคู่
  โปรเจคนี้เพิ่ม token `brand.link` เป็นน้ำเงิน-ฟ้าแยกออกมา

## 8.4 ข้อจำกัดทางฟิสิกส์ของแดงบนพื้นเข้ม — ต้องรู้ก่อนออกแบบ

แดงบริสุทธิ์บนพื้นน้ำเงินเข้มได้ contrast แค่ ~2.6-2.9:1 จึง **ใช้เป็นข้อความขนาดปกติในโหมดมืดไม่ได้เลย**

ทางออกที่ใช้ และควรเป็นแม่แบบ

| ใช้ทำอะไร | เกณฑ์จริง | ทำยังไง |
|---|---|---|
| พื้นปุ่มทึบ | ปุ่มต้องแยกจากการ์ด 3:1 · ตัวหนังสือบนปุ่ม 4.5:1 | แดงสด `#E8323E` + **ตัวหนังสือหมึกเกือบดำ** ไม่ใช่ครีม (ครีมได้แค่ 3.98:1) |
| ไอคอน เส้นขอบ วงแหวน focus แถบ | 3:1 | แดงอ่อนกว่า `#FF6B6B` |
| ข้อความขนาดปกติ | 4.5:1 | **ไม่ใช้แดง** ใช้ `text.*` หรือ `brand.link` |

‼️ **การตั้งเกณฑ์ 4.5:1 กับทุกอย่างเป็นการตั้งเกณฑ์ผิด** — WCAG ให้ 3:1 กับสิ่งที่ไม่ใช่ข้อความ
ตั้ง 4.5 ไปทั้งหมดจะบังคับให้แดงในโหมดมืดจางเป็นสีชมพูโดยไม่มีเหตุผลรองรับ ซึ่งเป็นสิ่งที่ผมทำในรอบแรกของการแก้นี้

## 8.5 component ที่ออกแบบไว้สำหรับสถานะเดียว

**อาการ** พับเมนูแล้วไอคอนดูเล็กลงจนเล็งกดยาก

**ต้นเหตุ** ขนาดไอคอน 20px ถูกเลือกมาให้ **อยู่คู่กับข้อความ** — ข้อความเป็นตัวบอกความหมาย ไอคอนเป็นตัวช่วย
ตัดข้อความออกแล้ว **ไอคอนกลายเป็นตัวบอกความหมายตัวเดียว** แต่ขนาดยังเป็นขนาดของตัวช่วย

ขนาดไม่ได้เล็กลงจริง แต่ **หน้าที่ของมันใหญ่ขึ้น** ขณะที่ขนาดเท่าเดิม

**ทางแก้** พับแล้วไอคอนเป็น 24px และจัดกลางแนวรางเมนู · พื้นที่กดยังคง 44px ตามที่มาตรฐานบังคับ

→ กฎที่ควรเขียนใน `standard/components.md`: **component ที่มีหลายสถานะ ต้องตรวจทุกสถานะ**
และเฉพาะเมนูพับได้ ให้เขียนไว้เลยว่า **สถานะพับต้องเพิ่มขนาดไอคอน** เพราะเป็นสถานะที่ไอคอนต้องสื่อความหมายเอง
ในโครงเปล่ามี `data-collapsed` มาให้แล้วแต่ไม่มี CSS ของสถานะนั้นเลยนอกจากซ่อนข้อความ

## 8.6 ผมอ่านภาพหน้าจอผิดเป็นครั้งที่สาม

รอบนี้ผมดูภาพเมนูที่พับแล้วในโหมดสว่าง และสรุปว่า **"รางเมนูเป็นสีเข้มในโหมดสว่าง"** ซึ่งจะเป็นบั๊กใหญ่ถ้าจริง
สุ่มพิกเซลมาวัดแล้วได้ `#FFFBF2` — **เป็นสีครีมถูกต้องอยู่แล้ว ผมอ่านภาพผิด**

รวมทั้งหมดที่ผมอ่านภาพผิดในงานนี้: คิดว่า sidebar โหมดสว่างเป็นสีเข้ม (ผิด) · คิดว่าจอแคบล้นแนวนอน (ผิด) · คิดว่ารางเมนูพับเป็นสีเข้ม (ผิด) — **ผิดทางเดียวกันทั้งสามครั้ง คือเห็นว่ามืดทั้งที่สว่าง**

→ กฎที่ควรอยู่ใน `standard/testing.md`: **ห้ามสรุปเรื่องสีจากการดูภาพ ต้องสุ่มพิกเซลมาเทียบกับ token**
การดูภาพใช้ตัดสินได้เรื่อง **การจัดวาง ลำดับสายตา และช่องว่าง** แต่ **เรื่องสีต้องวัด**

# ภาคผนวก — วิธีตรวจหน้าตาที่ใช้ได้จริงบนเครื่องนี้

มาตรฐานสั่งให้ "เปิดหน้าจริงในเบราว์เซอร์ดู" แต่ไม่ได้บอกวิธี ทำให้ข้อนี้ถูกข้ามง่ายที่สุด
**ควรใส่ 3 ท่านี้ลงใน `standard/testing.md`** เพราะเป็นสิ่งที่ทำให้ข้อ 3 ของนิยาม "เสร็จ" ทำได้จริง

**1. ถ่ายภาพหน้าที่ล็อกอินแล้ว** — Chrome headless ไม่มี cookie ของ session
ดึง HTML ด้วย `curl` ที่ถือ cookie อยู่ แล้วแทรก `<base href="http://localhost:PORT/">` เข้าไปใน `<head>` ก่อนบันทึกเป็นไฟล์
CSS ฟอนต์ และรูปจะโหลดกลับจาก server ตัวจริง แล้วสั่ง `chrome --headless --screenshot` บนไฟล์นั้น

**2. ตรวจจอแคบจริงที่ 375px** — Chrome บน Windows บังคับความกว้างหน้าต่างขั้นต่ำ ~485px
`--window-size=390,x` จะได้ภาพที่ crop มาจาก viewport ที่กว้างกว่านั้น ซึ่ง **อ่านผลผิดได้ว่าไม่ล้นจอทั้งที่ล้น หรือกลับกัน**
ทางที่ได้ผลจริงคือทำหน้า host แล้ววาง `<iframe width="375">` ชี้ไปที่ไฟล์ที่เซฟไว้ แล้วอ่าน `clientWidth` เทียบ `scrollWidth` จากใน iframe

**3. ตรวจสีด้วยการอ่านพิกเซล ไม่ใช่ด้วยตา** — ในรอบนี้ผมอ่านภาพผิดสองครั้ง (คิดว่า sidebar โหมดสว่างเป็นสีเข้ม ทั้งที่พิกเซลจริงคือ `#FFFBF2`)

**4. ตรวจ component ที่ต้องกดก่อนจะเห็น** (dropdown, ปฏิทิน, modal) — ถ่ายภาพเฉยๆ ไม่เจอ
ทำหน้า host ที่วาง `<iframe>` ชี้ไปไฟล์ที่เซฟไว้ แล้วสั่ง `.click()` เข้าไปใน iframe ก่อนถ่าย
