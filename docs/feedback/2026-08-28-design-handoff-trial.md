## ก.4 รายการ component ที่ขอให้ออกแบบ

> ‼️ **ข้อที่คิดว่าสำคัญที่สุด และยังไม่เคยลอง**
>
> สถาปัตยกรรมของมาตรฐานคือ *ทุกอย่างเป็นของกลาง แก้ที่เดียวเปลี่ยนทั้งระบบ*
> ออกแบบทีละหน้า 41 หน้า จะได้ 41 ดีไซน์ที่ค่อยๆ เพี้ยนจากกัน
> **ออกแบบ component แล้วทุกหน้าได้ตามไปเอง เพราะทุกหน้าประกอบจากชุดเดียวกันอยู่แล้ว**

| component | สถานะที่ต้องมี |
|---|---|
| ปุ่ม — primary · secondary · ghost · danger · ไอคอนล้วน | ปกติ · hover · focus · active · disabled |
| ช่องกรอก (`field`) — text · textarea · select · date | ปกติ · focus · ผิดพลาด · disabled · มีคำอธิบาย |
| ตารางหน้ารายงาน (`table`) | มีข้อมูล · **ว่าง** · **โหมดการ์ดบนมือถือ** |
| หัวเพจ (`page-head`) | มีปุ่มหลัก · ไม่มีปุ่ม |
| แถบตัวกรอง | — |
| แบ่งหน้า (`pagination`) | — |
| กล่อง modal (`dialog`) + กล่องยืนยัน (`confirm`) | เดสก์ท็อป · มือถือ |
| toast (`flash`) | สำเร็จ · เตือน · ผิดพลาด · ข้อมูล |
| สถานะว่าง (`empty-state`) | ไม่มีข้อมูลเลย · ตัวกรองไม่เจอ |
| แนบไฟล์ (`upload`) | ปกติ · ขณะลากผ่าน · มีไฟล์แล้ว · ไฟล์ไม่ผ่านเงื่อนไข |
| เมนู (`nav`) | กาง · พับ · มือถือ |
| tooltip · badge | — |
| footer | — |

### ทำไมถึงเพี้ยน — และมันไม่ใช่ความผิดของใคร

**`DESIGN.md` บรรทุกได้แค่ token ไม่ได้บรรทุกดีไซน์ของ component**

`design-sync.php` เขียนทับเฉพาะบล็อกระหว่าง `TOKENS:BEGIN` / `TOKENS:END` เท่านั้น
กฎของ component — แถวสูงเท่าไหร่ · หัวตารางมีพื้นไหม · badge มุมมนแค่ไหน — อยู่ในชั้น `@layer components` ของ `app.css` **ซึ่งไม่มีอะไรในขั้นตอนนี้แตะเลย**

ผลคือ **สีกับฟอนต์เปลี่ยนตามดีไซน์ 100% แต่รูปทรงยังเป็นของโครงเปล่าทั้งหมด**

> ‼️ **ข้อที่เจ็บที่สุดคือ badge** — `design.md` 5.6 บังคับว่า *"ประเภทกับสถานะต้องต่างกันด้วยรูปทรง ไม่ใช่แค่สี"*
> **ดีไซน์ทำตามกฎนี้แล้ว** (ประเภทใช้เส้นประ มุม 4px · สถานะใช้เส้นทึบ) แต่ `.badge` ของโครงมีแบบเดียว
> **กฎที่มาตรฐานบังคับ ถูกดีไซน์ทำให้แล้ว แล้วหายไปตอนแปลงกลับ**

### สิ่งที่ข้อนี้บอก

ข้อ 7 ตอบว่า "ไม่ต้องเขียน CSS ต่อหน้า" ซึ่งฟังดูดี — **แต่ราคาของมันคือหน้าไม่ตรงกับดีไซน์**
ถ้าอยากให้ตรง ต้องแก้ชั้น `@layer components` ใน `app.css` ซึ่ง**ทำได้และไม่ผิดกฎ** (ยังเป็นไฟล์เดียว เป็นของกลาง)

แต่การแก้นั้น**ไม่ถูกบันทึกไว้ที่ไหนเลย** — `DESIGN.md` ไม่รู้เรื่อง · รอบหน้าที่เปลี่ยนดีไซน์ ไม่มีใครรู้ว่าต้องแก้อะไรบ้าง
ซึ่งขัดกับหลัก *"ทุกอย่างเป็นของกลาง แก้ที่เดียวเปลี่ยนทั้งระบบ"* ที่มาตรฐานยึดไว้

**ตัดสินว่ากฎการเข้าถึงชนะสเปคหน้าตา** และบันทึกไว้ตรงนี้เพื่อไม่ให้คนถัดไป "แก้" ด้วยการย่อปุ่มลง

> **ข้อนี้คือสิ่งที่ขั้นตอนนี้ต้องมีถ้าเข้ามาตรฐาน — กติกาว่าใครชนะเมื่อดีไซน์ขัดกับกฎ**
> ไม่มีกติกา แล้ววันหนึ่งจะมีคนย่อปุ่มลงเหลือ 40px เพื่อให้ "ตรงดีไซน์" โดยไม่รู้ว่ากำลังแลกอะไรไป

# ส่วน ค2 — สิ่งที่เจอระหว่างทดลอง (ก่อนถึงขั้นส่งให้ Claude Design)

เจอตั้งแต่ยังไม่ทันส่งอะไรไปเลย · **ทั้งสองข้อเป็นข้อบกพร่องของมาตรฐานเอง ไม่ใช่ของวิธีใหม่**

## ‼️ ข้อ 1 — ประตูของมาตรฐานบล็อกไม่ให้ commit wireframe ได้เลย

`design/design-md-decided` เป็น **error** และมันเริ่มทำงานทันทีที่มี `project/STATE.md`
แต่ `STATE.md` ถูกสร้างตั้งแต่**เริ่มโปรเจค** ไม่ใช่ตอนผ่านช่วง B

ผลคือ **ตั้งแต่วินาทีที่เริ่มโปรเจค จนถึงวินาทีที่ `DESIGN.md` เสร็จ จะ commit อะไรไม่ได้เลย** เพราะ pre-commit hook บล็อก

กระทบวิธีใหม่โดยตรง เพราะลำดับที่ทดลองคือ **wireframe → ดีไซน์ → `DESIGN.md`**
แปลว่างาน wireframe ทั้งหมด (8 ไฟล์) ต้องค้างอยู่ในเครื่องโดยไม่มี commit จนกว่าจะได้ผลจาก Claude Design กลับมา — ซึ่งอาจเป็นวันถัดไป

> **แต่ปัญหานี้มีอยู่แล้วในลำดับเดิมด้วย** — ลำดับเดิมคือ B3 `DESIGN.md` → B4 wireframe
> ซึ่งแปลว่า `SCOPE.md` และ `PLAN.md` ที่ทำก่อนหน้าก็ commit ไม่ได้เหมือนกัน
> **เป็นข้อบกพร่องของมาตรฐานที่ยังไม่มีใครเจอเพราะยังไม่เคยมีใครรันช่วง B จนจบจริงๆ**

**ทางที่เป็นไปได้** — ยังไม่ตัดสิน รอคุยกับผู้ใช้
1. ลดเป็น `warn` แล้วให้เป็น **เงื่อนไขก่อนเข้าช่วง C** แทนที่จะเป็น error ตลอดเวลา
2. ให้ตรวจเฉพาะเมื่อ `STATE.md` บอกว่าอยู่ช่วง C ขึ้นไป
3. ปล่อยไว้แล้วยอมรับว่าช่วง B ต้องทำรวดเดียวจบโดยไม่ commit

## ‼️ ข้อ 2 — แม่แบบ `PLAN.md` ในมาตรฐาน ทำให้ชุดตรวจของมาตรฐานเอง fail

`docs/project-docs` นับ phase ที่กำลังทำด้วย `substr_count($plan, '🔄')` **ทั้งไฟล์**

แต่แม่แบบใน `flow.md` ข้อ 9 เขียนบรรทัดคำอธิบายสัญลักษณ์ไว้ว่า

```
> อัปเดตล่าสุด: [วันที่] | ⬜ ยังไม่เริ่ม · 🔄 กำลังทำ · ✅ เสร็จแล้ว
```

บรรทัดนี้มี `🔄` อยู่ · พอมาร์ค phase ที่กำลังทำจริง 1 อัน จะกลายเป็น 2 ทันที แล้ว fail

**ใครก็ตามที่ทำตามแม่แบบเป๊ะๆ จะเจอข้อนี้ตั้งแต่ phase แรก** — เลี่ยงได้ทางเดียวคือไม่ใส่บรรทัดที่แม่แบบบอกให้ใส่

**ทางแก้ที่ชัด:** นับเฉพาะบรรทัดที่ขึ้นต้นด้วย `## ` หรือข้ามบรรทัดที่ขึ้นต้นด้วย `>`
