# Claude Workflow — เอกสารออกแบบ

วันที่ตกลง: 2026-08-20
สถานะ: อนุมัติแล้ว รอลงมือสร้างทีละไฟล์

---

## 1. ปัญหาที่ต้องแก้

ทีมทำงานด้วยการสั่ง AI (vibe code) แทนการเขียนเอง จึงเกิดปัญหา 4 ข้อ

| # | ปัญหา | รากของปัญหา |
|---|---|---|
| 1 | AI ทำงานไม่สม่ำเสมอ สั่งเหมือนกันได้ผลไม่เหมือนกัน | AI เริ่มทุก session ด้วยความจำเป็นศูนย์ ไม่รู้ว่าเคยตกลงอะไรไว้ |
| 2 | AI เลือกทางที่เร็วที่สุด พองานเยอะทุกอย่างเละ | ไม่มีนิยามของคำว่า "เสร็จ" และไม่มีอะไรมาตรวจ |
| 3 | UX/UI ไม่มีเอกลักษณ์ ทุกโปรเจคหน้าเหมือนกัน | ไม่มีการตัดสินใจเรื่องเอกลักษณ์ AI จึงตกกลับไปที่ค่า default ของตัวเอง |
| 4 | ไม่มีขั้นตอนการทำงานที่ชัดเจน | ไม่มีเฟส ไม่มีประตูตรวจ ไม่มีของที่ตกทอดระหว่างขั้น |

## 2. เป้าหมาย

สร้างมาตรฐานกลาง 1 ตัวที่ทุกคนในทีม clone ไปใช้ได้ทุกโปรเจค แล้วได้งานที่อยู่ในมาตรฐานเดียวกัน
ผู้ใช้สั่งครั้งเดียวแล้วไปทำอย่างอื่นได้ กลับมาตรวจเฉพาะจุดที่คุ้มค่าจะตรวจ

**สิ่งที่ workflow นี้จะทำให้:** ไม่ต้องพูดเรื่องเดิมซ้ำทุกครั้ง (โครงสร้าง มาตรฐาน ขั้นตอน นิยามของเสร็จ)

**สิ่งที่ยังต้องทำเอง:** อธิบายเจตนาเฉพาะของโปรเจคนั้น (ใครใช้ แก้ปัญหาอะไร อะไรสำคัญกว่าอะไร)

## 3. ข้อจำกัดที่กำหนดทุกอย่าง

| เรื่อง | ข้อเท็จจริง |
|---|---|
| ภาษา/ฐานข้อมูล | PHP + MySQL |
| Hosting | shared host — มี cron job, FTP, phpMyAdmin |
| ไม่มี | SSH, git บนเซิร์ฟเวอร์, remote MySQL |
| เครื่อง dev ของทีม | มี PHP + Composer เท่านั้น **ไม่มี Node/npm** |
| Deploy | **GitHub Actions** — push `main` → CI อัปไฟล์ผ่าน FTP ขึ้น **server ทดสอบ** |
| Production | ผู้ใช้ทำเอง ไม่อยู่ในขอบเขตของ workflow |

ผลที่ตามมาโดยบังคับ

- **CI คือกำแพงสุดท้าย** — `.github/workflows/deploy.yml` รัน `scripts/check.php` ก่อน ถ้าไม่ผ่านห้ามอัปไฟล์
- **Migration** — `scripts/migrate.php` รันได้ 2 ทาง: CLI บนเครื่อง หรือ route ลับที่ป้องกันด้วย token ใน `.env` ซึ่ง CI ยิงเรียกหลังอัปไฟล์เสร็จ (เลิกต้อง import ผ่าน phpMyAdmin มือ) — มีคำสั่ง export เป็นไฟล์ `.sql` ไว้เป็นทางสำรอง
- **Cron** — backup DB, ตัด log, งานเบื้องหลังตามเวลา
- **CSS** — เขียนมือด้วย CSS custom properties + `@layer` ไม่มี build step **และไม่ใช้ CSS framework**
  มาตรฐานเดิมใช้ Bootstrap 5 แต่ตัดออกรอบนี้ เพราะ `old/CLAUDE.md` เองบันทึกไว้ว่า "ถ้าปล่อยว่างไว้ผลลัพธ์จะออกมาเป็น Bootstrap เปล่าทุกครั้ง" — นั่นคือปัญหาข้อ 3 ตรงๆ
  CSS สมัยใหม่ (grid, flex, custom properties, `@layer`, container query) ทำ layout ได้ครบโดยไม่ต้องมี framework
  ส่วน component ที่ต้องใช้ JS (modal, dropdown, tooltip, tabs) เขียนไว้ใน skeleton ครั้งเดียวแล้วใช้ทุกโปรเจค
- **ชุดตรวจอัตโนมัติ** — เป็น PHP ทั้งหมด (PHPStan + สคริปต์ที่เขียนเอง) เพราะต้องรันได้ทั้งบนเครื่องและใน CI
- **E2E test** — ใช้เบราว์เซอร์ของ Claude Code ขับจริง สรุปผลเป็น Artifact **รันใน CI ไม่ได้** จึงต้องทำก่อน push

## 4. สถาปัตยกรรม

repo นี้เป็น **template** ไม่ใช่ library — clone แล้วเป็นโปรเจคใหม่ทันที

```
standard/   มาตรฐานกลาง อ่านอย่างเดียว ห้ามแก้ในโปรเจค (มี VERSION)
project/    ของเฉพาะโปรเจคนี้ AI เขียนที่นี่
app/ core/ config/ database/ public/ lang/ scripts/ storage/   โค้ดจริง
```

**กฎข้อเดียวที่ทำให้ระบบอยู่รอด:** `standard/` ห้ามแก้ในโปรเจคเด็ดขาด

อยากแก้ต้องแก้ที่ repo กลางแล้วปล่อยเวอร์ชันใหม่ ไม่งั้นผ่านไป 3 เดือนแต่ละโปรเจคจะมีมาตรฐานคนละตัว แล้วกลับไปสู่ปัญหาข้อ 1

อัปเดตมาตรฐาน: `php scripts/standard-update.php` ทับเฉพาะ `standard/` + `CLAUDE.md` ไม่แตะโค้ดโปรเจค แล้วรายงานว่ากฎอะไรเปลี่ยนตั้งแต่เวอร์ชันที่โปรเจคนี้ใช้อยู่

```

│   ├── index.php          entry point เดียวของระบบ
│   ├── .htaccess
│   └── assets/            css/app.css · js/ · images/ · manuals/
├── scripts/               ชุดตรวจ · migrate · design-sync · standard-update · backup

├── storage/               logs/ · uploads/ (นอก public/) · backups/
```

## 5. กลไกบังคับ 4 ชั้น

จุดที่ทำให้ workflow นี้ต่างจากเอกสารที่ AI อ่านแล้วลืม

| ชั้น | กลไก | บังคับอะไร | เหตุผล |
|---|---|---|---|
| 1 | `CLAUDE.md` (~150 บรรทัด) | กฎเหล็ก ต้อง/ห้าม + นิยามของ "เสร็จ" + ตารางชี้ทาง | โหลดอัตโนมัติทุก session ไม่ต้องพึ่งความขยันของ AI ในการไปอ่าน ต้องสั้นพอที่จะไม่ถูกกลืน |
| 2 | Slash command `/wf` | โหลดคู่มือเฉพาะช่วงที่กำลังทำ | กฎทุกช่วงพร้อมกัน = ไม่มีกฎเลย |
| 3 | Hooks + **CI** | pre-commit รันชุดตรวจ, CI รันซ้ำก่อนอัปไฟล์ | ไม่ขึ้นกับว่า AI หรือคนจะจำได้ไหม |
| 4 | `scripts/check.php` | ตัดสินผ่าน/ไม่ผ่านเป็นตัวเลข | **กฎที่แปลงเป็นสคริปต์ได้ ต้องแปลง** |

หลักการ: ข้อความเป็นคำแนะนำ สคริปต์เป็นกำแพง เก็บข้อความไว้เฉพาะสิ่งที่บังคับด้วยเครื่องไม่ได้

**ความเป็นเจ้าของ `CLAUDE.md`** — เป็นของมาตรฐาน 100% ห้ามแก้ในโปรเจค `standard-update.php` ทับทั้งไฟล์ได้เลย
ของเฉพาะโปรเจค (เช่น ต้องต่อกับตารางเก่าที่ตั้งชื่อไม่ตามมาตรฐาน) ไปอยู่ `project/NOTES.md` ซึ่ง `CLAUDE.md` สั่งให้ไปอ่านถ้ามี

## 6. Flow การทำงาน — คำสั่งเดียว `/wf`

พิมพ์ `/wf` ครั้งเดียวตอนเริ่ม หลังจากนั้นตอบเป็นภาษาคนธรรมดา ไม่ต้องพิมพ์คำสั่งอีก
AI อ่าน `project/STATE.md` เพื่อรู้ว่าตัวเองอยู่ตรงไหน — พิมพ์ `/wf` ซ้ำเมื่อไหร่ก็ได้ มันทำงานต่อจากจุดเดิม

### ช่วง A — เก็บข้อมูล (ผู้ใช้ต้องอยู่)

| ขั้น | ทำอะไร |
|---|---|
| A1 | ถามผู้ใช้ว่า **มี prompt อธิบายโปรเจคไหม** — ถ้ามีให้อ่านแล้วสกัดข้อมูลออกมา |
| A2 | ถามคำถามชุดระบบ **เฉพาะช่องที่ยังขาด** (ชื่อโปรเจค · ระบบนี้คืออะไร · ใครใช้บ้าง · กี่ภาษา · ทำอะไรได้บ้าง) |
| A3 | **วิเคราะห์แล้วเสนอสิ่งที่ควรเพิ่ม** — ทำหน้าที่เหมือน dev ที่ทักลูกค้า ไม่ใช่รับคำสั่งอย่างเดียว |
| A4 | ถามคำถามชุดดีไซน์ (โลโก้ · สีของแบรนด์ · อารมณ์ที่ต้องการ · reference · อุปกรณ์หลัก) ตามช่องที่ `DESIGN.md` ต้องการ |
| → | เขียน `project/BRIEF.md` + `project/BRIEF-DESIGN.md` |

**ประตู A** — ผู้ใช้เลือกว่าจะเอาข้อเสนอจาก A3 ข้อไหนบ้าง

> ข้อควรระวังของ A1: prompt ยาวแทบไม่เคยครบ AI ต้องไล่เทียบกับรายการช่องที่ต้องรู้แล้วถามเฉพาะที่ขาด ห้ามข้ามการถามทั้งหมดเพราะเห็นว่ามี prompt แล้ว

### ช่วง B — วางแผน + ออกแบบ (AI ทำเองรวดเดียว ผู้ใช้ไปทำอย่างอื่นได้)

| ขั้น | ทำอะไร |
|---|---|
| B1 | `project/SCOPE.md` — สรุปขอบเขต สิ่งที่ทำ/ไม่ทำ |
| B2 | `project/PLAN.md` — แบ่ง phase + checklist ทุกข้อ |
| B3 | `project/DESIGN.md` — **ตัดสิน design system ครั้งเดียวจบ** ใช้ร่วมกันทุก phase |
| B4 | `project/wireframes/*.html` — wireframe ขาวดำ **ทุกหน้าของทุก phase** กดลิงก์เดินระหว่างหน้าได้ |
| B5 | `php scripts/design-sync.php` → `public/assets/css/app.css` |

**ประตู B** — ผู้ใช้ตรวจ แผน + wireframe + design system ทีเดียว

### ช่วง C — ลงมือทีละ phase

ต่อ 1 phase ทำ 5 ขั้นนี้เรียงกัน

1. **Frontend** — ประกอบหน้าจาก wireframe ที่อนุมัติแล้ว + token จาก `DESIGN.md` สร้าง component ที่ใช้ซ้ำได้
2. **Backend** — Controller/Service/Model + migration + route + middleware
3. **Animation** — ตาม `standard/design.md` หมวด motion
4. **ทดสอบเฉพาะ phase** — `scripts/check.php` + กดใช้จริงด้วยเบราว์เซอร์ของ Claude Code
5. **ติ๊ก checklist ใน `PLAN.md` แล้วรายงานผู้ใช้**

**ประตูย่อย** — จบทุก phase หยุดให้ผู้ใช้ดู 1 ครั้ง

### ช่วง D — ตรวจรวมทั้งระบบ

| ด้าน | วิธี |
|---|---|
| ความปลอดภัย | `scripts/check.php` + ไล่ตาม `standard/security.md` |
| ประสิทธิภาพ | นับจำนวน query ต่อหน้า, หา N+1, ตรวจ index, ขนาดหน้า |
| System Testing (E2E) | เบราว์เซอร์ของ Claude Code เดิน flow จริงตั้งแต่ต้นจนจบ |

→ สรุปผลเป็น **Artifact** + เขียน `project/QA-REPORT.md`

**ประตู D** — ผู้ใช้อ่านผลตรวจ

### ช่วง E — ส่งขึ้น server ทดสอบ

`git push main` → GitHub Actions รัน `check.php` → ผ่านแล้วอัปไฟล์ผ่าน FTP → ยิง route migrate
**ขึ้น production ผู้ใช้ทำเอง ไม่อยู่ในขอบเขต workflow**

### จำนวนจุดที่ผู้ใช้ต้องกลับมา

ประตู A + ประตู B + 1 ครั้งต่อ phase + ประตู D
โปรเจคที่มี 4 phase = **หยุด 7 ครั้ง** โดย 5 ครั้งเป็นแค่การดูแล้วบอกว่าผ่าน

### กฎที่ทำให้ flow มีผลจริง

1. **ห้ามข้ามช่วง** — ช่วง C จะปฏิเสธถ้าไม่มี `PLAN.md` และ `DESIGN.md`
2. **artifact คือความจำ** — session ใหม่หรือเพื่อนร่วมทีมมารับช่วง อ่าน `project/` แล้วทำต่อได้ทันที
3. **checklist อยู่ในไฟล์ ไม่ได้อยู่ในแชท** — แชทหาย ความคืบหน้าไม่หาย

### 2 กลไกที่กันไม่ให้ AI หยุดกลางทางแบบไร้สาระ

- **`project/QUESTIONS.md`** — ระหว่างช่วง B/C ถ้าเจอเรื่องกำกวม ห้ามหยุดถาม ให้จดลงไฟล์นี้ เลือกทางที่สมเหตุสมผลที่สุด บันทึกว่าเลือกอะไรเพราะอะไร แล้วทำต่อ เอาไปถามรวมทีเดียวที่ประตูถัดไป งานที่ไม่เกี่ยวกับข้อสงสัยนั้นต้องเดินหน้าต่อให้หมดก่อน

## 9. การทดสอบ

ระดับที่เลือก: **สคริปต์ตรวจ + smoke test + E2E ด้วยเบราว์เซอร์ของ Claude Code**
ไม่ทำ PHPUnit เต็มรูปแบบ เพราะทีม vibe code มักทิ้งเทสต์ใน 3 เดือน แล้วกลายเป็นภาระ

`php scripts/check.php` — รันได้ทั้งบนเครื่องและใน CI

- SQL ต่อสตริง (ไม่ใช้ prepared statement)
- `echo` ที่ไม่ escape
- route ที่ไม่มี middleware
- `.env` หรือซอร์สเข้าถึงได้จากเบราว์เซอร์
- hex color นอก token
- ข้อความ hardcode ที่ไม่ผ่าน `lang/`
- **path ดิบใน View** — `grep -rn 'href="/\|action="/\|src="/' app/Views/` ต้องว่าง ทุกลิงก์ต้องผ่าน `url()`
- **ไฟล์ `.sql` ที่ไม่ขึ้นต้นด้วย `SET NAMES utf8mb4 COLLATE utf8mb4_unicode_ci;`**
- **คอลัมน์ status/type/role ที่เก็บข้อความไทย** แทน key ภาษาอังกฤษ
- ตารางที่ไม่มี audit log
- **ลิงก์ตายในไฟล์มาตรฐาน** — ทุก `[...](...)` ต้องชี้ไปหาไฟล์ที่มีอยู่จริง
- `standard/` ถูกแก้หรือไม่ (เทียบ hash)
- PHPStan
- smoke test: ทุก route ตอบ 200

**E2E** — Claude Code เปิดเบราว์เซอร์เดิน flow จริง จับภาพ อ่าน console error สรุปเป็น Artifact
ข้อจำกัดที่ต้องรู้: **รันใน GitHub Actions ไม่ได้** ต้องทำในช่วง D ก่อน push

## ภาคผนวก ก — สเปค component กลาง

บันทึกไว้ที่นี่ก่อน จะนำไปเขียนเป็นเนื้อหาจริงใน `standard/design.md`
ทุกตัวต้องอยู่ใน `app/Views/partials/` เป็นของกลาง ห้ามสร้างเวอร์ชันเฉพาะหน้า

### 1. หน้ารายงาน (หน้าที่มีตารางข้อมูล)

- ต้องมีตารางข้อมูล + ตัวกรอง
- ตัวกรองต้องค้นหาแบบ **ช่วงวัน** ได้
- ตารางที่ค้นแบบช่วงวันได้ ต้องมี **ปุ่มลัด**: วันนี้ · สัปดาห์นี้ · เดือนนี้ · 6 เดือน · 1 ปี
- ต้องมีตัวเลือก **จำนวนแถวที่แสดง**
- **หัวตารางกดเพื่อเรียงลำดับได้**

### 2. ตัวอัปโหลดไฟล์ — 2 แบบ

| แบบ | ใช้เมื่อไหร่ |
|---|---|
| ปกติ | แนบไฟล์ทั่วไป |
| ใหญ่ + preview | ต้องเห็นรูปก่อนอัป |

ทั้งสองแบบต้อง **ลากวางได้** และ **เลือกหลายไฟล์พร้อมกันได้**

### 3. Alert / Toast

- **ต้องเป็นแบบลอย ห้ามเป็นแบบแทรกในหน้า** เพราะแบบแทรกจะดัน component อื่นเลื่อน
- alert ตอนบันทึก/ลบ ต้องมี **ไอคอนหรือ SVG ที่สื่อความหมาย** ทำเอง ไม่ใช้ SweetAlert2 (คุมได้มากกว่า)

### 4. การใช้ไอคอนและภาพ

ข้อความกับ component ล้วนๆ ทำให้หน้าสวยได้จำกัด — ใช้ไอคอน/SVG ช่วยได้ แต่ใส่เยอะเกินจะรก
`design.md` ต้องกำหนดเกณฑ์ว่าใส่ตรงไหนถึงช่วย ตรงไหนถึงรก

### 5. Sidebar

- ต้องมีปุ่ม hamburger สำหรับพับเสมอ
- **พับแล้วต้องย่อ ไม่ใช่ปิดหาย** — ตัดข้อความออกเหลือแต่ไอคอน ผู้ใช้ยังกดใช้งานได้

### 6. อื่นๆ ที่เป็นกฎระดับระบบ (ย้ายไป `CLAUDE.md` แล้ว)

component กลางทุกตัว · โหมดสว่าง/มืด · footer ทุกหน้า · git ทำงานใน branch

### 7. กฎที่ AI ไม่ทำถ้าไม่สั่ง — อนุมัติแล้วทั้งหมด

รูปแบบร่วมของทุกข้อ: **AI สร้างเฉพาะกรณีที่ทุกอย่างสมบูรณ์** แล้วหยุด

| # | กฎ | ไปอยู่ที่ | เหตุผล |
|---|---|---|---|
| 1 | ทุก component ต้องมี 3 สถานะ: **ว่าง / กำลังโหลด / ผิดพลาด** · empty state ต้องบอกด้วยว่าทำอะไรต่อได้ ("ยังไม่มีคิววันนี้ · กดปุ่มออกบัตรเพื่อเริ่ม") | `design.md` | เป็นตัวชี้ว่าระบบดูเสร็จหรือดูค้าง มากกว่าสีหรือฟอนต์ |
| 2 | **ปุ่ม submit ต้องกันกดซ้ำ** — disable + spinner ทันทีที่กด | `design.md` | กดรัวแล้วได้ข้อมูลซ้ำในฐานข้อมูล แก้ทีหลังต้องไล่ทุกฟอร์ม |
| 3 | **ฟอร์มคืนค่าที่กรอกไว้เมื่อ validate ไม่ผ่าน** (`old()`) + error อยู่**ใต้ช่องที่ผิด** ไม่กองรวมบนสุด | `design.md` | ฟอร์ม 15 ช่องแล้วต้องกรอกใหม่หมดเพราะผิดช่องเดียว คือเหตุผลที่คนเลิกใช้ระบบ |
| 4 | **ตัวกรอง หน้า และการเรียง เก็บใน URL query string ไม่ใช่ session** | `rule.md` | เก็บใน session แล้วแชร์ลิงก์รายงานไม่ได้ · กด back ค่าหาย · เปิด 2 แท็บตีกัน |
| 5 | **confirm ก่อนลบต้องบอกว่าลบอะไร** — `ลบ "ใบสั่งซื้อ #1042" ?` และปุ่มยืนยันเขียนว่า **"ลบ"** ไม่ใช่ "ตกลง" | `design.md` | คนอ่านปุ่ม ไม่อ่านข้อความ |
| 6 | **seeder ต้องมีข้อมูล 50-100 แถว** ไม่ใช่ 3 แถว | `stages/2-develop.md` | seed 3 แถวแล้วไม่มีใครเห็นว่า pagination พัง เรียงผิด หรือ query ช้า จนขึ้นใช้จริง |
| 7 | **ตารางบนมือถือให้ยุบเป็นการ์ด** ไม่ใช่ scroll แนวนอน | `design.md` | ตัดสินเป็นมาตรฐานไปเลย ไม่งั้นแต่ละหน้าทำไม่เหมือนกัน |
| 8 | **ต้องมีหน้า 403** ไม่ใช่มีแค่ 404/500 | `design.md` · `rule.md` | ระบบที่มี role ต้องบอกได้ว่า "เข้าได้แต่ไม่มีสิทธิ์" ต่างจาก "ไม่มีหน้านี้" |
| 9 | **คีย์บอร์ดใช้ได้ครบ** — `Esc` ปิด modal · `Enter` submit · `Tab` เดินได้ · focus เห็นชัด | `design.md` | |
| 10 | **ปุ่ม export CSV ในหน้ารายงาน** ทำเป็น component กลาง | `design.md` | ผู้ใช้ขอทุกครั้ง |
| 11 | **ชื่อไฟล์อัปโหลดภาษาไทยต้อง sanitize ตอนเก็บ แต่เก็บชื่อเดิมไว้แสดง** | `rule.md` · `security.md` | ชื่อไฟล์ไทยพังบน server จริง |
| 12 | **soft delete เป็นค่าเริ่มต้น** | `rule.md` | ลบจริงแล้ว audit log จะชี้ไปหาของที่ไม่มีอยู่ |
| 13 | **ปุ่มในตารางข้อมูลต้องเป็นไอคอนเท่านั้น** ห้ามใช้คำ เพราะทำให้คอลัมน์ยาวเกิน · ต้องมี `aria-label` และ tooltip กำกับทุกปุ่ม | `design.md` | ไอคอนล้วนโดยไม่มีชื่อกำกับ = ผู้ใช้เดาไม่ออก และ screen reader อ่านไม่ได้ |
| 14 | **ทุก resource ต้องครบลูป ดู/เพิ่ม/แก้ไข/ลบ** พร้อมสิทธิ์ของแต่ละอัน · จะไม่ทำอันไหนต้องระบุใน `SCOPE.md` ว่าจงใจไม่ทำ | **`CLAUDE.md` นิยามของเสร็จ ข้อ 1** | AI ทำส่วนที่ง่ายแล้วหยุด — หน้าสินค้าที่เพิ่มได้แต่แก้ไม่ได้ลบไม่ได้ ใช้งานจริงไม่ได้ |
