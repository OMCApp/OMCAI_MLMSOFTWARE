# หน้าคู่มือการใช้งาน (User Manual)

> **บังคับทุกโปรเจค** — อ่านเมื่อสร้าง/แก้บทความคู่มือ และ**ทุกครั้งที่เพิ่มหรือแก้โมดูล**
> จุดเข้าถึงอยู่ที่ [`support-system.md`](support-system.md) · คำแปลทำตาม [`i18n.md`](i18n.md) · หน้าตาทำตาม [`../components.md`](../components.md)

ทุกระบบต้องมี**หน้าคู่มือของตัวเอง**ที่อธิบายวิธีใช้งานแต่ละหน้าเป็นขั้นตอนพร้อมรูปประกอบ เข้าถึงได้จากปุ่มซัพพอร์ตที่มีอยู่ทุกหน้าแล้ว

**เหตุผลที่บังคับ:** ถ้ามีแต่ช่องถามแอดมิน ผู้ใช้ 100 คนที่สงสัยเรื่องเดียวกันทำให้แอดมินต้องตอบ 100 ครั้งด้วยคำตอบเดียวกัน — **คู่มือคือการตอบครั้งเดียวแล้วใช้ได้กับทุกคน**

---

## 1. ความสัมพันธ์กับระบบแจ้งปัญหา — คู่มือมาก่อน ถามแอดมินเป็นทางออกสุดท้าย

```
กดปุ่มซัพพอร์ต ──▶ เลือก "วิธีใช้งาน"
                       │
                       ▼
         เปิดบทความคู่มือ "ของหน้าที่ยืนอยู่" ทันที      ◀── จบที่นี่เป็นส่วนใหญ่
                       │
                       ▼  อ่านแล้วยังไม่เข้าใจ
         ปุ่ม "ยังไม่ได้คำตอบ ถามแอดมิน"
                       │
                       ▼
         ส่งเป็น support_requests (type = how_to) พร้อม manual_slug ที่อ่านไปแล้ว
```

‼️ **ต้องพาไปบทความของหน้าที่ผู้ใช้ยืนอยู่โดยตรง ไม่ใช่โยนไปหน้ารวมให้หาเอง** — ทำได้ฟรีเพราะระบบแจ้งปัญหาเก็บ `page_url` จากฝั่งเซิร์ฟเวอร์อยู่แล้ว ระบบรู้อยู่แล้วว่าผู้ใช้กดปุ่มจากหน้าไหน

### ห้ามตัดประเภท `how_to` ออกทั้งหมด

แม้คู่มือจะรับภาระคำถามซ้ำไปเกือบทั้งหมดแล้ว ยังต้องเหลือช่องถามไว้ ด้วยเหตุผล 2 ข้อ

1. **ถ้าอ่านคู่มือแล้วยังไม่เข้าใจและไม่มีทางถาม ผู้ใช้จะไปกรอกเป็น "แจ้งบัค" แทน** — คิวบัคของแอดมินจะปนเปื้อนด้วยคำถามวิธีใช้ ซึ่งทำลายประโยชน์ของคอลัมน์ `type` ที่ออกแบบมาแยกไว้ตั้งแต่ต้น
2. **เรื่องที่ถูกถามหลังอ่านคู่มือแล้ว = สัญญาณว่าบทความนั้นอธิบายไม่พอ** ซึ่งมีค่ามาก แก้บทความ 1 ครั้งแล้วคนต่อไปไม่ถามอีก — **เปลี่ยนงาน "ตอบซ้ำ 100 ครั้ง" ให้เป็น "แก้เอกสาร 1 ครั้ง"**

> **"คู่มือ" ไม่ใช่ค่าที่ 4 ของคอลัมน์ `type`** — การเปิดอ่านคู่มือไม่มีเรื่องอะไรถูกส่งถึงแอดมินและไม่มีอะไรถูกบันทึกเป็นคำร้อง มันคือปุ่มนำทาง · ถ้าเอาไปใส่ใน `type` คิวแอดมินจะรกด้วยแถวที่ไม่มีใครต้องทำอะไร

## 2. ที่เก็บเนื้อหา — เป็นไฟล์ในโปรเจค ไม่ใช่ตารางในฐานข้อมูล

```
app/Views/manuals/{lang}/{slug}.php     เนื้อหาบทความ แยกตามภาษา
config/manuals.php                      ทะเบียนบทความ (โครงสร้าง สิทธิ์ การผูกกับหน้า)
public/assets/manuals/{slug}/01.png     รูปประกอบ ใช้ร่วมกันทุกภาษา
```

**เหตุผลที่ไม่เก็บใน DB พร้อมหน้าแอดมินแก้**

1. ‼️ **คู่มือใน DB เพี้ยนออกจากโค้ดแบบเงียบๆ** — แก้ UI วันนี้ คู่มือยังบอกวิธีเดิมและไม่มีใครรู้ · **คู่มือที่เป็นไฟล์บังคับให้แก้พร้อมโค้ดใน commit เดียวกันได้ และเห็นใน `git diff` ตอน review**
2. ตัวแก้ไขแบบ WYSIWYG ต้องลง JS package ซึ่งชนกฎเหล็กข้อ 2
3. ไม่มีช่อง stored XSS จากตัวแก้ไข และไม่ต้องทำระบบอัปโหลดรูปสำหรับแอดมิน

**สิ่งที่แลกไป:** แอดมินที่ไม่ใช่ dev แก้เองไม่ได้ ต้อง deploy — ยอมรับได้ เพราะคู่มือควรเปลี่ยนพร้อมโค้ดที่มันอธิบายอยู่แล้ว · ถ้าวันหนึ่งจำเป็นต้องให้แอดมินแก้เอง ให้เสนอเป็นงานแยกและบันทึกใน `SCOPE.md` **ห้ามค่อยๆ ย้ายเข้า DB เอง**

## 3. โครงของบทความ 1 ชิ้น

```php
<?php
// app/Views/manuals/th/products-create.php
$manual_title   = 'วิธีเพิ่มสินค้า';
$manual_summary = 'ขั้นตอนการเพิ่มสินค้าใหม่เข้าระบบ พร้อมข้อกำหนดของแต่ละช่อง';
?>
<h2>ต้องมีสิทธิ์อะไร</h2>
<p>ผู้ใช้ระดับพนักงานขึ้นไป</p>

<h2>ขั้นตอน</h2>
<ol>
  <li>เข้าเมนู <strong>สินค้า</strong></li>
  <li>กดปุ่ม <strong>เพิ่มสินค้า</strong> มุมขวาบน</li>
  <li>กรอกรหัสสินค้า ชื่อ และราคา แล้วกดบันทึก</li>
</ol>

<figure>
  <img src="<?= e(url('/assets/manuals/products-create/01.png')) ?>" alt="หน้าฟอร์มเพิ่มสินค้า">
  <figcaption>① ปุ่มเพิ่มสินค้า ② ช่องรหัสสินค้า ห้ามซ้ำกับของเดิม ③ ปุ่มบันทึก</figcaption>
</figure>

<h2>ข้อผิดพลาดที่พบบ่อย</h2>
<ul>
  <li>รหัสสินค้าซ้ำกับที่มีอยู่แล้ว — ระบบจะไม่บันทึกและขึ้นข้อความที่ช่องนั้น</li>
</ul>
```

**หัวข้อบังคับของทุกบทความ:** ทำอะไรได้ · สิทธิ์ที่ต้องมี · ขั้นตอนเป็นข้อๆ เรียงลำดับ · รูปประกอบ · ข้อผิดพลาดที่พบบ่อย

> **ข้อยกเว้นของกฎ "ห้าม hardcode ข้อความ" ใน [`i18n.md`](i18n.md):**
> เนื้อความของบทความคู่มือเขียนตรงในไฟล์ภาษานั้นได้เลย ไม่ต้องผ่าน `__()` เพราะเป็นเนื้อความยาว ไม่ใช่ UI string — การยัดย่อหน้ายาวลงไฟล์ภาษาทำให้อ่านและ review ไม่ได้
> **แต่ต้องมีไฟล์ครบทุกภาษาที่เปิดใช้** และโฟลเดอร์นี้เป็นที่เดียวที่ถูกยกเว้นจากคำสั่งตรวจข้อความ hardcode

## 4. ทะเบียนบทความ

```php
<?php
// config/manuals.php
return [
    'products-create' => [
        'group'  => 'products',
        'icon'   => 'plus',                      // ชื่อจากชุดไอคอนกลางเท่านั้น
        'order'  => 10,
        'roles'  => ['admin', 'staff'],          // ว่าง = ทุกคนดูได้
        'routes' => ['/products/create'],        // หน้าที่กดปุ่มคู่มือแล้วมาที่บทความนี้
    ],
    'products-list' => [
        'group'  => 'products',
        'icon'   => 'view',
        'order'  => 20,
        'roles'  => [],
        'routes' => ['/products'],
    ],
];
```

- `icon` — ไอคอนของการ์ดทางเข้าในหน้ารวม · **ต้องเป็นชื่อจากชุดกลาง `check.php` จับชื่อที่ไม่มีอยู่**
- `routes` คือสิ่งที่ทำให้ deep link ในข้อ 1 ทำงาน — เทียบกับ `page_url` ที่เก็บมาจากฝั่งเซิร์ฟเวอร์
- `roles` — **บทความของแอดมินห้ามโผล่ให้ผู้ใช้ทั่วไปเห็น** ทั้งในหน้ารวมและตอนเปิดตรง **ต้องกันด้วยการเช็คสิทธิ์จริง ไม่ใช่แค่ซ่อนลิงก์**
- ‼️ **ห้ามเอา slug จาก URL ไปประกอบเป็น path ไฟล์ตรงๆ ต้องเทียบกับทะเบียนนี้ก่อนเสมอ** ไม่งั้นกลายเป็นช่องอ่านไฟล์นอกโฟลเดอร์ (path traversal)
- หน้าที่ยังไม่มีบทความ → กดคู่มือแล้วไปหน้ารวมพร้อมข้อความบอกว่ายังไม่มีบทความของหน้านี้ **ห้าม 404**

## 5. รูปประกอบ — ใช้ชุดเดียวกับทุกภาษา

- ‼️ **ห้ามฝังข้อความอธิบายลงในรูป** ให้แปะแค่ตัวเลข ①②③ ทับจุดที่ต้องกด แล้ว**เอาคำอธิบายไปไว้ใน `<figcaption>` ซึ่งแปลได้**
  > ถ้าฝังข้อความไทยในรูป รูปนั้นใช้ในคู่มือภาษาอื่นไม่ได้เลย ต้องถ่ายใหม่ทุกภาษา (1 บทความ × n ภาษา) และแก้คำผิดครั้งเดียวต้องถ่ายรูปใหม่ทั้งชุด
  > วิธีแปะเลขทำให้ **รูปชุดเดียวเสิร์ฟได้ทุกภาษา และแก้คำอธิบายได้โดยไม่ต้องถ่ายใหม่**
- เก็บที่ `public/assets/manuals/{slug}/` ตั้งชื่อเรียงเลข `01.png` `02.png`
- ทุกรูปต้องมี `alt`
- **ห้ามใช้ข้อมูลจริงของลูกค้าในภาพหน้าจอ** — ใช้ข้อมูลตัวอย่างหรือเบลอทิ้ง เพราะคู่มือเปิดดูได้กว้างกว่าหน้าที่ถ่ายมา
- ย่อขนาดไฟล์ก่อนใส่ **ห้ามแปะ screenshot ดิบความละเอียดเต็ม** เพราะหน้าคู่มือจะหนักกว่าทุกหน้าในระบบ
- ถ่ายเฉพาะจุดที่จำเป็น — **รูปยิ่งมาก ยิ่งเน่าเร็ว** ทุกรูปคือภาระที่ต้องถ่ายใหม่เมื่อ UI เปลี่ยน

## 6. หน้ารวมคู่มือ

| Method | URL | หน้าที่ |
|---|---|---|
| GET | `/manual` | หน้ารวม จัดกลุ่มตามโมดูล |
| GET | `/manual/{slug}` | บทความเดียว |

### ‼️ หน้ารวมเป็น "การ์ดทางเข้า" ไม่ใช่ "รายการลิงก์"

หน้านี้ทำหน้าที่ **เลือกทางเข้า** ไม่ใช่ **อ่านรายการ** — ใช้ `.tile-grid` / `.tile` ซึ่งเป็น component กลาง
แต่ละใบมี **ไอคอน + ชื่อบทความ + คำโปรย**

- **ชื่อบทความต้องมาจาก `$manual_title` ในตัวบทความ ห้ามแสดง slug**
  > อาการจริง: หน้ารวมขึ้นเป็นลิงก์เปล่าที่มีแต่ `getting-started` `signing-in` `audit-logs`
  > ทั้งที่ทุกบทความมี `$manual_title` / `$manual_summary` อยู่แล้วตามที่ข้อ 3 บังคับ
  > **มีข้อมูลอยู่แล้วแต่ไม่ได้เอามาใช้** — slug เป็นภาษาอังกฤษเสมอและไม่ใช่ภาษาคน
- **ห้ามเก็บชื่อบทความไว้ในทะเบียนซ้ำอีกที่** วันหนึ่งจะไม่ตรงกับชื่อในบทความ
  Controller ต้อง `include` ไฟล์บทความแล้วกลืน output ทิ้ง เพื่ออ่าน meta — **ทำในเมธอดแยก** ไม่งั้นตัวแปรของบทความรั่วไปทับตัวแปรของ Controller
- **ชื่อกลุ่มต้องผ่าน `__()`** ห้ามแสดงคีย์ดิบจากทะเบียน (`basics` `admin`) ให้ผู้ใช้เห็น
- **ไอคอนต่อบทความเก็บที่ `config/manuals.php` คีย์ `icon`** ไม่ใช่ hardcode ในหน้า
  ต้องเป็นชื่อจากชุดไอคอนกลางเท่านั้น **ห้ามไฟล์ SVG แยก**

- จัดกลุ่มตามโมดูล **ไม่ใช่เรียงตามที่นึกออก** — ใช้ `group` และ `order` จากทะเบียน
- ใช้ layout กลางและ partial เดิมทั้งหมด **ห้ามทำสไตล์แยกเฉพาะหน้าคู่มือ**
  `.tile` เป็น component กลาง หน้าสรุปและหน้าเลือกโมดูลจะใช้ตัวเดียวกันนี้
- เข้าถึงได้แม้ยังไม่ล็อกอิน สำหรับบทความที่ `roles` ว่าง — เหตุผลเดียวกับที่ปุ่มซัพพอร์ตต้องแสดงในหน้า login
- **ยังไม่มีคำแปลในภาษาที่ผู้ใช้เลือก → แสดงภาษาหลักพร้อมหมายเหตุว่ายังไม่มีคำแปล ห้าม 404 และห้ามหน้าว่าง**
- ช่องค้นหา: ใส่เมื่อบทความเยอะจนหาไม่เจอจริงๆ — **บทความไม่กี่ชิ้นไม่ต้องทำ**

## 7. ทำให้คู่มือไม่เน่า — ข้อที่สำคัญที่สุดของไฟล์นี้

**คู่มือที่บอกวิธีผิดแย่กว่าไม่มีคู่มือ** เพราะผู้ใช้ทำตามแล้วไม่ได้ผลจะเสียความเชื่อถือทั้งระบบ

- ‼️ **โมดูลที่ยังไม่มีบทความคู่มือครบทุกภาษาที่เปิดใช้ = ยังไม่ผ่านการทดสอบระดับ phase** ([`../testing.md`](../testing.md) ข้อ 2.8)
  > เหตุผลเดียวกับที่บังคับ audit log ตั้งแต่วันแรก — **ถ้าไม่ผูกกับเกณฑ์ผ่าน จะเขียนรอบเดียวตอนแรกแล้วไม่มีใครกลับมาแก้อีก**
- **แก้ UI ของหน้าไหน ต้องเปิดบทความของหน้านั้นดูว่ายังตรงอยู่ไหม ในคอมมิตเดียวกัน** ไม่ใช่ตั้งใจว่าจะกลับมาทำ
- หน้าแอดมินของระบบแจ้งปัญหาควรแสดงว่า **`manual_slug` ไหนถูกถามต่อบ่อยที่สุด** — นั่นคือรายการบทความที่ต้องแก้ก่อน เรียงตามความจริงไม่ใช่ตามความรู้สึก
- เรื่องที่ตอบแล้วซึ่งเป็นคำถามซ้ำ ให้เอาคำตอบไปเติมในบทความ **ไม่ใช่ตอบในเรื่องนั้นแล้วปิดไป**
