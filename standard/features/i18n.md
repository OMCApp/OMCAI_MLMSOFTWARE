# ระบบหลายภาษา (i18n)

> **บังคับทุกโปรเจค** — อ่านเมื่อเพิ่ม/แก้ข้อความที่ผู้ใช้เห็น สร้างหน้าใหม่ หรือเพิ่มภาษาใหม่
> กฎ escape ทำตาม [`../security.md`](../security.md) ข้อ 5 · ผลกระทบต่อ layout ทำตาม [`../design.md`](../design.md)

**บังคับอย่างน้อย `th` + `en` ทุกโปรเจค** ภาษาอื่นเปิดเพิ่มตามที่โปรเจคต้องการ — ระบุภาษาที่เปิดใช้ใน `project/BRIEF.md` และ `config/config.php`

**เหตุผลที่บังคับ:** ต้นทุนจริงของ i18n ไม่ได้อยู่ที่ไฟล์คำแปล แต่อยู่ที่ **"ทุกข้อความต้องไม่ hardcode"** ซึ่งเป็นกฎที่ทำตั้งแต่วันแรกแทบไม่มีต้นทุน แต่ย้อนกลับมาทำทีหลังต้องไล่ทุก view ทุกข้อความ validation ทุกข้อความ error ในระบบ — เหตุผลเดียวกับ audit log และ design token คือ **ของที่เพิ่มทีหลังยากที่สุด**

---

## 1. ขอบเขต — อะไรแปล อะไรไม่แปล

| ประเภท | แปลไหม | ตัวอย่าง |
|---|---|---|
| **ข้อความของระบบ** | ✅ แปล | เมนู ปุ่ม label ในฟอร์ม หัวคอลัมน์ ข้อความ validation ข้อความ error ชื่อรายงาน ชื่อสถานะ empty state |
| **ข้อมูลที่ผู้ใช้กรอก** | ❌ ไม่แปล | ชื่อสินค้า หมายเหตุ ข้อความในระบบแจ้งปัญหา ชื่อผู้ใช้ — เก็บและแสดงตามที่กรอกมา |

> **ทำไมไม่แปลข้อมูลที่ผู้ใช้กรอก:** ถ้าต้องแปลด้วย ทุกตารางที่มีข้อความต้องมีตารางคำแปลแยกหรือคอลัมน์ JSON และทุกฟอร์มต้องกรอกทุกภาษา — กระทบทุก migration ทุกฟอร์ม ทุกหน้ารายการ ตลอดอายุโปรเจค
> **ถ้าโปรเจคไหนต้องการจริง ถือว่าโจทย์เปลี่ยน ต้องกลับไปทบทวน `SCOPE.md` ก่อน ห้ามค่อยๆ แทรกเอาเอง**

## 2. ที่เก็บคำแปล

```
lang/
├── th.php      ← บังคับ
├── en.php      ← บังคับ
└── xx.php      ← เปิดเพิ่มเมื่อโปรเจคต้องการ
```

```php
<?php
// lang/th.php
return [
    'common' => [
        'save'   => 'บันทึก',
        'cancel' => 'ยกเลิก',
        'search' => 'ค้นหา',
    ],
    'product' => [
        'title'   => 'สินค้า',
        'create'  => 'เพิ่มสินค้า',
        'deleted' => 'ลบ :name แล้ว',
        'status'  => [
            'active'   => 'ใช้งานอยู่',
            'inactive' => 'ปิดใช้งาน',
        ],
    ],
];
```

- **key เป็นภาษาอังกฤษ `snake_case` จัดกลุ่มตามโมดูล** + กลุ่ม `common` สำหรับของที่ใช้ทั้งระบบ
- ‼️ **ห้ามใช้ข้อความไทยเป็น key** เช่น `__('บันทึก')` — วันที่แก้คำไทย key จะพังทั้งระบบพร้อมกัน และหาไม่เจอว่าตรงไหนใช้อยู่
- **ทุกไฟล์ภาษาต้องมี key ครบเท่ากัน** ตรวจอัตโนมัติได้ตามข้อ 9
- ไฟล์ภาษาไม่ใช่ที่เก็บเนื้อความยาว — คู่มือการใช้งานอยู่ที่ [`manual.md`](manual.md)

## 3. helper กลางจุดเดียว

ต้องมี `core/Lang.php` + ฟังก์ชัน `__()` เป็นตัวย่อ **จุดเดียวทั้งระบบ** ห้ามอ่านไฟล์ภาษาตรงๆ กระจายหลายที่ (แนวเดียวกับ `Auth::id()`)

```php
__('common.save');                            // บันทึก
__('product.deleted', ['name' => $name]);     // ลบ เก้าอี้ไม้ แล้ว
__('product.status.' . $product['status']);   // แปล key ที่เก็บในฐานข้อมูล (ดูข้อ 5)
```

### กฎความปลอดภัยของ helper — สำคัญ

- **ห้ามใส่แท็ก HTML ในไฟล์ภาษา** ทุกค่าต้องเป็นข้อความเปล่า
- **helper ต้อง `htmlspecialchars()` ค่าที่แทนใน placeholder ทุกตัวอัตโนมัติ** เพราะค่าที่แทนมักเป็นข้อมูลจากผู้ใช้
- สองข้อข้างบนรวมกันทำให้ **ผลลัพธ์ของ `__()` เอาไปแสดงได้ตรงๆ อย่างปลอดภัย ไม่ต้อง escape ซ้ำ**
- ⚠️ **ข้อมูลจากฐานข้อมูลหรือผู้ใช้ที่ไม่ได้ผ่าน `__()` ยังต้องผ่าน `e()` ตามกฎเหล็กข้อ 6 เหมือนเดิม** — i18n ไม่ได้ยกเว้นข้อนั้น

**key ที่หาไม่เจอ:** `APP_ENV=development` ให้แสดง key ดิบให้เห็นชัดว่าตกหล่น · `production` ให้ fallback เป็นภาษาหลัก **ห้ามแสดงเป็นช่องว่างเปล่า** เพราะจะกลายเป็นปุ่มไม่มีข้อความบนเครื่องจริงโดยไม่มีใครรู้

## 4. การเลือกภาษาของผู้ใช้

ลำดับความสำคัญ — ตัวบนสุดที่มีค่าชนะ

| # | แหล่ง | ใช้ตอน |
|---|---|---|
| 1 | `?lang=` ใน URL | ส่งลิงก์ให้คนอื่นดูภาษาที่ระบุ / ทดสอบ |
| 2 | `users.locale` | ผู้ใช้ที่ล็อกอินและตั้งค่าไว้แล้ว |
| 3 | `$_SESSION` | ผู้ใช้ที่กดสลับภาษาในรอบนี้ |
| 4 | `Accept-Language` | ผู้ใช้ใหม่ที่ยังไม่เคยเลือก |
| 5 | ค่า default ใน `config/config.php` | ทางสุดท้าย |

```php
// config/config.php
'locales'        => ['th', 'en'],
'default_locale' => 'th',
```

- ‼️ **ต้องตรวจค่าภาษากับ allowlist ก่อนใช้ทุกครั้ง** — **ห้ามเอาค่าจาก `$_GET['lang']` ไปประกอบเป็นชื่อไฟล์ตรงๆ เด็ดขาด** เพราะจะกลายเป็นช่องอ่านไฟล์นอกโฟลเดอร์ (path traversal) ทันที
- ปุ่มสลับภาษาอยู่ใน **layout กลาง** ไม่ใช่ใส่แยกทีละหน้า · **สลับแล้วต้องอยู่หน้าเดิม ไม่เด้งกลับหน้าแรก**
- ต้องมีคอลัมน์ `users.locale` เพื่อจำค่าข้ามอุปกรณ์ — สลับแล้วต้องคงอยู่หลัง logout/login
- **ไม่ต้องบันทึก audit log ตอนผู้ใช้สลับภาษาตัวเอง** เพราะไม่ใช่การเปลี่ยนข้อมูลธุรกิจ — แต่การที่**แอดมินเปลี่ยน locale ของผู้ใช้คนอื่น** ถือเป็นการแก้ข้อมูล ต้องลง log ตามปกติ

## 5. ค่าที่เก็บในฐานข้อมูลต้องเป็น key ไม่ใช่ข้อความแสดงผล

**นี่คือข้อที่พลาดแล้วแก้ทีหลังแพงที่สุดในไฟล์นี้**

| | ❌ ผิด | ✅ ถูก |
|---|---|---|
| `status` | `'เสร็จสิ้น'` | `'done'` แล้วแปลตอนแสดงด้วย `__('support.status.done')` |
| `type` | `'แจ้งบัค'` | `'bug'` |
| `role` | `'ผู้ดูแลระบบ'` | `'admin'` |

เหตุผล

1. ข้อความไทยในฐานข้อมูลแปลเป็นภาษาอื่นไม่ได้เลย
2. วันที่แก้คำแสดงผล ข้อมูลเก่าทั้งหมดจะไม่ match กับค่าใหม่
3. query กรองตามสถานะจะผูกกับภาษา

- `audit_logs.action` ทำถูกอยู่แล้ว (`create` / `update` / `delete`) — ใช้เป็นแบบอย่าง
- ค่าที่เอาไปประกอบเป็น key แปล (`__('x.status.' . $row['status'])`) **ต้องผ่าน allowlist มาแล้วเสมอ**

## 6. วันที่ เวลา และตัวเลข

- timezone ตั้ง `Asia/Bangkok` **ที่จุดเดียว** ตามเดิม — แต่ **รูปแบบการแสดงผลต้องผูกกับภาษา** ไม่ใช่ format ตายตัวทั้งระบบ
- `th` → พุทธศักราช · ภาษาอื่น → คริสต์ศักราช
- ต้องมี helper กลาง `formatDate()` / `formatMoney()` **ห้ามเรียก `date()` กระจายในหลาย view** ไม่งั้นเพิ่มภาษาแล้วต้องไล่แก้ทุกหน้า
- ‼️ **ฐานข้อมูลเก็บเป็นคริสต์ศักราชเสมอ แปลงเป็น พ.ศ. ตอนแสดงเท่านั้น** — เผลอเก็บ พ.ศ. ลงฐานข้อมูล การเรียงลำดับและการคำนวณช่วงวันจะเพี้ยนทั้งระบบและกู้ยาก
- **ตัวกรองช่วงวันในหน้ารายงานรับค่าเป็น ค.ศ. เสมอ** ไม่ว่าจะแสดงเป็น พ.ศ. ให้ผู้ใช้เห็นก็ตาม
- ข้อนี้เป็นข้อยกเว้นของกฎ "รูปแบบวันที่เหมือนกันทั้งระบบ" ใน [`../components.md`](../components.md) — ให้อ่านว่า **เหมือนกันทั้งระบบภายในภาษาเดียวกัน**

## 6ก. ‼️ ข้อความฝั่ง JavaScript

**JS อ่านไฟล์ภาษาของ PHP ไม่ได้ และ CSP ห้าม inline script** — ถ้าไม่มีทางส่งข้อความข้ามฝั่ง คนเขียนจะ hardcode ภาษาไทยลง `app.js` แล้ววันที่เพิ่มภาษาใหม่ ข้อความฝั่ง JS จะไม่แปลตาม **โดยไม่มีอะไรจับได้**

### กฎ

1. **ห้าม hardcode ข้อความใดๆ ใน `public/assets/js/app.js`** ทุกคำที่ผู้ใช้เห็นต้องผ่าน `__()` ก่อน
2. **ของทั้งระบบ** ส่งผ่าน `app/Views/partials/js-lang.php` ซึ่ง layout กลางทุกตัว include ไว้แล้ว
3. **ของเฉพาะหน้า** ใส่เป็น `data-*` ที่ element ของหน้านั้น ไม่ต้องยัดเข้าของกลาง
4. ‼️ **สิ่งที่ `Intl` ของเบราว์เซอร์ให้ได้ ห้ามส่ง** — ชื่อเดือน ชื่อวัน รูปแบบวันที่ พ.ศ.
   ใช้ `Intl.DateTimeFormat(locale)` แทน · ส่งมาเองเมื่อไหร่ = มีคำแปลซ้ำสองที่ แล้ววันหนึ่งจะไม่ตรงกัน

```php
<!-- partials/js-lang.php -->
<span id="js-lang" hidden
      data-locale="<?= e(locale()) ?>"
      data-clear="<?= e(__('ui.clear')) ?>"
      data-no-results="<?= e(__('ui.no_results')) ?>"></span>
```

```js
const L = document.getElementById('js-lang').dataset;
// ชื่อเดือนไม่ต้องส่งมา — เบราว์เซอร์รู้อยู่แล้ว
const month = new Intl.DateTimeFormat(L.locale, { month: 'long' }).format(date);
```

> ‼️ ข้อนี้เคยไม่มีอยู่ในมาตรฐานเลย ทั้งที่ JS มีข้อความที่ผู้ใช้เห็นอยู่จริง
> (ชื่อเดือนในปฏิทิน · ปุ่มล้าง · placeholder ของช่องค้นหา · ข้อความตอนไม่พบผลลัพธ์)

## 7. ผลกระทบต่อหน้าตา — ออกแบบเผื่อไว้ ไม่ใช่ไปแก้ทีหลัง

- **ฟอนต์:** ไม่มีฟอนต์ตัวเดียวที่ครอบคลุมไทย + จีน + ละตินได้ดีพร้อมกัน **ถ้าโปรเจคเปิดภาษาจีนหรือญี่ปุ่น ต้องมี fallback CJK ใน font stack** · ไทยมีสระบน-ล่างซ้อนกัน จีนเป็นตัวสี่เหลี่ยมทึบ — ความสูงบรรทัดและความสูงแถวตารางต้องทดสอบใหม่ทุกภาษา
- **ความยาวข้อความต่างกันมาก** — อังกฤษยาวกว่าไทยประมาณ 20-30% จีนสั้นกว่าไทย · ปุ่ม หัวคอลัมน์ และ label ที่พอดีในภาษาไทยจะพังในภาษาอังกฤษ
- **ห้ามกำหนดความกว้างปุ่มหรือคอลัมน์แบบตายตัวให้พอดีข้อความภาษาไทย**
- ‼️ **ห้ามต่อประโยคจากหลาย key** เช่น `__('deleted') . $name . __('success')` — ลำดับคำแต่ละภาษาไม่เหมือนกัน **ต้องใช้ประโยคเต็มที่มี placeholder** (`'ลบ :name แล้ว'`) เสมอ
- **ห้ามใช้รูปภาพที่มีข้อความฝังอยู่เป็นส่วนของ UI** เพราะแปลไม่ได้ (ข้อยกเว้นเรื่องรูปในคู่มือดู [`manual.md`](manual.md) · ภาพที่ตัดจากภาพแบบของผู้ใช้ดู [`../design.md`](../design.md) 7ก.5)
- ตอนตรวจงานต้อง**เปิดหน้าจอจริงครบทุกภาษาที่เปิดใช้** ไม่ใช่แค่ 3 ขนาดจอ

## 8. เพิ่มภาษาใหม่ภายหลัง

1. ก็อป `lang/en.php` เป็นไฟล์ภาษาใหม่ แล้วแปลให้ครบทุก key
2. เพิ่มรหัสภาษาใน `config/config.php` ช่อง `locales`
3. ตรวจว่าฟอนต์รองรับตัวอักษรของภาษานั้น ([`../design.md`](../design.md))
4. เปิดหน้าจอจริงตรวจทุกหน้าหลัก — **ความยาวข้อความที่เปลี่ยนไปคือจุดที่พังบ่อยที่สุด**
5. เพิ่มบทความคู่มือของภาษานั้นตาม [`manual.md`](manual.md)

> **ถ้าทำตามข้อ 1-7 ครบ การเพิ่มภาษาใหม่ไม่ต้องแตะโค้ดแม้แต่บรรทัดเดียว** — นี่คือผลตอบแทนทั้งหมดของกฎในไฟล์นี้
> **ถ้าเพิ่มภาษาแล้วยังต้องไล่แก้ view แปลว่ามีข้อความ hardcode หลุดอยู่**

## 9. ตรวจอัตโนมัติ — ไม่ต้องพึ่งว่าใครจำได้

สองอย่างนี้ตรวจด้วยเครื่องได้ 100% จึงอยู่ใน `scripts/check.php` และ pre-commit hook **ไม่ฝากไว้กับความจำของคนหรือ AI**

```bash
php scripts/check.php lang
```

### ก. ไฟล์ภาษาครบตรงกัน — ตรวจ 5 อย่างในครั้งเดียว

| ตรวจอะไร | ทำไมสำคัญ |
|---|---|
| **key ที่ขาด** ในบางภาษา | ปุ่มไม่มีข้อความบนเครื่องจริงโดยไม่มีใครรู้ |
| **ค่าว่าง** — key มีแต่ยังไม่ได้แปล | อาการเหมือนข้างบน แต่หาไม่เจอเพราะ key มีอยู่ |
| **โครงสร้างไม่ตรงกัน** — ภาษาหนึ่งเป็นข้อความ อีกภาษาเป็นกลุ่มย่อย | `__('x.status.active')` จะพังเฉพาะบางภาษา |
| **แท็ก HTML ในไฟล์ภาษา** | ผิดข้อ 3 และทำให้สัญญา "ผลลัพธ์ของ `__()` แสดงได้ตรงๆ อย่างปลอดภัย" ใช้ไม่ได้ |
| **placeholder ไม่ตรงกัน** (`:name` มีในภาษาหนึ่งแต่ขาดในอีกภาษา) | ค่าที่ส่งเข้าไปจะหายเงียบๆ ไม่มี error ให้เห็น |

- ขาดโฟลเดอร์ `lang/` หรือขาด `th.php`/`en.php` → fail ทันที เพราะเป็นมาตรฐานบังคับ
- ภาษาอ้างอิงสำหรับเทียบ placeholder คือ `th`

### ข. ไม่มีข้อความ hardcode ค้างในโค้ด

- ตรวจ `app/` และ `core/` ทั้งหมด
- **คอมเมนต์ภาษาไทยไม่ถูกจับ** เพราะสคริปต์แยกส่วนของโค้ดด้วย `token_get_all()` แล้วตรวจเฉพาะ inline HTML และ string literal — คอมเมนต์เป็นสิ่งที่อนุญาต
- โฟลเดอร์ `app/Views/manuals/` ถูกยกเว้นเพราะเป็นเนื้อความยาวของคู่มือ
- สคริปต์เดียวกันตรวจค่าสี/ขนาดที่หลุดออกนอก design token ให้ด้วยในครั้งเดียว

## 10. เกณฑ์ตรวจก่อนบอกว่าเสร็จ

- [ ] ไม่มีข้อความที่ผู้ใช้เห็น hardcode อยู่ใน view, Controller หรือ Service — ผ่านคำสั่งตรวจข้อ 9
- [ ] ไฟล์ภาษาทุกไฟล์มี key ครบเท่ากัน ไม่มีตกหล่น
- [ ] ค่า `status` / `type` / `role` ในฐานข้อมูลเป็น key อังกฤษ ไม่ใช่ข้อความแสดงผล
- [ ] สลับภาษาแล้วทุกหน้าเปลี่ยนครบ ไม่มีคำค้างภาษาเดิม **รวมข้อความ validation และ error**
- [ ] เปิดหน้าจอจริงครบทุกภาษา × 3 ขนาดจอ × ทั้งสองโหมด — ไม่มีปุ่มหรือคอลัมน์ที่ข้อความล้นหรือถูกตัด
- [ ] วันที่แสดงตามภาษาถูกต้อง และค่าในฐานข้อมูลยังเป็น ค.ศ.
- [ ] สลับภาษาแล้วค่าคงอยู่หลัง logout/login (บันทึกลง `users.locale` จริง)
- [ ] **ไม่มีประโยคที่ประกอบจากหลาย key ต่อกัน**
