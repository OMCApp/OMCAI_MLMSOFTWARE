# ระบบแจ้งปัญหาจากผู้ใช้ (Support System)

> **บังคับทุกโปรเจค** — อ่านเมื่อสร้างหรือแก้ไขระบบแจ้งปัญหา
> กฎความปลอดภัยทำตาม [`../security.md`](../security.md) · รายละเอียดหน้าตาทำตาม [`../components.md`](../components.md) — ไฟล์นี้บอกแค่ว่าต้องมีอะไร
> **หน้าคู่มืออยู่ที่ [`manual.md`](manual.md)** — ปุ่มในไฟล์นี้เป็นจุดเข้าถึงคู่มือด้วย และประเภท "วิธีใช้งาน" ต้องให้คู่มือตอบก่อนเสมอ

ทุกระบบต้องมีช่องทางให้ผู้ใช้ส่งเรื่องถึงแอดมินได้โดยตรงจากในระบบ ครอบคลุม **3 ประเภท**: แจ้งบัค · ขอเพิ่มฟีเจอร์ · ถามวิธีใช้งาน

**เหตุผลที่บังคับ:** ถ้าไม่มีช่องทางนี้ ผู้ใช้จะแจ้งปัญหาทางโทรศัพท์หรือแชทด้วยข้อมูลที่สืบต่อไม่ได้ ("กดแล้วไม่ขึ้น") แอดมินต้องเสียเวลาสอบถามย้อนหลังว่าอยู่หน้าไหน ทำอะไรอยู่ ตอนกี่โมง — **ปัญหาหลายอย่างหาไม่เจอเพราะข้อมูลไม่พอ**

---

## 1. UI ที่ผู้ใช้เห็น

### 1.1 ปุ่ม Support

- **เป็นปุ่มไอคอนลอย ตำแหน่งคงที่ทุกหน้า** วางในมุมที่ไม่บังเนื้อหาหลัก (ค่าเริ่มต้น: มุมล่างขวา)
- **ต้องอยู่ใน layout กลาง** (`app/Views/layouts/`) ไม่ใช่ใส่แยกทีละหน้า
- **แสดงทุกหน้ารวมถึงหน้าที่ยังไม่ล็อกอิน** เพราะผู้ใช้ที่เข้าระบบไม่ได้ก็ต้องแจ้งปัญหาได้เช่นกัน
- ถ้าระบบมีปุ่มลอยอื่นอยู่แล้ว ต้องจัดตำแหน่งไม่ให้ทับกัน
- ต้องมี `aria-label` และ tooltip ตามกฎปุ่มไอคอนล้วน

### 1.2 Modal เมื่อกดปุ่ม

กดแล้วเปิด modal ทันที ไม่เปลี่ยนหน้า มี 2 ส่วน

**ส่วนที่ 1 — เลือกประเภท** (แสดงเป็นตัวเลือกให้กดก่อนเห็นฟอร์ม)

| ประเภท | ใช้เมื่อ | ปลายทาง |
|---|---|---|
| 🐛 **แจ้งบัค** | ระบบทำงานผิดพลาด | ฟอร์ม → `type = bug` |
| ✨ **ขอเพิ่มฟีเจอร์** | อยากได้ความสามารถที่ยังไม่มี | ฟอร์ม → `type = feature_request` |
| ❓ **วิธีใช้งาน** | ไม่แน่ใจว่าหน้าที่กำลังดูอยู่ใช้ยังไง | **เปิดบทความคู่มือของหน้านั้นก่อน** → ยังไม่ได้คำตอบค่อยส่งฟอร์ม `type = how_to` |
| 📖 **คู่มือทั้งระบบ** | อยากดูวิธีใช้หน้าอื่นด้วย | ลิงก์ไป `/manual` — **ไม่ใช่ประเภทของคำร้อง ไม่มีอะไรถูกบันทึก** |

> ‼️ **แถวสุดท้ายไม่ใช่ค่าที่ 4 ของคอลัมน์ `type`** — `type` มี 3 ค่าเท่านั้น การเปิดอ่านคู่มือไม่มีเรื่องถูกส่งถึงแอดมิน ถ้าเอาไปใส่ใน `type` คิวแอดมินจะรกด้วยแถวที่ไม่มีใครต้องทำอะไร และกฎอัตโนมัติในข้อ 6 จะตัดสินผิด
>
> ‼️ **ประเภท "วิธีใช้งาน" ต้องให้คู่มือตอบก่อนเสมอ ห้ามพาเข้าฟอร์มถามแอดมินทันที** — ผู้ใช้ 100 คนสงสัยเรื่องเดียวกัน แอดมินจะต้องตอบ 100 ครั้งด้วยคำตอบเดียวกัน

**ส่วนที่ 2 — ฟอร์ม** (เปลี่ยนคำอธิบายตามประเภทที่เลือก)

- ช่องข้อความ (บังคับ) — label เปลี่ยนตามประเภท เช่น "อธิบายปัญหาที่พบ" / "อธิบายฟีเจอร์ที่ต้องการ" / "อยากรู้เรื่องอะไรเกี่ยวกับหน้านี้"
- แนบภาพหน้าจอ (ไม่บังคับ) — ใช้ component อัปโหลดกลาง
- ปุ่มส่ง (กันกดซ้ำตามกฎปุ่ม)

**หลังส่ง:** แสดงข้อความยืนยันใน modal เดิม แล้วปิด — ไม่ต้อง reload หน้า

## 2. ข้อมูลที่ระบบต้องเก็บ "อัตโนมัติ" — สำคัญที่สุด

**ผู้ใช้ทั่วไปอธิบายปัญหาเชิงเทคนิคไม่ได้ ระบบต้องเก็บบริบทให้เอง ไม่ใช่รอให้ผู้ใช้กรอก**

| ข้อมูล | อัตโนมัติ | หมายเหตุ |
|---|---|---|
| URL ของหน้าที่กดปุ่ม | ✅ | **สำคัญมากสำหรับประเภท "วิธีใช้งาน"** เพราะคำถามผูกกับหน้านั้นโดยตรง — วิธีเก็บดู 2.1 |
| ผู้ใช้ที่แจ้ง | ✅ | ถ้าล็อกอิน — เก็บ `user_id` ผ่าน `Auth::id()` ไม่ใช่ชื่อ |
| วันเวลาที่แจ้ง | ✅ | |
| รหัสอ้างอิง error | ✅ ถ้ามี | เก็บรหัสอ้างอิง error ล่าสุดของ session นี้ถ้าเพิ่งเกิดขึ้น — **ว่างได้ ไม่ต้องบังคับผู้ใช้กรอกเอง** |
| browser / อุปกรณ์ | ✅ | จาก User-Agent |
| ภาษาและโหมดที่ใช้อยู่ | ✅ | บั๊กหลายอย่างเกิดเฉพาะบางภาษาหรือโหมดมืด |
| ข้อความที่ผู้ใช้พิมพ์ | ผู้ใช้กรอก | |
| ประเภท | ผู้ใช้เลือก | |
| ภาพหน้าจอ | ผู้ใช้แนบ (ถ้ามี) | ต้องทำตามกฎ file upload ใน [`../security.md`](../security.md) ทุกข้อ |

### 2.1 วิธีเก็บ URL ให้ถูกต้อง — ผู้ใช้ห้ามต้องกรอกเอง

ปุ่ม support อยู่ใน layout กลาง ตัว Controller ที่ render หน้านั้น **รู้ URL ปัจจุบันอยู่แล้วจากฝั่งเซิร์ฟเวอร์** ไม่ต้องใช้ JavaScript อ่านจากเบราว์เซอร์ ให้ฝังเป็น hidden field ตั้งแต่ตอน render

```php
<input type="hidden" name="page_url" value="<?= e($_SERVER['REQUEST_URI']) ?>">
```

- ‼️ **ต้องเก็บ URL แบบเต็มรวม query string** (เช่น `/dashboard?month=2026-07&branch=2`) ไม่ใช่แค่ path
  > เคส "ข้อมูลแสดงผิด" มักขึ้นกับตัวกรองที่เลือกอยู่ตอนนั้น ถ้าเก็บแค่ path แอดมินเปิดตามไปดูแล้วจะไม่เห็นข้อมูลชุดเดียวกับที่ผู้ใช้เจอ — และมาตรฐานนี้บังคับให้ตัวกรองอยู่ใน query string อยู่แล้ว จึงได้ประโยชน์นี้ฟรี
- ผู้ใช้ **ไม่มีช่องให้แก้ค่านี้ในฟอร์ม** เป็นค่าที่ระบบกำหนดให้เท่านั้น
- ห้ามเชื่อค่าที่ส่งมาจาก client โดยไม่ validate รูปแบบก่อนบันทึก

## 3. โครงสร้างข้อมูล

ตาราง `support_requests`

| คอลัมน์ | หมายเหตุ |
|---|---|
| `id` | |
| `user_id` | ว่างได้ (ผู้ใช้ที่ไม่ล็อกอินก็แจ้งได้) |
| `type` | `bug` / `feature_request` / `how_to` |
| `page_url` | หน้าที่กดปุ่ม รวม query string |
| `error_reference` | ว่างได้ — เชื่อมกับ log (มีความหมายเฉพาะ `type = bug`) |
| `manual_slug` | ว่างได้ — บทความคู่มือที่ผู้ใช้อ่านไปแล้วก่อนกดถามแอดมิน (มีความหมายเฉพาะ `type = how_to`) |
| `message` | ข้อความจากผู้ใช้ |
| `user_agent` | browser/อุปกรณ์ |
| `locale` · `theme` | ภาษาและโหมดที่ใช้อยู่ตอนแจ้ง |
| `ip_address` | **จำเป็นสำหรับ rate limit ของผู้ใช้ที่ไม่ได้ล็อกอิน** — ไม่เก็บแล้วจำกัดจำนวนครั้งต่อ IP ไม่ได้เลย |
| `attachment_path` | ว่างได้ |
| `status` | `new` / `acknowledged` / `in_progress` / `done` / `rejected` |
| `admin_note` | บันทึกของแอดมิน — **ห้ามแสดงให้ผู้ใช้เห็น** |
| `created_at` · `updated_at` · `resolved_at` | |

> ‼️ **`status` และ `type` ต้องเก็บเป็น key ภาษาอังกฤษ ห้ามเก็บข้อความไทยที่ใช้แสดงผล** แปลตอนแสดงด้วย `__('support.status.' . $row['status'])`

> **เหตุผลที่ทั้ง 3 ประเภทอยู่ตารางเดียวกัน:** โครงสร้างข้อมูลเหมือนกันเกือบทั้งหมด (ต่างแค่ความหมายของบางฟิลด์) และแอดมินอยากเห็นทุกเรื่องที่เข้ามาในที่เดียว — การกรองตาม `type` ในหน้าแอดมินง่ายกว่าเขียน query รวมหลายตาราง

## 4. หน้าแอดมิน

ทำตามสเปกหน้ารายงานใน [`../components.md`](../components.md) — ตัวกรอง + ช่วงวัน + เรียงลำดับ + แบ่งหน้า ครบ

- กรองได้ตาม `type` · `status` · ช่วงวัน · ผู้ใช้
- คลิกเข้าไปดูรายละเอียด พร้อมแก้ `status` และเขียน `admin_note`
- **ถ้ามี `error_reference` ให้มีลิงก์พาไปดู log ที่เกี่ยวข้องโดยตรง** ไม่ต้องให้แอดมินไปค้นเอง
- **ถ้ามี `page_url` ให้กดเปิดหน้านั้นได้เลย** เพื่อดูสิ่งที่ผู้ใช้เห็น
- แสดงว่า **`manual_slug` ไหนถูกถามต่อบ่อยที่สุด** — นั่นคือรายการบทความคู่มือที่ต้องแก้ก่อน
- เข้าถึงได้เฉพาะบทบาทที่มีสิทธิ์แอดมิน ผ่าน Middleware

## 5. ความปลอดภัยของระบบแจ้งปัญหาเอง

**ระบบนี้เป็นจุดที่ผู้ใช้ภายนอกส่งข้อมูลเข้ามาตรงๆ จึงต้องระวังเป็นพิเศษ**

- ‼️ **ข้อความจากผู้ใช้ต้องผ่าน `e()` ก่อนแสดงในหน้าแอดมินเสมอ** — ลืมแล้วผู้ใช้ที่ไม่หวังดีส่งสคริปต์เข้ามา สคริปต์นั้นจะรันในเบราว์เซอร์ของแอดมินที่มีสิทธิ์สูงสุด (stored XSS) · นี่คือช่องโหว่ที่มักถูกมองข้ามเพราะคิดว่า "หน้าแอดมินอยู่ข้างใน ปลอดภัยแล้ว"
- **ต้องจำกัดจำนวนครั้งการส่ง (rate limit)** เช่นไม่เกิน 5 ครั้งต่อชั่วโมงต่อผู้ใช้/IP ไม่งั้นจะถูกยิงสแปมจนตารางเต็ม
- ฟอร์มต้องมี CSRF token เหมือนฟอร์มอื่น
- validate ความยาวข้อความ · `type` ต้องอยู่ใน 3 ค่าที่กำหนดเท่านั้น · ชนิดไฟล์แนบ ก่อนบันทึกทุกครั้ง
- **`manual_slug` ที่รับมาต้องเทียบกับทะเบียนใน `config/manuals.php` ก่อนบันทึก** ห้ามเชื่อค่าจาก client ตรงๆ
- **ห้ามเก็บข้อมูล sensitive ลงในบริบทที่เก็บอัตโนมัติ** — เก็บ URL ได้ แต่ห้ามเก็บ session token, cookie, หรือค่าในช่องรหัสผ่านที่ผู้ใช้กรอกไว้ในหน้านั้น
- ไฟล์แนบต้องเก็บนอก `public/` และเสิร์ฟผ่าน Controller ที่ตรวจสิทธิ์แอดมินก่อน

## 6. การเตรียมรองรับระบบอัตโนมัติด้วย AI

เป้าหมายระยะถัดไปคือให้ AI รับเรื่องจากผู้ใช้แล้วช่วยจัดการโดยไม่ต้องผ่านแอดมินทุกครั้ง — **แต่ความปลอดภัยที่ทำได้ต่างกันตามประเภท ต้องแยกพิจารณา ไม่ใช่เปิดอัตโนมัติทั้งหมดพร้อมกัน**

| ประเภท | ระดับอัตโนมัติที่ปลอดภัย | เหตุผล |
|---|---|---|
| **วิธีใช้งาน** | ✅ ทำอัตโนมัติได้ก่อนเพื่อน | เป็นการตอบคำถาม ไม่แก้โค้ด/ข้อมูล ความเสี่ยงต่ำที่สุด — **ให้ AI ตอบจากบทความคู่มือของหน้านั้นเป็นแหล่งความรู้** ตอบไม่ได้ค่อยส่งต่อแอดมิน |
| **แจ้งบัค** | ⚠️ ให้ AI *วิเคราะห์และเสนอวิธีแก้* ได้ แต่**ห้ามแก้โค้ดหรือข้อมูลใน production โดยไม่มีคนตรวจ** | ปัญหาที่ผู้ใช้แจ้งมักมาจากความเข้าใจผิด ไม่ใช่บัคจริงเสมอไป ปล่อยให้แก้อัตโนมัติจะสร้างปัญหาใหม่ที่หนักกว่าเดิม |
| **ขอเพิ่มฟีเจอร์** | ❌ ไม่ควรให้ AI ตัดสินใจทำเอง | เป็นการตัดสินใจเชิงผลิตภัณฑ์และลำดับความสำคัญ ไม่ใช่เรื่องที่มี "คำตอบถูก" ให้ AI หา ต้องอยู่ในมือแอดมินเสมอ |

**สิ่งที่ต้องทำตอนนี้เพื่อไม่ต้องรื้อทีหลัง**

- **เก็บข้อมูลเป็นคอลัมน์แยก ไม่ใช่ก้อนข้อความเดียว** เพราะ AI ต้องอ่านบริบทแบบมีโครงสร้าง — เก็บเป็นข้อความยาวก้อนเดียวหรือส่งเข้าอีเมลแอดมินอย่างเดียว จะต่อยอดไม่ได้เลย
- **คอลัมน์ `type` คือฐานของการแยกกฎอัตโนมัติข้างบน**
- **เชื่อม `error_reference` กับ log จริงให้ได้** — เป็นสะพานเดียวที่พาไปถึงรายละเอียดทางเทคนิคของปัญหานั้น
- **เก็บประวัติเรื่องที่แก้แล้ว/ตอบแล้วไว้ ไม่ต้องลบ** — เป็นฐานข้อมูลที่ใช้ตอบผู้ใช้คนต่อไปที่เจอเรื่องเดียวกัน
- ‼️ **คำถามประเภท "วิธีใช้งาน" ที่ตอบแล้ว ต้องเอาคำตอบไปเติมในบทความคู่มือ ไม่ใช่ตอบในเรื่องนั้นแล้วปิดไป** — ไม่งั้นคนต่อไปก็ถามซ้ำอีก

- [ ] ส่งเรื่องเข้า `support_requests` ได้จริง พร้อมบริบทอัตโนมัติครบ (URL เต็มรวม query string · user · error_reference · user_agent · locale · theme)
- [ ] หน้าแอดมินเปิดดู กรอง และแก้สถานะได้ · **escape ข้อความจากผู้ใช้แล้ว**
- [ ] ผู้ใช้ที่ไม่ใช่แอดมินเปิดหน้าแอดมินไม่ได้ **ทดสอบด้วยการเรียก URL ตรง**
- [ ] rate limit ทำงานจริง — ลองส่งเกินจำนวนแล้วถูกกัน
- [ ] `type` และ `status` ในฐานข้อมูลเป็น key อังกฤษ
- [ ] `manual_slug` ที่บันทึกผ่านการเทียบทะเบียนแล้ว
- [ ] ไฟล์แนบเก็บนอก `public/` และคนที่ไม่มีสิทธิ์เปิดไม่ได้
