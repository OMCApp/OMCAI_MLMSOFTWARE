# ระบบบันทึกการใช้งาน (Audit Log)

> **บังคับทุกโปรเจค** — อ่านเมื่อสร้าง/แก้ audit log **หรือเมื่อเพิ่มจุดที่เปลี่ยนแปลงข้อมูลในระบบ**
> กฎความปลอดภัยทำตาม [`../security.md`](../security.md) · การแบ่งชั้นและ convention ทำตาม [`../rule.md`](../rule.md)

บันทึกว่า **ใครทำอะไร กับข้อมูลไหน เมื่อไหร่**

| | Error Log ([`../rule.md`](../rule.md) ข้อ 8) | Audit Log (ไฟล์นี้) |
|---|---|---|
| บันทึกเมื่อ | ระบบทำงานผิดพลาด | คนทำสำเร็จ |
| ตัวอย่าง | "เชื่อมต่อฐานข้อมูลไม่ได้" | "user #5 แก้ราคาสินค้า A001 จาก 500 เป็น 50" |
| ใช้ตอบคำถาม | ระบบพังเพราะอะไร | ใครทำอะไรไว้ |

**เหตุผลที่บังคับ:** คำถามที่เจอบ่อยที่สุดในระบบธุรกิจคือ "ใครลบข้อมูลนี้" / "ใครแก้ราคา" / "สต็อกหายไปไหน" — ไม่มี audit log ตอบไม่ได้เลย

และเป็นสิ่งที่**เพิ่มทีหลังยากที่สุด** เพราะ (1) ต้องไล่แทรกโค้ดทุกจุดที่แก้ข้อมูล ซึ่งมักลืมบางจุดจนได้ log ที่ไม่ครบและเชื่อถือไม่ได้ (2) **ประวัติที่ผ่านมากู้คืนไม่ได้** — log ที่เพิ่มวันนี้ตอบคำถามเรื่องเมื่อวานไม่ได้

## 1. สิ่งที่ต้องบันทึก

| ข้อมูล | หมายเหตุ |
|---|---|
| ผู้ใช้ที่ทำ | เก็บ `user_id` **ไม่ใช่ชื่อ** เพราะชื่อเปลี่ยนได้ภายหลัง |
| การกระทำ | `create` / `update` / `delete` / `login` / `logout` / `permission_change` — **เก็บเป็น key อังกฤษ แปลตอนแสดง** ([`i18n.md`](i18n.md)) |
| ตารางและแถวที่ถูกกระทำ | เช่น `products` id `12` |
| ค่าก่อนและหลัง | **สำคัญที่สุด** — สำหรับ `update` เก็บเฉพาะฟิลด์ที่เปลี่ยนจริง |
| วันเวลา | เก็บเป็น ค.ศ. ตามกฎใน [`../rule.md`](../rule.md) |
| IP address | |

## 2. บันทึกอะไร ไม่บันทึกอะไร

**ต้องบันทึก**

- ทุกการเปลี่ยนแปลงข้อมูล (create / update / delete)
- การเข้าสู่ระบบและออกจากระบบ **รวมถึงการล็อกอินที่ล้มเหลว** ← ใช้ตรวจการเดารหัสผ่าน
- การเปลี่ยนสิทธิ์ผู้ใช้ และการเปลี่ยนค่าตั้งของระบบ
- การส่งออกข้อมูลจำนวนมาก (กดปุ่ม export CSV) ← เป็นช่องทางที่ข้อมูลออกจากระบบไปทั้งก้อน

**ไม่ต้องบันทึก**

- การเปิดดูหน้าทั่วไป — ตารางจะบวมเร็วมากโดยไม่ได้ประโยชน์
- **ยกเว้น**การเปิดดูข้อมูลที่ละเอียดอ่อนจริงๆ (ข้อมูลส่วนบุคคลของลูกค้า รายงานการเงิน) กรณีนี้บันทึกการเข้าดูด้วย

## 3. โครงสร้างข้อมูล

ตาราง `audit_logs`

| คอลัมน์ | หมายเหตุ |
|---|---|
| `id` | |
| `user_id` | ว่างได้ (กรณี login ล้มเหลวที่ยังไม่รู้ว่าเป็นใคร) |
| `action` | `create` · `update` · `delete` · `restore` · `login` · `login_failed` · `logout` · `permission_change` · `setting_change` · `export` · `view_sensitive` |
| `table_name` | ตารางที่ถูกกระทำ (ว่างได้กรณี login) |
| `record_id` | id ของแถวที่ถูกกระทำ (ว่างได้) |
| `old_values` | JSON เฉพาะฟิลด์ที่เปลี่ยน (ว่างได้) |
| `new_values` | JSON เฉพาะฟิลด์ที่เปลี่ยน (ว่างได้) |
| `ip_address` | |
| `created_at` | |

> ‼️ **ห้ามมีคอลัมน์ `updated_at` หรือ `deleted_at` ในตารางนี้** — audit log ต้องแก้ไม่ได้ (ดูข้อ 5)
> เป็นข้อยกเว้นเดียวของกฎ "ทุกตารางต้องมี `created_at`/`updated_at`" และของกฎ soft delete ใน [`../rule.md`](../rule.md)

**index ที่ต้องมี:** `user_id` · `table_name` + `record_id` · `created_at` · `action`
ตารางนี้โตเร็วที่สุดในระบบและถูกค้นด้วยตัวกรองเหล่านี้ตลอด

## 4. วิธีทำให้บันทึกครบทุกจุดโดยไม่ต้องไล่เขียนซ้ำ

**ห้ามเขียนคำสั่งบันทึก log กระจัดกระจายในแต่ละ Controller** เพราะจะลืมบางจุดแน่นอน

ใส่ไว้ที่ **`core/Model.php` (base Model)** ให้ทุกการเขียนข้อมูลผ่านทางเดียวกันแล้วบันทึกอัตโนมัติ

**`user_id` ต้องมาจาก `Auth::id()` เท่านั้น** ห้ามรับเป็นพารามิเตอร์ที่ Controller ส่งเข้ามาเอง เพราะจะเผลอส่งผิดคนได้ — base Model ต้องดึงเองจาก session ปัจจุบันเสมอ

**การเปรียบเทียบค่าก่อน-หลัง:** ตอน `update` ให้อ่านค่าเดิมก่อนเขียนทับ แล้วเก็บเฉพาะฟิลด์ที่ค่าต่างกันจริง — **ไม่ใช่เก็บทุกฟิลด์ทั้งแถว** เพราะจะดูไม่ออกว่าอะไรเปลี่ยน

### ‼️ 3 ช่องที่หลุดบ่อยที่สุด

| ช่องที่หลุด | ต้องทำ |
|---|---|
| **query ตรงหรือ bulk insert/update** ที่ไม่ผ่าน base Model | บันทึก audit log เองที่จุดนั้น **ห้ามปล่อยผ่าน** · bulk ให้บันทึกเป็นรายการเดียวที่ระบุจำนวนแถวและเงื่อนไข ไม่ใช่บันทึกทีละแถวจนตารางบวม |
| **soft delete** | ต้องบันทึกเป็น `delete` เหมือนลบจริง และการกู้คืนบันทึกเป็น `restore` — ถ้าไม่บันทึกจะดูไม่ออกว่าใครทำของหาย |
| **การกระทำที่เกิดจาก cron หรือ CI** | `user_id` ว่างได้ แต่ต้องระบุใน `new_values` ว่ามาจากระบบอัตโนมัติตัวไหน ไม่ใช่ปล่อยว่างเปล่าจนดูเหมือนข้อมูลเปลี่ยนเอง |

> **ต้องเสร็จก่อนเขียน CRUD ตัวแรกของระบบ** ตาม [`../stages/1-setup.md`](../stages/1-setup.md)

## 5. ความปลอดภัยและความน่าเชื่อถือ

- ‼️ **audit log ต้องแก้ไขและลบไม่ได้ แม้แต่แอดมิน** — ถ้าแก้ได้ก็ไม่มีความหมาย เพราะคนที่ทำผิดลบร่องรอยตัวเองได้ · **ระบบต้องไม่มีหน้าจอหรือ endpoint สำหรับแก้/ลบ audit log เลย**
- **ห้ามบันทึกรหัสผ่าน token หรือข้อมูลบัตรลงใน `old_values`/`new_values`** — ถ้าฟิลด์ที่เปลี่ยนคือรหัสผ่าน ให้บันทึกแค่ว่า "มีการเปลี่ยนรหัสผ่าน" ไม่เก็บค่า
- **ต้องมีหน้าให้แอดมินดูและค้นหาได้** (กรองตามผู้ใช้ / ตาราง / ช่วงวัน / ประเภทการกระทำ) ไม่ใช่เก็บไว้ในตารางที่ต้องเปิด phpMyAdmin ดู — หน้านี้ทำตามสเปกหน้ารายงานใน [`../components.md`](../components.md)
- ผู้ใช้ทั่วไปเข้าดูไม่ได้ เฉพาะบทบาทที่มีสิทธิ์สูงสุดเท่านั้น
- **หน้าแอดมินต้อง escape ค่าใน `old_values`/`new_values` ก่อนแสดง** — ค่าเหล่านี้มาจากผู้ใช้ ถ้าลืม escape จะกลายเป็น stored XSS ที่ยิงใส่คนที่มีสิทธิ์สูงสุดพอดี
- **วางแผนเรื่องขนาดตารางไว้** — ตารางนี้โตเร็วที่สุดในระบบ ต้องมีนโยบายว่าเก็บย้อนหลังกี่เดือนแล้วย้ายของเก่าไป archive **ไม่ใช่ลบทิ้ง** · ทำผ่าน cron ใน `scripts/backup.php`

## 6. เกณฑ์ตรวจก่อนบอกว่าเสร็จ

- [ ] แก้ข้อมูล 1 รายการแล้ว**เปิดตาราง `audit_logs` ดูจริง** → มีแถวเกิดขึ้น
- [ ] `user_id` ตรงกับคนที่ทำจริง · `action` `table_name` `record_id` ถูกต้อง
- [ ] `old_values` / `new_values` เก็บเฉพาะฟิลด์ที่เปลี่ยนจริง
- [ ] ทดสอบ **สร้าง / แก้ / ลบ** ครบทั้ง 3 แบบ
- [ ] soft delete บันทึกเป็น `delete` และการกู้คืนบันทึกเป็น `restore`
- [ ] ล็อกอินสำเร็จและล็อกอินล้มเหลว บันทึกทั้งคู่
- [ ] ไม่มีรหัสผ่านหรือ token โผล่ในตาราง
- [ ] ไม่มี endpoint ใดในระบบที่แก้หรือลบ audit log ได้
- [ ] หน้าแอดมินดู ค้นหา และกรองได้จริง และ escape ค่าแล้ว
