## 1. ดีไซน์แบ่งเป็น 2 ชั้น — เข้าใจข้อนี้ก่อนอย่างอื่น

| ชั้น | อยู่ที่ไหน | เปลี่ยนตามโปรเจค | คืออะไร |
|---|---|---|---|
| **คุณภาพ** | ไฟล์นี้ + `components.md` | ไม่เปลี่ยน | ลำดับสายตา · สเกลระยะห่าง · contrast · สถานะครบทุก component · responsive · a11y |
| **เอกลักษณ์** | `project/DESIGN.md` | เปลี่ยนทุกโปรเจค | ฟอนต์คู่ที่เลือก · ตระกูลสี · ความมนของมุม · ความหนาแน่น · บุคลิกของ motion |

**ความดีมาจากชั้นแรก ความต่างมาจากชั้นสอง**

ถ้ามาตรฐานกลางกำหนดสไตล์ตายตัว ทุกโปรเจคจะหน้าเหมือนกัน — ซึ่งเป็นปัญหาเดียวกับที่ AI เติมค่า default ของตัวเอง แค่เปลี่ยนคนกำหนด ไฟล์นี้จึงกำหนดแต่**เกณฑ์** ไม่กำหนด**รสนิยม**

### กฎของไฟล์นี้

1. **ทุก token สีต้องมีค่าครบทั้ง light และ dark** ห้ามมี token ที่มีค่าโหมดเดียว — `check.php` จับข้อนี้
2. **ห้ามใช้ค่าที่ไม่อยู่ในสเกล** ระยะห่างต้องมาจาก `space` ขนาดตัวอักษรจาก `scale` มุมจาก `radius`
3. ต้องการค่าใหม่ → **เพิ่มลง `DESIGN.md` แล้ว sync** ไม่ใช่เขียนตรงใน CSS
4. **แก้ธีมทั้งระบบ = แก้ไฟล์นี้ไฟล์เดียว**
5. **`component:` เป็นชั้นที่ถูกลืมบ่อยที่สุด** — ถ้าเติมแต่สีกับฟอนต์ หน้าจะได้สีของดีไซน์แต่ความสูงแถว ระยะในเซลล์ และรูปทรง badge ยังเป็นค่าของโครงเปล่า ซึ่งวัดได้ว่าเพี้ยนทันทีที่หน้าแรก
6. **ดีไซน์ที่ขัดกับกฎการเข้าถึง ให้กฎชนะ** แล้ว**เขียนไว้ในหัวข้อ `## สิ่งที่จงใจไม่ทำในโปรเจคนี้` ว่าไม่ทำตามดีไซน์ตรงไหนเพราะอะไร** — ไม่งั้นวันหนึ่งจะมีคนย่อปุ่มลงเพื่อให้ "ตรงดีไซน์" โดยไม่รู้ว่ากำลังแลกอะไรไป

## 3. แปลงคำตอบจาก `BRIEF-DESIGN.md` เป็น token ยังไง

| คำตอบผู้ใช้ | แปลงเป็น |
|---|---|
| ทางการ น่าเชื่อถือ | สีหลักโทนเย็นหรือกลาง · radius เล็ก (4-8px) · เงาบาง · ฟอนต์เรขาคณิตหรือ neo-grotesque |
| เป็นกันเอง เข้าถึงง่าย | สีหลักอุ่นหรือสด · radius ใหญ่ (12-16px) · ฟอนต์ปลายมน · ระยะห่างเยอะขึ้น |
| เรียบ สงบ | สีเน้นใช้จุดเดียวต่อหน้า · พื้นหลังใกล้ขาว/ดำสนิท · ความต่างของน้ำหนักตัวอักษรน้อย |
| สดใส มีพลัง | สีเน้นใช้ได้หลายจุด · หัวข้อใหญ่และหนัก · motion เร็วขึ้น |
| โปร่ง เว้นว่างเยอะ | `density: comfortable` · ระยะห่างฐาน 16-24px · ตารางแถวสูง |
| แน่น เห็นข้อมูลเยอะ | `density: compact` · ระยะห่างฐาน 8-12px · ตารางแถวเตี้ย ฟอนต์เล็กลง 1 ขั้น |
| ทันสมัย | เส้นบาง · contrast สูง · เงาน้อยหรือไม่มี · พึ่งระยะห่างแทนกรอบ |
| คุ้นเคย ปลอดภัย | มีกรอบและเส้นแบ่งชัด · ปุ่มดูเป็นปุ่ม · pattern ที่คนเคยเห็น |
| ผู้ใช้ไม่คุ้นคอมพิวเตอร์ | ปุ่มใหญ่ขึ้น 1 ขั้น · label เป็นคำเต็ม · คำอธิบายใต้ช่องกรอก · ไอคอนคู่กับข้อความ |

## 4. ฟอนต์

**ห้ามโหลดจาก CDN** (กฎเหล็กข้อ 2) — ต้องดาวน์โหลดไฟล์ `.woff2` มาเก็บใน `public/assets/fonts/` แล้วประกาศ `@font-face` ใน `app.css`

**ทุกฟอนต์ที่เลือกต้องมีตัวอักษรไทยครบ** ฟอนต์ที่สวยแต่ไม่มีตัวไทยใช้ไม่ได้ — เวลาไม่มีตัวไทย เบราว์เซอร์จะสลับไปฟอนต์ระบบทำให้หน้าดูไม่เป็นชุดเดียวกัน

### ชุดคู่ที่แนะนำ

ทั้งหมดหาได้จาก Google Fonts และดาวน์โหลดมา self-host ได้ — **ตรวจ license ในหน้าฟอนต์ก่อนใช้งานเชิงพาณิชย์ทุกครั้ง**

| ชุด | หัวข้อ | เนื้อความ | เหมาะกับ |
|---|---|---|---|
| A | IBM Plex Sans Thai | IBM Plex Sans Thai | ทางการ เป็นระบบ ข้อมูลเยอะ |
| B | Kanit | Noto Sans Thai | ทันสมัย คม มีน้ำหนัก |
| C | Mitr | Sarabun | อบอุ่น เข้าถึงง่าย |
| D | Anuphan | Sarabun | เรียบ สงบ อ่านสบาย |
| E | Chakra Petch | IBM Plex Sans Thai | เทคนิค เครื่องมือ dashboard |

## 5. กฎการจัดหน้า — ข้อที่ตัดสินว่าหน้าดูดีหรือไม่

> ‼️ **หัวข้อนี้เกิดจากความเจ็บจริง** — โปรเจคแรกที่ใช้มาตรฐานนี้ผ่าน `check.php` 0 ข้อ ชุดทดสอบ 103 ข้อผ่านหมด
> **แต่ผู้ใช้เปิดดูแล้วบอกว่าหน้าใช้ไม่ได้ และเขาถูก**
>
> สาเหตุคือมาตรฐานคุม **token** (สีอะไร ขนาดเท่าไหร่) แต่ไม่เคยคุม **การจัดหน้า** (หน้าหนึ่งประกอบขึ้นมายังไง)
> ผลคือ AI ปั้น token ครบ 152 ตัวแล้วเอา component มาต่อกันตรงๆ ซึ่งผ่านทุกกฎแต่ไม่มีลำดับสายตา
>
> ทุกข้อด้านล่างมีอาการจริงกำกับ ไม่ใช่ข้อควรระวังที่คิดขึ้นมา

### 5.0 ‼️ แบบที่ผู้ใช้อนุมัติ กับกฎในไฟล์นี้ — อะไรชนะ

> **ที่มา (3.17.0):** ผู้ใช้ออกแบบหน้ามาเป็นภาพ บอกว่าต้องเป็นแบบนี้ 100% แล้วได้หน้าที่ไม่เหมือนภาพ
> AI ถือกฎทุกข้อในมาตรฐานเป็นกฎแข็ง รวมข้อ 5.4 "หน้าเดียวคอลัมน์เดียว" และคอมเมนต์ในโค้ดที่ AI session ก่อนเขียนไว้เอง
> ของในภาพที่ partial ทำไม่ได้ (ภาพบนหัวเพจ · breadcrumb · การ์ดสรุปด้านข้าง) ถูกตัดทิ้งเงียบๆ แทนการเพิ่มช่อง

กฎในมาตรฐานมีสองชนิด และแพ้แบบของผู้ใช้ไม่เท่ากัน

| ชนิด | ได้แก่ | เมื่อขัดกับแบบ |
|---|---|---|
| **กฎแข็ง** | การเข้าถึง (contrast · พื้นที่กด 44px · focus · label · ไม่ใช้สีอย่างเดียว) · ความปลอดภัย · ข้อความผ่าน `__()` · ค่ามาจาก token · component เป็นของกลางใน `partials/` · สองโหมด · footer | **กฎชนะ** — ปรับให้ใกล้แบบที่สุดภายในกฎ แล้วบันทึกใน `## สิ่งที่จงใจไม่ทำในโปรเจคนี้` |
| **กฎเริ่มต้น** | การจัดหน้า 5.1–5.15 · ค่าเริ่มต้นของ partial · ความกว้างหน้า · สิ่งที่หัวเพจมีหรือไม่มี · **คอมเมนต์ ‼️ ในโค้ดของโปรเจค** | **แบบชนะ** — กฎเหล่านี้คือคำตอบเมื่อไม่มีใครออกแบบมา ไม่ใช่ข้อห้าม |

- **คอมเมนต์ในโค้ดไม่ใช่กฎ** — เหตุผลที่ AI session ก่อนเขียนไว้ ไม่ได้ผ่านการอนุมัติของใคร · ลำดับความสำคัญยังเป็น คำสั่งผู้ใช้ > `CLAUDE.md` > `standard/` และแบบที่ผู้ใช้อนุมัติคือคำสั่งผู้ใช้
- **ของที่แบบต้องการแต่ partial ทำไม่ได้ → ขยาย partial** (เพิ่มตัวแปร เพิ่มคลาส) ให้ทุกหน้าใช้ได้ **ห้ามตัดทิ้ง และห้ามเขียน markup เองในหน้าเดียว**
- **ก่อนสร้างหรือแก้หน้าที่มีแบบ ต้องรายงานทุกจุดที่ขัดในข้อความเดียว** — จุดไหน · ขัดกับกฎชนิดไหน · จะทำยังไง · ใช้ทุกโหมด รวมงานเล็กและโหมดเร็ว
- ทำตามแบบแล้วต่างจากกฎเริ่มต้นตรงไหน บันทึกใน `project/NOTES.md` ว่าหน้าไหนเบี่ยงเพราะแบบ — คนที่มารับช่วงจะได้ไม่ "แก้กลับ" ให้ตรงกฎ

> ‼️ **ข้อ 5.1-5.15 เขียนสำหรับหน้าหลังบ้าน** ซึ่งต้องการความสม่ำเสมอมากกว่าความประทับใจ
> **หน้าสาธารณะมีข้อยกเว้นและมีเกณฑ์ของตัวเองที่ข้อ 5.16** — อ่านข้อนั้นก่อนลงมือทำหน้า landing หรือเว็บโชว์

### 5.1 ทุกหน้าเปิดด้วยหัวเพจ

ชื่อหน้า + ประโยคบอกว่า**ใครใช้ได้และผลของการกระทำ** · มาจาก layout กลางเหมือน footer · **ห้ามซ้ำใน topbar**

> อาการตอนไม่มีกฎนี้: 10 หน้าไม่มีหัวเพจเลย ชื่อหน้าไปอยู่ใน topbar ตัวเล็ก คำอธิบายหายไปหมด
> **ทุกอย่างในหน้ามีน้ำหนักเท่ากัน ไม่มีจุดเริ่มให้สายตา** — นี่คือสาเหตุอันดับหนึ่งที่หน้า "ดูแย่"

ใช้ `partials/page-head.php` ของโครง ห้ามเขียน `<h1>` เองทีละหน้า

**ยกเว้นหน้าที่มีส่วนเปิด (`partials/hero.php`)** ซึ่งวาด `<h1>` ของตัวเองอยู่แล้ว — ดูข้อ 5.14

### 5.2 ปุ่มหลักของหน้าอยู่ในหัวเพจ ไม่ปนกับตัวกรอง

> อาการ: ปุ่ม "เพิ่มผู้ใช้" ชนฟอร์มกรองในแถวเดียวกัน และเส้นฐานไม่ตรงกันเพราะช่องกรองมี label อยู่ข้างบน

### 5.3 ตัวกรองเป็นแถบเดียว label อยู่ข้างหน้าช่อง ไม่ใช่ข้างบน

> อาการ: ความสูงของแต่ละชิ้นไม่เท่ากัน แถบเครื่องมือดูเละแม้ทุกชิ้นถูกต้องตามกฎ token

### 5.4 ความกว้างเป็นเรื่องของ "หน้า" ไม่ใช่ของ component

หนึ่งหน้ามี**คอลัมน์เดียว ความกว้างเดียว อยู่กลางพื้นที่** — Controller ส่งมาเป็นคำเดียวผ่าน `.page[data-width]`

| ค่า | ใช้กับ |
|---|---|
| `form` | หน้าฟอร์ม หน้าตั้งค่า |
| `list` | หน้ารายการ ตาราง |
| `wide` | แดชบอร์ด จอที่เปิดค้าง |
| `split` | **ข้อยกเว้นที่เลือกโดยตั้งใจ** — การ์ดหรือสรุปด้านข้างคู่กับเนื้อหาหลัก เช่นหน้าแก้ไขที่ด้านซ้ายสรุปสิ่งที่กำลังแก้ · ใช้เมื่อแบบของผู้ใช้กำหนด หรือเมื่อด้านข้างช่วยตัดสินใจเรื่องในเนื้อหาหลักจริง · แบ่งพื้นที่ด้วย `.split-layout` > `.split-aside` + `.split-main` · ความกว้างด้านข้างจาก `layout.asideWidth` · จอแคบเรียงเป็นคอลัมน์เดียว |

‼️ **ห้ามให้ component คุมความกว้างของตัวเอง ห้ามใส่ `fit-content` หรือ `max-width` ทีละชิ้น**

**ยกเว้นส่วนที่ตั้งใจให้ชนขอบจอบนหน้าสาธารณะ** ซึ่งใช้ `.bleed` — ดูข้อ 5.16

> อาการตอนปล่อยให้ component คุมเอง: ตาราง 5 คอลัมน์สั้นๆ ยืดเป็น 1,160px ปุ่มจัดการห่างจากข้อมูลเกิน 400px
> พอให้ component หุบเอง กลับได้ **ที่ว่างข้างขวาโล่งอยู่ข้างเดียว** เพราะหัวเพจกว้างเต็มแต่การ์ดกว้าง 760px และชิดซ้าย
>
> เป็นบทเรียนว่ากฎ "ทุกอย่างเป็นของกลาง" ต้องครอบถึง **ความกว้างของหน้า** ด้วย ไม่ใช่แค่สีกับระยะห่าง

### 5.5 สิ่งที่วางเรียงกันในแนวตั้งต้องขอบตรงกัน

> อาการ: แถบตัวกรองกว้างเต็มจอ ขณะที่ตารางใต้มันหุบตามเนื้อหา ขอบขวาไม่ตรงกัน
> **ข้อนี้มองจากโค้ดไม่เห็นเลย** เห็นเฉพาะตอนถ่ายภาพหน้าจริง

### 5.6 "ประเภท" กับ "สถานะ" ต้องต่างกันด้วยรูปทรง ไม่ใช่แค่สี

> อาการ: badge ของสิทธิ์กับของสถานะหน้าตาเหมือนกัน กวาดตาแล้วแยกความหมายไม่ออก

### 5.7 ฟอร์มเกิน 4 ช่องต้องแบ่งกลุ่ม

ใช้ `fieldset` + `legend` และช่องสั้นเรียงกันเป็น grid

> อาการ: หน้าตั้งค่าเป็นช่องกรอก 7 ช่องเรียงลงมา ความกว้าง 680px เท่ากันหมด รวมช่องที่ใส่ได้แค่เลขหลักเดียว

### 5.8 ความกว้างของช่องกรอกต้องบอกความยาวที่คาดหวัง

ส่ง `$fieldWidth` = `short` / `medium` / `full` ให้ `partials/field.php`

> **ช่องกว้างเต็มฟอร์มที่รับได้ 3 ตัวอักษร คือการบอกผู้ใช้ผิด**

### 5.9 สิ่งที่ทำงานทันทีเมื่อกด ต้องไม่อยู่ปนกับสิ่งที่ต้องกดยืนยันอีกที

> อาการ: ปุ่มลัดช่วงวัน (กดแล้วค้นหาเลย) ถูกวางในการ์ดตัวกรอง (กรอกแล้วต้องกดค้นหา)
> ผู้ใช้จึงไม่รู้ว่ากดแล้วต้องกดค้นหาอีกไหม และแถบกรองยาวจนต้องห่อบรรทัด

### 5.10 ประโยคอธิบายท้ายหน้าต้องอยู่ในกรอบ ไม่ลอยเป็นข้อความเปล่า

> อาการ: ประโยคสำคัญลอยใต้การ์ดเหมือนข้อความที่หลุดมา

### 5.11 ของที่ทำงานได้เพราะ JS ต้องถูกสร้างโดย JS

ช่องค้นหาที่กรองด้วย JS · ปุ่มที่ต้องมี JS ถึงทำงาน — **ห้ามเขียนไว้ในหน้า ให้ JS สร้างขึ้นมาเอง**

> ถ้าเขียนไว้ในหน้าแล้ว JS พัง ผู้ใช้จะได้ช่องที่พิมพ์แล้วไม่เกิดอะไรเลย
> ซึ่ง **แย่กว่าไม่มีช่อง** เพราะเขาจะสรุปว่าระบบพังหรือไม่มีข้อมูล

### 5.12 control ที่กางอะไรออกมาเมื่อกด ต้องปั้นใหม่ ห้ามใช้ของ OS

`select` · ปฏิทิน · แถบเลื่อน — จัดสไตล์กล่องอย่างเดียวไม่พอ

> อาการ: ตั้งสี `option` แล้ว แต่รายการที่กางออกมายังเป็นกล่องของ Windows โผล่บนพื้นครีม
> **การตั้งสี `option` เปลี่ยนได้แค่ 2 ค่าจากสิบกว่าค่าที่ตาเห็น** — control ของ OS คือจุดที่ระบบหลุดคาแรกเตอร์ชัดที่สุด

### 5.13 component ที่มีหลายสถานะ ต้องออกแบบทุกสถานะ

> อาการ: พับเมนูแล้วไอคอนดูเล็กจนเล็งกดยาก
> ขนาดไม่ได้เล็กลงจริง แต่ **หน้าที่ของมันใหญ่ขึ้น** — ตอนมีข้อความ ไอคอนเป็นตัวช่วย พอตัดข้อความออก ไอคอนกลายเป็นตัวบอกความหมายตัวเดียว
>
> เฉพาะเมนูพับได้: **สถานะพับต้องเพิ่มขนาดไอคอน** และจัดกลางแนวราง · พื้นที่กดยังต้อง 44px

### 5.14 หน้าสาธารณะกับหน้าหลังบ้านใช้กฎการเปิดหน้าคนละข้อ

กฎ 5.1 ถูกเขียนตอนที่มาตรฐานนี้มีแต่หน้าหลังบ้าน — หน้าที่ผู้ใช้ล็อกอินเข้ามาทำงาน จึงต้องรู้ทันทีว่ากำลังอยู่หน้าไหน
**หน้าสาธารณะไม่ได้ทำงานแบบนั้น** คนที่เพิ่งกดเข้ามาไม่ได้ต้องการชื่อหน้า เขาต้องการรู้ว่าที่นี่คืออะไรภายในห้าวินาที

| | เปิดหน้าด้วยอะไร | ทำไม |
|---|---|---|
| **หน้าหลังบ้าน** | `partials/page-head.php` | ชื่อหน้า + ใครใช้ได้ + ปุ่มหลักของหน้า |
| **หน้าสาธารณะ** | `partials/hero.php` | พาดหัวที่ขายเรื่อง + ภาพ + ปุ่มพาไปต่อ |

> ‼️ **ใช้ทั้งสองอันในหน้าเดียวไม่ได้** จะได้ `<h1>` สองตัว ซึ่งแปลว่าไม่มีตัวไหนเป็นหัวจริง และ screen reader อ่านโครงหน้าผิด
>
> **แต่ไม่ต้องจำข้อนี้** — `hero.php` เรียก `hero_rendered(true)` แล้ว `page-head.php` เช็คเองว่าจะไม่วาดซ้ำ
> ทำเป็นกลไกเพราะสิ่งที่ต้องจำคือสิ่งที่จะถูกลืม · เจอจริงตอนทำหน้าแรกของเว็บโชว์เป็นครั้งแรก แล้วได้ `<h1>` สองตัวโดยไม่มีอะไรรายงาน

### 5.15 รูปแบบเมนูมาจาก `DESIGN.md` ที่เดียว และ layout ต้องอ่านมันจริง

`layout.nav` ใน `DESIGN.md` ตัดสินว่าเป็น `sidebar` หรือ `header` — **ที่เดียวจบ ไม่ต้องไปตั้งซ้ำที่ไหนอีก**

`design-sync.php` generate ค่านี้ลง `config/design.php` ให้ แล้ว layout กลางอ่านผ่าน `config('ui.nav')` · `css-in-sync` จับให้ถ้าลืม sync

| เมนู | ใช้กับ |
|---|---|
| `sidebar` | ระบบหลังบ้านที่มีเมนูเยอะและผู้ใช้อยู่กับมันทั้งวัน |
| `header` | **เว็บสาธารณะทุกกรณี** — sidebar กินพื้นที่มือถือและไม่มีเว็บโชว์เจ้าไหนทำ |

> ‼️ **เคยมี `config('ui.nav_style')` อยู่ใน `config.php` แต่ไม่มีโค้ดบรรทัดไหนอ่านมันเลย**
> layout จึงวาด sidebar เสมอ · โปรเจคที่ตอบ `header` ไว้ตั้งแต่ช่วง A ได้ sidebar ของหลังบ้านมาครอบหน้าสาธารณะ
> **และไม่มีอะไรรายงานว่าผิด เพราะไม่มีอะไรผิดในสายตาของชุดตรวจ — มันแค่ไม่ตรงกับสิ่งที่ผู้ใช้สั่งไว้**
>
> บทเรียน: **config ที่ไม่มีใครอ่าน อันตรายกว่าไม่มี config เลย** เพราะมันทำให้ทุกคนเชื่อว่าตั้งค่าได้แล้ว
>
> ‼️ **และทางแก้แรกยังไม่พอ** — 3.7.0 ให้ layout อ่าน `APP_NAV_STYLE` จาก `.env` ซึ่งแก้เรื่อง "ไม่มีใครอ่าน" แต่สร้างเรื่องใหม่คือ**ค่าเดียวกันอยู่สองที่แล้วเถียงกันได้เงียบๆ**
> ตั้ง `DESIGN.md` เป็น `header` แต่ `.env` เป็น `sidebar` แล้ว `check.php` ผ่านหมด — 3.9.0 จึงยุบให้เหลือแหล่งเดียว

### 5.15ก ‼️ หน้าไหนเป็น "หน้าสาธารณะ" ต้องมีตัวบอก ไม่ใช่ให้เดา

ข้อ 5.16 ให้สิทธิ์ยกเว้นกับหน้าสาธารณะ ซึ่งแปลว่ามีกฎการจัดหน้า **สองชุดที่ขัดกันโดยตรง** อยู่ในไฟล์เดียวกัน

| ชุด | บอกว่า |
|---|---|
| 5.1–5.15 | ความกว้างเดียวทั้งหน้า · ขอบต้องตรงกัน · ไม่มีอะไรเซอร์ไพรส์ |
| 5.16 | ชนขอบจอได้ · ข้อความทับภาพได้ · พาดหัวใหญ่กว่าหลายเท่า |

**ไม่มีตัวบอกว่าหน้าไหนใช้ชุดไหน = ปล่อยให้เดา ซึ่งผิดได้สองทาง** — เอากฎหลังบ้านไปใช้กับ landing ได้หน้าจืด · เอา 5.16 ไปใช้กับหน้ารายงานได้หน้าหลังบ้านที่มี hero เต็มจอ

```php
page_public(true);   // หน้าสาธารณะที่ไม่มี hero — บทความ นโยบาย
```

- **หน้าที่ include `hero.php` ถูกทำเครื่องหมายให้เองอัตโนมัติ** ไม่ต้องเรียกเพิ่ม
- layout เขียนออกมาเป็น `data-page="public"` บน `.page` ให้ CSS และชุดตรวจใช้
- `design/public-page-boldness` ใช้เครื่องหมายนี้หาว่าจะบังคับเกณฑ์ของ 5.16 กับหน้าไหน

> ‼️ **เป็นกลไก ไม่ใช่กฎที่ต้องจำ** ด้วยเหตุผลเดียวกับ `hero_rendered()` ในข้อ 5.14 — **สิ่งที่ต้องจำคือสิ่งที่จะถูกลืม**

### 5.16 ‼️ หน้าสาธารณะได้รับอนุญาตให้แหกกรอบ — และควรใช้สิทธิ์นั้น

**กฎ 5.1 ถึง 5.15 ทั้งหมดถูกเขียนตอนที่มาตรฐานนี้มีแต่หน้าหลังบ้าน** ซึ่งเป็นหน้าที่คนเปิดทั้งวันเพื่อทำงาน
หน้าแบบนั้นต้องการความสม่ำเสมอมากกว่าความประทับใจ — ขอบตรงกัน ความกว้างเดียว ไม่มีอะไรเซอร์ไพรส์

**หน้าสาธารณะทำงานตรงข้าม** คนที่เพิ่งกดเข้ามาให้เวลาห้าวินาที ถ้าไม่มีอะไรสะดุดตาเขาก็ปิด

> ‼️ **เอากฎของหน้าหลังบ้านไปใช้กับหน้าสาธารณะ จะได้หน้าที่ผ่านทุกข้อแต่ไม่มีใครจำได้**
> วัดจริงเทียบกับ landing page ที่ทำด้วยเครื่องมือสำหรับงานนี้โดยเฉพาะ — ต่างกันทุกตัวเลข
> พาดหัว 52px ต่อ 90px · ภาพกิน 39% ของจอ ต่อ 100% · อัตราส่วนพาดหัวต่อ eyebrow 3.5:1 ต่อ 7:1
>
> **ไม่มีข้อไหนในชุดตรวจ 58 ข้อที่บอกได้ว่า "อันนี้ปลอดภัยเกินไปจนจืด"** ทุกข้อพูดได้แค่ว่าอะไรผิด
> AI ที่เดินตาม checklist จึงเลือกทางที่ปลอดภัยที่สุดเสมอ ซึ่งคือทางที่จืดที่สุด

|---|---|---|
| **ภาพชนขอบจอทั้งสองด้าน** | 5.4 ความกว้างเดียวทั้งหน้า | `.bleed` ครอบ section นั้น |
| **ข้อความทับภาพ** | 5.5 ขอบต้องตรงกัน | `hero` แบบ `$heroFullBleed = true` |
| **พาดหัวใหญ่กว่าหัวข้ออื่นหลายเท่า** | — | `--text-display` ซึ่งมีเฉพาะเพื่อการนี้ |
| **ส่วนเปิดสูงเต็มจอ** | — | `--hero-min-height` |

### ‼️ เกณฑ์ที่ต้องผ่าน ไม่ใช่แค่ "ทำได้"

หน้าสาธารณะที่ผ่านสามข้อนี้ไม่ได้ **ถือว่ายังไม่เสร็จ** แม้ `check.php` จะผ่านหมด

1. **ส่วนเปิดต้องกินความสูงอย่างน้อย 70% ของจอแรก** — hero ที่สูง 300px คือแถบหัวเรื่อง ไม่ใช่ส่วนเปิด
2. **อัตราส่วนพาดหัวต่อข้อความรอง ต้องไม่ต่ำกว่า 4:1** — ต่ำกว่านี้ตาจะอ่านว่าทุกอย่างสำคัญเท่ากัน
3. **ต้องมีอย่างน้อยหนึ่งอย่างในหน้าที่ไม่ได้อยู่ในกรอบ `maxWidth`** — ภาพเต็มความกว้าง แถบสีเต็มความกว้าง หรือส่วนเปิดที่ชนขอบ

> ‼️ **สามข้อนี้เป็นเกณฑ์ ไม่ใช่รสนิยม** — วัดได้ด้วยเบราว์เซอร์ทุกข้อ และเป็นสิ่งที่ต่างกันชัดที่สุดตอนเทียบ 1 ต่อ 1
> ทำครบสามข้อไม่ได้แปลว่าหน้าจะสวย แต่ทำไม่ครบแปลว่าหน้าจะจืดแน่นอน

**`design/public-page-boldness` บังคับทั้งสามข้อให้แล้ว** — ไม่ใช่ข้อความที่ต้องจำ

| เกณฑ์ | ตัวจับดูอะไร |
|---|---|
| 1 · ส่วนเปิด ≥ 70% ของจอ | `component.hero.minHeight` ≥ 560px และ `minHeightMobile` ≥ 420px |
| 2 · พาดหัว ≥ 4:1 | `typography.scale.display` หารด้วย `base` |
| 3 · ต้องมีของหลุดกรอบ | หน้าที่ `data-page="public"` ต้องมี `$heroFullBleed` หรือ `.bleed` |

> ‼️ **นี่คือด่านแรก ไม่ใช่ด่านสุดท้าย** — ตัวจับดูที่ **ต้นทาง** ของค่า ส่วนความสูงและอัตราส่วนที่เรนเดอร์ออกมาจริง ยังต้องวัดในเบราว์เซอร์ตาม [`testing.md`](testing.md) ข้อ 4ก
> token ถูกแต่หน้าจริงยังเตี้ยได้ ถ้ามีอย่างอื่นไปทับ

### ที่ยังบังคับเหมือนเดิม ไม่มีข้อยกเว้น

**ความปลอดภัยและการเข้าถึงไม่เคยมีข้อยกเว้น** — contrast · พื้นที่กด 44px · โฟกัสคีย์บอร์ด · โหมดมืด · ทุกข้อความผ่าน `__()` · ทุกค่ามาจาก token

**และข้อความทับภาพต้องผ่าน contrast จริง** — ภาพถ่ายมีทั้งส่วนสว่างและมืด วางตัวอักษรขาวบนภาพเฉยๆ แล้ววัดไม่ผ่านเป็นเรื่องปกติ
ต้องมีชั้นไล่สีคั่นเสมอ และวัดที่จุดที่ตัวอักษรอยู่จริง ไม่ใช่วัดค่าเฉลี่ยของภาพ

## 6. กฎคุณภาพที่ต้องผ่านทุกหน้า

### ลำดับสายตา

- **หนึ่งหน้ามีสิ่งสำคัญที่สุดได้อย่างเดียว** ถ้าทุกอย่างเด่นเท่ากัน แปลว่าไม่มีอะไรเด่น
- ลำดับต้องสร้างด้วย **ขนาด → น้ำหนัก → สี** ตามลำดับนั้น ไม่ใช่ใช้สีเป็นเครื่องมือแรก
- **สีเน้น (`brand.primary`) ใช้กับสิ่งที่คลิกได้เท่านั้น** ห้ามใช้ตกแต่งข้อความธรรมดา ไม่งั้นผู้ใช้จะแยกไม่ออกว่าอะไรกดได้

### ระยะห่าง

- ทุกค่ามาจากสเกล `space` เท่านั้น
- **ของที่เกี่ยวข้องกันต้องอยู่ใกล้กว่าของที่ไม่เกี่ยวข้อง** — label กับช่องกรอกต้องชิดกว่าระยะระหว่างช่องกรอกสองช่อง ข้อนี้ทำให้ฟอร์มอ่านง่ายขึ้นมากกว่าการตกแต่งใดๆ
- ระยะห่างในแนวตั้งของหน้าเดียวกันต้องมาจากชุดค่าไม่เกิน 3-4 ค่า

### สีและ contrast

- ข้อความปกติต้องมี contrast อย่างน้อย **4.5:1** กับพื้นหลัง · ข้อความใหญ่ (≥24px หรือ ≥19px ตัวหนา) อย่างน้อย **3:1**
- **ห้ามใช้สีเป็นตัวสื่อความหมายอย่างเดียว** สถานะต้องมีข้อความหรือไอคอนกำกับด้วยเสมอ (คนตาบอดสีแยกแดง/เขียวไม่ออก)
- ตรวจ contrast ทั้งสองโหมด ไม่ใช่แค่โหมดสว่าง

### ตัวอักษร

- ความกว้างบรรทัดของเนื้อความยาว **45-80 ตัวอักษร** — เต็มจอกว้าง 1920px แล้วอ่านไม่ไหว
- `line-height` เนื้อความ 1.6-1.8 · หัวข้อ 1.2-1.35
- **ภาษาไทยไม่มีช่องว่างระหว่างคำ** ต้องเผื่อ `line-height` มากกว่าภาษาอังกฤษ และระวังการตัดคำผิดตำแหน่ง
- ห้ามใช้ตัวอักษรเล็กกว่า `sm` (14px) กับข้อความที่ผู้ใช้ต้องอ่านจริง

### สถานะที่ทุก component ต้องมีครบ

| กลุ่ม | สถานะ |
|---|---|
| การโต้ตอบ | ปกติ · hover · **focus (ต้องเห็นชัด)** · active · disabled |
| ข้อมูล | มีข้อมูล · **ว่าง** · **กำลังโหลด** · **ผิดพลาด** |

- **empty state ต้องบอกด้วยว่าทำอะไรต่อได้** ไม่ใช่แค่ "ไม่มีข้อมูล" — เช่น "ยังไม่มีรายการ · กดปุ่มเพิ่มเพื่อเริ่ม"
- **error state ต้องบอกว่าเกิดอะไรและทำยังไงต่อ** พร้อมรหัสอ้างอิง error
- ห้ามใช้ `outline: none` โดยไม่ใส่ focus แบบอื่นแทน

### คีย์บอร์ดและ a11y

- `Tab` เดินได้ทุกจุดที่กดได้ ตามลำดับที่สมเหตุสมผล
- `Esc` ปิด modal / dropdown · `Enter` ส่งฟอร์ม
- ปุ่มที่มีแต่ไอคอนต้องมี `aria-label` และ tooltip เสมอ
- รูปที่สื่อความหมายต้องมี `alt` · รูปตกแต่งใส่ `alt=""`
- ทุกช่องกรอกต้องมี `<label>` ผูกจริง ไม่ใช่ใช้ placeholder แทน label

### Responsive

- ออกแบบจากจอเล็กขึ้นไป
- พื้นที่กดบนมือถืออย่างน้อย **44×44px**
- **ตารางบนมือถือให้ยุบเป็นการ์ด** ไม่ใช่ scroll แนวนอน (รายละเอียดใน `components.md`)
- ทดสอบอย่างน้อย 3 ขนาด: มือถือ 375px · แท็บเล็ต 768px · เดสก์ท็อป 1280px
- ถ้าโปรเจคมีจอที่เปิดค้างตลอดวัน ต้องทดสอบขนาดจอนั้นด้วย

## 7. สีแบรนด์ — มี token ไม่เท่ากับหน้าดูเป็นสีนั้น

> ‼️ เกิดขึ้นจริง: ผู้ใช้ให้ **แดง** มาเป็นสีหลักตั้งแต่ช่วง A
> AI กลัวว่าปุ่ม "เรียกคิว" (กดวันละร้อยครั้ง) จะสับสนกับ "ยกเลิกคิว" (กดผิดแล้วเดือดร้อน) จึงยกสีหลักให้น้ำเงินเข้ม
> **ความกลัวนั้นถูก แต่ทางแก้ผิด** — ความสับสนของปุ่มเป็นปัญหาของ **รูปทรง** ไม่ใช่ของ **สีแบรนด์**
> แก้ได้ด้วยกฎเดียวคือ "ปุ่มทำลายข้อมูลเป็นปุ่มโครงร่างพร้อมไอคอน ห้ามเป็นปุ่มทึบ" ซึ่งไม่ต้องเอาแดงออกจากแบรนด์เลย
>
> **จ่ายด้วยตัวตนของแบรนด์ เพื่อซื้อความชัดของปุ่ม ทั้งที่ซื้อได้ด้วยเงินคนละกระเป๋า**

### 7.1 สีที่ผู้ใช้ระบุมาเองเป็นข้อกำหนด ไม่ใช่ข้อเสนอ

เบี่ยงเบนได้ แต่ **ต้องถามที่ประตู A พร้อมภาพเทียบสองทาง** ไม่ใช่บันทึกเหตุผลไว้แล้วทำเลย

### 7.2 สีเดียวกันในโหมดต่างกันให้ความรู้สึกคนละอย่าง

`#780000` บนพื้นเข้มคือ **แดงเข้ม** · บนพื้นครีมอ่านออกมาเป็น **น้ำตาล**

ต้องเลือกค่าให้ **หมวดสีที่คนเรียก** ตรงกันทั้งสองโหมด ไม่ใช่แค่ contrast ผ่าน

> คำถามที่ต้องมีในเกณฑ์ผ่านของช่วง B: *"เปิดหน้าจริงแล้วเห็นสีที่ผู้ใช้ให้มาไหม ทั้งสองโหมด"*

### 7.3 ต้องมีรายการว่าสีแบรนด์ปรากฏที่ไหน

ถ้าไม่มีรายการ สีจะไปกองอยู่แค่ปุ่มหลัก แล้วหน้าที่เหลือเป็นเทากับกลางๆ ซึ่งผู้ใช้เรียกว่า **"จืด"**

| ที่ | ใช้อะไร |
|---|---|
| ปุ่มหลักของหน้า | พื้นทึบ `primary` |
| เมนูที่เลือกอยู่ | พื้นทึบ `primary` เต็มความกว้าง |
| แถบใต้/บนแท็บที่เปิด | เส้นสี `primary` |
| หัวเพจและหัวข้อย่อย | แถบสั้นสี `accent` นำหน้า |
| กรอบไอคอนของการ์ดทางเข้า | สี `accent` · ชี้แล้วเป็นพื้นทึบ `primary` |
| วงแหวน focus | `primary` |
| เลขหน้าที่เปิดอยู่ | พื้นทึบ `primary` |

**ที่ห้ามใช้**

- ‼️ **ห้ามพาดเส้นสีแบรนด์เต็มความกว้างของการ์ด** — ทดลองแล้วมันอ่านออกมาเป็น *"แถบแจ้งเตือนว่ามีอะไรผิด"* ไม่ใช่สีแบรนด์
  สีแบรนด์ต้องอยู่กับสิ่งที่ **มีความหมาย** (กดได้ / บอกตำแหน่ง / เป็นหัวเรื่อง) ไม่ใช่พาดไปทั่วเพื่อให้เห็นสี
- **ลิงก์ในเนื้อความ** — ถ้าลิงก์สีเดียวกับปุ่มหลักและข้อความผิดพลาด ทั้งสามจะชนกัน · แยก token `brand.link` ออกมา

### 7.4 เกณฑ์ contrast ไม่ได้มีค่าเดียว

‼️ **การตั้ง 4.5:1 กับทุกอย่างคือการตั้งเกณฑ์ผิด** — WCAG ให้ 3:1 กับสิ่งที่ไม่ใช่ข้อความ
ตั้ง 4.5 ไปหมดจะบังคับให้สีเข้มๆ จางเป็นสีอ่อนโดยไม่มีเหตุผลรองรับ

| ใช้ทำอะไร | เกณฑ์ |
|---|---|
| ข้อความขนาดปกติ | 4.5:1 |
| ข้อความใหญ่ (≥24px หรือ ≥19px ตัวหนา) | 3:1 |
| **เส้นขอบของ control · ไอคอน · แถบกราฟิก** | **3:1** (WCAG 1.4.11) |
| ตัวหนังสือบนปุ่มทึบ | 4.5:1 กับพื้นปุ่ม · และพื้นปุ่มต้องต่างจากการ์ด 3:1 |

**ตัวอย่างข้อจำกัดทางฟิสิกส์ที่ต้องรู้ก่อนออกแบบ** — แดงบริสุทธิ์บนพื้นน้ำเงินเข้มได้แค่ ~2.6-2.9:1 จึงใช้เป็นข้อความขนาดปกติในโหมดมืดไม่ได้เลย
ทางออก: พื้นปุ่มใช้แดงสด + **ตัวหนังสือหมึกเกือบดำ** (ไม่ใช่ครีม) · ไอคอนและเส้นขอบใช้แดงอ่อนกว่า · ข้อความปกติ **ไม่ใช้แดง**

### 7.5 ห้ามเขียนผลการตรวจเป็นประโยคในเอกสาร ถ้าไม่มีคำสั่งที่รันซ้ำได้กำกับ

> `DESIGN.md` เคยเขียนว่า *"ตรวจ contrast แล้วทุกคู่ 48 คู่ผ่าน 4.5:1 ทั้งสองโหมด"*
> พอเขียนสคริปต์ตรวจจริงกับพาเลตต์เดิม **ตก 7 คู่** — ขอบช่องกรอกได้แค่ 1.85:1 ซึ่งผู้ใช้สายตาไม่ดีจะหาช่องกรอกไม่เจอ
>
> ประโยคในเอกสาร **ไม่ใช่การตรวจ** เพราะไม่มีใครรันซ้ำได้ ไม่มีอะไรบอกว่ามันหมดอายุแล้วตอนแก้สีรอบต่อไป
> และคนเขียนนับเฉพาะคู่ "ข้อความบนพื้น" แล้วลืมคู่ "เส้นขอบของ control" ซึ่งเป็นคนละเกณฑ์กัน

ใช้ `php scripts/check-contrast.php` ซึ่งอ่านค่าจาก `project/DESIGN.md` โดยตรง และถูกเรียกจาก `check.php`

## 7ก. ภาพประกอบ — เอามาจากไหนและเก็บยังไง

หน้าสาธารณะที่ไม่มีภาพเลย **ดูไม่ดีไม่ว่าดีไซน์จะแม่นแค่ไหน** — ภาพหนึ่งใบทำงานแทน layout ได้เกือบทั้งส่วน
แต่ภาพก็เป็นของที่ทำผิดแล้วเจ็บที่สุดเช่นกัน จึงมีกฎ 4 ข้อ

### 7ก.1 ภาพแบ่งเป็นสองกอง และแก้คนละวิธี

| กอง | เอามาจากไหน |
|---|---|
| **ภาพที่ต้องเป็นของจริง** — ตัวสินค้า อาคาร ทีมงาน | **ลูกค้าเท่านั้น** ไม่มีทางลัด |
| **ภาพประกอบและภาพบรรยากาศ** | เครื่องมือสร้างภาพ หรือภาพ stock ที่ใช้เชิงพาณิชย์ได้ |
| **ของตกแต่งที่ไม่ใช่ภาพถ่าย** — ลวดลาย gradient texture | **ต้องเป็น SVG/CSS ห้ามเป็นไฟล์รูป** เพราะเปลี่ยนสีตามโหมดมืดได้เอง ไม่มีไฟล์ให้โหลด และคมทุกความละเอียด |

> ‼️ **ภาพที่สร้างด้วย AI ห้ามใช้แทนของจริงของลูกค้า** — ขวดที่ไม่มีอยู่จริงบนเว็บบริษัทจริง คือการหลอกผู้ใช้
> ใช้ได้กับ prototype และภาพบรรยากาศ แต่ต้องบอกลูกค้าเสมอว่าอันไหนเป็นภาพจริงอันไหนไม่ใช่

### 7ก.2 ‼️ ต้องดาวน์โหลดมาเก็บในโปรเจคเสมอ

```bash
php scripts/fetch-image.php --url "https://..." --out hero-bottle --ratio 3:4
```

**เครื่องมือสร้างภาพทุกเจ้าคืน URL บนคลาวด์ ไม่ใช่ไฟล์** ปล่อยให้หน้าอ้าง URL นั้นตรงๆ คือโหลดจาก CDN ซึ่งกฎเหล็กข้อ 2 ห้าม
และวันที่ลิงก์หมดอายุ **รูปหายทั้งเว็บโดยไม่มีใครรู้ล่วงหน้า**

สคริปต์นี้ดาวน์โหลด ครอปตามสัดส่วน ย่อ แปลง WebP ให้จบในขั้นเดียว · **วัดจริง 4.2 MB เหลือ 90 KB**
ไฟล์ที่ได้จากเครื่องมือสร้างภาพมักหนัก 3-5 MB ซึ่ง**ใช้บนหน้าเว็บไม่ได้** โดยเฉพาะเมื่อผู้ใช้เข้าจากเน็ตมือถือ

### 7ก.3 ‼️ คำสั่ง "ห้ามมีตัวหนังสือ" ไม่ได้ผล

สั่งว่า `no text, no labels` ไปแล้ว **ยังได้ฉลากมั่วกลับมา 4 จาก 5 ใบ** — `Jasmine Jea` · `Taie Pu—KA!` · `CHRNETI`
เพราะขวดสินค้าในข้อมูลที่โมเดลเรียนมามีฉลากทุกใบ

| ทางแก้ที่ได้ผล | |
|---|---|
| **ครอปมาโครให้ไม่เห็นส่วนที่ฉลากอยู่** | ได้ผลจริง ทดสอบแล้ว — สั่งถ่ายเฉพาะคอขวด ผิวน้ำ หรือมุมที่ฉลากไม่อยู่ในเฟรม |
| ถ่ายของที่ไม่มีฉลากโดยธรรมชาติ | ใบชา ดอกไม้ ไร่ วัตถุดิบ ภาพบรรยากาศ |
| ใช้โมเดลที่เก่งเรื่องตัวหนังสือ | แพงกว่าหลายเท่า และให้ตัวหนังสือที่**อ่านออกแต่ผิดแบรนด์** ซึ่งแย่กว่าตัวมั่วที่อ่านไม่ออก |

### 7ก.3ก ‼️ ต้องถามว่าจะใช้โมเดลไหน ห้ามเลือกเอง

**เจอมาแล้วจริง — สร้างรูปโดยไม่ถาม แล้วได้รูปที่ไม่ตรงกับที่ผู้ใช้ต้องการ**

เครื่องมือสร้างภาพมีหลายโมเดล และ**แต่ละตัวให้ผลคนละแบบชัดเจน** ทั้งความสมจริง สไตล์ ความเร็ว และราคาต่อใบ · การหยิบตัวแรกที่เจอมาใช้ คือการตัดสินใจเรื่องหน้าตาแทนผู้ใช้โดยที่เขาไม่รู้ตัว

> ‼️ **นี่เป็นการตัดสินใจระดับเดียวกับสีแบรนด์** — ข้อ 8.2 บอกไว้แล้วว่าเรื่องที่ลดทอนตัวตนของแบรนด์ **ต้องถามเสมอ ห้ามตัดสินเองแล้วบันทึกเหตุผล**
> โมเดลที่ให้ภาพแนวการ์ตูนกับแนวภาพถ่ายสตูดิโอ เปลี่ยนบุคลิกของทั้งเว็บ

**ถามครั้งเดียวก่อนสร้างใบแรก แล้วใช้ตัวเดิมตลอดโปรเจค**

| ต้องทำ | |
|---|---|
| **ดึงรายการโมเดลที่มีจริงจากเครื่องมือมาให้เลือก** | ห้ามเดาชื่อจากความจำ — รายการเปลี่ยนได้ และชื่อที่ไม่มีอยู่จริงทำให้ล้มเหลวเงียบๆ |
| บอก**ความต่างที่ใช้ตัดสินได้** | สไตล์ที่ได้ · เก่งเรื่องอะไร · ความเร็ว · ราคาต่อใบ |
| **เสนอตัวที่คิดว่าเหมาะกับ mood ในโปรเจคนี้ พร้อมเหตุผล** | ผู้ใช้ส่วนใหญ่ไม่รู้จักชื่อโมเดล แต่ปัดตกข้อเสนอได้ |
| ‼️ **บอกว่าใช้เครดิตของบัญชีเขา** และจะสร้างกี่ใบ | ให้เขาประเมินได้ก่อนกดเริ่ม |
| **บันทึกลง `project/NOTES.md`** ว่าใช้โมเดลไหน | ใบที่ 20 ต้องเข้าชุดกับใบที่ 1 · และคนที่มารับช่วงต้องรู้ว่าจะสร้างเพิ่มด้วยอะไร |

> ‼️ **เรื่องวิดีโอถามแยกจากรูป** — คนละโมเดล คนละราคา และแพงกว่ามาก · ห้ามเหมาว่าตอบเรื่องรูปแล้วคือตอบเรื่องวิดีโอด้วย
>
> ‼️ **เส้นทาง ข ต้องระบุลงใน `design-brief.md` ด้วย** ว่าจะให้ใช้โมเดลไหน ไม่งั้น Claude Design จะเลือกเองแบบเดียวกัน

### 7ก.5 ‼️ ตัดภาพจากภาพแบบของผู้ใช้ — ทางสำรอง ไม่ใช่ของจริง

ผู้ใช้ที่ออกแบบเอง (เส้นทาง ค) มักให้แค่ภาพทั้งหน้า · ถ้าไม่มีภาพประกอบ export แยก และสร้างภาพไม่ได้ **ตัดจากภาพแบบมาใช้ได้ทุกอย่าง** — ภาพถ่าย ภาพประกอบ ไอคอน โลโก้ และภาพที่มีตัวหนังสือ

> **ผู้ใช้ตัดสินเอง (3.17.0)** — ภาพที่ตัดจากภาพแบบได้รับยกเว้นจาก [`features/i18n.md`](features/i18n.md) ข้อ 7 (ภาพที่มีข้อความฝัง) และ [`components.md`](components.md) ข้อ 12 (ไอคอนต้องเป็น SVG ชุดกลาง)
> ภาพเหล่านี้มาจากแบบที่ผู้ใช้อนุมัติ และแบบของผู้ใช้ชนะกฎเริ่มต้น (ข้อ 5.0)

สิ่งที่ภาพตัดทำไม่ได้ — บอกผู้ใช้เมื่อเกี่ยว ไม่ต้องหยุดถาม: ความละเอียดเท่าภาพแบบ อาจแตกบนจอความละเอียดสูง · ตัวหนังสือในภาพไม่เปลี่ยนตามภาษา · สีไม่เปลี่ยนตามโหมดมืด


**ลำดับที่ต้องลองก่อน:** ภาพใน `refs/assets/` ที่ผู้ใช้ export แยก → ขอไฟล์จากผู้ใช้ → เครื่องมือสร้างภาพ (ถ้าเข้ากับแบบ) → ตัดจากภาพแบบ

## 8. โลโก้

### 8.1 ที่ที่โลโก้ปรากฏ — ไล่ให้ครบทุกครั้งที่โลโก้เปลี่ยน

การเปลี่ยนโลโก้เกิดขึ้นทีเดียวแต่ปรากฏหลายที่ และ**ที่ที่ลืมง่ายที่สุดคือที่ที่ไม่อยู่ในหน้า**

| ที่ไหน | ข้อควรระวัง |
|---|---|
| แถบเมนู / topbar | โลโก้ที่มีมุมโปร่งใสและหมึกเข้ม จะจมบนพื้นเข้ม — ต้องวางบนวงกลมพื้นอ่อน |
| หน้าเข้าสู่ระบบ | ขนาดใหญ่ ต้องคมบนจอความละเอียดสูง |
| **แท็บเบราว์เซอร์ (favicon)** | ‼️ **แถบแท็บเป็นสีเข้มหรือสว่างตามธีมของเครื่องผู้ใช้ ไม่ใช่ตามธีมของระบบเรา** — ต้องมีพื้นทึบ |
| จอที่เปิดค้าง / เอกสารที่พิมพ์ | ถ้าพิมพ์ขาวดำ ต้องมีเวอร์ชันที่อ่านออกเมื่อไม่มีสี |

### 8.1ก สร้าง favicon ด้วยสคริปต์ ห้ามทำด้วยมือ

```bash
php scripts/make-favicon.php
```

**การทำด้วยมือทุกครั้งคือเหตุผลที่ทำให้คนข้ามมัน** — สคริปต์อ่านสีแบรนด์จาก `project/DESIGN.md` เอง แล้วเขียนไฟล์ที่ layout กลางอ้างถึงอยู่แล้ว ไม่ต้องแก้ HTML เพิ่ม

| หาต้นทางยังไง | เรียงตามลำดับ |
|---|---|
| 1 | `--source path/to/logo.png` ถ้าระบุมา |
| 2 | `public/assets/images/logo.{png,jpg,webp,gif}` ถ้ามี |
| 3 | ตัวอักษรแรกของชื่อระบบ บนพื้นสี `brand.primary` — ใช้เมื่อโปรเจคยังไม่มีโลโก้ (คำตอบข้อ 1 ของชุดดีไซน์) |

ได้ออกมา 3 ไฟล์ใน `public/assets/images/` — `favicon.ico` (16/32/48) · `favicon-32.png` · `apple-touch-icon.png`
**สร้างเฉพาะขนาดที่ `partials/favicon.php` อ้างถึงจริง** — เพิ่มขนาดใหม่เมื่อไหร่ ต้องเพิ่มลิงก์ในไฟล์นั้นในคอมมิตเดียวกันเสมอ ไม่งั้นได้ไฟล์ที่ไม่มีอะไรใช้
**พื้นทึบเสมอ** ตามเหตุผลในตารางข้างบน · `partials/favicon.php` เป็นที่เดียวที่ประกาศลิงก์เหล่านี้

> ‼️ **ต้องรันซ้ำทุกครั้งที่เปลี่ยนโลโก้หรือเปลี่ยนสีแบรนด์** — แท็บเบราว์เซอร์ไม่ได้อยู่ในหน้า จึงไม่มีใครเห็นว่ามันยังเป็นสีของแบรนด์เดิม
>
> ‼️ **GD อ่าน SVG ไม่ได้** ถ้าโลโก้เป็น SVG ต้องส่งออกเป็น PNG ≥ 512×512 ก่อน · และโหมดตัวอักษรต้องมีไฟล์ `.ttf`/`.otf` (`.woff2` ที่เก็บไว้ตามกฎห้าม CDN ใช้กับ GD ไม่ได้) — สคริปต์ไล่หาให้เองจากเครื่อง ไม่เจอถึงจะบอกให้ระบุ `--font`

### 8.2 เรื่องที่ต้องถามผู้ใช้เสมอ ห้ามตัดสินเองแล้วบันทึกเหตุผล

การบันทึกเหตุผลไว้ **ไม่พอ** เมื่อการตัดสินใจนั้นลดทอนตัวตนของแบรนด์

- **การใช้โลโก้แบบตัดส่วน** — ตัดเฉพาะสัญลักษณ์มาใช้เป็น mark ย่อ ทำให้ **จำแบรนด์ไม่ได้** ซึ่งเป็นหน้าที่หลักของโลโก้ ตรงกว่าเรื่องความคมชัด
- **การเปลี่ยนสีหลักของแบรนด์**
- **การตัดฟีเจอร์ที่ผู้ใช้เอ่ยถึงเอง**

- จำค่าที่ผู้ใช้เลือกไว้ — บันทึกลงตาราง `users` สำหรับคนที่ล็อกอิน และ cookie สำหรับคนที่ยังไม่ล็อกอิน
- `app.css` ประกาศ token 2 ชุด: `:root` (สว่าง) และ `[data-theme="dark"]` — สลับด้วยการเปลี่ยน attribute ที่ `<html>` ไม่ใช่โหลด CSS คนละไฟล์
- ต้องกัน **flash ตอนโหลดหน้า** — เขียนค่าโหมดลง `<html data-theme="...">` ตั้งแต่ฝั่ง PHP ไม่ใช่รอ JS ทำงาน
- **โหมดมืดไม่ใช่การกลับสี** พื้นหลังดำสนิทกับข้อความขาวสนิททำให้ตาล้า ให้ใช้เทาเข้ม (`#0E1014` แนวนี้) กับข้อความเทาอ่อน และลดความอิ่มของสีเน้นลง

## 11. Motion

**หลัก: motion อธิบายความสัมพันธ์ ไม่ใช่ของตกแต่ง** ถ้าเอาออกแล้วผู้ใช้ไม่เสียอะไรเลย แปลว่าไม่ควรมี

### ใช้ตอนไหน

| ใช้ | ไม่ใช้ |
|---|---|
| บอกว่าของมาจากไหน (modal ขยายจากปุ่มที่กด) | ทำให้หน้าดูมีอะไร |
| บอกว่าระบบกำลังทำงาน (spinner, skeleton) | เคลื่อนไหวข้อความหรือหัวข้อตอนโหลดหน้า |
| ดึงสายตาไปที่สิ่งที่เพิ่งเปลี่ยน (แถวใหม่ในตาราง) | เอฟเฟกต์ตอน scroll ทุกส่วนของหน้า |
| บอกว่าทำอะไรไม่ได้ (ปุ่มสั่นเมื่อกรอกผิด) | เปลี่ยนหน้าแล้วมีทรานซิชันยาว |

### กฎ

- ระยะเวลาใช้จาก `motion.duration` — **ส่วนใหญ่ควรอยู่ที่ `fast` (120ms)** สิ่งที่ยาวกว่า 320ms จะเริ่มรู้สึกช้า
- เคลื่อนแค่ `transform` และ `opacity` เท่านั้น — เคลื่อน `width`/`height`/`top` ทำให้เบราว์เซอร์คำนวณ layout ใหม่ทุกเฟรมแล้วกระตุก
- ของที่เข้ามาเร็วกว่าของที่ออกไป
- **ต้องเคารพ `prefers-reduced-motion`** — ผู้ใช้บางคนเวียนหัวจากการเคลื่อนไหว

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .01ms !important;
    transition-duration: .01ms !important;
  }
}
```

- **ห้ามใช้ animation กับสิ่งที่ผู้ใช้ต้องทำซ้ำหลายสิบครั้งต่อวัน** — ทรานซิชันของ dropdown ที่พนักงานเปิดวันละ 200 ครั้ง กลายเป็นความหน่วงที่น่ารำคาญ

### ‼️ `animation` ที่แตะ `transform` ต้องใช้ `fill-mode: backwards` ห้ามใช้ `both` หรือ `forwards`

```css
/* ผิด — transform ค้างอยู่หลัง animation จบ */
.page > .stack > * { animation: rise 200ms both; }

/* ถูก — ได้สถานะเริ่มต้นตอนรอ delay แล้วปล่อยคืนทุกค่าเมื่อจบ */
.page > .stack > * { animation: rise 200ms backwards; }
```

`both` กับ `forwards` ทำให้ค่าที่คีย์เฟรมกำหนด **ค้างอยู่หลัง animation จบ** ซึ่งรวมถึง `transform`
ต่อให้ค่าสุดท้ายเป็น `matrix(1, 0, 0, 1, 0, 0)` ที่ไม่ทำอะไรเลย — **`transform` ที่ไม่ใช่ `none` ก็สร้าง stacking context**
ทุกบล็อกในหน้าจึงกลายเป็นกรงขัง `z-index` ของลูกตัวเอง

> อาการจริง: แผงปฏิทินเปิดแล้วโดนการ์ดที่อยู่ถัดไปทับ ทั้งที่ตั้ง `z-index: 30` แล้ว
>
> เป็นบั๊กที่ **มองไม่เห็นจนกว่าจะมี dropdown ตัวแรกในระบบ** ซึ่งอาจเป็นอีกหลาย phase ถัดไป
> อ่าน CSS แล้วดูถูกทุกบรรทัด และตอนเจอทีหลังต้องไล่หาว่าใครสร้าง stacking context ซึ่งใช้เวลานาน

`check.php` จับข้อนี้ให้ (`design/animation-fill-mode`)
