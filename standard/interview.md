# ชุดคำถามสัมภาษณ์ — ช่วง A

> ใช้ในช่วง A ของ [`flow.md`](flow.md)
> เป้าหมาย: เปลี่ยนสิ่งที่ผู้ใช้พูด → เป็นเอกสารที่ยืนยันแล้ว ก่อนแตะโค้ดแม้แต่บรรทัดเดียว

---

## 1. ทำไมต้องมีชุดคำถามตายตัว

ถ้าปล่อยให้ผู้ใช้เล่าเอง คนหนึ่งเล่าละเอียด อีกคนพิมพ์มาบรรทัดเดียว **ผลลัพธ์จะออกมาคนละมาตรฐานทั้งที่อ่านกฎชุดเดียวกัน**

ความไม่สม่ำเสมอเริ่มที่ input ไม่ได้เริ่มที่กฎ — ชุดคำถามนี้คือการทำให้ input มีมาตรฐานเท่ากันทุกโปรเจค

---

## 2. กฎการถาม

| กฎ | เหตุผล |
|---|---|
| **ถามเป็นชุด ไม่ถามทีละข้อ** | ผู้ใช้จะได้ตอบรวดเดียวแล้วไปทำอย่างอื่น ไม่ต้องนั่งเฝ้าตอบทีละคำถาม |
| **ตอบไม่ได้ → เสนอค่าที่แนะนำแล้วให้เลือก** | ห้ามข้ามไปเงียบๆ แล้วเดาเอง การเดาที่ไม่ได้บันทึกคือต้นเหตุของการรื้องาน |
| **ห้ามถามซ้ำสิ่งที่มีคำตอบอยู่ใน `project/` แล้ว** | เสียเวลาผู้ใช้และทำให้ดูเหมือนไม่ได้อ่านของเดิม |
| **ถามชุดระบบให้จบก่อน แล้วค่อยถามชุดดีไซน์** | ต้องรู้ก่อนว่าระบบมีหน้าอะไรบ้าง ถึงจะถามเรื่องหน้าตาได้ตรง |
| **บันทึกคำตอบทันทีที่ได้** | session หลุดแล้วไม่ต้องถามใหม่ |

## 3. ขั้น A1 — หา prompt ก่อนถาม

ถามผู้ใช้ก่อนเสมอ: **"มี prompt หรือเอกสารที่อธิบายโปรเจคนี้อยู่แล้วไหม"**

ถ้ามี ให้อ่านจนจบ แล้ว**ไล่เทียบทีละข้อ**กับรายการคำถามข้างล่าง ทำตารางแบบนี้ให้ผู้ใช้ดู

```
จาก prompt ได้ข้อมูลครบแล้ว 12 ข้อ  ขอถามเพิ่ม 5 ข้อ

✅ ระบบทำอะไร · role · ข้อมูลหลัก · flow หลัก · ภาษา · …
❓ ข้อมูลไหนที่ผิดพลาดไม่ได้ · ปริมาณผู้ใช้พร้อมกัน · ใครดูแลต่อ · โลโก้ · อุปกรณ์หลัก
```

> ‼️ **ห้ามข้ามการถามทั้งหมดเพราะเห็นว่ามี prompt แล้ว** — prompt ยาวแทบไม่เคยครบทุกช่อง โดยเฉพาะเรื่องที่ผู้ใช้ไม่ได้นึกถึง (สิทธิ์ · ข้อมูลที่ผิดพลาดไม่ได้ · ปริมาณการใช้งาน · ใครดูแลต่อ)

## 4. ขั้น A2 — ชุดคำถามเรื่องระบบ

### ก. ระบบนี้คืออะไร

1. **ชื่อโปรเจค**
2. ระบบนี้ทำอะไร **แก้ปัญหาอะไรให้ใคร**
3. ใครใช้บ้าง มี role อะไรบ้าง **แต่ละ role ทำอะไรได้และทำอะไรไม่ได้**
4. ใช้ภายในองค์กรอย่างเดียว หรือมีคนนอกเข้าถึงด้วย

### ข. ข้อมูล

5. ข้อมูลหลักในระบบมีอะไรบ้าง (เช่น สินค้า ใบสั่งซื้อ ลูกค้า) และ**เกี่ยวข้องกันอย่างไร**
6. **ข้อมูลไหนที่ผิดพลาดไม่ได้เด็ดขาด** (ยอดเงิน สต็อก สิทธิ์ คิว) ← จุดเหล่านี้ต้องทดสอบหนักเป็นพิเศษ
7. มีระบบเดิมหรือข้อมูลเดิมที่ต้องย้ายมาหรือเชื่อมต่อด้วยไหม

### ค. งานที่ต้องทำได้

8. flow หลักที่ผู้ใช้ต้องทำได้มีอะไรบ้าง **เรียงตามความสำคัญ**
9. ต้องมีรายงานอะไรบ้าง **ใครดู ใช้ตัดสินใจอะไร**
10. **อะไรที่ยังไม่ต้องมีในเวอร์ชันแรก** ← ตอบไม่ได้ให้เสนอรายการที่ควรตัดออกแล้วให้ยืนยัน
11. มีอะไรที่ต้อง**พิมพ์ออกกระดาษ**ไหม (ใบเสร็จ บัตรคิว รายงาน) ← กระทบการทำ print stylesheet
12. ต้องมีการ**แจ้งเตือน**ไหม ถ้ามี ไปทางไหน (อีเมล / LINE / ในระบบ)

### ง. ขนาดและสภาพการใช้งาน

13. **ผู้ใช้พร้อมกันกี่คนโดยประมาณ** และข้อมูลจะโตปีละเท่าไหร่ ← กระทบ index และการทำ pagination
14. มีหน้าจอที่**เปิดค้างไว้ตลอดวัน**ไหม (จอแสดงคิว จอรายงาน dashboard) ← ต้องออกแบบการรีเฟรชและการกู้สถานะเป็นพิเศษ
15. ใช้งานตอนเน็ตไม่เสถียรไหม

### จ. สภาพแวดล้อม

16. จะขึ้น server ไหน · PHP กับ MySQL/MariaDB เวอร์ชันอะไรบนเครื่องจริง
17. มีกำหนดส่งไหม
18. **ใครดูแลต่อหลังส่งมอบ** ← กระทบว่า README และคู่มือต้องละเอียดแค่ไหน

### ฉ. ภาษา

19. ต้องรองรับภาษาอะไรบ้าง และ**ภาษาไหนเป็นค่าเริ่มต้น**เมื่อผู้ใช้เข้ามาครั้งแรก

> **`th` + `en` เป็นค่าบังคับทุกโปรเจค** ถ้าผู้ใช้บอกว่า "ใช้แต่ภาษาไทย" ยังต้องทำ `en` ด้วย แต่อธิบายให้ทราบว่า**กลไกนี้ทำวันแรกแทบไม่มีต้นทุน ส่วนที่แพงคือย้อนกลับมาทำทีหลัง** เพราะต้องไล่แก้ทุกข้อความในทุกหน้าและ migrate ข้อมูลเก่าทั้งตาราง

### ช. วิธีทำงาน

20. **โหมดการทำงานของช่วงลงมือ** — ปกติ หรือ เร็ว

| ตอบ | ผู้ใช้ได้อะไร | แลกกับอะไร |
|---|---|---|
| **ปกติ** | ตรวจทุกหน้าตอนจบแต่ละ phase และหยุดให้ดู 1 ครั้งต่อ phase · ผิดตรงไหนรู้เร็ว แก้แค่ phase เดียว | ช้ากว่า และต้องกลับมาตอบทุก phase |
| **เร็ว** | ทำต่อยาวจนครบทุก phase โดยไม่หยุด · ไปทำอย่างอื่นได้ · **ดีไซน์ยังตรวจครบทุก phase** · ตรวจฟังก์ชันรวมทีเดียวที่ช่วง D | **ฟังก์ชัน สิทธิ์ และข้อความที่ผิดจะรู้ตอนท้าย และอาจต้องแก้หลาย phase พร้อมกัน** |

> **ตอบไม่ได้ = ปกติ** · บันทึกลง `STATE.md` บรรทัด `โหมด:` · เปลี่ยนได้ตลอดเวลาด้วยการบอกว่า "โหมดเร็ว" หรือ "โหมดปกติ"
> ทั้งสองโหมดยังหยุดที่ประตู A · B · D และ phase แรกตรวจเต็มเสมอ — รายละเอียดที่ [`flow.md`](flow.md) ข้อ 15

## 5. ขั้น A3 — วิเคราะห์แล้วเสนอ

**ขั้นที่ทำให้ workflow นี้ต่างจากการรับคำสั่งเฉยๆ** — หน้าที่ตรงนี้คือทำตัวเป็น dev ที่ทักลูกค้า ไม่ใช่พนักงานรับออเดอร์

### มองหา 5 อย่าง

| มองหาอะไร | ตัวอย่างสมมติ — ระบบบัตรคิว (ใช้ประกอบความเข้าใจเท่านั้น ไม่ใช่โปรเจคจริง) |
|---|---|
| **ลูปที่ไม่ครบ** | มีออกบัตร มีเรียกคิว แต่ไม่มีทางจัดการเมื่อลูกค้าไม่มา → เสนอระบบข้ามคิวและเรียกซ้ำ |
| **สิ่งที่ผู้ใช้จริงจะขอในสัปดาห์แรก** | จอแสดงคิวมีแต่ตัวเลข → เสนอพื้นที่โฆษณา/ประชาสัมพันธ์ |
| **ช่องทางที่ขาด** | รับบัตรได้เฉพาะหน้าร้าน → เสนอจองคิวออนไลน์ล่วงหน้า |
| **สิ่งที่ต้องมีเพื่อดูแลระบบได้** | ไม่มีรายงานย้อนหลัง → เสนอสถิติคิวรายวัน เวลารอเฉลี่ย ช่วงที่คนแน่น |
| **กรณีที่จะพังตอนใช้จริง** | ไฟดับหรือรีเฟรชจอแล้วคิวหาย → เสนอเก็บสถานะใน DB ไม่ใช่ session |

### เสนอยังไง

- เสนอเป็น**รายการที่เลือกได้** ไม่ใช่ยัดเข้าไปเอง
- แต่ละข้อต้องบอก **3 อย่าง**: ทำอะไร · ทำไมถึงควรมี · **ทำตอนนี้คุ้มไหม หรือทำทีหลังได้**
- เรียงจากที่คิดว่าจำเป็นที่สุดลงมา
- **ถ้าเห็นสิ่งที่จะทำให้ระบบใช้งานจริงไม่ได้ ต้องบอกตรงๆ** ไม่ใช่เสนอเป็นตัวเลือกเฉยๆ

ตัวอย่างรูปแบบการนำเสนอ (เนื้อหาเป็นระบบสมมติ ใช้ดูโครงเท่านั้น)

```
ข้อเสนอ 4 ข้อ — เลือกได้ว่าเอาข้อไหน

1. ระบบข้ามคิว  ⚠️ ผมคิดว่าจำเป็น ไม่ใช่ตัวเลือก
   ถ้าเรียกแล้วลูกค้าไม่มา พนักงานจะติดอยู่กับคิวนั้นทั้งวัน ระบบใช้งานจริงไม่ได้
   ทำตอนนี้ — เพราะกระทบโครงสร้างสถานะของคิวโดยตรง

2. จองคิวออนไลน์
   ลูกค้าจองล่วงหน้าแล้วมารับบัตรที่ร้าน ลดคนยืนรอ
   ทำทีหลังได้ — แต่ต้องเผื่อช่องในตาราง queues ไว้ตั้งแต่ตอนนี้

3. พื้นที่โฆษณาบนจอแสดงคิว …
4. รายงานสถิติคิวรายวัน …
```

**บันทึกทั้งข้อเสนอและคำตอบของผู้ใช้ลง `project/BRIEF.md`** รวมถึงข้อที่ผู้ใช้ปฏิเสธ พร้อมเหตุผล — เพื่อไม่ให้มีใครมาเสนอซ้ำอีกในอนาคต

## 6. ขั้น A4 — ชุดคำถามเรื่องดีไซน์

ชุดนี้คือวัตถุดิบของ [`project/DESIGN.md`](design.md) **ถามให้ครบ ไม่งั้นช่องจะว่าง แล้ว AI จะเติมค่า default ของตัวเองซึ่งคือต้นเหตุที่ทุกโปรเจคหน้าเหมือนกัน**

### ก. แบรนด์

1. **มีโลโก้ไหม** ถ้ามีขอไฟล์ (SVG ดีที่สุด) — ถ้าไม่มี ระบบจะใช้ชื่อระบบเป็นตัวอักษรแทน
2. **มีสีของแบรนด์ที่ต้องใช้ไหม** ถ้ามีขอรหัสสี และถามว่า**บังคับต้องใช้หรือแค่ให้อ้างอิง**
3. มีฟอนต์ที่องค์กรกำหนดไว้ไหม
   > **ต้องรองรับภาษาไทย** ฟอนต์ที่สวยแต่ไม่มีตัวไทยใช้ไม่ได้ · และเราไม่โหลดจาก CDN ตามกฎเหล็กข้อ 2 จึงต้องเก็บไฟล์ฟอนต์ไว้ใน `public/assets/fonts/` เอง

### ข. อารมณ์ที่ต้องการ

ถามเป็น**คู่ตรงข้ามให้เลือกตำแหน่ง** ได้คำตอบที่ใช้งานได้จริงกว่าถามว่า "อยากได้แนวไหน"

| ด้านหนึ่ง | ↔ | อีกด้าน |
|---|---|---|
| ทางการ น่าเชื่อถือ | ↔ | เป็นกันเอง เข้าถึงง่าย |
| เรียบ สงบ | ↔ | สดใส มีพลัง |
| โปร่ง เว้นว่างเยอะ | ↔ | แน่น เห็นข้อมูลเยอะในหน้าเดียว |
| ดูทันสมัย | ↔ | ดูคุ้นเคย ปลอดภัย |

4. เลือกตำแหน่งของทั้ง 4 คู่

### ค. บุคลิกและแรงบันดาลใจ

**5. Mood ของระบบ — ถ้าคนใช้ระบบนี้ครั้งแรก แล้วต้องบอกความรู้สึกเป็น 3 คำ อยากให้เป็นคำว่าอะไร**

เลือกจากนี้หรือคิดเองก็ได้ — สงบ · คม · อบอุ่น · จริงจัง · สนุก · เรียบง่าย · หรูหรา · ทันสมัย · มั่นคง · เป็นมิตร · รวดเร็ว · ประณีต

> ‼️ หลังได้คำตอบ **AI ต้องสรุป mood เป็นประโยคเดียวที่พูดออกเสียงได้ แล้วให้ผู้ใช้ยืนยัน**
> ผู้ใช้ไม่ต้องคิดประโยคเอง แค่บอกว่าใช่หรือไม่ใช่ — คนที่ไม่ใช่ดีไซน์เนอร์อธิบายไม่ได้ แต่ปัดตกได้

**6. Visual Weight — ของแต่ละชิ้นบนหน้าจอ อยากให้ดูหนักหรือเบา**

```
เบา บาง โปร่ง ───────┼─────── หนัก แน่น ทึบ
```

| เบา | หนัก |
|---|---|
| ตัวอักษรบาง · เส้นขอบบางหรือไม่มี · สีจาง · แทบไม่มีเงา · ใช้ที่ว่างแทนกรอบ | ตัวอักษรหนา · เส้นขอบหนา · สีทึบเต็ม · เงาชัด · กรอบชัด |

> ‼️ **คนละเรื่องกับคู่ "โปร่ง ↔ แน่น" ในข้อ 4** — ข้อนั้นถามว่า *มีของเยอะแค่ไหน* ข้อนี้ถามว่า *ของแต่ละชิ้นดูหนักแค่ไหน*
> หน้าที่มีของน้อยแต่ทุกชิ้นหนา กับหน้าที่มีของเยอะแต่ทุกชิ้นบาง เป็นคนละหน้าตากันคนละโลก

**7. Brand Feeling — อยากให้คนที่เห็นระบบนี้รู้สึกยังไงกับ "องค์กร" ไม่ใช่กับตัวระบบ**

น่าเชื่อถือ ปลอดภัย · มืออาชีพ · ใส่ใจรายละเอียด · เข้าถึงง่าย · ทันสมัยล้ำ · คุ้มค่า · พรีเมียม

> ‼️ **แยกจาก mood ในข้อ 5** — mood คือความรู้สึกตอนใช้ · brand feeling คือความรู้สึกต่อองค์กรที่ทำระบบนี้
> ระบบเดียวกัน mood อาจเป็น "สงบ เรียบง่าย" แต่แบรนด์ต้องรู้สึก "ล้ำและแพง" ได้

**7ก. รูปภาพมาจากไหน** ← ไม่ถามแล้วจะไปรู้ตอนลงมือทำว่าไม่มีรูป ซึ่งตอนนั้นออกแบบหน้าไปแล้วโดยสมมติว่ามี

| ตอบ | ผลต่อการออกแบบ |
|---|---|
| **ลูกค้ามีภาพจริงให้** | ขอดูก่อนออกแบบ · คุณภาพและสัดส่วนของภาพจริงเป็นข้อจำกัดของ layout |
| **ยังไม่มี จะไปถ่าย** | ออกแบบได้เต็มที่ แต่ต้องระบุสัดส่วนที่ต้องการให้ชัดตั้งแต่ต้น |
| **ไม่มีและจะไม่มี** | ‼️ ต้องออกแบบหน้าที่ไม่พึ่งภาพถ่าย — ใช้ตัวอักษร ที่ว่าง และลวดลาย SVG แทน |

> ‼️ **ภาพที่เป็นตัวสินค้าหรือสถานที่จริงของลูกค้า ต้องมาจากลูกค้าเท่านั้น** ภาพที่สร้างด้วย AI ใช้แทนไม่ได้
> ส่วนภาพประกอบและภาพบรรยากาศ สร้างหรือใช้ stock ได้ ดู [`design.md`](design.md) ข้อ 7ก

**7ข. ภาพประกอบและภาพบรรยากาศ จะใช้ภาพที่สร้างขึ้นไหม** ← **คนละคำถามกับข้อ 7ก**

> ‼️ **7ก ถามว่า *ลูกค้า* มีภาพไหม · 7ข ถามว่า *เครื่องเรา* สร้างภาพได้ไหม**
> เดิมมีช่องให้ตอบช่องเดียว ทำให้ *"ลูกค้าไม่มีภาพ"* กับ *"เครื่องผมสร้างภาพไม่ได้"* ปนกัน
> ทั้งที่นำไปสู่การออกแบบคนละแบบ — อันแรกยังใช้ภาพที่สร้างขึ้นได้ อันหลังต้องออกแบบที่ไม่พึ่งภาพถ่ายเลย

| ตอบ | ต้องทำอะไรต่อทันที |
|---|---|
| **ใช้** | ‼️ **AI ต้องตรวจว่าตัวเองมีเครื่องมือสร้างภาพหรือยัง** — ไม่มีให้**เตือนผู้ใช้ตรงนั้นเลยว่าต้องต่อ Higgsfield MCP** ([`skills.md`](skills.md) ข้อ 4ก)<br>มีแล้ว → ‼️ **ถามต่อทันทีว่าจะใช้โมเดลไหน ห้ามเลือกเอง** ([`design.md`](design.md) 7ก.3ก) |
| **ไม่ใช้ / ไม่มีเครื่องมือ** | เดินทางสำรองตาม [`design.md`](design.md) 7ก.3ค และบันทึกลง `project/NOTES.md` |

> ‼️ **ห้ามเงียบแล้วไปเจอตอนช่วง C** — ตอนนั้นออกแบบหน้าไปแล้วโดยสมมติว่ามีภาพ การรื้อคือรื้อ layout ทั้งหน้า
> และถ้าเดินเส้นทาง ข ต้องเตือนอีกรอบก่อนส่ง brief เพราะ **Claude Design ใช้เครื่องมือของฝั่งเขาเอง ไม่ใช่ของฝั่งเรา**

**8. Reference — มีเว็บ แอป หรือระบบที่ชอบหน้าตาไหม** ส่งลิงก์ ภาพหน้าจอ หรือบอกแค่ชื่อก็ได้

นึกไม่ออก → ไปดูที่ **`styles.refero.design`** แล้วเลือกมา 1-3 อัน
เว็บนี้ให้สเปคมาพร้อม (พาเลตต์ · ฟอนต์ · สเกล · radius) ซึ่งเอามาใช้ต่อได้ทันที

**และมีอันไหนที่ไม่ชอบไหม** — ตอบข้อนี้ง่ายกว่า และมีประโยชน์พอกัน

> ‼️ ไม่มี reference ก็ไปต่อได้ แต่ **AI ต้องเสนอทิศทางให้เลือกก่อน ห้ามเดาเอง**

### ง. สภาพการใช้งาน

9. **ใช้บนอะไรเป็นหลัก** — มือถือ / เดสก์ท็อป / แท็บเล็ต / จอใหญ่ที่เปิดค้าง
10. **รูปแบบเมนู** — `header` หรือ `sidebar` ← เลือกแบบเดียวแล้วยึดทั้งระบบ ห้ามผสม
11. **โหมดเริ่มต้น** — สว่างหรือมืด (ระบบมีทั้งสองโหมดเสมอ นี่คือถามว่าเปิดมาเจออันไหนก่อน)
12. ผู้ใช้ส่วนใหญ่คุ้นเคยกับคอมพิวเตอร์แค่ไหน ← กระทบขนาดปุ่ม ความชัดของ label และปริมาณคำอธิบาย

### จ. ความคาดหวัง

13. ระบบนี้ต้องดู**พิเศษ**แค่ไหน — ใช้ในองค์กรพอใช้งานได้ก็พอ / ลูกค้าเห็นด้วยต้องดูดี / เป็นหน้าตาของแบรนด์ต้องโดดเด่น

### ฉ. วิธีออกแบบ

**14. ใครออกแบบหน้าตา** ← คำถามนี้เปลี่ยนลำดับงานทั้งช่วง B จึงต้องถามตั้งแต่ตอนนี้

| ตอบ | ช่วง B จะเป็นแบบไหน |
|---|---|
| **ให้ AI ตัดสินเอง** → **เส้นทาง ก** | AI ตัดสิน `DESIGN.md` เองจากคำตอบข้อ 1-13 → ทำ wireframe เอง → ประตูเดียวจบ |
| **ใช้ Claude Design** → **เส้นทาง ข** | **ไม่ทำ wireframe** — เขียนสเปคหน้าเป็นข้อความ → ประตูตรวจสเปค → **ผู้ใช้ต้องลงมือเอง 1 รอบ** เอา brief ไฟล์เดียวไปเข้า Claude Design แล้วเอา HTML กลับมา → ประตูตรวจดีไซน์ |
| **มีแบบของตัวเองแล้ว** (ภาพต่อหน้า) → **เส้นทาง ค** | **ไม่ทำ wireframe** — นำเข้าโฟลเดอร์ภาพแบบ → จับคู่ภาพกับหน้า → `DESIGN.md` ที่สีวัดจากพิกเซลจริง → รายการจุดที่แบบขัดกับกฎ → ประตูเดียว |

> คำว่า **เส้นทาง ก / ข / ค** คือคำที่ [`flow.md`](flow.md) ข้อ 5 ใช้ — ตอบข้อนี้แล้วชื่อเส้นทางถูกล็อกไปจนจบช่วง B

#### ‼️ ตอบว่า "มีแบบของตัวเองแล้ว" — ถามต่อ 4 ข้อทันที

| ถาม | เพราะ |
|---|---|
| **path ของโฟลเดอร์ภาพแบบ** | AI คัดลอกเข้า `project/design/refs/` ทันที — path ในเครื่องผู้ใช้เปิดไม่ได้ใน session ถัดไป |
| **ชื่อฟอนต์ที่ใช้ในแบบ** | ชื่อฟอนต์อ่านจากภาพไม่ได้ · เดาผิดคือหน้าตาทั้งระบบเพี้ยน |
| **หน้าไหนต้องตรงแบบ หน้าไหนใช้เป็นแนวทาง** | ตรงแบบ = ต้องเทียบและอธิบายทุกความต่าง · แนวทาง = ใช้บุคลิก ไม่บังคับโครง · ไม่ตอบ = ตรงแบบทุกหน้า |
| **มีภาพประกอบ export แยกไหม** | ภาพที่ตัดจากภาพแบบมักแตก และติดตัวหนังสือที่วางทับมาด้วย ([`design.md`](design.md) 7ก.5) |

บอกผู้ใช้ด้วยว่าเตรียมโฟลเดอร์ยังไงให้ได้ผลดีที่สุด

```
ชื่อโฟลเดอร์ของคุณ/
  login.png              ตั้งชื่อตามหน้า — AI จับคู่เองได้
  plans-edit.png
  plans-edit@375.png     แบบมือถือ (ถ้ามี)
  plans-edit-dark.png    แบบโหมดมืด (ถ้ามี) · หรือ -empty -error สำหรับสถานะอื่น
  assets/                ภาพประกอบที่ export แยกจากเครื่องมือออกแบบ ขนาด 2 เท่า
```

ชื่อที่ไม่เป็นแบบนี้ก็ใช้ได้ — AI จะถามรวมทีเดียวว่าภาพไหนคือหน้าไหน

> ‼️ **ต้องบอกให้ชัดว่าเส้นทาง ข ผู้ใช้ต้องทำงานเองหนึ่งรอบ** ไม่ใช่ AI ทำให้ทั้งหมด
> เขาต้องเปิด Claude Design แนบไฟล์เอง แล้วเอาผลกลับมาวางในโปรเจค — ไม่บอกไว้ก่อน แล้วไปเจอตอนกลางทางคือการหยุดงานที่ไม่ได้นัดไว้

> ‼️ **บอกด้วยว่าเส้นทาง ข และ ค ได้ดีไซน์ที่สวยกว่าเกือบแน่นอน** เพราะ AI ที่เขียนโค้ดทำ wireframe ได้แค่พอใช้ ไม่ได้สวย
> ส่วนเส้นทาง ก เร็วกว่าและไม่ต้องออกไปทำอะไรนอกที่นี่

**ยังไม่แน่ใจ = เส้นทาง ก** · เปลี่ยนใจตอนช่วง B ได้ ต้นทุนแค่ทำ `DESIGN.md` กับ wireframe ทิ้ง

> ‼️ **ผู้ใช้ส่งภาพแบบมาเมื่อไหร่ก็ได้ ไม่ว่าเลือกเส้นทางไหน** — ภาพของหน้าเดียวที่ส่งมากลางช่วง C ก็นับ
> คัดลอกเข้า `project/design/refs/` และลงตาราง "แบบของแต่ละหน้า" ในคำตอบเดียวกันเสมอ ([`flow.md`](flow.md) ข้อ 5 "ทุกเส้นทาง")
