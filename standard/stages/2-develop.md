# การเขียนโค้ดใน 1 phase

> **วนซ้ำต่อ phase** ในช่วง C · ภาพรวมอยู่ที่ [`../flow.md`](../flow.md)
> เป้าหมาย: ทำ **1 phase** ให้ครบทุกเส้นทางก่อนขึ้น phase ถัดไป

**ทำทีละ phase ตาม `project/PLAN.md` เท่านั้น ห้ามเปิดหลาย phase พร้อมกัน** — `PLAN.md` ห้ามมี 🔄 เกิน 1 รายการ

---

## ก่อนเริ่มเขียน

1. อ่าน `project/PLAN.md` ว่า phase นี้มีอะไรบ้าง และ `project/SCOPE.md` ว่าใครใช้ได้บ้าง
2. อ่าน [`../rule.md`](../rule.md) และ [`../security.md`](../security.md) ถ้า phase นี้แตะ auth/input/upload
3. เปิด **แบบที่อนุมัติแล้ว** ของ phase นี้จากช่วง B — เส้นทาง ก คือ wireframe · เส้นทาง ข คือไฟล์ดีไซน์ + `design-brief.md` · เส้นทาง ค คือภาพใน `project/design/refs/` ([`../flow.md`](../flow.md) ข้อ 5) · **หน้าที่มีแถวในตาราง `## แบบของแต่ละหน้า` ใช้ภาพนั้นเสมอ ไม่ว่าเส้นทางไหน**
4. **สำรวจของเดิมก่อนเสมอ** — มี Service, Model, partial หรือ helper ที่ใช้ซ้ำได้ไหม **reuse ก่อนสร้างใหม่**
5. เรียก skill `test-driven-development` ถ้า business logic ซับซ้อน (คำนวณหลายชั้น หรือแตะยอดเงิน/สต็อก/สิทธิ์)

## ลำดับการเขียน

### C1 — Frontend

> ‼️ **ขั้นนี้ต้องเรียก skill `frontend-design`** — คำถามแรกที่มันบังคับให้ตอบคือ
> *"ทิศทางคืออะไร และอะไรทำให้หน้านี้จำได้"* ซึ่งเป็นคำถามระดับ**หน้า** ไม่ใช่ระดับ token
> ไม่ถามคำถามนี้ตั้งแต่ C1 กฎการจัดหน้าจะไม่เกิดขึ้นเลย แล้วได้หน้าที่ผ่านทุกกฎแต่ไม่มีลำดับสายตา

**ประกอบหน้าจากแบบที่อนุมัติแล้ว** + token จาก `project/DESIGN.md` ใช้ข้อมูลปลอมไปก่อน

> ‼️ **เส้นทาง ก — หน้าสาธารณะที่ต้องมีภาพ ให้ตรวจเครื่องมือสร้างภาพก่อนเริ่มวาง layout**
> มีแล้วแต่ยังไม่เคยถามว่าใช้โมเดลไหน → **ถามก่อนสร้างใบแรก** ([`../design.md`](../design.md) 7ก.3ก)
> ไม่มี → **เตือนผู้ใช้ให้ต่อ Higgsfield MCP** แล้วรอคำตอบ · ไม่ต่อก็เดินทางสำรองตาม [`../design.md`](../design.md) 7ก.3ค
> **ห้ามวาง layout ที่เผื่อที่ให้ภาพไว้ก่อนแล้วค่อยไปหาว่าจะเอาภาพจากไหน** — ได้กรอบเปล่าที่ต้องรื้อทั้งหน้า
> (เส้นทาง ข ไม่ต้องทำข้อนี้ ภาพมาพร้อมดีไซน์ตั้งแต่ช่วง B แล้ว)

#### ‼️ ต้องเปิดแบบขึ้นมาเทียบจริง ไม่ใช่ทำตามที่จำได้

| เส้นทาง | เปิดอะไร | ไล่ทีละบล็อกว่ามีครบไหม |
|---|---|---|
| **ก** | `project/wireframes/<หน้านั้น>.html` | เทียบกับ wireframe ตรงๆ |
| **ข** | `php -S 127.0.0.1:8140 -t project/design` แล้วเปิด `<section id="...">` ของหน้านั้น **คู่กับ**หมวดของหน้านั้นใน `project/design-brief.md` | ‼️ **ต้องเทียบกับสเปคด้วย ไม่ใช่ดูแต่ไฟล์ดีไซน์** — สเปคคือของที่มาแทน wireframe และเป็นที่เดียวที่บอกว่าแต่ละบล็อกแบกข้อมูลอะไร |
| **ค** และหน้าที่มีภาพแบบ | **อ่านไฟล์ภาพ** ที่ตาราง `## แบบของแต่ละหน้า` ชี้ไป รวมภาพเสริม `@375` `-dark` `-empty` `-error` | ‼️ **ไล่ทีละบล็อก ของที่ partial ทำไม่ได้ให้ขยาย partial ห้ามตัดทิ้ง** · จุดที่ขัดกับกฎต้องรายงานก่อนลงมือ ([`../design.md`](../design.md) ข้อ 5.0) · ภาพประกอบตาม 7ก.5 |

> ‼️ **เส้นทาง ข อ่านไฟล์ดีไซน์ด้วย `grep` ไม่ได้** มันเป็น bundle ที่แตกตัวเองด้วย JavaScript
> `grep '<section id'` ได้ 0 บรรทัดทั้งที่มีจริงครบทุกหน้า — ต้องอ่าน DOM จากเบราว์เซอร์เท่านั้น ([`../flow.md`](../flow.md) ข้อ 5 B5)

> อาการจริงตอนไม่ทำข้อนี้: ทำ wireframe ครบ 41 หน้าในช่วง B แล้วตอน C1 เขียนหน้าใหม่จากศูนย์
> ไม่เปิด wireframe เทียบแม้แต่ครั้งเดียว
> ผลที่วัดได้: wireframe ทุกหน้ามี `<h1>` กับประโยคอธิบาย แต่หน้าจริง **ไม่มีทั้งสองอย่างครบ 10 หน้า**

คำว่า "ประกอบหน้าจากแบบ" กำกวมพอที่จะถูกตีความว่า "ทำหน้าตามที่เข้าใจ" — จึงต้องเป็นคำสั่งให้**เปิดไฟล์**

#### ‼️ C1 ต้องมี output ที่ตรวจได้ ก่อนเริ่ม C2

**"หน้าที่เปิดดูได้ในเบราว์เซอร์ด้วยข้อมูลปลอม"** ไม่ใช่แค่ไฟล์ view ที่ยังไม่มีใครเรียก

> อาการจริงตอนไม่มีเงื่อนไขนี้: ไล่ทำ migration → model → service → controller → route ให้จบก่อน
> แล้วค่อยเขียนหน้าตอนท้าย ผลคือหน้าถูกทำแบบเร่ง กลายเป็นการ**ห่อ component ให้พอมีที่ยัดข้อมูล** ไม่ใช่การออกแบบหน้า
> และไม่มีใครรู้ เพราะ `PLAN.md` มี checkbox 5 ช่องเรียงกันที่ติ๊กย้อนหลังพร้อมกันตอนจบก็ได้

| ทำอะไร | ตรวจอะไร |
|---|---|
| ประกอบหน้าจาก partial กลาง | **ห้าม copy markup จากหน้าอื่น** เห็นรูปแบบซ้ำต้องดึงเป็น partial |
| component ที่ยังไม่มี ให้สร้างเข้า `partials/` | ตามสเปกใน [`../components.md`](../components.md) |
| ทุกข้อความผ่าน `__()` ตั้งแต่ตอนเขียน | **ห้ามเขียนภาษาไทยตรงๆ ไว้ก่อนแล้วคิดว่าจะกลับมาแก้** |
| ทุกลิงก์และ asset ผ่าน `url()` | |
| ทำสถานะว่าง / กำลังโหลด / ผิดพลาด ไปพร้อมกัน | **ไม่ใช่ทำแต่กรณีข้อมูลครบแล้วค่อยกลับมาเติม** |

> **ข้อยกเว้น:** ถ้าโครงข้อมูลของ phase นี้ยังไม่ชัดจนออกแบบหน้าไม่ได้ ให้ร่าง migration ก่อนแล้วค่อยกลับมาทำ C1

### C2 — Backend

เขียนจากชั้นในออกนอก เพื่อให้ทดสอบได้ก่อนเชื่อมเข้าหน้า

| # | ทำอะไร | ตรวจอะไร |
|---|---|---|
| 1 | migration ของตารางที่ phase นี้ใช้ | เลขนำหน้าต่อจากไฟล์ล่าสุด · `SET NAMES utf8mb4` ต้นไฟล์ · มี `deleted_at` ถ้าลบได้ · index ครบ · **ห้ามแก้ไฟล์ที่ apply แล้ว** |
| 2 | Model | CRUD อย่างเดียว ไม่มี business logic ปน · prepared statement 100% |
| 3 | Service | business logic + validate input ทั้งหมดอยู่ที่นี่ · ออกแบบให้เรียกซ้ำจากหลาย Controller ได้ |
| 4 | Controller | เรียก Service แล้วส่งให้ View เท่านั้น · **ถ้าเริ่มมี `if` เงื่อนไขธุรกิจ แปลว่าวางผิดชั้น ให้ย้ายลง Service** |
| 5 | route + middleware | ผูก middleware ให้ครบทุกเส้นของ phase นี้ · ตั้งชื่อ URL ตาม [`../rule.md`](../rule.md) ข้อ 4 |
| 6 | เชื่อมหน้าเข้ากับข้อมูลจริง | ตัวกรอง/หน้า/การเรียง อ่านจาก query string · ปุ่ม submit กันกดซ้ำ · `old()` คืนค่าเมื่อ validate ไม่ผ่าน |
| 7 | ไฟล์ภาษา + บทความคู่มือ | key ครบทุกไฟล์ภาษา · ทุกหน้าของ phase นี้มีบทความคู่มือครบทุกภาษาและผูกทะเบียนแล้ว |

### C3 — Animation

ใส่ตาม [`../design.md`](../design.md) หมวด motion — **ถ้าเอาออกแล้วผู้ใช้ไม่เสียอะไร แปลว่าไม่ควรมี**

> ‼️ **ขั้นนี้ไม่ใช่ที่ตัดสินว่า motion ควรเป็นแบบไหน — ที่นั่นคือช่วง B**
> เปิด `project/DESIGN.md` หัวข้อ `## ลายเซ็นของระบบนี้` อ่านบุคลิกที่ตัดสินไว้แล้วทำตาม
> **ไม่มีเขียนไว้ = ช่วง B ทำไม่ครบ** ให้จดลง `QUESTIONS.md` แล้วเลือกทางที่เข้ากับ mood ในนั้น — ห้ามตัดสินบุคลิกใหม่เงียบๆ ตรงนี้
>
> เหตุผล: ระบบเดียวกันที่ของเลื่อนขึ้นช้าๆ กับที่ของเด้งเข้ามาเร็ว **ให้ความรู้สึกคนละแบรนด์** ทั้งที่สีและฟอนต์เหมือนกันทุกตัว
> เป็นการตัดสินใจระดับบุคลิก ไม่ใช่ระดับ implementation

#### รายการขั้นต่ำที่ทุกโปรเจคต้องมี

ปล่อยขั้นนี้ว่างเมื่อไหร่ มันจะถูกตัดสินว่า "ไม่ทำทั้งขั้น" แล้วติ๊กผ่านไป

- [ ] หน้าเข้า (เนื้อหาปรากฏตอนโหลดหน้า)
- [ ] feedback ตอนกดปุ่ม
- [ ] การเข้าและออกของ toast / modal / dropdown
- [ ] `prefers-reduced-motion` ครอบทุกตัวที่ใส่ไป

> ‼️ **ห้ามใช้ `animation-fill-mode: both` หรือ `forwards` กับ animation ที่แตะ `transform`** — ใช้ `backwards`
> `both` ทำให้ `transform` ค้างเป็น identity matrix ซึ่งยังสร้าง stacking context อยู่ แล้ว dropdown ทุกตัวในระบบถูกทับ
> มองไม่เห็นจนกว่าจะมี dropdown ตัวแรก ซึ่งอาจเป็นอีกหลาย phase ถัดไป

> ‼️ **การตัดสินว่า "ไม่ทำ" ไม่ใช่ "ทำแล้ว"** — ติ๊ก `[-]` พร้อมเหตุผล ห้ามติ๊ก `[x]`
> และ `DESIGN.md` ที่ห้าม animation กับปุ่มที่กดซ้ำทั้งวัน **ไม่ได้ห้าม animation ทั้งหมด**

## กฎระหว่างเขียน

- **audit log ต้องมาเองจาก base Model** — ถ้า phase นี้เขียนข้อมูลด้วยวิธีที่ไม่ผ่าน base Model (query ตรง หรือ bulk insert) **ต้องบันทึก audit log เองที่จุดนั้น ห้ามปล่อยผ่าน**
- **ทุก input จากผู้ใช้ validate ใน Service ก่อนใช้เสมอ** ห้ามเชื่อ `$_POST`/`$_GET`/`$_FILES` ตรงๆ
- ทุก error ที่จับได้ต้องมีรหัสอ้างอิงและลง log — **ห้ามโยน stack trace ให้ผู้ใช้เห็น**
- **ค่า `status` / `type` / `role` ที่เขียนลงฐานข้อมูลต้องเป็น key ภาษาอังกฤษ**
- ถ้ามี AJAX ต้องตอบ `{success, data, message}` ตามรูปแบบเดียวทั้งระบบ
- **ไฟล์เริ่มใหญ่เกินไป = ทำหลายหน้าที่เกินไป ให้แยกออกทันที อย่ารอ**
- เจอเรื่องกำกวม → `project/QUESTIONS.md` แล้วทำต่อ **ห้ามหยุดถาม**
- เจอสิ่งที่น่าจะดีกว่าแต่ไม่อยู่ใน `SCOPE.md` → `QUESTIONS.md` **ห้ามทำเพิ่มเอง**

## เกณฑ์ผ่านด่าน

- [ ] **ครบลูป ดู / เพิ่ม / แก้ไข / ลบ** ทุก resource ของ phase นี้ พร้อมสิทธิ์ของแต่ละอัน ← ขาดข้อใดข้อหนึ่งถือว่ายังไม่เสร็จ
- [ ] ไม่มี business logic หรือ query อยู่ใน Controller
- [ ] ทุก route ของ phase นี้ผูก middleware ถูกต้องแล้ว
- [ ] audit log บันทึกครบทุกจุดที่เขียน/แก้/ลบข้อมูล
- [ ] `storage/logs/app.log` และ console เบราว์เซอร์ไม่มี error หรือ warning
- [ ] ‼️ **ไม่มี PHP warning/notice ปรากฏในเนื้อหน้าเว็บ**

```bash
curl -s "http://localhost:8000/หน้าที่ทำ" | grep -nE "Warning|Notice|Deprecated|Fatal error"
```

> ตัวอย่างที่เคยหลุด: `in_array($x ?? 'ค่าเริ่มต้น', [...]) ? $x : 'ค่าเริ่มต้น'` — ถ้าไม่ส่ง `$x` มาและค่าเริ่มต้นอยู่ในรายการที่อนุญาต เงื่อนไขเป็นจริงแล้วไปอ่าน `$x` ที่ไม่มีอยู่ · **ให้กำหนดค่าก่อนแล้วค่อยตรวจเสมอ**
