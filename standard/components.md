# สเปค component กลาง

> อ่านก่อนสร้างหรือแก้ component ใดๆ
> หลักคุณภาพและ token อยู่ที่ [`design.md`](design.md)

---

## 1. กฎที่ใช้กับทุก component

1. **อยู่ใน `app/Views/partials/` เท่านั้น** ห้ามสร้าง component ที่ใช้แค่หน้าเดียว
2. **เห็นรูปแบบเดิมโผล่ครั้งที่สอง ต้องดึงเป็น partial กลางทันที** ห้าม copy markup ไปวาง
3. รับค่าผ่านตัวแปรที่ตั้งชื่อชัดเจน มีค่าเริ่มต้นให้ทุกตัวที่ไม่บังคับ
4. **ทุกข้อความผ่าน `__()`** ห้าม hardcode แม้แต่คำว่า "บันทึก"
5. **ทุกลิงก์ผ่าน `url()`** · **ทุก output ของผู้ใช้ผ่าน `e()`**
6. ทุกค่าสี/ระยะ/ขนาด มาจาก token — ไม่มีค่าดิบ
7. ต้องมีครบทั้ง 5 สถานะการโต้ตอบ (ปกติ · hover · focus · active · disabled) และทำงานได้ทั้งโหมดสว่างและมืด
8. **แก้ component กลาง 1 จุด ต้องเปลี่ยนทั้งระบบ** — ถ้าแก้แล้วมีหน้าไหนไม่เปลี่ยนตาม แปลว่ามีสำเนาซ่อนอยู่ ต้องตามไปลบ
9. **component ที่มีหลายสถานะ ต้องออกแบบทุกสถานะ** ไม่ใช่ออกแบบสถานะหลักแล้วให้สถานะอื่นเป็นผลพลอยได้
   > อาการจริง: เมนูพับแล้วไอคอนดูเล็กจนเล็งกดยาก — ขนาดไม่ได้เล็กลงจริง แต่ **หน้าที่ของมันใหญ่ขึ้น**
   > ตอนมีข้อความ ไอคอนเป็นตัวช่วย พอตัดข้อความออก ไอคอนกลายเป็นตัวบอกความหมายตัวเดียว
   > เฉพาะเมนูพับได้: **สถานะพับต้องเพิ่มขนาดไอคอน** และจัดกลางแนวราง · พื้นที่กดยังต้อง 44px

## 1ก. ‼️ สัญญาของตัวแปรใน partial — ข้อที่พังแล้วหายากที่สุด

**PHP `include` ใช้ขอบเขตตัวแปรร่วมกับหน้าที่เรียก** ซึ่งเป็นจุดอ่อนที่ใหญ่ที่สุดของ pattern นี้ และเป็นต้นเหตุของบั๊กสองตัวที่หายากที่สุดเท่าที่เจอมา

### กฎ 1 — ตัวแปรของ partial ต้องขึ้นต้นด้วยชื่อ partial

`$fieldRows` ไม่ใช่ `$rows` · `$thSortLabel` ไม่ใช่ `$label` · `$pageActions` ไม่ใช่ `$actions`

> อาการจริง: `partials/field.php` ตั้ง `$rows = 4` (จำนวนบรรทัดของ textarea)
> หน้ารายการใช้ `$rows` เป็นข้อมูลของตาราง
> ฟอร์มแจ้งปัญหาใน layout กลางมี textarea อยู่**ทุกหน้า** → **ตารางหายทั้งระบบ**
> พร้อม error `foreach() argument must be of type array, int given`
>
> หายากมาก เพราะจุดที่พังกับจุดที่ตั้งค่าอยู่คนละไฟล์ และไม่มีอะไรเชื่อมให้เห็น

`check.php` จับข้อนี้ (`structure/partial-generic-var`)

### กฎ 2 — ต้องประกาศในหัวไฟล์ว่าค่าไหน "ค้างข้ามการ include"

ค่าที่ตั้งไว้จะค้างถึงการ include ครั้งถัดไปในหน้าเดียวกัน ซึ่ง**จำเป็น** เพราะหลายหน้าตั้ง `$fieldType` ครั้งเดียวแล้วอาศัยให้ค้างถึงช่องถัดไปโดยเจตนา

แต่ค่าที่ไม่ควรค้าง (ความกว้าง ตัวเลือก คำอธิบาย) **partial ต้องล้างเองตอนจบ**

> อาการจริง: `select` แคบตามช่องข้อความที่อยู่ก่อนหน้ามัน โดยไม่มีใครสั่ง

### กฎ 3 — partial รับ "ข้อมูล" ไม่ใช่ HTML

รับ HTML แปลว่ามีจุดที่ output ไม่ผ่าน `e()` ซึ่งขัดกฎเหล็กข้อ 6 ตรงๆ และเปิดช่องให้หน้าฉีด markup เองซึ่งขัดกฎ "component ต้องเป็นของกลาง"

```php
// ผิด
$pageActions = '<a class="btn" href="...">เพิ่ม</a>';

// ถูก
$pageActions = [['label' => __('user.add'), 'url' => '/users/create', 'icon' => 'plus']];
```

## 2. ปุ่ม

| ชนิด | ใช้เมื่อไหร่ | หน้าตา |
|---|---|---|
| `primary` | การกระทำหลักของหน้า — **มีได้อันเดียวต่อหน้า** | พื้นสีเน้น |
| `secondary` | การกระทำรอง | มีเส้นขอบ พื้นโปร่ง |
| `ghost` | การกระทำที่ไม่อยากดึงสายตา | ไม่มีขอบ ไม่มีพื้น |
| `danger` | ลบหรือสิ่งที่ย้อนกลับไม่ได้ | ใช้ `state.danger` |

**กฎ**

- **ข้อความบนปุ่มต้องเป็นคำกริยาที่บอกว่าจะเกิดอะไร** — `บันทึก` `ลบรายการ` ไม่ใช่ `ตกลง` `OK`
- **ต้องกันกดซ้ำ** — กดแล้ว disable ทันทีพร้อมแสดง spinner ในปุ่ม จนกว่าจะได้ผลลัพธ์ · **ไม่มีข้อยกเว้น** เพราะกดรัวแล้วได้ข้อมูลซ้ำในฐานข้อมูล และแก้ทีหลังต้องไล่ทุกฟอร์ม
- ปุ่มที่มีแต่ไอคอนต้องมี `aria-label` และ tooltip เสมอ
- ความสูงขั้นต่ำบนมือถือ 44px
- ห้ามใช้ `<div>` หรือ `<a>` ทำปุ่มที่ส่งฟอร์ม — ใช้ `<button>` เพื่อให้คีย์บอร์ดใช้ได้

## 3. ฟอร์ม

- ทุกช่องมี `<label>` ผูกกับ `id` จริง — **placeholder ไม่ใช่ label** เพราะหายไปตอนพิมพ์
- ช่องบังคับทำเครื่องหมายชัดเจน และบอกครั้งเดียวบนสุดว่าเครื่องหมายนั้นแปลว่าอะไร
- คำอธิบายเพิ่มเติมอยู่ **ใต้ label ก่อนช่องกรอก** ไม่ใช่ใน placeholder
- **error แสดงใต้ช่องที่ผิด** ไม่กองรวมบนสุด · ถ้ามีหลายช่องผิด ให้เลื่อนหน้าไปที่ช่องแรกที่ผิด
- **validate ไม่ผ่านต้องคืนค่าที่ผู้ใช้กรอกไว้ทุกช่องด้วย `old()`** — ฟอร์ม 15 ช่องแล้วต้องกรอกใหม่หมดเพราะผิดช่องเดียว คือเหตุผลที่คนเลิกใช้ระบบ
- ทุกฟอร์มที่เปลี่ยนข้อมูลต้องมี `csrf_field()`
- ปุ่มหลักอยู่ขวาล่างของฟอร์ม ปุ่มยกเลิกอยู่ซ้ายของมันเสมอ (ยึดตำแหน่งเดียวทั้งระบบ)
- ฟอร์มยาวต้องแบ่งเป็นกลุ่มที่มีหัวข้อ ไม่ใช่ไล่ช่องยาวเป็นพืด
  **เกิน 4 ช่องต้องใช้ `fieldset` + `legend`** และช่องสั้นเรียงกันเป็น grid (`.field-grid`)
- **ความกว้างของช่องต้องบอกความยาวที่คาดหวัง** — ส่ง `$fieldWidth` = `short` / `medium` / `full`
  ช่องกว้างเต็มฟอร์มที่รับได้ 3 ตัวอักษร คือการบอกผู้ใช้ผิด

### ‼️ control ที่กางอะไรออกมาเมื่อกด ต้องปั้นใหม่ ห้ามใช้ของ OS

`select` · ปฏิทิน (`input[type="date"]`) · แถบเลื่อน — **จัดสไตล์กล่องอย่างเดียวไม่พอ**

> อาการจริง: ตั้งสี `option` เรียบร้อยแล้ว แต่รายการที่กางออกมายังเป็นกล่องของ Windows โผล่บนพื้นครีม
> **การตั้งสี `option` เปลี่ยนได้แค่ 2 ค่าจากสิบกว่าค่าที่ตาเห็น** — ขอบ เงา ระยะห่าง ไฮไลต์ตอนชี้ ฟอนต์ ล้วนเป็นของ OS
>
> **control ของ OS คือจุดที่ระบบหลุดคาแรกเตอร์ชัดที่สุด** เพราะมันโผล่มาทับหน้าที่ออกแบบมาอย่างดี

**สิ่งที่ต้องทำ**

| | |
|---|---|
> ‼️ **ทำแล้วในโครงตั้งแต่ 3.20.0 สำหรับ `select` · checkbox · radio** — ไม่ต้องทำเอง และ**ห้ามเขียน control ของตัวเองซ้ำ**
> `app.js` ครอบ `<select>` ทุกตัวเป็น listbox ของระบบเอง · `app.css` วาด checkbox/radio เอง · ที่เหลือที่ยังเป็นของ OS คือ **ปฏิทินกับแถบเลื่อน**
> ก่อนหน้านี้กฎข้อนี้มีมาตั้งแต่ 3.2.0 แต่ไม่มีใครทำจริง ทุกโปรเจคจึงได้กล่องสีฟ้าของ Windows — กฎที่ไม่มีของจริงในโครงรองรับ จะไม่ถูกทำ

| ปิด `appearance` ของ control เดิม | แล้วปั้น listbox / ปฏิทินขึ้นมาเอง |
| **JS ต้องเป็นคนสร้าง** | ไม่ใช่เขียน markup ไว้ในหน้า — JS พังแล้วต้องเหลือ `<select>` ปกติที่ใช้งานได้ ไม่ใช่ control ที่กดแล้วไม่เกิดอะไร |
| คีย์บอร์ดต้องครบ | `↑` `↓` เลื่อน · `Enter` เลือก · `Esc` ปิด · `Tab` ออก · พิมพ์เพื่อกระโดด |
| ARIA ต้องครบ | `role="listbox"` / `role="option"` / `aria-expanded` / `aria-activedescendant` |
| **ต้องมีภาพตอนกางออก** | ถ่ายภาพตอนปิดอย่างเดียวไม่พิสูจน์อะไรเลย ([`testing.md`](testing.md) ข้อ 4ก.4) |
| ผูก `color-scheme` กับ `data-theme` | ไม่งั้น control ที่เหลือจะตามธีมของเครื่อง ไม่ใช่ธีมที่ระบบเลือก |

> ‼️ ข้อนี้มีต้นทุนสูงและ **ต้องขออนุญาตผู้ใช้ก่อนถ้าจะใช้ library** ตามกฎเหล็กข้อ 2
> แต่การทำเองมีต้นทุนความถูกต้องสูงเช่นกัน (คีย์บอร์ด + ARIA) — เสนอทั้งสองทางให้ผู้ใช้เลือกที่ประตู B

### 3ข. ติ๊กถูก · ตัวเลือกเดียว · กลุ่มตัวเลือก

> **ที่มา (3.20.0):** ทุกโปรเจคที่ใช้มาตรฐานได้ checkbox กับ radio สีฟ้าของ Windows เพราะ `app.css` ไม่เคยมีสไตล์ของสองอย่างนี้เลย
> และ `field.php` ไม่รองรับชนิดเหล่านี้ คนเขียนจึงต้องเขียน markup เองทุกหน้า ซึ่งขัดกับกฎเหล็กข้อ 18

```php
$fieldType = 'checkbox';                               // ติ๊กเดียว ป้ายอยู่ข้างกล่อง
$fieldType = 'radio';     $fieldOptions = [...];       // เลือกได้อย่างเดียวจากกลุ่ม
$fieldType = 'checkboxes'; $fieldOptions = [...];      // เลือกได้หลายอย่าง ส่งเป็น name[]
```

| กฎ | เพราะ |
|---|---|
| **กลุ่มตัวเลือกใช้ `fieldset` + `legend`** ไม่ใช่ label ลอยๆ | screen reader ต้องอ่านหัวข้อของกลุ่มก่อนอ่านตัวเลือก ไม่งั้นผู้ใช้ได้ยินแค่ "ต่ำ ปกติ สูง" โดยไม่รู้ว่าถามอะไร |
| **ทั้งแถวกดได้ และสูงอย่างน้อย 44px** | กล่อง 20px เล็กเกินไปสำหรับนิ้ว — ป้ายต้องอยู่ใน `<label>` เดียวกับกล่อง |
| **เครื่องหมายวาดด้วย `clip-path` ไม่ใช่ไฟล์ภาพหรือฟอนต์ไอคอน** | เปลี่ยนสีตามโหมดได้ ไม่ต้องโหลดอะไรเพิ่ม และไม่พังตอนออฟไลน์ |
| **มีสถานะครึ่งๆ กลางๆ (`indeterminate`)** | หัวตารางที่เลือกบางแถวต้องบอกได้ว่า "บางอัน" ไม่ใช่ "ทั้งหมด" |
| สีมาจาก token ของธีม | `accent-color` ของเบราว์เซอร์ให้คุมได้แค่สีเดียว ขอบ มุม และขนาดยังเป็นของ OS |

### 3ก. ‼️ dropdown ที่ค้นได้ — ตัดสินจากจำนวนรายการ ไม่ใช่ตัดสินทีละหน้า

> **ที่มา (3.19.0):** ทีมที่ใช้จริงเจอหน้าที่มี dropdown ยาวจนหาเองไม่ไหว และบางหน้าโหลด master data ทั้งตารางลงหน้าเว็บ
> เกณฑ์อยู่ที่นี่เพื่อให้ทุกหน้าได้พฤติกรรมเดียวกัน **ห้ามตัดสินใจใหม่ทีละหน้า และห้ามแก้ทีละหน้า**

| จำนวนรายการ | ต้องทำ |
|---|---|
| **1–8** | ไม่ต้องมีช่องค้น — **แต่รายการที่กางออกมายังเป็นของระบบ ไม่ใช่ของ OS** (ข้อ 5.12) |
| **9–50** | **ค้นได้** โหลดรายการมาครั้งเดียวแล้วกรองฝั่งหน้าเว็บ |
| **เกิน 50** | **ค้นจากฝั่ง server** ห้ามโหลดทั้งหมดลงหน้า |

**master data ที่โตขึ้นเรื่อยๆ ให้ถือว่าเกิน 50 ตั้งแต่วันแรก** — ผู้ใช้ ลูกค้า บริษัท สินค้า สาขา สนาม
วันที่ข้อมูลโต ไม่มีใครกลับมาแก้หน้าที่เคยเขียนไว้ตอนมี 20 แถว

**วิธีใช้ — ไม่ต้องเขียน component เอง** ([`field.php`](../app/Views/partials/field.php))

```php
$fieldType    = 'select';
$fieldOptions = $branches;   // 9–50 รายการ → เปิดช่องค้นให้เองเมื่อเกิน 8
$fieldSource  = 'users';     // เกิน 50 → คีย์ใน config/options.php ค้นจากฝั่ง server
```

| กติกาของฝั่ง server | ค่า | เพราะ |
|---|---|---|
| เริ่มค้นเมื่อพิมพ์ | **2 ตัวอักษร** | 1 ตัวได้เกือบทั้งตาราง และยิง query ทุกครั้งที่กดคีย์ |
| ผลต่อครั้ง | **25 รายการ** (เพดาน 50) | มากกว่านี้ผู้ใช้ไม่ไล่อ่านอยู่ดี พิมพ์ต่อเร็วกว่า |
| หน่วงก่อนยิง | **250ms** | พิมพ์ติดกันเร็วๆ ต้องได้ query เดียว ไม่ใช่ทุกตัวอักษร |
| ยังมีต่อ | ปุ่ม **ดูเพิ่ม** ท้ายรายการ | ไม่ใช่โหลดทั้งหมดเมื่อผู้ใช้เลื่อนถึงท้าย |

**แหล่งข้อมูลประกาศที่ [`config/options.php`](../config/options.php) ที่เดียว** — ตาราง คอลัมน์ที่ค้นได้ เงื่อนไขตายตัว และ**สิทธิ์ของแหล่งนั้น**
หน้าเว็บส่งแค่คีย์ ไม่เคยส่งชื่อตาราง · เพิ่มแหล่งใหม่คือเพิ่มรายการในไฟล์นี้ ไม่ใช่เขียน endpoint ใหม่

> ‼️ **การค้นคือการอ่านข้อมูล ไม่ใช่แค่ช่วยกรอกฟอร์ม** — สิทธิ์ของแต่ละแหล่งบังคับที่ `OptionAccessMiddleware` ที่เดียว (กฎเหล็กข้อ 4)
> แหล่งที่ปล่อยให้ทุกคนค้นได้ = ให้ใครก็ได้ไล่อ่านรายชื่อทั้งตารางทีละตัวอักษร
>
> ‼️ **ค่าที่ฟอร์มส่งกลับมาต้อง validate ซ้ำเสมอด้วย `OptionService::allows()`** ([`security.md`](security.md) ข้อ 4ก)
> รายการที่หน้าเว็บเคยเห็น ไม่ใช่ขอบเขตของค่าที่ส่งกลับมาได้

**`<select>` ทุกตัวถูกครอบเป็น listbox ของระบบเสมอ** (3.20.0) ช่องค้นต่างหากที่โผล่เฉพาะเมื่อเกิน 8 ตัวเลือกหรือมี `$fieldSource`
หน้าที่อยากได้ control ของ OS จริงๆ ต้องใส่ `data-native` เอง — เป็นข้อยกเว้นที่ต้องตั้งใจเลือก

**ของที่ต้องคงไว้เสมอ** — `<select>` ตัวจริงยังอยู่ในหน้า เป็นตัวถือค่าและตัวที่ฟอร์มส่ง JS พังก็ยังใช้งานได้
**ห้ามซ่อน `<select>` ด้วย `display:none`** เพราะ `required` ที่ซ่อนแบบนั้นทำให้ฟอร์มส่งไม่ได้โดยไม่มีข้อความให้ผู้ใช้เห็น

## 4. หน้ารายงาน — ตารางข้อมูล

component ที่ซับซ้อนที่สุดและใช้บ่อยที่สุด ต้องทำครั้งเดียวให้ครบ

### ส่วนประกอบบังคับ

| ส่วน | รายละเอียด |
|---|---|
| **ตัวกรอง** | อยู่เหนือตาราง · ค้นหาข้อความ + กรองตามฟิลด์ที่เกี่ยวข้อง |
| **กรองช่วงวัน** | ตารางที่มีข้อมูลผูกกับเวลาต้องมี |
| **ปุ่มลัดช่วงวัน** | วันนี้ · สัปดาห์นี้ · เดือนนี้ · 6 เดือน · 1 ปี ← บังคับเมื่อมีการกรองช่วงวัน |
| **เลือกจำนวนแถว** | เช่น 10 / 25 / 50 / 100 |
| **หัวตารางกดเรียงได้** | คลิกสลับ น้อย→มาก / มาก→น้อย · แสดงลูกศรบอกทิศทางที่กำลังเรียง |
| **แบ่งหน้า** | พร้อมบอกว่ากำลังดูรายการที่เท่าไหร่จากทั้งหมดกี่รายการ |
| **ปุ่มส่งออก CSV** | ส่งออกตาม**ตัวกรองที่ใช้อยู่** ไม่ใช่ส่งออกทั้งตาราง |

### ‼️ ตัวตารางมีในโครงแล้ว — ห้ามเขียน `<table>` เองในหน้า

```php
$tableColumns = [
    ['key' => 'created_at', 'label' => __('common.created_at'), 'sort' => 'created_at',
     'primary' => true, 'format' => 'datetime'],
    ['key' => 'status',  'label' => __('order.status'), 'sort' => 'status',
     'format' => 'badge', 'lang' => 'order.status_'],
    ['key' => 'note',    'label' => __('common.note'), 'limit' => 80],
    ['key' => 'amount',  'label' => __('order.amount'), 'format' => 'number'],
];
$tableRows     = $rows;
$tableSort     = $sort;
$tableDir      = $dir;
$tableFiltered = $hasFilter;
$tableActions  = [
    ['icon' => 'view',  'label' => __('common.view'),   'url' => '/orders/{id}'],
    ['icon' => 'trash', 'label' => __('common.delete'), 'url' => '/orders/{id}', 'confirm' => 'code'],
];
include __DIR__ . '/../../partials/table.php';
```

**นิยาม 1 คอลัมน์**

| คีย์ | ทำอะไร |
|---|---|
| `key` | คีย์ในแถว (บังคับ) |
| `label` | หัวคอลัมน์ (บังคับ) ผ่าน `__()` มาแล้ว |
| `sort` | ใส่แล้วหัวตารางกดเรียงได้ · **ต้องอยู่ในรายการ `SORTABLE` ของ Model** |
| `primary` | `true` = เป็นหัวการ์ดบนมือถือ · ควรมีคอลัมน์เดียว |
| `format` | `text` · `date` · `datetime` · `number` (ชิดขวา + `tabular-nums`) · `badge` |
| `lang` | prefix สำหรับแปลค่าที่เก็บเป็น key อังกฤษในฐานข้อมูล เช่น `'order.status_'` |
| `limit` | ตัดข้อความยาวที่กี่ตัวอักษร — คอลัมน์ข้อความยาวที่ไม่ตัดจะกินความกว้างทั้งตาราง |

**นิยาม 1 ปุ่มท้ายแถว** — `icon` · `label` · `url` (ใช้ `{key}` แทนค่าจากแถวได้) · `confirm` (ใส่ชื่อคีย์ = ต้องยืนยันก่อน โดยใช้ค่าจากคีย์นั้นเป็นชื่อรายการ)

ตัวตารางจัดการให้ครบ: หัวตารางกดเรียงได้ · โหมดการ์ดบนมือถือ · ปุ่มไอคอนพร้อม `aria-label` · confirm ก่อนลบ · **สถานะว่างที่แยกระหว่าง "ไม่มีข้อมูลเลย" กับ "ตัวกรองไม่เจอ"**

การแบ่งหน้ายังเรียก `pagination.php` แยก เพราะมันต้องรู้ `total` ซึ่งมาจาก Controller ไม่ใช่จากตัวตาราง

### กฎสำคัญ

> ‼️ **ตัวกรอง หน้า และการเรียง ต้องเก็บใน URL query string ไม่ใช่ session**
>
> เก็บใน session แล้วจะ: แชร์ลิงก์รายงานให้คนอื่นดูไม่ได้ · กด back แล้วค่าหาย · เปิดสองแท็บแล้วค่าตีกัน

- **ปุ่มในแถวต้องเป็นไอคอนเท่านั้น** ห้ามใช้คำ เพราะทำให้คอลัมน์กว้างเกินจนตารางอ่านยาก · ทุกปุ่มต้องมี `aria-label` และ tooltip
- คอลัมน์ตัวเลขชิดขวาและใช้ `tabular-nums` · คอลัมน์วันที่รูปแบบเดียวกันทั้งระบบ
- ปุ่มลบในแถวต้องผ่าน confirm dialog เสมอ
- ต้องมีสถานะ **ว่าง / กำลังโหลด / ผิดพลาด** ครบ

### บนมือถือ — ยุบเป็นการ์ด

**ห้าม scroll แนวนอน** ตารางกว้างบนจอเล็กใช้งานไม่ได้จริง

แต่ละแถวกลายเป็นการ์ด 1 ใบ:

```
┌─────────────────────────────┐
│ [ค่าคอลัมน์หลัก]      [สถานะ] │  ← หัวการ์ด = คอลัมน์ที่สำคัญที่สุด
│ ─────────────────────────── │
│ ชื่อคอลัมน์      ค่า          │
│ ชื่อคอลัมน์      ค่า          │
│ ─────────────────────────── │
│              [ไอคอน] [ไอคอน] │  ← ปุ่มในแถว
└─────────────────────────────┘
```

- ต้องกำหนดว่าคอลัมน์ไหนเป็น "คอลัมน์หลัก" ที่ขึ้นหัวการ์ด
- คอลัมน์ที่ไม่สำคัญซ่อนได้บนมือถือ แต่ต้องเข้าถึงได้จากหน้ารายละเอียด

## 5. Alert และ Toast

> ‼️ **ต้องเป็นแบบลอย ห้ามเป็นแบบแทรกในหน้า** เพราะแบบแทรกจะดัน component อื่นเลื่อนตำแหน่ง ทำให้ผู้ใช้กดผิดที่

| ชนิด | ใช้เมื่อไหร่ | พฤติกรรม |
|---|---|---|
| **Toast** | ผลของการกระทำ (บันทึกสำเร็จ ลบแล้ว) | ลอยมุมจอ หายเองใน 4-6 วินาที มีปุ่มปิด |
| **Alert กลางจอ** | สิ่งที่ผู้ใช้ต้องรับรู้จริงๆ ก่อนทำอะไรต่อ | ต้องกดปิดเอง |

**กฎ**

- **ต้องมีไอคอนหรือ SVG ที่สื่อความหมาย** ไม่ใช่มีแต่ข้อความสี — เขียนเอง ไม่ใช้ไลบรารีภายนอก (คุมได้มากกว่าและไม่ผิดกฎเรื่อง dependency)
- 4 แบบ: สำเร็จ · เตือน · ผิดพลาด · ข้อมูล — **แต่ละแบบต่างกันทั้งสีและไอคอน** ห้ามต่างกันแค่สี
- **ต้องมี `aria-live`** ไม่งั้น screen reader ไม่รู้ว่ามีอะไรเกิดขึ้น เพราะ toast ลอยอยู่นอกลำดับการอ่าน
- toast หลายอันซ้อนกันเป็นคิว ไม่ทับกัน
- **error ต้องแสดงรหัสอ้างอิง** (`ERR-7X4K2`) เพื่อให้ผู้ใช้แจ้งปัญหาแล้วสืบต่อได้

## 6. Confirm dialog

ใช้ก่อนทุกการกระทำที่ย้อนกลับยาก

**กฎที่สำคัญที่สุด: ต้องบอกว่ากำลังทำอะไรกับอะไร**

```
❌  ยืนยันการลบ?                    [ยกเลิก] [ตกลง]
✅  ลบ "ใบสั่งซื้อ #1042" ?          [ยกเลิก] [ลบ]
    รายการนี้จะถูกซ่อนจากระบบ แต่ยังกู้คืนได้ภายหลัง
```

- **ปุ่มยืนยันเขียนคำกริยาที่จะเกิดขึ้น** (`ลบ`) ไม่ใช่ `ตกลง` — คนอ่านปุ่ม ไม่อ่านข้อความ
- ปุ่มยืนยันการลบใช้ชนิด `danger` · ปุ่มยกเลิกเป็น default ที่ focus อยู่แต่แรก
- `Esc` = ยกเลิก
- บอกด้วยว่า**ผลลัพธ์ย้อนกลับได้หรือไม่**

### ‼️ มีในโครงแล้ว — ห้ามปั้นเอง

```php
$confirmUrl     = '/products/' . $product['id'];
$confirmTitle   = __('confirm.delete_title', ['name' => $product['name']]);
$confirmBody    = __('confirm.delete_body');
$confirmTrigger = __('common.delete');
include __DIR__ . '/../../partials/confirm.php';
```

ได้ฟอร์ม `DELETE` พร้อม CSRF และปุ่มไอคอนที่กดแล้วเปิดกล่องยืนยัน

| ตัวแปร | ค่าเริ่มต้น |
|---|---|
| `$confirmUrl` | — (บังคับ) |
| `$confirmTitle` | — (บังคับ) **ต้องมีชื่อของสิ่งที่จะถูกกระทำอยู่ในนั้น** |
| `$confirmBody` | ว่าง — ใช้บอกว่าย้อนกลับได้หรือไม่ |
| `$confirmLabel` | `__('common.delete')` |
| `$confirmTrigger` | ค่าเดียวกับ `$confirmTitle` |
| `$confirmIcon` | `trash` |
| `$confirmMethod` | `DELETE` |

**กล่องถูกสร้างโดย `app.js` ไม่ได้เขียนไว้ในหน้า** ตามข้อ 5.11 ของ [`design.md`](design.md) — JS พังเมื่อไหร่ ฟอร์มยัง submit ได้ตามปกติ ซึ่งดีกว่าปุ่มที่กดแล้วเงียบ

กล่องเดียวถูกใช้ซ้ำทุกปุ่มในหน้า และข้อความถูกใส่ด้วย `textContent` เสมอ **ห้ามเปลี่ยนเป็น `innerHTML`** เพราะค่าที่ใส่มีชื่อรายการจากฐานข้อมูลอยู่ข้างใน

## 7. Modal

### ‼️ เปลือกมีในโครงแล้ว — ห้ามเขียน `<dialog>` เองในหน้า

```php
$dialogId    = 'export-dialog';
$dialogTitle = __('report.export');
$dialogBody  = __DIR__ . '/../../partials/export-body.php';
include __DIR__ . '/../../partials/dialog.php';
```

| ตัวแปร | ค่าเริ่มต้น |
|---|---|
| `$dialogId` | — (บังคับ) · ใช้ประกอบ `id` ของหัวข้อให้เอง จึงไม่ชนกันข้ามกล่อง |
| `$dialogTitle` | — (บังคับ) |
| `$dialogBody` | — (บังคับ) **path ของไฟล์ ไม่ใช่ HTML** |
| `$dialogSmall` | `false` · `true` = กล่องเล็กที่ไม่เต็มจอบนมือถือ |

**รับ path ของไฟล์ ไม่ใช่ HTML** ตามข้อ 1ก กฎ 3 — รับ HTML แปลว่ามีจุดที่ output ไม่ผ่าน `e()`
ส่วนการส่งชื่อไฟล์ทำให้เนื้อหายังเป็นเทมเพลตปกติที่ทุกค่าผ่าน `e()` ตามเดิม

ปุ่มปิดมาพร้อมเปลือกและใช้ `data-dialog-close` ซึ่ง `app.js` ผูกให้ทุกกล่องในระบบพร้อมกัน — **กล่องใหม่ไม่ต้องเขียน JS เพิ่มเลย**

- `Esc` ปิดได้ · คลิกพื้นหลังปิดได้ (ยกเว้นฟอร์มที่กรอกไปแล้ว — ต้องถามก่อน)
- **focus ต้องถูกขังไว้ใน modal** และกลับไปที่ปุ่มที่เปิดมันเมื่อปิด
- ล็อกการ scroll ของหน้าหลังขณะเปิด
- ห้ามซ้อน modal ในmodal — ถ้าต้องซ้อนแปลว่า flow ออกแบบผิด
- เนื้อหายาวให้ scroll ในตัว modal โดยหัวและปุ่มล่างอยู่กับที่
- บนมือถือให้เต็มจอ ไม่ใช่กล่องเล็กลอยกลาง

## 8. ตัวอัปโหลดไฟล์ — 2 แบบ

| แบบ | ใช้เมื่อไหร่ |
|---|---|
| **ปกติ** | แนบไฟล์ทั่วไป แสดงเป็นรายการชื่อไฟล์ |
| **ใหญ่ + preview** | ต้องเห็นภาพก่อนอัป แสดงเป็นตารางรูปย่อ |

**ทั้งสองแบบต้องมี**

- **ลากวางได้** พร้อมสถานะตอนลากผ่าน
- **เลือกหลายไฟล์พร้อมกันได้**
- แสดงชื่อไฟล์ ขนาด และปุ่มลบทีละไฟล์ก่อนส่ง
- แถบความคืบหน้าตอนอัป
- บอกล่วงหน้าว่า**รับไฟล์ชนิดไหน ขนาดไม่เกินเท่าไหร่ กี่ไฟล์**
- ไฟล์ที่ไม่ผ่านเงื่อนไขต้องบอกเหตุผลรายไฟล์ ไม่ใช่ปฏิเสธทั้งชุด
- **ชื่อไฟล์ภาษาไทยต้อง sanitize ตอนเก็บ แต่เก็บชื่อเดิมไว้แสดงผล**

ฝั่งเซิร์ฟเวอร์ต้องทำตาม [`security.md`](security.md) — ตรวจชนิดไฟล์จริงไม่ใช่ดูนามสกุล และเก็บนอก `public/`

### ‼️ มีในโครงแล้ว — ห้ามเขียน `<input type="file">` เองในหน้า

```php
$uploadName     = 'attachment';
$uploadLabel    = __('support.attachment');
$uploadAccept   = ['jpg', 'jpeg', 'png', 'webp', 'pdf'];
$uploadMaxBytes = (int) config('upload.max_bytes');
$uploadMultiple = true;
$uploadPreview  = true;
include __DIR__ . '/../../partials/upload.php';
```

| ตัวแปร | ค่าเริ่มต้น |
|---|---|
| `$uploadName` | `attachment` · หลายไฟล์ให้ลงท้ายด้วย `[]` เอง |
| `$uploadLabel` | — (บังคับ) |
| `$uploadAccept` | `['jpg','jpeg','png','webp','pdf']` |
| `$uploadMaxBytes` | `5242880` |
| `$uploadMultiple` · `$uploadPreview` | `false` |

**เงื่อนไขที่บอกผู้ใช้ต้องตรงกับที่ `Uploader` ยอมรับจริง** — บอกว่ารับ 10MB แล้วเซิร์ฟเวอร์ตัดที่ 5MB คือการโกหกผู้ใช้

กรอบลากวางถูกสร้างโดย `app.js` ตามข้อ 5.11 ของ [`design.md`](design.md) — JS พังแล้วเหลือ `<input type="file">` ที่ใช้งานได้จริง
ไฟล์ที่ไม่ผ่านเงื่อนไข **แสดงพร้อมเหตุผลรายไฟล์และไม่ถูกส่ง** ส่วนไฟล์ที่ผ่านยังส่งได้ตามปกติ — ไม่ปฏิเสธทั้งชุด

> ‼️ **การตรวจฝั่งหน้าเป็นความสะดวก ไม่ใช่ความปลอดภัย** เซิร์ฟเวอร์ต้องตรวจ mime จริงด้วย `finfo` ซ้ำเสมอ
>
> ‼️ รูปย่อใช้ `URL.createObjectURL()` ซึ่งได้ `blob:` URL — CSP จึงต้องมี `blob:` ใน **`img-src` เท่านั้น**
> ห้ามเติมลง `script-src` เด็ดขาด · ถ้าลืม รูปย่อจะถูกบล็อกเงียบๆ โดย `<img>` ยังอยู่ในหน้า **เห็นได้ทางเดียวคืออ่าน console**

## 9. Sidebar และเมนู

**เลือก `header` หรือ `sidebar` แบบเดียวตั้งแต่ `DESIGN.md` แล้วยึดทั้งระบบ ห้ามผสม**

### ถ้าเป็น sidebar

- **ต้องมีปุ่ม hamburger สำหรับพับเสมอ**
- **พับแล้วต้องย่อ ไม่ใช่ปิดหาย** — ตัดข้อความออกเหลือแต่ไอคอน ผู้ใช้ยังกดใช้งานได้ทุกเมนู
- ตอนย่อแล้ว hover ที่ไอคอนต้องมี tooltip บอกว่าเมนูนั้นคืออะไร
- **จำสถานะพับ/กางไว้** ผู้ใช้ไม่ต้องพับใหม่ทุกครั้งที่เปลี่ยนหน้า
- เมนูที่กำลังอยู่ต้องเห็นชัดว่า active ทั้งตอนกางและตอนย่อ
- บนมือถือให้เป็นแบบเลื่อนออกมาทับหน้า พร้อมพื้นหลังมืด กดนอกพื้นที่แล้วปิด

## 11. สถานะว่าง / กำลังโหลด / ผิดพลาด

**ทุกส่วนที่แสดงข้อมูลต้องมีครบทั้งสาม** ไม่ใช่ทำแต่กรณีข้อมูลครบ

### ว่าง

ต้องมี 3 อย่าง: **บอกว่าว่าง · บอกว่าทำไม (ถ้าเกี่ยวกับตัวกรอง) · บอกว่าทำอะไรต่อได้**

```
ยังไม่มีรายการในระบบ
กดปุ่ม "เพิ่มรายการ" เพื่อเริ่มต้น          [เพิ่มรายการ]
```

แยกให้ออกระหว่าง **ไม่มีข้อมูลเลย** กับ **มีข้อมูลแต่ตัวกรองไม่เจอ** — กรณีหลังต้องมีปุ่มล้างตัวกรอง

### กำลังโหลด

- ใช้ skeleton ที่มีรูปร่างใกล้เคียงของจริง ดีกว่า spinner กลางจอ เพราะบอกได้ว่ากำลังจะเห็นอะไร
- โหลดนานเกิน ~10 วินาที ต้องบอกว่ายังทำงานอยู่
- ห้ามให้หน้ากระโดดตอนข้อมูลมาถึง — จองพื้นที่ไว้ก่อน

### ผิดพลาด

ต้องมี: **เกิดอะไรขึ้น (ภาษาคน) · ทำอะไรต่อได้ · ปุ่มลองใหม่ · รหัสอ้างอิง error**

## 12. ไอคอนและภาพ

ข้อความกับกล่องล้วนๆ ทำให้หน้าสวยได้จำกัด ไอคอนช่วยได้ — แต่ใส่เยอะเกินจะรก

| ใส่ตรงไหนช่วย | ใส่ตรงไหนรก |
|---|---|
| ปุ่มในแถวตาราง (บังคับ) | ทุกหัวข้อในหน้า |
| สถานะและ alert | ทุกบรรทัดของรายการ |
| เมนูหลัก | ทุกปุ่มในฟอร์ม |
| empty state (ภาพประกอบขนาดกลาง 1 ชิ้น) | หลายชิ้นในหน้าเดียว |
| หน้า error 404/403/500 | — |

**กฎ**

- ใช้ **ชุดไอคอนเดียวทั้งระบบ** เป็น SVG inline เก็บใน `partials/icons/` — ห้ามผสมหลายชุดเพราะน้ำหนักเส้นและมุมมนจะไม่เข้ากัน · ยกเว้นไอคอนที่ตัดจากภาพแบบของผู้ใช้ ([`design.md`](design.md) 7ก.5)
- ไอคอนใช้ `currentColor` เพื่อให้เปลี่ยนตามโหมดและ token เอง
- **ไอคอนที่ใช้แทนความหมายต้องมีข้อความกำกับ** ไม่ว่าจะเป็น label, tooltip หรือ `aria-label`
- ห้ามโหลดชุดไอคอนจาก CDN — เก็บไฟล์ในโปรเจค
- ภาพประกอบใน empty state ให้ใช้ SVG ที่ใช้สีจาก token ไม่ใช่ภาพ raster ที่สีตายตัวแล้วเพี้ยนในโหมดมืด

## 13. อื่นๆ

**Badge / ป้ายสถานะ** — ต้องมีทั้งสีและข้อความ ห้ามสื่อด้วยสีอย่างเดียว · ค่าที่แสดงต้องแปลจาก key ในฐานข้อมูลผ่าน `__()` ไม่ใช่เก็บข้อความไทยไว้ในตาราง

**Tooltip** — ใช้กับข้อมูลเสริมเท่านั้น ห้ามใส่ข้อมูลที่จำเป็นไว้ใน tooltip เพราะบนมือถือไม่มี hover

> ‼️ **มีในโครงแล้ว ไม่ต้องทำอะไรเพิ่ม** — เขียน `title="..."` ตามปกติ แล้ว `app.js` เปลี่ยนให้เป็น tooltip ที่ตามธีมเอง
> ย้าย `title` ไปเก็บที่ `data-tip` ตอนเริ่ม เพื่อไม่ให้ tooltip ของ OS โผล่ซ้อน · JS พังแล้ว `title` ยังอยู่ครบและ tooltip ของ OS ยังทำงาน
> ขึ้นตอน **focus** ด้วย ไม่ใช่แค่ hover — คีย์บอร์ดและจอสัมผัสจึงยังเห็น · ชนขอบบนแล้วพลิกไปอยู่ใต้ปุ่มให้เอง
>
> tooltip ของ OS ขึ้นช้าราว 1 วินาที ใช้ฟอนต์และสีของ Windows และไม่ตามธีมที่ระบบเลือก — เป็นจุดที่ระบบหลุดคาแรกเตอร์แบบเดียวกับ `select` ในข้อ 5.12 และเจอทุกหน้าเพราะกฎบังคับว่าปุ่มไอคอนล้วนทุกตัวต้องมี tooltip

**Tabs** — ใช้เมื่อเนื้อหาแยกกันชัดเจนและผู้ใช้ไม่ต้องเทียบข้ามแท็บ · แท็บที่เปิดอยู่ต้องอยู่ใน URL เพื่อให้แชร์ลิงก์และกด back ได้

**Card** — ใช้พื้นและเส้นขอบจาก token · ห้ามใช้เงาลึกเพื่อสร้างความสำคัญ ให้ใช้ระยะห่างและขนาดแทน

**Breadcrumb** — จำเป็นเมื่อโครงหน้าลึกเกิน 2 ชั้น · **มีในโครงแล้ว** (`partials/breadcrumb.php`) — Controller ส่ง `pageBreadcrumb` มา หัวเพจแสดงให้เอง ตัวสุดท้ายคือหน้านี้ ไม่ต้องมี url

**ภาพหรือไอคอนข้างหัวเพจ** — **มีในโครงแล้ว** Controller ส่ง `pageMedia` (`['src' =>, 'alt' =>, 'width' =>, 'height' =>]` หรือ `['icon' =>]`) · ขนาดจาก `layout.pageMediaWidth` / `pageMediaHeight` · ใช้เมื่อแบบกำหนด ไม่ใช่ใส่ทุกหน้า

> ‼️ **`pageLead` คือประโยคอธิบายหน้า ไม่ใช่ชื่อของข้อมูลที่กำลังแก้** — หน้าแก้ไขที่ส่งชื่อรายการเป็น lead ได้บรรทัดใต้หัวข้อที่อ่านว่า "START" แทนคำอธิบาย · ชื่อรายการให้อยู่ในชื่อหน้า หรือท้าย breadcrumb

**ด้านข้างคู่เนื้อหาหลัก** — `pageWidth => 'split'` แล้ววางเนื้อหาใน `.split-layout` > `.split-aside` + `.split-main` · ข้อยกเว้นของ "หน้าเดียวคอลัมน์เดียว" ที่ต้องเลือกโดยตั้งใจ ([`design.md`](design.md) ข้อ 5.4)

**หน้า error** — ต้องมีครบ **403 (ไม่มีสิทธิ์) · 404 (ไม่พบ) · 500 (ระบบผิดพลาด) · maintenance** ทุกหน้าใช้ layout กลางและมีทางกลับเสมอ · 403 ต้องต่างจาก 404 ให้ชัด เพราะ "เข้าได้แต่ไม่มีสิทธิ์" กับ "ไม่มีหน้านี้" คนละเรื่องกัน

## 13ก. component ของหน้าสาธารณะ — คนละชุดกับของหลังบ้าน

component ที่เหลือในไฟล์นี้เป็นของ**ระบบหลังบ้าน** — ตาราง ฟอร์ม modal แบ่งหน้า
**เว็บโชว์และหน้า landing ต้องการอีกชุดหนึ่งซึ่งโครงไม่เคยมี** และเจอครั้งแรกตอนทดลองทำเว็บโชว์จริง

| partial | ใช้ทำอะไร | ห้ามเอาอะไรมาทำแทน |
|---|---|---|
| `hero.php` | ส่วนเปิดหน้า — พาดหัว ภาพ ปุ่มพาไปต่อ | ‼️ ห้ามใช้คู่กับ `page-head.php` ดู [`design.md`](design.md) 5.14 · ส่ง `$heroFullBleed = true` ได้ภาพเต็มจอข้อความทับภาพ ตามข้อ 5.16 |
| `product-card.php` | ตะแกรงการ์ดที่มี**ภาพเป็นตัวนำ** | ‼️ **ห้ามใช้ `table.php` แทน** ตารางเรียงข้อมูลให้เทียบค่ากัน ตะแกรงเรียงของให้ดู · เอาตารางมาทำจะได้หน้าที่อ่านเหมือนรายงานสต๊อก |
| `news-item.php` | รายการข่าว — ภาพ วันที่ หัวข้อ ย่อหน้านำ | ‼️ ห้ามใช้ `table.php` แทน · ข่าวถูกอ่านเพื่อ**เลือกว่าจะเปิดอันไหน** ไม่ใช่เพื่อเทียบค่า หัวข้อจึงต้องใหญ่กว่าวันที่ชัดเจน |
| `.prose` | บล็อกเล่าเรื่องยาว | ความกว้างมาจาก `--prose-max-width` ห้ามใส่ `ch` ดิบ |

### กฎของชุดนี้

1. **ทุกใบในตะแกรงต้องใช้สัดส่วนภาพเดียวกัน** ไม่งั้นขอบล่างของชื่อไม่ตรงกันทั้งแถว ซึ่งเป็นสิ่งแรกที่ตาจับได้ว่าหน้าไม่เรียบร้อย
2. **ทุก `<img>` ต้องระบุ `width`/`height`** กันหน้ากระตุกตอนภาพโหลดเสร็จ
3. **ภาพในส่วนเปิดใช้ `fetchpriority="high"` ที่เหลือใช้ `loading="lazy"`**
4. **ข้อความต้องอ่านรู้เรื่องแม้ภาพโหลดไม่ขึ้น** — ภาพเป็นของประกอบ ไม่ใช่ของที่สื่อความหมายแทนข้อความ
5. ค่ารูปทรงทั้งหมดมาจาก `component:` ใน `DESIGN.md` — `hero.*` `productCard.*` `prose.*` `newsItem.*`

- [ ] ทำงานได้ทั้งโหมดสว่างและมืด
- [ ] ใช้งานด้วยคีย์บอร์ดได้ครบ และ focus เห็นชัด
- [ ] มีชื่อกำกับสำหรับ screen reader ครบ
