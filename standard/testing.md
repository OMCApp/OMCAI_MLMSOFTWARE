> **เป้าหมาย: พิสูจน์ว่ามันทำงานถูกจริงด้วยการทดลองใช้ ไม่ใช่อ่านโค้ดแล้วสรุปว่าน่าจะได้**
> ทีมไม่บังคับ test framework เพื่อความเบา จึงใช้ **สคริปต์ตรวจอัตโนมัติ + การกดใช้จริงตาม checklist** แทน

## 1. ทดสอบ 2 ระดับ

| ระดับ | เมื่อไหร่ | ขอบเขต |
|---|---|---|
| **ต่อ phase** (ช่วง C4) | ทุกครั้งที่จบ phase ก่อนให้ผู้ใช้ตรวจ | เฉพาะสิ่งที่เพิ่งทำใน phase นั้น |
| **ต่อ phase — โหมดเร็ว** (ช่วง C4 ตั้งแต่ phase ที่ 2) | ทุกครั้งที่จบ phase ไม่หยุดรอ | **ข้อ 2.2 ดีไซน์ครบเหมือนโหมดปกติ** + ตรวจขั้นต่ำ ([`flow.md`](flow.md) ข้อ 15) · ข้อ 2.3–2.8 เลื่อนไปข้อ 3.0 |
| **ตรวจรวม** (ช่วง D) | หลังทุก phase เสร็จหมด | ทั้งระบบ ข้าม phase — ความปลอดภัย ประสิทธิภาพ E2E · **และตรวจย้อนหลังของโหมดเร็ว** |

> **ห้ามเขียนโค้ดทุก phase จนจบแล้วค่อยตรวจทีเดียว** ความผิดพลาดเรื่องระยะห่าง component และ pattern จะถูกคัดลอกต่อไปทุกหน้า สุดท้ายต้องรื้อพร้อมกันทั้งระบบ — ตรวจทีละ phase คือการจ่ายทีละนิดแทนการจ่ายก้อนใหญ่ตอนท้าย
>
> **ยกเว้นเมื่อผู้ใช้เลือกโหมดเร็ว** ซึ่งคือการเลือกจ่ายก้อนใหญ่ตอนท้ายโดยรู้ตัว — phase แรกยังตรวจเต็มเสมอเพราะเป็นตัววาง pattern ([`flow.md`](flow.md) ข้อ 15)
> **แต่ข้อ 2.2 ไม่อยู่ในของที่เลื่อนได้** ตั้งแต่ 3.18.0 — ทีมที่ใช้โหมดเร็วรอบแรกได้หน้าที่ไม่ตรงกับแบบที่อนุมัติแล้ว (wireframe ของเส้นทาง ก · ไฟล์ดีไซน์ของเส้นทาง ข · ภาพแบบของเส้นทาง ค) และบล็อกหายไปหลายหน้า เพราะไม่มีใครเทียบกับแบบเลยทั้ง phase

## 2. ระดับ 1 — ทดสอบต่อ phase

### 2.1 สคริปต์ตรวจ

```bash
php scripts/check.php
```

ต้อง exit 0 — ถ้าไม่ผ่าน **แก้ที่โค้ด ห้ามแก้ที่สคริปต์ตรวจ**

**ระดับนี้คือตรวจเต็ม** — ระหว่างเขียนใช้ `php scripts/check.php --changed` ได้ (ไฟล์ที่เปลี่ยน + การตรวจทั้งโปรเจค) แต่ **ก่อนบอกว่า phase เสร็จต้องรันเต็มทุกครั้ง** · ดู [`flow.md`](flow.md) ข้อ 13

### 2.2 ตรวจหน้าตา

> ‼️ **ข้อนี้ทำทุก phase ทุกโหมด** — โหมดเร็วเลื่อนข้อ 2.3–2.8 ได้ แต่เลื่อนข้อนี้ไม่ได้ ([`flow.md`](flow.md) ข้อ 15)

**เปิดแบบที่อนุมัติแล้ววางคู่กับหน้าจริงแล้วไล่ทีละบล็อก** — บล็อกครบ · ลำดับตรง · ตำแหน่งและสัดส่วนตรง · แบบของแต่ละเส้นทางอยู่ที่ [`flow.md`](flow.md) ข้อ 5
**บล็อกที่หายไปคือสิ่งที่การอ่านโค้ดและการเปิดดูเฉยๆ ไม่มีวันจับได้** เพราะหน้าที่ขาดบล็อกก็ยังดูเรียบร้อยดีเมื่อไม่มีอะไรวางเทียบ

ก่อนเริ่มปรับ ให้เรียก skill `frontend-design` (และ `impeccable` ถ้ามี) — **ถ้าไม่เรียก ผลลัพธ์จะกลับไปเป็นค่าเริ่มต้นของ AI ซึ่งไม่ผิดกฎข้อไหนเลยแต่จืดและซ้ำแบบเดิมทุกโปรเจค**

- [ ] ตรงกับทิศทางที่ตัดสินไว้ใน `project/DESIGN.md` — ไม่ใช่แค่ "ดูดี" แต่ต้องเป็นบุคลิกเดียวกับหน้าอื่นในระบบ
- [ ] **หน้าใหม่วางข้างหน้าเก่าแล้วดูเป็นระบบเดียวกัน** ไม่ใช่ดูดีเดี่ยวๆ
- [ ] ไม่มี component ที่ทำหน้าที่เหมือนของเดิมแต่หน้าตาต่างกัน — **ถ้า copy markup มาจากหน้าอื่นต้องแยกเป็น partial แล้วให้ทั้งสองหน้าใช้ร่วมกัน**
- [ ] ผ่าน checklist ท้าย [`design.md`](design.md) และ [`components.md`](components.md) ครบ
- [ ] เปิดจริง **3 ขนาดจอ × ทุกภาษาที่เปิดใช้ × ทั้งโหมดสว่างและมืด**
- [ ] **หน้าที่มีภาพแบบระดับ "ตรงแบบ" เทียบกับภาพแบบแล้ว** ตามข้อ 4ข และช่อง `ต่างจากแบบ` ใน `DESIGN.md` ไม่ว่าง

> **ฟังก์ชันถูกแต่หน้าตายังไม่ดี ถือว่างานยังไม่เสร็จ** ห้ามผ่านด้วยเหตุผลว่า "เดี๋ยวค่อยกลับมาปรับ"

### 2.3 เส้นทางปกติ

- [ ] สร้างข้อมูลใหม่ได้ และเข้าฐานข้อมูลถูกต้องครบทุกฟิลด์
- [ ] แสดงรายการ · ค้นหา · กรอง · **กรองช่วงวันและปุ่มลัด** · เรียงลำดับ · เปลี่ยนจำนวนแถว · แบ่งหน้า ทำงานถูกทุกตัว
- [ ] **ค่าตัวกรองอยู่ใน URL** — copy ลิงก์ไปเปิดแท็บใหม่แล้วได้ผลเดิม และกด back แล้วค่าไม่หาย
- [ ] เปิดดูรายละเอียดได้ · แก้ไขแล้วค่าเปลี่ยนจริง · ลบแล้วหายจากรายการจริง
- [ ] **ครบลูป ดู/เพิ่ม/แก้/ลบ** ทุก resource ของ phase นี้ ← ถ้าขาดข้อใดข้อหนึ่ง phase นี้ยังไม่เสร็จ
- [ ] ปุ่มส่งออก CSV ได้ไฟล์ที่เปิดใน Excel แล้วภาษาไทยไม่เพี้ยน และได้เฉพาะแถวตามตัวกรองที่ใช้อยู่
- [ ] หลังทุก action ผู้ใช้ได้ feedback ว่าสำเร็จหรือไม่

### 2.4 เส้นทางที่ผิดพลาด

- [ ] ส่งฟอร์มเปล่า → บอกว่าต้องกรอกอะไร **และข้อความอยู่ติดช่องที่ผิด**
- [ ] **validate ไม่ผ่านแล้วค่าที่กรอกไว้ยังอยู่ครบ** ไม่ต้องกรอกใหม่
- [ ] กรอกผิดรูปแบบ (ตัวอักษรในช่องตัวเลข อีเมลผิดรูป วันที่ย้อนหลังเกินจริง) → ปฏิเสธ ไม่ใช่บันทึกดื้อๆ
- [ ] กรอกค่าเกินขอบเขต (ติดลบ ศูนย์ ยาวเกินคอลัมน์) → ปฏิเสธและบอกเหตุผล
- [ ] **กดปุ่มบันทึกรัวๆ → ได้ข้อมูลแถวเดียว ไม่ใช่หลายแถว**
- [ ] เรียก id ที่ไม่มีอยู่จริง → หน้า 404 ไม่ใช่หน้าขาวหรือ error ดิบ
- [ ] ทำให้เกิด error จริง 1 ครั้ง → ผู้ใช้เห็นข้อความทั่วไปพร้อม**รหัสอ้างอิง** และค้น log ด้วยรหัสนั้นเจอรายละเอียดจริง

### 2.5 สิทธิ์ — ข้อที่คนข้ามบ่อยที่สุด

- [ ] **ล็อกอินด้วยผู้ใช้ที่ไม่มีสิทธิ์ แล้วพิมพ์ URL ของ phase นี้เข้าไปตรงๆ** → ต้องถูกกัน
  > การที่เมนูไม่แสดงไม่ใช่การกัน ต้องกันที่ Middleware
- [ ] ทดสอบ action ที่เปลี่ยนข้อมูล (POST/PUT/DELETE) ด้วยผู้ใช้ที่ไม่มีสิทธิ์ด้วย ไม่ใช่แค่หน้าที่เปิดดู
- [ ] **เข้าถึงข้อมูลของคนอื่นด้วยการเปลี่ยน id ใน URL** → ต้องถูกกัน (สิทธิ์ระดับแถว)
- [ ] ยังไม่ล็อกอินแล้วเรียก URL ตรง → เด้งไปหน้า login
- [ ] แถวที่ถูก soft delete แล้วเรียก id ตรง → เข้าไม่ได้

### 2.6 Audit log

- [ ] แก้ข้อมูล 1 รายการ แล้ว**เปิดตาราง `audit_logs` ดูจริง** → มีแถวเกิดขึ้น
- [ ] `user_id` ตรงกับคนที่ทำจริง · `action` `table_name` `record_id` ถูกต้อง
- [ ] **`old_values` / `new_values` เก็บเฉพาะฟิลด์ที่เปลี่ยนจริง** ไม่ใช่ทั้งแถว
- [ ] ทดสอบ **สร้าง / แก้ / ลบ** ครบทั้ง 3 แบบ
- [ ] ถ้ามีฟิลด์รหัสผ่านหรือ token → ต้อง**ไม่มี**ค่าจริงโผล่ใน audit log

### 2.7 ข้อมูลจริงและกรณีสุดขอบ

- [ ] ไม่มีข้อมูลเลย → **empty state ที่บอกว่าทำอะไรต่อได้** ไม่ใช่ตารางว่างเปล่า
- [ ] มีข้อมูลแต่ตัวกรองไม่เจอ → ข้อความต่างจากกรณีไม่มีข้อมูลเลย และมีปุ่มล้างตัวกรอง
- [ ] ข้อความยาวผิดปกติ → layout ไม่พัง
- [ ] **ข้อมูล 500-1000 แถว → หน้ายังเปิดเร็ว และ pagination ทำที่ฝั่งเซิร์ฟเวอร์จริง** ไม่ใช่โหลดทั้งหมดมาแล้วซ่อน
- [ ] ภาษาไทย จีน และ emoji แสดงถูกต้องไม่เพี้ยน (ตรวจ `utf8mb4`)
- [ ] ตัวเลขเงิน/จำนวนคำนวณถูกต้อง — **ถ้าข้อมูลนี้ถูกระบุใน `BRIEF.md` ว่าผิดพลาดไม่ได้ ให้ทดสอบด้วยตัวเลขจริงหลายชุด ไม่ใช่ชุดเดียว**

### 2.8 ภาษาและคู่มือ

- [ ] สลับภาษาแล้วเปลี่ยนครบ **รวมข้อความ validation และ error** ไม่มีคำค้างภาษาเดิม
- [ ] ไม่มี key ที่แสดงเป็นข้อความดิบหรือช่องว่างเปล่าเพราะคำแปลตกหล่น
- [ ] วันที่แสดงถูกตามภาษา และค่าในฐานข้อมูลยังเป็น ค.ศ.
- [ ] ค่า `status` / `type` ในฐานข้อมูลเป็น key อังกฤษ ไม่ใช่ข้อความไทย
- [ ] **ทุกหน้าของ phase นี้มีบทความคู่มือ ครบทุกภาษาที่เปิดใช้** ← ไม่ครบถือว่ายังไม่ผ่าน
- [ ] กดปุ่มซัพพอร์ต → วิธีใช้งาน จากหน้าจริง → **เปิดบทความของหน้านั้นได้ตรง** ไม่ใช่ไปหน้ารวม
- [ ] **ไล่ทำตามขั้นตอนในบทความทีละข้อแล้วได้ผลจริง** ไม่ใช่อ่านผ่าน

### 2.9 ปิดท้าย

- [ ] `storage/logs/app.log` ไม่มี error ใหม่จากการทดสอบรอบนี้
- [ ] console เบราว์เซอร์ไม่มี error หรือ warning
- [ ] **ผู้ใช้ตรวจและยืนยันแล้ว** ← ผ่านข้อนี้ถึงขึ้น phase ถัดไปได้ · **โหมดเร็วไม่รอข้อนี้** ผู้ใช้ตรวจรวมที่ประตู D

## 3. ระดับ 2 — ตรวจรวมทั้งระบบ (ช่วง D)

### 3.0 ตรวจย้อนหลังจากโหมดเร็ว — ทำก่อนข้ออื่น

ข้ามได้ถ้าไม่มี phase ไหนใน `PLAN.md` เป็น 🔨

ทำทีละ phase ที่เป็น 🔨 เรียงตามเลข phase

- [ ] **ไล่ข้อ 2.3–2.8 ครบทุกข้อ** เหมือนตอนจบ phase ในโหมดปกติ — ไม่ใช่เวอร์ชันย่อ
- [ ] **ข้อ 2.2 ทำไปแล้วตอนจบ phase** (3.18.0) — ที่นี่แค่ยืนยันว่ามีภาพและผลเทียบกับแบบของ phase นั้นอยู่จริง · **ไม่มี = การตรวจดีไซน์ถูกข้าม ให้ทำตอนนี้แล้วบันทึกลง `FEEDBACK.md`**
- [ ] **วางหน้าของทุก phase เรียงกันดูรอบเดียว** — ข้อเดียวที่ต้องรอจนครบทุก phase เพราะระบบเพิ่งครบตอนนี้
- [ ] เขียนผลลง `QA-REPORT.md` หัวข้อ `### Phase N — ชื่อ` ใต้ `## ตรวจย้อนหลังจากโหมดเร็ว` แล้วเปลี่ยน `PLAN.md` เป็น ✅ ตามรูปแบบใน [`flow.md`](flow.md) ข้อ 9
- [ ] **ปัญหาที่เจอเขียนเป็นข้อในหมวดความรุนแรง** พร้อม `มาจาก: ตรวจย้อนหลัง Phase N` และ `สถานะ:` (ข้อ 5) — ไม่ใช่เป็นรายการใต้หัวข้อ phase · บอร์ดจะได้แสดงเป็นการ์ดรวมกับผลตรวจอื่น

> ‼️ **เจอปัญหาชนิดเดียวกันซ้ำใน phase ที่สอง — หยุดไล่แก้ทีละหน้า** กลับไปหาต้นเหตุ (มักเป็น partial token หรือ pattern ที่ phase แรกวางไว้) แก้ครั้งเดียวแล้วตรวจทุก phase ที่กระทบซ้ำ
> นี่คือราคาที่โหมดเร็วเลือกจ่าย · บันทึกจำนวนลงสรุปของ `QA-REPORT.md` เพื่อให้ผู้ใช้ตัดสินได้ว่าคุ้มไหม

`docs/fast-mode-debt` ไม่ยอมให้ติ๊กว่าตรวจแล้วโดยไม่มีหัวข้อใน `QA-REPORT.md` และไม่ยอมให้ผ่านประตู D ถ้ายังมี 🔨

### 3.1 ความปลอดภัย

1. `php scripts/check.php`
2. เรียก `/security-review`
3. ไล่ checklist ท้าย [`security.md`](security.md) ครบทุกข้อ
4. ตรวจเพิ่มระดับระบบ:
   - [ ] `.env` เปิดจากเบราว์เซอร์ไม่ได้ · directory listing ปิด
   - [ ] security headers ครบ · CSP ไม่มี `unsafe-inline`
   - [ ] `/_migrate` ตอบ 404 เมื่อ token ผิด
   - [ ] ไม่มี route ไหนหลุด middleware — ไล่เทียบ `config/routes.php` ทีละบรรทัด

### 3.2 ประสิทธิภาพ

ทดสอบกับข้อมูลระดับที่ระบุใน `BRIEF.md` ข้อ 13 ไม่ใช่ข้อมูล 3 แถว

- [ ] **นับจำนวน query ต่อหน้า** — หน้ารายการไม่ควรเกิน ~10 query · **เจอ query ที่วิ่งตามจำนวนแถวคือ N+1 ต้องแก้**

  > ‼️ **ไม่ต้องรอมานับตอนนี้** — footer แสดง `N query · X ms` ให้ทุกหน้าอยู่แล้วในโหมด `development`

## 4ก. ‼️ เกณฑ์ภาพขั้นต่ำ — ข้อที่ทำให้ "นิยามเสร็จ ข้อ 3" ทำได้จริง

> มาตรฐานสั่งว่า **"เปิดหน้าจริงในเบราว์เซอร์ดู"** มาตั้งแต่ต้น แต่ไม่เคยบอกวิธี
> ข้อนี้จึงเป็นข้อที่ถูกข้ามง่ายที่สุด — AI ตีความว่า "เปิดดูแล้วไม่พัง" แทน "เปิดดูแล้วดี"
>
> ในรอบแก้จริงรอบเดียว การไล่ดูภาพทำให้เจอปัญหาเพิ่ม **14 จุดที่อ่านจากโค้ดไม่เห็นเลย**

**ทุกหน้าในทุก phase ต้องมีภาพ 2 โหมด × 2 ความกว้าง (1440 / 375)**
**และทุก component ที่ต้องกดก่อนจะเห็น ต้องมีภาพตอนเปิดอยู่**
**ผู้ทำต้องดูภาพเองก่อนบอกว่าเสร็จ** ไม่ใช่ถ่ายเก็บไว้เฉยๆ

### 4ก.1 ถ่ายภาพหน้าที่ล็อกอินแล้ว

Chrome headless ไม่มี cookie ของ session จึงถ่ายหน้าหลังล็อกอินตรงๆ ไม่ได้

ดึง HTML ด้วย `curl` ที่ถือ cookie อยู่ → แทรก `<base href="http://localhost:PORT/">` เข้าไปใน `<head>` → บันทึกเป็นไฟล์ → สั่ง `chrome --headless --screenshot` บนไฟล์นั้น
CSS ฟอนต์ และรูปจะโหลดกลับจาก server ตัวจริง

```bash
chrome --headless --disable-gpu --hide-scrollbars --window-size=1440,900 \
  --screenshot=out.png --virtual-time-budget=3000 "http://localhost:8000/หน้าที่จะดู"
```

### 4ก.2 ตรวจจอแคบจริงที่ 375px

‼️ **`--window-size=390,x` ให้ผลผิด** — Chrome บน Windows บังคับความกว้างหน้าต่างขั้นต่ำ ~485px
ภาพที่ได้จึงเป็นภาพที่ crop มาจาก viewport ที่กว้างกว่านั้น **อ่านผลผิดได้ทั้งสองทาง** (คิดว่าไม่ล้นทั้งที่ล้น หรือกลับกัน)

ทางที่ได้ผลจริง: ทำหน้า host แล้ววาง `<iframe width="375">` ชี้ไปไฟล์ที่เซฟไว้ แล้วอ่าน `clientWidth` เทียบ `scrollWidth` จากในนั้น

### 4ก.3 เรื่องสีต้องวัด ห้ามสรุปจากการดูภาพ

> ในงานจริงรอบเดียว AI อ่านภาพผิดเรื่องสี **สามครั้ง** และผิดทางเดียวกันทุกครั้ง คือ **เห็นว่ามืดทั้งที่สว่าง**
> (คิดว่า sidebar โหมดสว่างเป็นสีเข้ม · คิดว่าจอแคบล้นแนวนอน · คิดว่ารางเมนูพับเป็นสีเข้ม — ผิดทั้งสามครั้ง)
> ค่าพิกเซลจริงคือ `#FFFBF2` ซึ่งเป็นสีครีมถูกต้องอยู่แล้ว

**การดูภาพใช้ตัดสินได้เรื่อง การจัดวาง ลำดับสายตา และช่องว่าง — แต่เรื่องสีต้องสุ่มพิกเซลมาเทียบกับ token**

### 4ก.3ก ‼️ ค่าที่วัดจากเบราว์เซอร์ที่ยังไม่ได้แสดงผล เชื่อไม่ได้เลย

**ก่อนเชื่อค่าที่วัดได้ ต้องยืนยันก่อนว่า `window.innerWidth` ไม่ใช่ `0`**

หน้าต่างที่ยังไม่ถูกแสดงผลจะมี viewport ขนาด 0×0 ทุกความกว้างที่วัดได้จึงเป็นขยะ
และมันไม่ error ไม่เตือนอะไรเลย — ได้ตัวเลขที่ดูเหมือนจริงกลับมาเสมอ

> เกิดขึ้นจริงในรอบเดียว **สองครั้ง** — อ่านว่ากรอบลากวางกว้าง 42px และหน้าล้นแนวนอน
> วัดใหม่หลังตั้ง viewport เป็น 1440×900 ได้ 526×112 และไม่ล้น · **ไม่มีบั๊กอยู่เลยตั้งแต่แรก**

และเวลาสลับธีมเพื่อวัดสี ต้อง**บังคับให้คำนวณสไตล์ใหม่ก่อนอ่าน** ไม่งั้นจะได้ค่าของธีมเดิม

```js
el.style.transition = 'none';
void el.offsetHeight;          // บังคับคำนวณใหม่
getComputedStyle(el).backgroundColor;
```

> อาการ: สลับเป็นโหมดมืดแล้วอ่านค่าได้เป็นสีของโหมดสว่าง จนเกือบรายงานว่าโหมดมืดพัง

### 4ก.4 component ที่ต้องกดก่อนจะเห็น

dropdown · ปฏิทิน · modal · เมนูย่อย — **ถ่ายภาพเฉยๆ ไม่เจอ**

ทำหน้า host ที่วาง `<iframe>` ชี้ไปไฟล์ที่เซฟไว้ แล้วสั่ง `.click()` เข้าไปใน iframe ก่อนถ่าย
ถ้าอ่าน `getComputedStyle` ของ ancestor ทุกตัวออกมาด้วย จะได้คำตอบทันทีว่าใครทับใคร ไม่ต้องเดา

> ท่านี้คือตัวที่จับบั๊ก stacking context ได้ (`animation-fill-mode: both` ทำให้ dropdown ทุกตัวถูกทับ)
>
> ‼️ และเป็นข้อเดียวที่กันความผิดพลาดชนิด **"ลดอาการแล้วรายงานว่าแก้แล้ว"** ได้จริง
> เคยเกิดขึ้น: ตั้งสี `option` แล้วรายงานว่าแก้ปัญหา `select` แล้ว โดย**ไม่ได้ถ่ายภาพตอนรายการกางออกมา**
> ผู้ใช้เปิดดูแล้วบอกว่า "มันยังไม่มี css เหมือนเดิม" ซึ่งถูก
> ถ้าถ่ายก็จะเห็นทันทีว่ายังเป็นแผงของ OS — มันเปลี่ยนจาก "เชื่อคำอธิบายของตัวเอง" เป็น "ดูภาพ"

## 4ข. ‼️ เทียบกับภาพแบบ — หน้าที่ผู้ใช้ออกแบบมาเอง

> ข้อ 4ก ตัดสินภาพเทียบกับ **กฎคุณภาพ** · ข้อนี้ตัดสินภาพเทียบกับ **แบบ**
> ก่อน 3.17.0 ไม่มีขั้นนี้ — หน้าที่ผ่านทุกกฎแต่ไม่เหมือนแบบที่ผู้ใช้วาดมาเลย จึงถือว่าเสร็จได้

ใช้กับทุกหน้าที่มีแถวระดับ **ตรงแบบ** ในตาราง `## แบบของแต่ละหน้า` ของ `DESIGN.md` — ทุกเส้นทาง ทุกโหมด รวมงานเล็ก

1. **เปิดภาพแบบดูจริง** — ไม่ใช่ทำตามที่จำได้
2. **ถ่ายหน้าจริงที่ความกว้างเดียวกับภาพแบบ** (ภาพกว้าง 1440 = viewport 1440) เก็บที่ `project/design/built/<ชื่อเดียวกับภาพแบบ>.png` · ภาพเสริม `@375` `-dark` ถ่ายคู่ด้วย
3. **วางคู่กัน แล้วไล่ทีละบล็อกจากบนลงล่าง** — ลำดับของบล็อก · ตำแหน่งและสัดส่วนของภาพ · ขนาดและน้ำหนักของหัวข้อเทียบกับเนื้อความ · ระยะห่างระหว่างบล็อก · สี · สิ่งที่มีในแบบแต่ไม่มีในหน้า
4. **เรื่องสีให้วัด ไม่ใช่ดู** — `php scripts/design-refs.php --pick` บนภาพแบบเทียบกับค่าที่วัดจากหน้าจริง (ข้อ 4ก.3)
5. **ทุกความต่างต้องแก้ หรือมีเหตุผลที่ผู้ใช้รู้แล้ว** (จุดที่ขัดกับกฎแข็งซึ่งรายงานไปแล้วตามข้อ 5.0 ของ [`design.md`](design.md)) · เขียนลงช่อง `ต่างจากแบบ` ในตาราง — ไม่มีก็เขียน `ไม่มี`

**"ตรงแบบ" ที่ทำได้จริง** คือโครง ลำดับ ตำแหน่งภาพ ลำดับสายตา และสีตรงตามแบบ **ไม่ใช่ตรงทุกพิกเซล** — หน้าจริงต้องรองรับหลายขนาดจอ สองโหมด และข้อความภาษาอังกฤษที่ยาวกว่า ซึ่งภาพแบบมักมีแค่ขนาดเดียวโหมดเดียว ส่วนที่แบบไม่ได้บอก ให้ทำให้เข้ากับแบบแล้วบอกผู้ใช้ว่าตัดสินเองตรงไหน

> ‼️ `design/reference-compared` ตรวจได้แค่ว่าเทียบแล้ว — มีภาพหน้าจริงคู่กับภาพแบบ และช่อง `ต่างจากแบบ` ไม่ว่าง
> **ตรวจไม่ได้ว่าเหมือนจริง** · การเขียน `ไม่มี` ทั้งที่ยังต่างคือการรายงานเท็จ ชนิดเดียวกับ "ลดอาการแล้วรายงานว่าแก้แล้ว"

| `แก้แล้ว รอตรวจซ้ำ` | แก้แล้ว + ใส่ `แก้ใน:` แต่ยังไม่ได้ทำขั้นตอน "ทำยังไงถึงเจอ" ซ้ำ | แก้แล้ว รอตรวจซ้ำ |
| `ปิด` | **ทำขั้นตอนที่เจอซ้ำแล้วผลถูก** · หรือพิสูจน์แล้วว่าไม่ใช่ปัญหา (`แก้ใน: ไม่ต้องแก้ — เหตุผล`) | ปิด |

> ‼️ **"แก้แล้ว" ไม่ใช่ "ปิด"** — ข้อที่แก้แล้วแต่ไม่ได้ตรวจซ้ำ คือข้อที่อาจแค่ลดอาการ (`CLAUDE.md` ข้อ 4)
> แยกเลนไว้เพื่อให้ทุกคนเห็นว่ามีกี่ข้อที่ยังรอพิสูจน์ ไม่ใช่ถูกนับรวมกับข้อที่จบแล้ว

- เปลี่ยนสถานะ **ที่ไฟล์นี้เท่านั้น** แล้วอัปเดตบอร์ด — บอร์ดไม่มีอะไรให้แก้
- หมวด 🟢 ไม่ต้องใส่สถานะ ถือว่าปิด
- **ภาพหลักฐานเขียนเป็น path ในโปรเจค** — บอร์ดฝังภาพที่เล็กกว่า 400 KB ให้เห็นในกล่องรายละเอียด · ใหญ่กว่านั้นแสดงแค่ path
- `docs/qa-issue-state` เตือนข้อที่ไม่มีสถานะ · เตือนข้อที่ปิดโดยไม่มี `แก้ใน:` · **และบล็อกเมื่อผ่านประตู D ทั้งที่ยังมีข้อ 🔴 ที่ไม่ใช่ `ปิด`**

**สรุปเป็น Artifact ให้ผู้ใช้ดูควบคู่กับไฟล์** — ไฟล์คือหลักฐานที่อยู่กับ repo ส่วน Artifact คือสิ่งที่ผู้ใช้เปิดอ่านได้เร็วและส่งต่อให้คนอื่นดูได้ · **บอร์ดความคืบหน้าแท็บ "ผลตรวจ" ([`flow.md`](flow.md) ข้อ 16) คือ Artifact นี้** ไม่ต้องทำแยก

**ห้ามเขียนว่าผ่านโดยไม่ได้ทดสอบจริง** — ถ้าไม่ได้ทดสอบให้เขียนว่าไม่ได้ทดสอบและบอกเหตุผล

## 6. เมื่อเจอบั๊ก

1. เรียก skill `systematic-debugging` — **หาสาเหตุก่อนแก้ ห้ามเดาแล้วลองแก้ไปเรื่อยๆ**
2. ถ้าบั๊กมาจากที่ผู้ใช้แจ้ง ให้เริ่มจาก**รหัสอ้างอิง error** แล้วค้น log
3. แก้แล้ว **ต้องกลับมาไล่ checklist ของ phase นั้นใหม่ทั้งหมด ไม่ใช่ตรวจเฉพาะข้อที่พัง** — เพราะการแก้จุดหนึ่งมักทำให้อีกจุดพัง
   **ยกเว้นบั๊กที่เข้าเกณฑ์งานเล็ก** ([`flow.md`](flow.md) ข้อ 13) ซึ่งแก้ในไฟล์ที่ไม่ใช่ของกลาง — ไล่ทั้ง phase เพื่อแก้คำเดียวคือสิ่งที่ทำให้ทีมเจอว่า "แก้นิดเดียวแต่ช้ามาก"
4. บั๊กที่เกิดจากช่องว่างของมาตรฐาน (ไม่ใช่ความผิดพลาดของโค้ด) ให้บันทึกลง **`project/FEEDBACK.md`** ไม่ใช่ `QUESTIONS.md`
   > ‼️ `QUESTIONS.md` มีวงจร ถาม → ตอบ → ติ๊ก `[x]` · ช่องว่างของมาตรฐานที่ถูกติ๊กแปลว่า "จัดการแล้ว" ทั้งที่กฎกลางยังไม่ถูกแก้สักตัว ([`flow.md`](flow.md) ข้อ 9)
