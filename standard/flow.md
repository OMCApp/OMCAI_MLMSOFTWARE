# Flow การทำงาน — สมองของ `/wf`

> อ่านไฟล์นี้ทุกครั้งที่เริ่ม session
> ไฟล์นี้บอกว่า **อยู่ตรงไหน ทำอะไรต่อ หยุดตอนไหน และไฟล์ใน `project/` หน้าตายังไง**
> รายละเอียดวิธีทำแต่ละเรื่องอยู่ในไฟล์เฉพาะทาง ไฟล์นี้เป็นแผนที่ ไม่ใช่คู่มือ

## 1. หลักการ 5 ข้อ

1. **ผู้ใช้พิมพ์ `/wf` ครั้งเดียว** หลังจากนั้นตอบเป็นภาษาคนธรรมดา ไม่ต้องพิมพ์คำสั่งอีก
2. **`project/STATE.md` คือความจริง** ไม่ใช่บทสนทนา — session หลุด เพื่อนร่วมทีมมารับช่วง หรือพิมพ์ `/wf` ซ้ำ ต้องทำงานต่อจากจุดเดิมได้โดยไม่ต้องให้ผู้ใช้เล่าใหม่
3. **ระหว่างช่วง เดินยาวจนจบ ห้ามหยุดถามทีละขั้น** — เจอเรื่องกำกวมให้จดลง `QUESTIONS.md` แล้วทำต่อ
4. **ที่ประตู หยุดจริง** ห้ามเดินต่อเองไม่ว่าจะมั่นใจแค่ไหน
5. **ห้ามข้ามช่วง** — แต่ละช่วงมีของที่ต้องมีอยู่ก่อน ถ้าไม่มีให้ย้อนกลับไปทำ

ประตูรวม **A + B + (1 ต่อ phase) + D** — โปรเจค 4 phase = หยุด 7 ครั้ง โดย 5 ครั้งเป็นแค่ดูแล้วบอกผ่าน · เส้นทาง ข มีประตูช่วง B สองบานจึงหยุด 8 ครั้ง

**โหมดเร็ว** (ข้อ 15) ตัดประตูย่อยของช่วง C ออก — หยุดแค่ **A + B + D** ไม่ว่ากี่ phase · **การตรวจดีไซน์ยังทำครบทุก phase** ส่วนการตรวจที่ไม่ใช่ดีไซน์ของ phase ที่ 2 เป็นต้นไปเลื่อนไปรวมที่ช่วง D

## 3. เริ่ม session ยังไง

```
มี project/STATE.md ไหม?
├── ไม่มี  → โปรเจคใหม่ → เริ่มช่วง A ขั้น A0 (รัน setup.php ก่อน)

```

**ห้ามเริ่มทำงานก่อนอ่าน `STATE.md`** และห้ามถามผู้ใช้ซ้ำในสิ่งที่มีคำตอบอยู่ใน `project/` แล้ว

งานที่ไม่ต้องเดินทั้ง flow มีสองแบบ — **งานเล็ก** (ข้อ 13) และ **อัปเดตมาตรฐาน** (ข้อ 14) · ทั้งสองยังต้องอ่าน `STATE.md` ก่อน เพื่อรู้ว่ากำลังอยู่กลาง phase หรือไม่

**อ่านบรรทัด `โหมด:` ใน `STATE.md` ทุกครั้ง** — เป็นตัวตัดสินว่าจบ phase แล้วหยุดรอหรือทำต่อ (ข้อ 15) · ไม่มีบรรทัดนี้ = โหมดปกติ

## 4. ช่วง A — เก็บข้อมูล

### A0 — ตั้งค่าเครื่องให้พร้อมก่อนทุกอย่าง

```bash
php scripts/setup.php
```

**รันเลย ไม่ต้องขออนุญาต และห้ามให้ผู้ใช้พิมพ์คำสั่งตั้งค่าเอง** — สคริปต์ทำแทนทั้ง `.env`, `MIGRATE_TOKEN`, pre-commit hook (พร้อมทดสอบว่าบล็อกได้จริง), สร้างฐานข้อมูล, migration และตรวจ plugin

จบแล้วอ่านหัวข้อ **"ต้องทำเอง"** ท้ายผลลัพธ์ แล้วจัดการตามนี้

| เจออะไร | ทำยังไง |
|---|---|
| **ยังผูกกับ repo มาตรฐานอยู่** | ถามผู้ใช้ **1 คำถาม** ว่า *"นี่เป็นโปรเจคใหม่ใช่ไหม จะตัด repo มาตรฐานออกให้"* → ตอบใช่ → รัน `php scripts/init-project.php --yes` **ให้เลย ห้ามให้ผู้ใช้พิมพ์เอง** · ดูกล่องข้างล่าง |
| **plugin กลุ่มบังคับไม่ครบ** | **หยุดรอ** — ส่งคำสั่ง `/plugin install ...` ให้ผู้ใช้ แล้วบอกว่าต้องเปิด session ใหม่ **ห้ามคุยเรื่องงานต่อ** เพราะติดตั้งทีหลังแปลว่าบทสนทนาที่เก็บความต้องการไว้หายหมด ผู้ใช้ต้องเล่าใหม่ทั้งหมด |
| **ต่อ MySQL ไม่ได้** | ถามรหัส MySQL ของเครื่องเขา **1 คำถาม** แล้วเติมให้เอง จากนั้นรันซ้ำ · ถ้าเขายังไม่ได้เปิด MySQL ให้บอกให้เปิดก่อน |
| **charset ของฐานข้อมูลไม่ใช่ `utf8mb4`** | **หยุดรอ** — ปล่อยไว้ภาษาไทยจะเพี้ยนตอนบันทึกโดยไม่มี error แจ้ง และกู้คืนยาก |
| อย่างอื่น | ทำตามที่สคริปต์บอก แล้วรันซ้ำ — รันซ้ำได้ไม่พัง |

รายละเอียด plugin แต่ละตัวอยู่ที่ [`skills.md`](skills.md)

#### ‼️ A0ก — ตัด repo มาตรฐานออกก่อนเริ่มงาน

`git clone` พา `.git` มาทั้งก้อน — **`origin` ยังชี้ไป repo มาตรฐาน และประวัติของมาตรฐานหลายสิบ commit ปนอยู่ในโปรเจคของลูกค้า**

ปล่อยไว้แล้วผู้ใช้จะรู้ตัว**ตอนกด push ครั้งแรก** ซึ่งเป็นตอนที่แก้ยากขึ้นแล้ว

```bash
php scripts/init-project.php --yes
```

เก็บ url เดิมลง `.standard-source` (ไว้ให้ `standard-update.php` ใช้) → เริ่ม git ใหม่ → commit แรก → เปิด pre-commit hook · **จบในคำสั่งเดียว**

> ‼️ **ถามผู้ใช้ก่อน 1 คำถาม แล้วรันให้เลย ห้ามให้เขาพิมพ์เอง**
> `setup.php` ตรวจเจอและบอกไว้ในหัวข้อ "ต้องทำเอง" แล้ว — หน้าที่ของ AI คือถามแล้วลงมือ ไม่ใช่ส่งคำสั่งให้เขาไปพิมพ์

> ‼️ **ทำไมไม่ตัดให้เองเงียบๆ ทั้งที่กฎบอกว่าห้ามให้ผู้ใช้พิมพ์คำสั่งตั้งค่าเอง**
> **repo มาตรฐานกลางกับ clone สดๆ หน้าตาเหมือนกันทุกอย่าง — ต่างกันแค่เจตนา ซึ่งเครื่องดูไม่ออก**
> เดาผิดคือลบประวัติของ repo กลางทิ้ง · คำถามนี้จึงเป็นราคาที่ถูกที่สุดที่จ่ายได้

**สคริปต์ปฏิเสธเองถ้าเงื่อนไขไม่ครบ 4 ข้อ** — มี origin · working tree สะอาด · ไม่มี commit ของตัวเอง · ยังไม่มี `STATE.md`
ครบทั้งสี่แปลว่า `.git` ก้อนนั้น**ไม่มีอะไรที่ไม่ได้อยู่บน repo มาตรฐานอยู่แล้ว** ลบแล้วกู้คืนได้ด้วยการ clone ใหม่ · ขาดข้อใดข้อหนึ่งแปลว่าอาจมีงานของใครอยู่ จึงหยุด

### A1 — หา prompt ก่อนถาม

ถามผู้ใช้ว่า **"มี prompt หรือเอกสารที่อธิบายโปรเจคนี้อยู่แล้วไหม"**

- **มี** → อ่านให้จบ สกัดคำตอบออกมาเทียบกับรายการคำถามใน [`interview.md`](interview.md)
- **ไม่มี** → ไป A2

> ‼️ **ห้ามข้ามการถามทั้งหมดเพราะเห็นว่ามี prompt แล้ว** — prompt ยาวแทบไม่เคยครบทุกช่อง ต้องไล่เทียบทีละข้อแล้วถามเฉพาะที่ขาด แล้วบอกผู้ใช้ด้วยว่า "จาก prompt ได้ข้อมูลครบแล้ว 12 ข้อ ขอถามเพิ่ม 5 ข้อ"

### A2 — ถามชุดระบบ

ใช้ชุดคำถามใน [`interview.md`](interview.md) **ถามเป็นชุด ไม่ถามทีละข้อ**

ถ้าผู้ใช้ตอบข้อไหนไม่ได้ ให้**เสนอค่าเริ่มต้นที่แนะนำแล้วให้เลือก** ห้ามข้ามไปเงียบๆ แล้วเดาเอง

### A3 — วิเคราะห์แล้วเสนอ ← ขั้นที่ทำให้ workflow นี้ต่างจากการรับคำสั่งเฉยๆ

หน้าที่ตรงนี้คือ **ทำตัวเป็น dev ที่ทักลูกค้า ไม่ใช่พนักงานรับออเดอร์**

อ่านสิ่งที่ผู้ใช้ตอบมาแล้วมองหา

| มองหาอะไร | ตัวอย่างสมมติ — ระบบบัตรคิว (ประกอบความเข้าใจเท่านั้น) |
|---|---|
| **ลูปที่ไม่ครบ** | มีออกบัตร มีเรียกคิว แต่ไม่มีทางจัดการเมื่อลูกค้าไม่มา → เสนอระบบข้ามคิว |
| **สิ่งที่ผู้ใช้จริงจะขอในสัปดาห์แรก** | หน้าจอแสดงคิวมีแต่ตัวเลข → เสนอพื้นที่โฆษณา/ประชาสัมพันธ์ |
| **ช่องทางที่ขาด** | รับบัตรได้เฉพาะหน้าร้าน → เสนอจองคิวออนไลน์ |
| **สิ่งที่ต้องมีเพื่อดูแลระบบได้** | ไม่มีรายงานย้อนหลัง → เสนอรายงานสถิติคิวรายวัน |
| **กรณีที่จะพังตอนใช้จริง** | ไฟดับ/รีเฟรชหน้าจอแล้วคิวหาย → เสนอวิธีกู้สถานะ |

เสนอเป็น**รายการที่เลือกได้** พร้อมบอกว่าแต่ละข้อ**คุ้มค่าทำตอนนี้หรือทำทีหลังได้** — ห้ามยัดทุกข้อเข้าไปเอง

### A4 — ถามชุดดีไซน์

ใช้ชุดคำถามดีไซน์ 16 ข้อใน [`interview.md`](interview.md) — โลโก้ · สีแบรนด์ · ฟอนต์ · คู่ตรงข้าม 4 คู่ · **mood · visual weight · brand feeling · รูปภาพมาจากไหน · จะใช้ภาพที่สร้างขึ้นไหม · reference** · อุปกรณ์หลัก · รูปแบบเมนู · โหมดเริ่มต้น · ความคุ้นเคยของผู้ใช้ · ระดับความคาดหวัง · **จะใช้ Claude Design ไหม**

> ‼️ **ข้อ 14 ตัดสินลำดับงานทั้งช่วง B** ถามให้ได้คำตอบตรงนี้ ไม่ใช่ไปถามตอนช่วง B ซึ่งอาจทำ `DESIGN.md` ทิ้งไปแล้ว

> ‼️ **ตอบข้อ 7ข ว่าจะใช้ภาพที่สร้างขึ้น → ตรวจทันทีว่าตัวเองมีเครื่องมือสร้างภาพหรือยัง**
> ไม่มี → **เตือนผู้ใช้ตรงนั้นเลยว่าต้องต่อ Higgsfield MCP** พร้อมบอกว่าถ้าไม่ต่อจะได้อะไรแทน ([`skills.md`](skills.md) ข้อ 4ก)
>
> **สคริปต์ตรวจแทนไม่ได้** — `setup.php` อ่านตัวเชื่อมของบัญชีไม่ได้เหมือนที่อ่าน `enabledPlugins` ได้
> **คนที่รู้คือ AI เอง เพราะเห็นเครื่องมือที่ตัวเองมีในมือ** เงียบไว้แล้วไปเจอตอนช่วง C คือการรื้อ layout ทั้งหน้า

### ผลลัพธ์ของช่วง A

#### ‼️ B3 — token ที่โครงใช้ แม้หน้าในสโคปจะไม่ใช้

**ผู้ออกแบบเห็นแค่หน้าที่อยู่ในสเปค แต่ `DESIGN.md` คุมทั้งระบบ รวมหน้าของโครงที่เขาไม่เคยเห็น** — ล็อกอิน แจ้งปัญหา คู่มือ จัดการผู้ใช้

**ค่าที่เขาตอบว่า "ไม่ต้องใช้" ไม่ได้แปลว่าระบบไม่ใช้** · ต้องเขียนกำกับ token กลุ่มนี้ในแบบฟอร์มว่า **ห้ามตอบ `0` ห้ามเว้นว่าง ห้ามตอบว่าไม่เกี่ยว**

| token | โครงใช้ทำอะไร | อาการถ้าปล่อยให้ตอบ `0` |
|---|---|---|
| `layout.formWidth` · `layout.fieldMinWidth` | ความกว้างฟอร์มและช่องกรอกทุกหน้าของโครง | ฟอร์มล็อกอินและฟอร์มแจ้งปัญหายุบเหลือศูนย์ |
| `layout.sidebarWidth` · `sidebarCollapsed` | ต่อให้โปรเจคเลือก `nav: header` `app.css` ก็ยังอ้างถึง | ค่าหาย CSS เพี้ยน |
| **`color.border.strong`** | **เส้นขอบของ control** ที่ WCAG 1.4.11 บังคับ **3:1** | ‼️ ดีไซน์เว็บโชว์มักถือว่าเส้นขอบทุกเส้นเป็นของตกแต่ง แล้วให้ค่าจางมาก — **ตกเกณฑ์ทันทีที่นำเข้า** |
| `component.table.*` · `badge.*` | ตารางและ badge ของหน้าหลังบ้าน | รูปทรงกลับไปเป็นของโครงเปล่า |

> ‼️ **`border.strong` เจอมาแล้วจริง** — โปรเจคที่ไม่มีฟอร์มสักหน้าได้ค่าที่ตก 3:1 ทั้ง 6 คู่
> `check-contrast.php` จับได้ตอนนำเข้า ซึ่งคือเหตุผลที่ B7 ต้องรันมันทุกครั้ง **ไม่ใช่รันเฉพาะตอนสงสัย**

#### ‼️ B3 — ต้องขอบล็อก YAML กลับมาเป็นข้อความ ไม่ใช่แค่ `:root`

`:root` ที่ได้กลับมา**ใช้ชื่อ custom property ของผู้ออกแบบเอง** ไม่ใช่ชื่อที่ `design-sync.php` ต้องการ — เจอมาแล้วเป็น `--fs-base` แทน `--text-base` · `--sp-4` แทน `--space-4` · `--table-row-h` แทน `--table-row-height`

**ต้องขอสองอย่างคู่กัน** — `:root` เอาไว้ดูของจริงในเบราว์เซอร์ · **บล็อก YAML ตามแบบฟอร์มเป๊ะๆ เป็นข้อความในหน้า** เอาไว้คัดลอกเข้า `DESIGN.md`

ขอแค่ `:root` อย่างเดียวแปลว่าต้องมานั่งเดาว่าชื่อไหนคู่กับชื่อไหน ซึ่งเดาผิดแล้ว**ค่าหายไปเงียบๆ**

#### ‼️ B3 — ให้เขาสร้างรูปเอง อย่าส่งกล่องเปล่าไปให้ออกแบบ

**Claude Design เรียก MCP สร้างรูปได้** — ต้องบอกไว้ใน brief ว่าเขาทำได้ ไม่งั้นเขาจะวาง `<image-slot>` เปล่าไว้ให้เหมือนเดิม

> ‼️ **ทำไมต้องให้เขาสร้าง แทนที่จะสร้างส่งไปให้**
> **ผู้ออกแบบที่สร้างรูปเองจะสร้างรูปที่เข้ากับ layout ที่กำลังปั้นอยู่** — ขวด ของประกอบ และพาดหัวประกอบกันเป็นภาพเดียว
> ส่งรูปสำเร็จไปให้ เขาได้แค่ "รูปที่ต้องหาที่วาง" ซึ่งจบลงที่ภาพในกรอบสี่เหลี่ยมข้างข้อความเสมอ
>
> วัดจริงตอนเทียบกับ landing page ที่ทำด้วยเครื่องมือเฉพาะทาง — ฝั่งที่มีรูปตอนออกแบบได้ภาพเต็มจอ ฝั่งที่ได้กล่องเปล่าได้ภาพกิน 39% ในคอลัมน์เรียบร้อย

**หมวดรูปภาพใน brief ต้องมี 4 อย่าง**

| ต้องมี | ทำไม |
|---|---|
| **บอกว่าเขาสร้างรูปเองได้** และให้สร้างเท่าที่ดีไซน์ต้องการจริง | ไม่บอกก็ได้กล่องเปล่า |
| ‼️ **ระบุโมเดลที่ผู้ใช้เลือกไว้** | ไม่ระบุ เขาจะเลือกเอง แล้วได้ภาพคนละบุคลิกกับที่ผู้ใช้ตั้งใจ ([`design.md`](design.md) 7ก.3ก) |
| **สัดส่วนของแต่ละที่** ตามที่สเปคหน้ากำหนดไว้ | รูปผิดสัดส่วนแล้วต้องรื้อ layout ทั้งหน้า |
| ‼️ **ข้อห้ามเรื่องฉลากและตัวหนังสือ** | ดูกล่องข้างล่าง — ข้อนี้จ่ายค่าเรียนรู้ไปแล้ว |
| ‼️ **ขอ manifest ของ URL เป็นข้อความในหน้า** | ไฟล์ที่ได้กลับมาเป็น bundle ที่ `grep` ไม่ได้ (B5) · ไม่ขอเป็นรายการแยก จะต้องไล่งัด URL ออกจาก DOM ทีละอัน |

> ‼️ **ต้องส่งข้อนี้ไปด้วยเสมอ ไม่งั้นเขาจะเจอปัญหาเดิมแล้วเราต้องมาแก้ทีหลัง**
>
> **สั่งว่า `no text, no labels` ไม่ได้ผล** — ทดสอบแล้วได้ฉลากมั่วกลับมา **4 จาก 5 ใบ** (`Jasmine Jea` · `Taie Pu—KA!` · `CHRNETI`)
> เพราะขวดสินค้าในข้อมูลที่โมเดลเรียนมามีฉลากทุกใบ
>
> **ทางแก้ที่ทดสอบแล้วได้ผล** — ครอปมาโครให้เห็นเฉพาะส่วนที่ไม่มีฉลาก · ถ่ายมุมที่ฉลากไม่อยู่ในเฟรม · หรือถ่ายของที่ไม่มีฉลากโดยธรรมชาติ (วัตถุดิบ ดอกไม้ บรรยากาศ)

**และภาพที่เป็นของจริงของลูกค้ายังห้ามสร้างเหมือนเดิม** — ตัวสินค้า อาคาร ทีมงาน ต้องมาจากลูกค้า ตาม [`design.md`](design.md) 7ก.1 · brief ต้องระบุว่าช่องไหนเป็นภาพจริงที่จะใส่ทีหลัง ช่องไหนสร้างได้


#### ‼️ B3 — ต้องขอ motion ไปด้วย ไม่งั้นจะได้ดีไซน์ที่นิ่งสนิท

**เจอมาแล้วจริง — ดีไซน์ที่ได้กลับมาไม่มี motion เลยสักตัว** เพราะ brief ไม่เคยขอ

แบบฟอร์ม token ขอแค่ `motion.duration` กับ `motion.easing` ซึ่งเป็น **ตัวเลขสองชุด** ไม่ใช่การออกแบบ
ได้ตัวเลขกลับมาแล้วก็ยังไม่มีใครรู้ว่า *อะไรเคลื่อน ตอนไหน และเคลื่อนยังไง* — แล้ว C3 ก็ไปเดาเอาเองทีหลัง ซึ่งเป็นตอนที่ผู้ออกแบบไม่อยู่แล้ว

> ‼️ **motion เป็นส่วนหนึ่งของบุคลิก ไม่ใช่ของแต่งท้ายงาน**
> ระบบเดียวกันที่ของเลื่อนขึ้นช้าๆ กับที่ของเด้งเข้ามาเร็ว **ให้ความรู้สึกคนละแบรนด์** ทั้งที่สีและฟอนต์เหมือนกันทุกตัว
> ปล่อยให้ตัดสินตอน C3 แปลว่ายกการตัดสินใจเรื่องบุคลิกไปให้คนที่กำลังไล่ checklist อยู่

**ขอ 4 อย่าง**

| ต้องมี | ทำไม |
|---|---|
| **บุคลิกของ motion เป็นคำ** — เช่น "คมและเร็ว" · "นุ่มและลื่น" · "แน่นอนไม่หวือหวา" | เป็นสิ่งที่ C3 เอาไปตัดสินกรณีที่สเปคไม่ครอบคลุมได้ |
| **รายการว่าอะไรเคลื่อนบ้าง** — ส่วนเปิด · การ์ดตอนชี้ · ปุ่มตอนกด · เมนู · toast/modal/dropdown เข้าและออก | ถ้าไม่ระบุ เขาจะทำเฉพาะที่นึกออก |
| **ค่า `motion.duration` และ `easing` ที่มาจากบุคลิกนั้นจริง** | ไม่ใช่ค่ากลางๆ ที่กรอกให้ครบช่อง |
| ‼️ **ตัวอย่างที่เคลื่อนไหวได้จริงในไฟล์ที่ส่งกลับมา** | **อ่านจากตัวเลขแล้วจินตนาการไม่ออก** ต้องเห็นของจริงถึงจะรู้ว่าใช่หรือไม่ใช่ |

**ข้อจำกัดที่ต้องส่งไปด้วย** — เคลื่อนเฉพาะ `transform` กับ `opacity` · ต้องเคารพ `prefers-reduced-motion` · **ห้ามใส่ motion กับสิ่งที่ผู้ใช้กดซ้ำทั้งวัน** · `animation` ที่แตะ `transform` ต้องใช้ `fill-mode: backwards` ([`design.md`](design.md) ข้อ 11)

> ‼️ **ข้อสุดท้ายต้องส่งไปทุกครั้ง** — `fill-mode: both` ทำให้ `transform` ค้างเป็น identity matrix ซึ่งยังสร้าง stacking context แล้ว **dropdown ทุกตัวในระบบถูกทับ**
> เป็นบั๊กที่มองไม่เห็นจนกว่าจะมี dropdown ตัวแรก ซึ่งอาจเป็นอีกหลาย phase ถัดไป · ไม่บอกไว้ เขามีโอกาสเขียนแบบนั้นมาให้สูงมากเพราะเป็นค่าที่คนใช้กันทั่วไป

#### B4 — บอกผู้ใช้เป็นขั้นตอน

**แนบไฟล์เดียวคือ `design-brief.md`** · **ตั้ง Design system เป็น `None`** · ไม่เลือก template · ขอกลับมาเป็น HTML ไฟล์เดียวที่มี `:root` เติมครบทั้งสองโหมด + **บล็อก YAML ตามแบบฟอร์มเป็นข้อความ** + **manifest ของ URL รูปเป็นข้อความ** + **motion ที่เคลื่อนไหวได้จริง** + หน้ารวม component ทุกสถานะ + `<section>` ต่อหน้าที่ `id` ตรงกับที่ระบุไว้ในสเปค + ปุ่มสลับโหมดที่กดได้จริง

> ‼️ **ต้องเตือนผู้ใช้ให้ต่อ Higgsfield MCP กับฝั่ง Claude Design ก่อน** ไม่งั้นเขาจะวางกล่องเปล่ามาให้เหมือนเดิม
> **ต่อไว้ฝั่ง Claude Code ไม่นับ** — คนละฝั่งกัน และเป็นจุดที่เข้าใจผิดง่ายที่สุดเพราะชื่อเครื่องมือเดียวกัน
> และเตือนว่าการสร้างรูป**ใช้เครดิตของบัญชีเขา** — บอกจำนวนรูปที่ brief ขอไว้ให้ชัด เพื่อให้เขาประเมินได้ก่อนกดเริ่ม
>
> **ผู้ใช้ไม่ต่อก็เดินต่อได้** — brief ยังส่งได้ตามปกติ แต่จะได้ `<image-slot>` เปล่ากลับมา แล้วต้องเดินทางสำรองตาม [`design.md`](design.md) 7ก.3ค

#### ‼️ B5 — ไฟล์ที่ได้กลับมาอ่านด้วย `grep` ไม่ได้

ไฟล์จาก Claude Design เป็น **bundle ที่แตกตัวเองด้วย JavaScript** เนื้อหาจริงไม่ได้อยู่ในไฟล์เป็นข้อความ

`grep '<section id'` จะได้ **0 บรรทัด ทั้งที่มีจริงครบทุกหน้า** — และนั่นคือกับดัก เพราะมันดูเหมือนผู้ออกแบบไม่ได้ทำตามสเปค

**ต้องเปิดในเบราว์เซอร์แล้วอ่าน DOM เท่านั้น** ทุกการตรวจในขั้นนี้จึงต้องทำผ่านเบราว์เซอร์ ไม่ใช่ผ่านการอ่านไฟล์

```
php -S 127.0.0.1:8140 -t project/design
```

> ‼️ **และวัดค่าต้องเก็บ snapshot ก่อนสลับโหมด**
> `getComputedStyle()` คืน object ที่มีชีวิต — อ่านค่าก่อนสลับ แล้วอ่านซ้ำหลังสลับโดยใช้ตัวแปรเดิม จะได้ค่าเท่ากันเสมอ แล้วสรุปผิดว่าโหมดมืดไม่ทำงาน

### ทุกเส้นทาง

#### ‼️ ภาพแบบที่ผู้ใช้ส่งมา — บันทึกทันที ไม่ว่าเส้นทางไหน ไม่ว่าช่วงไหน

ผู้ใช้ส่งภาพหรือ path ของโฟลเดอร์ภาพมาเมื่อไหร่ **ในคำตอบเดียวกันต้อง**

2. ลงแถวในตาราง `## แบบของแต่ละหน้า` ของ `DESIGN.md`

- แยก **"ต้องอนุมัติ"** ออกจาก **"คำถามที่ต้องตอบ"**
- ตอบไม่ครบรายการที่ต้องอนุมัติ = **ยังไม่อนุมัติ** ห้ามเดินต่อ

รายงานต้องมี: จำนวน phase · จำนวนหน้าที่ออกแบบไว้ · ทิศทางดีไซน์ที่เลือกและเหตุผล · ข้อสงสัยที่ค้างใน `QUESTIONS.md` · **สิ่งที่มาตรฐานไม่ครอบคลุมรอบนี้จาก `FEEDBACK.md`**

#### ‼️ B6 — ทำเอกสารสรุปเป็น Artifact ก่อนเปิดประตู (ทั้งสองเส้นทาง)

**ของที่ผู้ใช้ต้องส่งต่อให้คนอื่นดู ต้องอยู่ในรูปที่ส่งต่อได้** — `project/*.md` เปิดได้เฉพาะคนที่ clone repo แล้ว ซึ่งลูกค้าและคนในทีมที่ไม่ใช่ dev ไม่มีทางเปิด

> ‼️ **นี่คือข้อ 10.1 ในอีกรูปหนึ่ง** — เรามีกฎแล้วว่า "ของที่ต้องอนุมัติ ต้องถูกเปิดให้เห็น ไม่ใช่ถูกอ้างถึง"
> แต่กฎนั้นครอบแค่ **คนที่นั่งอยู่ตรงหน้า** · พอผู้ใช้ต้องเอาไปให้หัวหน้าหรือลูกค้าตัดสิน เขาต้องมานั่งเล่าเองทั้งหมด
> ซึ่งแปลว่าสิ่งที่คนตัดสินใจได้เห็น **ไม่ใช่สิ่งที่เราทำ** แต่เป็นสิ่งที่ผู้ใช้จำได้

**หนึ่งหน้า รวมทุกอย่างที่ต้องใช้ตัดสินใจ** — คนอ่านไม่ต้องเปิดอย่างอื่นประกอบเลย

| ต้องมี | เอามาจาก |
|---|---|
| ระบบนี้ทำอะไร ใครใช้ ขอบเขตแค่ไหน | `SCOPE.md` — **รวมหัวข้อ "ไม่อยู่ในขอบเขต"** ซึ่งเป็นส่วนที่ป้องกันการเข้าใจผิดได้มากที่สุด |
| **แผนงานทุก phase** เรียงตามลำดับ พร้อมสิ่งที่ทำได้จริงในแต่ละ phase | `PLAN.md` |
| **จานสีจริง** — แสดงเป็นช่องสีที่เห็นด้วยตา พร้อมรหัสสี **ครบทั้งโหมดสว่างและมืด** | `DESIGN.md` |
| **ตัวอักษร** — ชื่อฟอนต์ + ตัวอย่างจริงทุกขั้นของสเกล | `DESIGN.md` |
| **ความมนของมุม · เงา · ระยะห่าง · ความหนาแน่น** — แสดงเป็นตัวอย่างที่เห็น ไม่ใช่ตัวเลขเปล่า | `DESIGN.md` |

> ห้ามมีชื่อไฟล์หรือ path ของ repo · คนอ่านไม่ได้ clone อะไรทั้งนั้น
>
> ‼️ **ห้ามเป็นแค่ข้อความสรุป** — เรื่องสี ฟอนต์ และ motion ต้อง**เห็นของจริง** ไม่ใช่อ่านชื่อ
> ลูกค้าที่อ่านว่า "สีหลัก `#1F4FD8`" ตัดสินใจไม่ได้ · ลูกค้าที่เห็นช่องสีน้ำเงินตัดสินใจได้ทันที

**เปิด Artifact ให้ผู้ใช้ดูพร้อมรายงานที่ประตู** แล้วบอกว่าเขาส่งลิงก์นี้ต่อให้ใครดูก็ได้ — จบประตูแล้วถ้ามีการแก้ **ต้องอัปเดต Artifact เดิม ไม่ใช่สร้างใหม่** เพราะลิงก์อาจถูกส่งต่อไปแล้ว

## 8. ช่วง E — ส่งขึ้น server ทดสอบ

1. commit งานที่ค้างให้หมด **บน branch ไม่ใช่ `main`**
2. `fetch`/`pull` เช็ค conflict
3. เปิด PR แล้วแจ้งผู้ใช้ — **การ merge เข้า `main` ผู้ใช้ทำเอง**
4. merge แล้ว CI จะรัน `check.php` → ผ่านแล้วอัปไฟล์ผ่าน FTP → ยิง route migrate อัตโนมัติ
5. รายงานผลว่าขึ้นสำเร็จไหม

**ขึ้น production ผู้ใช้ทำเอง ไม่อยู่ในขอบเขตของ workflow นี้**

**ข้อเสนอ:** `components.md` ต้องระบุพฤติกรรมเมื่อปุ่มเกิน 2 ตัว
**ตรวจด้วยเครื่องได้ไหม:** ได้ — วัด `scrollWidth` ของการ์ดที่ 375px เทียบ `clientWidth`

**เมื่อไหร่ต้องเขียน — 6 สัญญาณ**

| สัญญาณ | ทำไมถึงนับ |
|---|---|
| ‼️ **ผู้ใช้ทักว่าทำผิดหรือไม่ถูกใจ** | **สัญญาณที่แรงที่สุดและเสียง่ายที่สุด** — บันทึกทันทีที่เขาทัก ไม่ใช่หลังแก้เสร็จ |

**กฎของไฟล์นี้**

- ‼️ **บันทึกตอนที่มันเกิด ไม่ใช่ตอนจบโปรเจค** — ย้อนเขียนตอนจบจะได้แต่ข้อที่จำได้ ซึ่งคือข้อที่เจ็บที่สุดไม่กี่ข้อ · ส่วนข้อเล็กที่เกิดบ่อยกว่าและแก้ง่ายกว่าหายหมด

- **ทุกข้อต้องตอบว่า "ตรวจด้วยเครื่องได้ไหม"** — ประวัติของมาตรฐานนี้พิสูจน์ซ้ำแล้วว่า **กฎที่ไม่มี `check.php` รองรับจะถูกข้ามเสมอ** · ข้อเสนอที่จบแค่ "เขียนกฎเพิ่ม" คือข้อเสนอที่ยังทำไม่เสร็จ
- **เขียนให้คนที่ไม่ได้อยู่ในบทสนทนานี้อ่านรู้เรื่อง** — คนที่แก้ repo มาตรฐานอาจเป็นคนละคน คนละเดือน

> ‼️ **ข้อจำกัดที่ต้องรู้: นี่คือ AI บันทึกความผิดของตัวเอง ซึ่งอ่อนโดยธรรมชาติ**
> สิ่งที่มันไม่รู้ว่าตัวเองทำผิด มันก็บันทึกไม่ได้ · **สัญญาณที่เชื่อถือได้ที่สุดจึงเป็นข้อแรก คือตอนที่ผู้ใช้ทัก** เพราะมาจากข้างนอก

## 10. กฎของประตู — ข้อที่ละเมิดแล้วแพงที่สุด

> **หลักเดียวที่ต้องจำ: ถ้าผู้ใช้ต้องหาวิธีเปิดของที่เราทำเอง แปลว่าเรายังไม่ได้ส่งของ**

เกิดขึ้นจริงแล้วและนี่คือราคาที่จ่าย — ที่ประตู B ส่ง path ของไฟล์ wireframe ไปให้ พร้อมถามคำถามอื่นอีก 2 ข้อ
ผู้ใช้ตอบแค่ 2 คำถามนั้น **ไม่เอ่ยถึง wireframe เลย** แล้ว AI ตีความว่าได้อนุมัติ จึงทำทั้ง phase บนดีไซน์ที่ไม่มีใครเคยเห็น
จบ phase ผู้ใช้เปิดดูแล้วบอกว่าใช้ไม่ได้ · ต้องรื้อทำใหม่ **สามรอบ**
ถ้าเขาเห็น wireframe ตั้งแต่ประตู B การแก้คือแก้ไฟล์ HTML ขาวดำ ไม่ใช่รื้อโค้ดที่ทำเสร็จแล้ว

### 10.1 ของที่ต้องอนุมัติ ต้องถูก "เปิดให้เห็น" ไม่ใช่ "ถูกอ้างถึง"

การส่ง path เป็นข้อความคือการบอกพิกัดแล้วโยนภาระการเปิดให้ผู้ใช้
ไฟล์ HTML ในเครื่องต้องเปิดจาก file explorer หรือลาก path ไปวางในเบราว์เซอร์ ซึ่ง **ไม่ใช่สิ่งที่คนที่ไม่ใช่ dev รู้ว่าต้องทำ**

| ของแบบไหน | ต้องทำยังไง |
|---|---|
| หน้าเว็บในเครื่อง | **เปิดในเบราว์เซอร์ให้เลย** (`Start-Process` · `open` · `xdg-open`) |
| หน้าบน dev server | เปิด URL ให้ |
| ภาพ | **แนบภาพในรายงาน** ไม่ใช่บอกว่าภาพอยู่ที่ไหน |
| เอกสาร | **สรุปสาระที่ต้องตัดสินใจลงในรายงาน** ไม่ใช่บอกให้ไปอ่านเอง |

> AI มีเครื่องมือเปิดเบราว์เซอร์อยู่ในมือตลอดเวลาและใช้มันถ่ายภาพให้ตัวเองดูหลายสิบครั้ง
> **ถ้าใช้ดูเองได้ ก็ต้องใช้เปิดให้ผู้ใช้ดูได้**

### 10.2 แยก "สิ่งที่ต้องอนุมัติ" ออกจาก "คำถามที่ต้องตอบ"

รายงานที่ประตูต้องมีสองหัวข้อนี้แยกกันเสมอ และ**สิ่งที่ต้องอนุมัติต้องตอบทีละข้อ**

```
**ต้องอนุมัติ** (ตอบทีละข้อ)
1. wireframe 41 หน้า → เปิดให้แล้วที่ ... → "โอเค" หรือ "ขอแก้ ..."
2. ทิศทางดีไซน์ (สี ฟอนต์ อารมณ์) → "โอเค" หรือ "ขอแก้ ..."

**คำถามที่ต้องตอบ**
1. ...
```

### 10.3 การเงียบไม่ใช่การอนุมัติ

**ถ้าคำตอบของผู้ใช้ไม่ครอบคลุมรายการที่ต้องอนุมัติ ห้ามเดินต่อ — ต้องถามย้ำเฉพาะรายการที่ขาด**

ผู้ใช้ตอบเรื่องฐานข้อมูลกับ push ไม่ได้แปลว่าเขาอนุมัติ wireframe
คำว่า "ทำเลย" ที่ตอบมาหลังคำถามอื่น **ไม่ใช่การอนุมัติดีไซน์** — การอนุมัติดีไซน์ด้วยคำกำกวมคือความกำกวมที่แพงที่สุดในทั้ง flow

### 10.4 เงื่อนไขเพิ่มก่อนออกจากช่วง B

**เส้นทาง ก — ประตู B**

- [ ] **เปิด wireframe ในเบราว์เซอร์ให้ผู้ใช้ดูแล้วจริง** ไม่ใช่ส่ง path
- [ ] **ผู้ใช้ตอบรับ wireframe เป็นข้อของมันเอง** ไม่ใช่ตอบข้อความอื่นในรายงานเดียวกัน

**เส้นทาง ข — ผ่านทั้งสองบาน**

- [ ] **ประตู B-1** สรุปสเปคหน้าลงในรายงานให้อ่านได้ทันที (บานนี้ไม่มีอะไรให้เปิด) และ**ผู้ใช้ตอบรับรายการหน้าเป็นข้อของมันเอง** — รวมหมวด **"หน้าที่จงใจไม่มี"**
- [ ] **ประตู B-2** เสิร์ฟไฟล์ดีไซน์ที่ได้กลับมาแล้ว**เปิดในเบราว์เซอร์ให้ผู้ใช้ดูจริง** ไม่ใช่ส่ง path และ**ผู้ใช้ตอบรับดีไซน์เป็นข้อของมันเอง**

> ‼️ **ทั้งสองบานอยู่ใต้กฎข้อ 10.3 เท่ากัน** — ผ่านบาน B-1 ไม่ได้แปลว่าผ่าน B-2
> และการที่ผู้ใช้ชมว่าดีไซน์สวยที่บาน B-2 **ไม่ย้อนกลับไปอนุมัติรายการหน้าที่บาน B-1** ถ้าเขายังไม่เคยตอบข้อนั้น

**เส้นทาง ค — ประตู B**

- [ ] ภาพแบบอยู่ใน `project/design/refs/` แล้ว และ**ทุกภาพจับคู่กับหน้าในตาราง** (`design/reference-compared` เตือนภาพที่ไม่มีคู่)
- [ ] **แสดงสีที่วัดได้เป็นช่องสีคู่กับภาพแบบ** ให้ผู้ใช้ตอบรับเป็นข้อของมันเอง — ไม่ใช่ส่งแค่รหัสสี
- [ ] **ผู้ใช้ตอบรับรายการจุดที่ขัดทีละข้อ** — ข้อที่แบบต้องแพ้กฎแข็ง ผู้ใช้ต้องรู้ก่อนเห็นหน้าจริง

## 11. กฎการหยุดและไม่หยุด

**ต้องหยุดเสมอ**

- ที่ประตู A · B · จบทุก phase (ยกเว้นโหมดเร็ว) · D
- ก่อนทำสิ่งที่ย้อนกลับยาก: ลบไฟล์ · `force push` · `reset` git · merge เข้า `main`
- skill กลุ่มบังคับไม่ครบ
- **ก่อนสร้างหรือแก้หน้าที่มีภาพแบบ ถ้าแบบขัดกับกฎ** — รายงานจุดที่ขัดพร้อมวิธีจัดการก่อน ([`design.md`](design.md) ข้อ 5.0) · ใช้ในโหมดเร็วและงานเล็กด้วย
- งานที่ผู้ใช้ขอ**ขัดกับ `CLAUDE.md` หรือ `standard/`** — แจ้งก่อน ห้ามเดาแล้วทำ

**ห้ามหยุด — ให้จดแล้วทำต่อ**

- เจอเรื่องกำกวมระหว่างช่วง B หรือ C → `QUESTIONS.md`
- เจอสิ่งที่น่าจะดีกว่าแต่ไม่อยู่ใน `SCOPE.md` → `QUESTIONS.md` ห้ามทำเพิ่มเอง
- ทำ phase หนึ่งแล้วเจอว่าแบบที่อนุมัติแล้วของอีก phase น่าจะต้องแก้ → จดไว้ ไปแก้ตอนถึง phase นั้น ไม่ต้องรื้อทั้งชุด

**`check.php` fail** → แก้ที่โค้ด **ห้ามแก้ที่สคริปต์ตรวจให้ผ่าน** ถ้าเชื่อว่ากฎในสคริปต์ผิดจริง ให้แจ้งผู้ใช้แล้วแก้ที่ repo มาตรฐาน ไม่ใช่แก้ในโปรเจค

## 13. งานเล็ก — เลนที่ไม่ต้องเดินทั้ง flow

> ‼️ **ก่อน 3.15.0 มาตรฐานนี้ไม่มีแนวคิดเรื่องขนาดของงานเลย** — ทุกคำสั่งถูกถือเป็นงานระดับ phase
> ทีมสั่งเปลี่ยนคำบนปุ่มคำเดียว แล้ว AI ไล่นิยามเสร็จ 10 ข้อ · ไล่ checklist ของทั้ง phase ใหม่ ([`testing.md`](testing.md) ข้อ 6) · ถ่ายภาพทุกหน้าที่มีปุ่มนั้น 2 โหมด × 2 ความกว้าง
> ไม่มีกฎข้อไหนผิด แต่ไม่มีข้อไหนบอกว่า **ใช้กับงานขนาดไหน** · กฎที่ไม่บอกขอบเขตถูกใช้กับทุกอย่าง

### เข้าเกณฑ์งานเล็กเมื่อ — ต้องครบทุกข้อ

| ต้องไม่ | เพราะ |
|---|---|
| เพิ่มหรือแก้ route · migration · ตาราง | เปลี่ยนโครงของระบบ |
| แตะ Controller · Service · Model · Middleware · `core/` | เปลี่ยนพฤติกรรมหรือสิทธิ์ |
| แตะ `partials/` · `layouts/` · `app.js` | ของกลาง — กระทบหน้าที่ไม่ได้แตะ |
| แก้ `project/DESIGN.md` | เปลี่ยนหน้าตาทั้งระบบ ต้องตรวจ contrast และดูทุกหน้า |
| แตะเรื่องใน [`security.md`](security.md) | auth · input · upload · query ไม่มีงานเล็ก |
| แตะเกิน 5 ไฟล์ | ไม่นับไฟล์ภาษา บทความคู่มือ และเอกสารใน `project/` |

ตัวอย่างที่เข้า: แก้คำบนปุ่ม · แก้คำแปล · แก้คำผิดในคู่มือ · ปรับการจัดวางในหน้าเดียวด้วย class ที่มีอยู่แล้ว · แก้บั๊กการแสดงผลที่อยู่ใน view ไฟล์เดียว

**`php scripts/check.php --changed` บอกให้เองทุกครั้งที่รัน** — บรรทัด `ขนาดงาน:` ตัดสินจากไฟล์ที่แตะจริง ไม่ใช่จากที่ตั้งใจ

### งานเล็กต้องทำแค่นี้

1. **บรรทัดแรกของคำตอบประกาศว่าเป็นงานเล็ก** พร้อมเหตุผลสั้นๆ — ผู้ใช้ค้านได้ทันที
2. ทำบน branch เหมือนเดิม — กฎ git ไม่มีข้อยกเว้น
3. `php scripts/check.php --changed` ผ่าน
4. **เปิดหน้าที่กระทบในเบราว์เซอร์ 1 ครั้ง** — ดูว่าข้อความที่ยาวขึ้นล้นหรือไม่ · แก้ข้อความให้ดูทุกภาษาที่แก้ · **หน้าที่มีภาพแบบระดับ "ตรงแบบ" ให้วางเทียบกับภาพแบบด้วย** ([`testing.md`](testing.md) ข้อ 4ข)
5. ข้อความที่แก้อยู่ในบทความคู่มือด้วย → แก้คู่มือในงานเดียวกัน ([`features/manual.md`](features/manual.md) ข้อ 7)
6. commit แล้วรายงาน 2-3 บรรทัด: แก้อะไร · ดูที่ไหน · `check.php` ผ่าน

**ไม่ต้องทำ:** ไล่ checklist ทั้ง phase · ภาพ 2 โหมด × 2 ความกว้างทุกหน้า · ทดสอบ role · เปิด `audit_logs` · ประตู · อัปเดต `PLAN.md`
อัปเดต `STATE.md` เฉพาะเมื่องานเล็กเกิดระหว่าง phase ที่ยังไม่จบ — บรรทัดเดียวใต้ "ตัดสินใจอะไรไปแล้ว"

> ‼️ **เกินเกณฑ์กลางทาง ต้องหยุดแล้วบอก** — เช่นจะแก้คำแล้วพบว่าข้อความถูกประกอบอยู่ใน Service
> ห้ามทำต่อในเลนงานเล็กเพราะเริ่มไปแล้ว · บอกผู้ใช้ว่าย้ายไปเลนปกติเพราะอะไร แล้วเดินตามนิยามเสร็จใน `CLAUDE.md` ข้อ 4

> ‼️ **งานเล็กไม่ใช่ข้อยกเว้นของกฎเหล็ก** — ข้อความยังต้องผ่าน `__()` · ไฟล์ภาษาต้องครบกัน · คำที่ขอขัดกับ [`components.md`](components.md) (เช่นปุ่มที่เขียนว่า "ตกลง" หรือ "OK" แทนคำกริยาที่บอกว่าจะเกิดอะไร) ยังต้องแจ้งก่อนตามเดิม
> สิ่งที่ลดคือ **ปริมาณการพิสูจน์** ไม่ใช่มาตรฐานของผลงาน

### ตรวจเฉพาะที่เปลี่ยน — ใช้กับงานทุกขนาดระหว่างทำ

`--changed` ตรวจไฟล์ที่เปลี่ยนตั้งแต่แตกจาก `main` บวกการตรวจที่ต้องเทียบข้ามไฟล์ทั้งหมด (ไฟล์ภาษาครบกัน · `app.css` ตรงกับ `DESIGN.md` · ครบลูป · ของมาตรฐานไม่ถูกแก้ ฯลฯ)
**แตะของกลาง (`core/` · `partials/` · `layouts/` · `config/` · CSS/JS · `DESIGN.md`) เมื่อไหร่ ยกระดับเป็นตรวจเต็มเอง** — เพราะของกลางพังหน้าที่ไม่ได้แตะได้

| จังหวะ | ใช้ |
|---|---|
| ระหว่างทำ · ก่อน commit (hook เรียกให้เอง) | `--changed` |
| **ปิด phase (C4) · ประตู D · ก่อนเปิด PR · CI** | **ตรวจเต็ม** `php scripts/check.php` |

> ‼️ **ทำไมไม่ตัดตาม phase** — "phase 1 ตรวจแล้ว" ใช้ไม่ได้กับสถาปัตยกรรมที่ทุกอย่างเป็นของกลาง
> phase 2 แก้ `partials/field.php` ทีเดียวพังตารางของ phase 1 ได้ และเคยเกิดจริง (บั๊ก `$rows` ใน 3.2.0) · หน่วยที่ถูกคือไฟล์ที่แตะจริง ไม่ใช่ phase ที่กำลังทำ

## 14. อัปเดตมาตรฐาน — ผู้ใช้สั่งแค่ "อัปเดตมาตรฐาน"

โปรเจคกับ repo มาตรฐานอยู่คนละ repo · `scripts/standard-update.php` ดึง repo กลางมาไว้ชั่วคราว แล้วให้ **updater ของเวอร์ชันใหม่** เป็นคนลงมือ — โปรเจคที่ updater เก่าจึงได้วิธีอัปเดตใหม่เสมอ

### อะไรถูกทับ อะไรไม่แตะ

| | ไฟล์ | ทำอะไร |
|---|---|---|
| **ของมาตรฐาน** | `standard/` · `CLAUDE.md` · `scripts/` · `.claude/commands/` · `.codex/hooks.json` | ทับให้ตรงต้นฉบับ · ห้ามแก้ในโปรเจค (`check.php` เทียบลายเซ็น) |
| **รวมค่า** | `.claude/settings.json` | hooks ของมาตรฐานชนะ · permission ของทั้งสองฝั่งรวมกัน |
| **ของโปรเจค** | `project/` ทั้งหมด · `app/` · `core/` · `lang/` · `database/` · `public/` · `config/` · `.github/` | **ไม่แตะ** — เปลี่ยนเฉพาะที่ขั้นอัปเกรดบอกว่าแก้ให้ |

**`project/` ไม่ถูกแตะเลย** — BRIEF · SCOPE · PLAN · STATE · DESIGN.md · แบบที่อนุมัติแล้ว อยู่ครบ

**โค้ดโครง (`core/` · `partials/`) ไม่ถูกทับ** เพราะโปรเจคแก้และเพิ่มในนั้นเป็นปกติ · บั๊กในโครงที่มาตรฐานแก้ภายหลังมาเป็น **ขั้นอัปเกรด** ใน `scripts/upgrades/<เวอร์ชัน>.php` ที่แก้ให้เองเมื่อแน่ใจ หรือบอกว่าต้องแก้ตรงไหน — ตั้งแต่ 3.15.0 ทุกเวอร์ชันที่มี ⚠️ ต้องมีไฟล์นี้ (`docs/upgrade-coverage`)

### ขั้นตอนเมื่อผู้ใช้สั่ง

1. **ดูว่าอยู่จังหวะที่เหมาะไหม** — แนะนำให้อัปเดตหลังผ่านประตู ไม่ใช่กลาง phase เพราะกฎใหม่อาจเปลี่ยนเกณฑ์ของงานที่ทำไปครึ่งทาง · ผู้ใช้ยืนยันว่าจะทำตอนนี้ก็ทำได้
2. **commit งานที่ค้างให้หมด** แล้ว **ถามชื่อ branch** (เสนอ `standard-update-<เวอร์ชัน>`)
3. `php scripts/standard-update.php` — **ดูอย่างเดียว ไม่เขียนอะไร**
4. **สรุปให้ผู้ใช้อ่านแล้วตัดสินได้** — เวอร์ชันเก่า → ใหม่ · ⚠️ ระหว่างทาง · ไฟล์ที่จะเปลี่ยน · ขั้นอัปเกรด · ข้อที่ต้องแก้ก่อน · ไฟล์ที่โปรเจคแก้เองแล้วจะถูกทับ → **รอคำตอบ** เพราะเป็นการทับไฟล์
5. `php scripts/standard-update.php --yes` — ทับไฟล์ · รันขั้นอัปเกรด · รันชุดตรวจเต็ม
6. commit การอัปเดตเป็นก้อนเดียว `chore: อัปเดตมาตรฐาน x → y` · บันทึกลง `STATE.md`
7. **ชุดตรวจไม่ผ่าน = กฎใหม่จับของที่มีอยู่เดิม** — ห้ามรวมการแก้เข้า commit ของการอัปเดต · รายงานเป็นรายการ แล้วแยกเป็นงานต่อจากนี้ (งานเล็กหรือเลนปกติตามขนาด)
8. ขั้นอัปเกรดที่ขึ้น `! ต้องแก้เอง` → รายงานผู้ใช้ทีละข้อ · ข้อที่ต้องแตะ `.env` หรือ server ให้ผู้ใช้ทำเอง

`--ref <tag>` เลือกเวอร์ชันได้ · ย้อนเวอร์ชันไม่รองรับ ให้ย้อนด้วย git

### ‼️ โปรเจคที่ updater ยังเป็นรุ่นเก่า

updater รุ่นเก่าทับได้แค่ `standard/` กับ `CLAUDE.md` — ถ้าเผลอใช้มัน `scripts/` จะยังเป็นรุ่นเก่า และชุดตรวจอาจ fail เพราะเอกสารใหม่อ้างถึงสคริปต์ที่ยังไม่มี

**อาการ:** `standard/VERSION` เป็น 3.15.0 ขึ้นไปแต่ไม่มีโฟลเดอร์ `scripts/upgrades/` · หรือ updater ไม่แสดงรายการ "ไฟล์ของมาตรฐาน — เพิ่ม · แก้ · ลบ"

**ทางแก้ครั้งเดียว:** clone repo กลางลงโฟลเดอร์ชั่วคราว แล้วรัน updater **ของตัวที่ clone มา** ชี้เข้าโปรเจค — `scripts/standard-update.php --apply --target <โฟลเดอร์โปรเจค>` จากในโฟลเดอร์ที่ clone มา (ดูก่อน แล้วค่อยเติม `--yes`) · หลังจากนั้นใช้ขั้นตอนปกติได้ตลอด

## 15. โหมดเร็ว — เลื่อนการตรวจที่ไม่ใช่ดีไซน์ไปรวมที่ช่วง D

> **ที่มา:** ทีมเจอว่าช่วง C ช้าเพราะทุก phase ต้อง *ทำ → ตรวจทุกหน้าที่ทำ → หยุดรอผู้ใช้* แล้วค่อยขึ้น phase ถัดไป
> ตัวที่กินเวลาไม่ใช่ `check.php` (ไม่กี่วินาที) แต่เป็นการไล่ checklist ทางผิดพลาด · role · audit log · ข้อมูล 500 แถว — และการรอคน

> ‼️ **แก้ใน 3.18.0 — การตรวจดีไซน์ไม่เลื่อนอีกต่อไป**
> รอบแรกของโหมดเร็วเลื่อนข้อ 2.2 ของ [`testing.md`](testing.md) ไปด้วย ทีมที่ใช้จริงรายงานว่า *"เร็วขึ้นจริงแต่คุณภาพของดีไซน์ลดลงอย่างเห็นได้ชัด · บางอย่างหาย ไม่ตรงกับ wireframe"*
> เพราะการเทียบกับแบบเป็นสิ่งเดียวที่จับ "บล็อกหาย" ได้ และมันเป็นงานของคนทำ ไม่ใช่ของผู้ใช้ที่รอที่ประตู — เลื่อนเมื่อไหร่คือไม่มีใครเทียบเลยทั้ง phase

**โหมดเร็วเลื่อนเฉพาะการตรวจที่ไม่ใช่ดีไซน์ และเลื่อนการรอผู้ใช้** — ทุกข้อที่เลื่อนยังต้องถูกตรวจครบที่ช่วง D และ `docs/fast-mode-debt` ไม่ยอมให้ส่งงานจนกว่าจะครบ

> ‼️ **ข้อแลกที่ผู้ใช้ต้องรู้ตอนเลือก** — สิ่งที่จะไปรู้ตอนท้ายคือ **ฟังก์ชัน สิทธิ์ และข้อความ** ไม่ใช่หน้าตา
> เช่น validate ที่หลุดเหมือนกันทุกหน้า หรือ role ที่เข้าถึงได้เกินสิทธิ์ ซึ่งแก้ทีเดียวที่ต้นเหตุได้บ่อยกว่าเรื่องหน้าตา

### ถามเมื่อไหร่ เปลี่ยนเมื่อไหร่

- **ถามในช่วง A** พร้อมชุดคำถามระบบ ([`interview.md`](interview.md) ข้อ 20) พร้อมบอกข้อแลกในประโยคเดียว · ตอบไม่ได้ = โหมดปกติ
- บันทึกลง `STATE.md` บรรทัด `- **โหมด:** ปกติ` หรือ `เร็ว` · ไม่มีบรรทัดนี้ = ปกติ
- **ผู้ใช้สั่งเปลี่ยนได้ตลอดเวลา** ("โหมดเร็ว" · "โหมดปกติ" · `/wf เร็ว` · `/wf ปกติ`) — แก้ `STATE.md` แล้วยืนยันกลับ 1 บรรทัด ไม่ต้องหยุดงาน

| เปลี่ยนจาก → เป็น | มีผลเมื่อไหร่ |
|---|---|
| ปกติ → เร็ว | ตั้งแต่ phase ที่กำลังทำอยู่ถ้ายังไม่ถึง C4 · ไม่งั้น phase ถัดไป |
| เร็ว → ปกติ | ตั้งแต่ phase ถัดไป · **phase ที่เป็น 🔨 อยู่แล้วยังรอตรวจที่ช่วง D** ไม่ต้องย้อนตรวจตอนนั้น |

### สิ่งที่ไม่เปลี่ยน

| คงเดิมทุกโหมด | เพราะ |

| **ประตู A และ B** | อนุมัติขอบเขตกับดีไซน์ — ประตูที่พลาดแล้วแพงที่สุด (ข้อ 10) |
| **phase แรกตรวจเต็มระดับ phase** | มันวาง pattern ที่ทุก phase ลอกต่อ · `docs/fast-mode-debt` จับถ้าเลื่อน |
| **การตรวจดีไซน์ทั้งหมด** — [`testing.md`](testing.md) ข้อ 2.2 · ภาพตามข้อ 4ก · เทียบกับภาพแบบตามข้อ 4ข · skill `impeccable` | **บล็อกที่หายจากแบบไม่มีใครเห็นถ้าไม่เทียบตอนนั้น** · และดีไซน์ที่เพี้ยนถูกลอกต่อทุก phase เหมือน pattern (3.18.0) |
| **ประตู D** และทุกอย่างของช่วง D | เป็นที่ที่งานที่เลื่อนมาถูกตรวจ |

| hook ตรวจตอน commit · CI | ไม่กี่วินาที และเป็นกำแพงที่ไม่ขึ้นกับความจำ |
| C1–C3 ทั้งหมด — สถานะว่าง/โหลด/ผิดพลาด · ข้อความผ่าน `__()` · บทความคู่มือ · ครบลูป | **เลื่อนแค่การตรวจ ไม่ได้เลื่อนการสร้าง** — ของที่ไม่ได้สร้าง ช่วง D ตรวจไม่เจอว่าขาด |

### จบ phase ในโหมดเร็ว (phase ที่ 2 เป็นต้นไป)

**ตรวจขั้นต่ำ — ต้องผ่านก่อนไปต่อ**

1. `php scripts/check.php` ตรวจเต็ม ผ่าน
2. **เปิดทุกหน้าของ phase นี้** — หน้าขึ้นจริง · ไม่มี PHP warning ในเนื้อหน้า (`curl ... | grep -nE "Warning|Notice|Deprecated|Fatal error"`) · console ไม่มี error
3. **ดีไซน์ครบตาม [`testing.md`](testing.md) ข้อ 2.2 ทั้งหมด** — ภาพ 2 โหมด × 2 ความกว้าง และ component ที่ต้องกดก่อนเห็น (ข้อ 4ก · ผู้ทำต้องดูภาพเอง) · เรียก `impeccable` · หน้าที่มีภาพแบบเทียบตามข้อ 4ข
4. **เทียบกับแบบที่อนุมัติแล้วทีละหน้า ทีละบล็อก** (ข้อ 5 ตารางแบบที่อนุมัติแล้ว) — บล็อกครบ · ลำดับตรง · ตำแหน่งและสัดส่วนตรง
   **ของที่หายหรือไม่ตรงต้องแก้ใน phase นี้ ห้ามจดไว้ตรวจทีหลัง** · ตั้งใจไม่ทำตามแบบต้องบันทึกเหตุผลใน `DESIGN.md`
5. `storage/logs/app.log` ไม่มี error ใหม่

**เลื่อนไปช่วง D** — [`testing.md`](testing.md) ข้อ 2.3–2.8 (ทางปกติ · ทางผิดพลาด · สิทธิ์ · audit log · ข้อมูลจริง · ภาษาและคู่มือ) และการรอผู้ใช้ตรวจ

> ‼️ **ข้อ 3 กับ 4 ไม่ใช่ของที่ย่อได้** — "เปิดดูแล้วหน้าขึ้น" ไม่ใช่การตรวจดีไซน์
> ต้องเปิดแบบขึ้นมาวางคู่กันจริงแล้วไล่ทีละบล็อก ไม่งั้นบล็อกที่หายจะผ่านไปทุก phase จนถึงช่วง D

**แล้วทำต่อทันที ไม่หยุดรอ**

- `PLAN.md` — หัว phase เป็น 🔨 · `C4ก` `C4ข` และ C5 เขียนตามรูปแบบในข้อ 9
- `STATE.md` — อัปเดตแล้วเริ่ม phase ถัดไป
- **อัปเดตบอร์ด** (ข้อ 16) — ในโหมดเร็วนี่คือที่เดียวที่ผู้ใช้ดูความคืบหน้าได้โดยไม่ต้องไล่อ่านแชท
- รายงานในแชท **ไม่ใช่ประตู ไม่มีคำถามให้ตอบ**: ลิงก์บอร์ด · ทำอะไรเสร็จ · เปิดดูที่ URL ไหน · ตัดสินใจเองไปกี่เรื่อง · กำลังเริ่ม phase อะไร
- เรื่องกำกวมยังลง `QUESTIONS.md` เหมือนเดิม — ไปถามรวมที่ประตู D

> ‼️ **ในโหมดเร็ว `QUESTIONS.md` แพงขึ้นทุก phase** — คำตอบที่ต่างจากที่เลือกไว้ต้องแก้ทุก phase ที่ทำต่อจากนั้น
> ถ้าเจอเรื่องที่ **เลือกผิดแล้วงานของ phase ที่เหลือใช้ไม่ได้ทั้งหมด** (เช่นความหมายของข้อมูลหลัก · ใครเห็นข้อมูลของใคร) ให้หยุดถามเฉพาะเรื่องนั้น — เป็นข้อยกเว้นเดียวของ "ไม่หยุด"

> ‼️ **ผู้ใช้เปิด URL ที่รายงานไว้ดูได้ตลอด** — เห็นอะไรผิดแล้วสั่ง ให้หยุดแก้ตามที่สั่งก่อนทำต่อ · การที่ผู้ใช้ไม่ทักไม่ใช่การอนุมัติ (ข้อ 10.3) ประตู D ยังต้องได้คำตอบทีละข้อ

### ช่วง D ของโปรเจคที่ใช้โหมดเร็ว

ทำ **ตรวจย้อนหลัง** ก่อนความปลอดภัย ประสิทธิภาพ และ E2E — ตรวจทั้งระบบบนหน้าที่ยังไม่ผ่านการตรวจระดับ phase คือเสียเวลาสองรอบ

1. ไล่ phase ที่เป็น 🔨 ทีละ phase ตาม [`testing.md`](testing.md) ข้อ 3.0
2. เจอปัญหา → แก้ · **ปัญหาชนิดเดียวกันที่ลามหลาย phase ให้แก้ที่ต้นเหตุครั้งเดียว** (มักเป็น partial หรือ token) แล้วตรวจทุก phase ที่กระทบซ้ำ
3. เขียนผลลง `QA-REPORT.md` หัวข้อ `## ตรวจย้อนหลังจากโหมดเร็ว` → `### Phase N — ชื่อ` แล้วเปลี่ยน `PLAN.md` ของ phase นั้นเป็น ✅ ตามรูปแบบในข้อ 9
4. ประตู D รายงานเพิ่ม **ราคาของโหมดเร็วรอบนี้** — เจอกี่ข้อ · กี่ข้อลามหลาย phase · ใช้เวลาแก้ประมาณเท่าไหร่ · ผู้ใช้จะได้ตัดสินได้ว่าโปรเจคหน้าจะเลือกโหมดไหน

> ‼️ **เจอปัญหาหน้าตาตอนตรวจย้อนหลัง แปลว่าการตรวจดีไซน์ตอนจบ phase ไม่ได้ทำจริง** — ไม่ใช่ราคาของโหมดเร็ว
> บันทึกลง `FEEDBACK.md` ว่าข้ามตรงไหน เพราะกฎที่ถูกข้ามเงียบๆ คือกฎที่ต้องแก้ที่มาตรฐาน ไม่ใช่ที่โปรเจค

## 16. บอร์ดความคืบหน้า — หน้าที่ทีมเปิดดูได้โดยไม่ต้องอ่านแชท

> **ที่มา:** ทีมเสนอให้ใช้ kanban จดสิ่งที่ Claude ทำ · `PLAN.md` เป็น kanban อยู่แล้ว (คอลัมน์ตามสถานะ · ห้ามมี 🔄 เกิน 1) และ Claude อ่าน `project/` ทุก session อยู่แล้ว
> ที่ขาดคือ **หน้าตาที่คนดูแวบเดียวแล้วรู้ว่าถึงไหน** — ขาดหนักขึ้นตั้งแต่มีโหมดเร็ว เพราะ Claude ไม่หยุดรายงานระหว่าง phase แล้ว

**บอร์ดเป็นหน้าจอ ไม่ใช่แหล่งข้อมูล** — `php scripts/board.php` อ่าน `PLAN.md` · `STATE.md` · `QUESTIONS.md` · `QA-REPORT.md` · `FEEDBACK.md` · git log ทางเดียว แล้วเผยแพร่เป็น Artifact

> ‼️ **ห้ามเพิ่มไฟล์บอร์ดใน repo และห้ามใช้บอร์ดสั่งงาน**
> ข้อมูลเดียวกันสองที่จะเพี้ยนจากกันเงียบๆ · บอร์ดที่ลากการ์ดได้คือการเพิ่มขอบเขตงานโดยไม่ผ่านประตู A
> อยากเปลี่ยนอะไรบนบอร์ด → บอก Claude → Claude แก้ที่ไฟล์ใน `project/` → สร้างบอร์ดใหม่

### บอร์ดแสดงอะไร

แถบบน: ช่วง A–E · โหมด · "ตอนนี้" จาก `ค้างอยู่ที่` · สถานะของแต่ละ phase · ท้ายหน้า: เรื่องที่รอคำตอบ · commit ล่าสุด · การตัดสินใจล่าสุด

**สองแท็บ แบบ kanban — การ์ดคืองานชิ้นเล็ก กดแล้วเปิดรายละเอียด**

| แท็บ | การ์ดคืออะไร | เลน | กดแล้วเห็น |
|---|---|---|---|
| **งาน** | ข้อใน checklist ของ `PLAN.md` (ครบลูป และหัวข้อที่โปรเจคเพิ่ม · ไม่รวม C1–C5) | ยังไม่เริ่ม → กำลังทำ → สร้างเสร็จ รอตรวจ → เสร็จ | phase · สถานะของข้อ · ขั้น C1–C5 ของ phase · หน้าใน phase |
| **ผลตรวจ** | ข้อใน `QA-REPORT.md` | เจอ → กำลังแก้ → แก้แล้ว รอตรวจซ้ำ → ปิด | ความรุนแรง · เจอที่ · วิธีทำซ้ำ · ผลที่ได้ vs ที่ควรเป็น · ภาพหลักฐาน · แก้ใน commit ไหน |

**เลนของแท็บงานมาจากสถานะของ phase** — ข้อที่ยังไม่ติ๊กใน phase ที่กำลังทำอยู่ "กำลังทำ" · ข้อที่ติ๊กแล้วใน phase ที่ยังไม่ผ่านการตรวจอยู่ "รอตรวจ" ไม่ใช่ "เสร็จ" · กฎเลนอยู่ที่ `ProjectDocs::itemLane()` ที่เดียว

**ช่วง D และ E บอร์ดเปิดมาที่แท็บผลตรวจ** พร้อมบรรทัดบอกว่าผ่านประตู D ได้หรือยัง

**URL ของหน้าที่ทำเสร็จ** มาจากหัวข้อ `### หน้า` ใน phase ของ `PLAN.md` (ไม่บังคับ แต่ควรมี — ข้อ 9) · ไม่เขียน บอร์ดก็ไม่มีให้

### สร้างและอัปเดตเมื่อไหร่

| จังหวะ | ทำอะไร |
|---|---|
| **ผ่านประตู B** — ก่อนเริ่ม phase แรก | สร้างครั้งแรก · เขียนลิงก์ลง `STATE.md` · บอกผู้ใช้ว่าเปิดลิงก์นี้ดูความคืบหน้าได้ตลอด |
